# Семантический поиск публичных чатов

Владелец — `ChatSearchService`. Источник — существующие `project_chat_messages` и PUBLIC `project_chat_rooms`, включая общий legacy-диалог. PRIVATE-диалоги, персональные чаты моделей и диалоги системных ролей не индексируются. Настройка RAG проекта не меняется.

Каждое новое действие требует явного выбора назначенной проекту проверенной embedding-модели, её точного pin и `consent:true`. Внешний embedding API может тарифицировать передачу фрагментов сообщения или поискового запроса. Открытие панели, история, восстановление запроса и отмена модель не вызывают.

## HTTP-контракт

| Метод | Путь после `/api/projects/:projectId/chat-search` | Результат |
| --- | --- | --- |
| GET | пустой | `{jobs}`: последние 20 собственных запросов, без текста результатов |
| POST | `/index` | новое ограниченное задание индексации или точный прежний receipt |
| POST | `/search` | новое задание поиска или точный прежний receipt |
| GET | `/jobs/:id` | состояние; SUCCEEDED search возвращает актуальные доступные результаты |
| DELETE | `/jobs/:id` | сохранённая отмена; поздний результат не сохраняется |

POST принимает `{requestKey,modelId,expectedModelPin,consent:true,roomId?,limit?}`. `requestKey` — UUID; `roomId` ограничивает публичный диалог. Поиск дополнительно принимает `query` до 8192 UTF-8 байт; `limit` — 1–20 сообщений. Индексация обрабатывает 1–32 фрагмента по 2048 Unicode-символов одного ожидающего сообщения. `hasMore:true` означает, что пользователь может явно запустить следующую порцию с новым UUID. Длинные сообщения продолжаются следующими порциями; текст не обрезается для имитации полного индекса.

Receipt: `{id,projectId,kind,state,modelId,modelPin,indexedChunks,hasMore,error,results?}`. Hit: `{messageId,roomId,roomTitle,revision,chunk,score,content,position,authorName}`. `content` — текущий фрагмент оригинала, максимум 2048 символов. Не сохраняется копия текста в индексе, журнале задания или Operations.

## Границы корректности

- Создание — рабочая роль проекта, текущие флаги `system_indexer`, `project_chat`, `rag_sync`, `model_hosting`. Ранее принятые receipt, история и отмена доступны после выключения флагов, с актуальными правами проекта. История запросов принадлежит пользователю.
- Вызов проходит через существующие `ModelRuntime`, rate-admission и журнал использования. Перед фактическим embedding и после ответа повторяются ACL, назначение модели, pin и ревизия исходного сообщения. Inference не держит SQL-блокировки.
- Ревизия и tombstone меняются транзакционным trigger при INSERT/семантическом UPDATE/DELETE. UPDATE удаляет прежние векторы; DELETE удаляет их через FK. Сохранённая выдача содержит только ссылки/ревизии/score, каждый GET выполняет live JOIN с исходником, PUBLIC-комнатой и текущей ревизией.
- Векторная близость — точный cosine по реальным embedding-векторам, без текстового `LIKE` и без лексического запасного пути. Размерность и ненулевой конечный результат провайдера проверяются. Пустой фрагмент отмечается нулевым внутренним маркером без обращения к модели и не участвует в выдаче.
- Векторы читаются keyset-страницами до примерно 1 МиБ сырых double-значений, максимум 64 строки на страницу. Предел — 10000 фрагментов и пять секунд вычисления; при превышении нет ложной полной выдачи, требуется выбрать один диалог. Это ограниченный точный поиск, не ANN-индекс для неограниченной истории. Во время конкурентных новых записей полнота соответствует уже обработанным фрагментам; live-фильтры гарантируют отсутствие удалённого/изменённого/закрытого текста.
- В одном проекте у пользователя одно RUNNING-задание. Время — до 105 секунд, durable deadline 120 секунд. STARTED/неизвестный результат не переигрывается автоматически после перезапуска. Новый платный повтор — только новое явное действие. Операция и её статус сохраняются в существующих Operations атомарно с заданием.

## Проверка

`test/chat-search.test.ts` проверяет входы, разрешения, Unicode, векторы и cosine. `test/chat-search-postgres.test.ts` требует явно переданный `CHAT_SEARCH_TEST_ADMIN_URL` для одноразового PostgreSQL на loopback-порту, отличном от 5432; создаёт и удаляет собственную БД. Runtime использует только контролируемые векторные fixtures. Эти проверки не доказывают качество выбранной настоящей embedding-модели и не обращаются к пользовательским чатам или внешним API.
