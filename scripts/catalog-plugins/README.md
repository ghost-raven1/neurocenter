# Публикация подготовленных расширений

## В интерфейсе

Главный администратор открывает **Каталог инструментов → Упаковать инструмент**. Достаточно указать npm-пакет, публичную ссылку GitHub или выбрать папку/архив JS/TS и нажать **Упаковать и добавить**. Версия npm или полный commit репозитория закрепляется перед сборкой, точка входа предлагается автоматически; название и описание можно изменить в дополнительном блоке. Ход сборки виден в этом окне и в «Операциях». Окно можно закрыть или перезагрузить страницу: сохранённый запрос находится без повторной отправки исходников.

Для архива выберите **Файлы или архив → Выбрать архив** или перетащите один файл в область загрузки. Поддерживаются `.zip`, `.tar`, `.tar.gz` и `.tgz` размером до 8 МиБ: до 100 текстовых файлов UTF-8, 1 МиБ на файл и 5 МиБ распакованного содержимого. Единственная внешняя папка снимается автоматически, вложенные пути сохраняются. Зависимости, `.git`, результаты сборки, файлы ключей и служебные файлы macOS пропускаются; лимит распакованного размера учитывает также пропущенные файлы. Архив с зависимостями стоит пересоздать только из исходников. Ссылки, зашифрованные ZIP, опасные/повторяющиеся пути, повреждения и превышение лимитов отклоняются до сборки.

Проверка архива (`POST /api/tool-builds/archive`, JSON `{name, contentBase64}`) доступна только главному администратору, не сохраняет архив и не запускает код. Проверенные файлы отправляются обычным источником `files` в `POST /api/tool-builds`: отдельного механизма установки нет. Загрузка архива рассчитана на исходники JS/TS; для Python, Java, .NET, Go, Rust и native используйте репозиторий с `neurocenter.tool.json` и готовыми поставками.

Исполняемые исходники поддерживают `.js`, `.mjs`, `.cjs`, `.ts`, `.tsx`, `.mts` и `.cts`. Декларации `.d.ts`, `.d.mts`, `.d.cts` не являются файлом запуска и отклоняются до сборки. Для MCP автоматически выбирается `bin`, для плагина — `module`/`main`: смена типа обновляет автоматический выбор, а ручной выбор сохраняется. Имена файлов Unicode сохраняются без переименования; эквивалентные NFC/NFD пути считаются дублями. Выбор папки также пропускает конфиги registry и метаданные macOS.

Для GitHub выберите **Репозиторий GitHub** и вставьте `https://github.com/owner/repository`. По умолчанию используется основная ветка; блок **Ветка и подпапка** позволяет указать тег, commit, пакет внутри монорепозитория или нестандартный файл запуска. Поддерживаются также ссылки `/tree/ветка/папка`. Если имя ветки содержит `/`, укажите канонический URL репозитория и ветку отдельным полем. Перед отправкой браузер закрепляет показанный полный commit: изменение ветки во время сборки не подменит исходники. Приватные репозитории, SSH и другие Git-серверы пока не поддерживаются.

Готовая карточка открывается кнопкой **Открыть в каталоге**. Добавьте её в проект и выполните установку через мост. Проекту один раз нужна связанная папка; первая установка точной версии требует одобрения администратора проекта, одобренная версия устанавливается одним нажатием. Проверка запуска остаётся отдельным действием и не подменяется успешной упаковкой.

Браузерный мастер и команды оператора вызывают один `buildRecipe`. В базе сохраняются запрос, реальная закреплённая версия, статус и результат. Очередь ограничена десятью заданиями; выполняется одна сборка. Ожидающие задания сохраняются после перезапуска, а прерванная запущенная сборка получает явную ошибку. Карточка и успешная операция публикуются одной транзакцией. Сборщик проверяет свободное место, SHA, размеры, переносимые пути и границы staging; исходники не выполняются во время сборки. Неизвестный исход перезагрузки клиента восстанавливается по UUID запроса. Аварийно прерванная серверная сборка завершается явной ошибкой, её процессы и временные файлы очищаются.

Команды из корня проекта выбирают установленный Node 24, включая доступный bundled runtime:

```sh
npm run tools:build -- --recipe scripts/catalog-plugins/examples/python-context/recipe.json --output output/python-context
npm run tools:publish -- --manifest output/python-context/ready.json
npm run tools:check
```

## Единая сборка по recipe

Новый MCP или плагин описывается JSON-рецептом. Все источники проходят одну цепочку: проверка recipe → подготовка файлов для каждой платформы → USTAR-архив → SHA-256 и descriptor → проверка публикации → `ready.json`. Сборка не запускает расширение и не меняет пользовательский OpenCode. Установка остаётся обычным одобренным действием каталога через мост.

```sh
node scripts/catalog-plugins/build.mjs --recipe scripts/catalog-plugins/examples/file-plugin/recipe.json --output output/example-context --dry-run
node scripts/catalog-plugins/build.mjs --recipe scripts/catalog-plugins/examples/file-plugin/recipe.json --output output/example-context
node scripts/catalog-plugins/publish.mjs --manifest output/example-context/ready.json --dry-run
node scripts/catalog-plugins/publish.mjs --manifest output/example-context/ready.json
```

Нужен Node.js 24 и собранный `catalog-service`. `--dry-run` только читает и проверяет recipe, исходные файлы и настройки; он не обращается к сети и не создаёт даже папку output. Обычная сборка не публикует карточку. Для сборки с немедленной dev-публикацией добавьте отдельный флаг `--publish`. Его нельзя совмещать с `--dry-run`.

Для отображения хода сборки добавьте `--progress`. stdout станет JSONL: события `{type:"build-progress",target,completed,total}` перед и после подготовки каждой платформы, затем итоговый JSON. `completed` считает реально упакованные платформы. API `buildRecipe` принимает такой же необязательный callback `onProgress`; без флага CLI сохраняет обычный единый JSON-результат.

Папка output должна быть новой или пустой и не пересекаться с исходными файлами. Готовый результат не перезаписывается. При неудачной публикации проверенный `ready.json` сохраняется: повторите публикацию того же manifest.

Минимальный recipe:

```json
{
  "schemaVersion": 1,
  "key": "team-context",
  "name": "Контекст команды",
  "kind": "plugin",
  "description": "Добавляет правила команды в контекст OpenCode.",
  "revision": "1.0.0",
  "source": { "type": "files", "directory": "source", "entrypoint": "index.mjs" }
}
```

`key` остаётся постоянным идентификатором рецепта, `revision` меняется при изменении поставки. Неизвестные поля, shell-команды и install hooks в JSON запрещены. Необязательные `tags` — до 20 строк. `targets` — неповторяющийся список целей моста; по умолчанию используются поддерживаемые источником цели. Наличие архива для платформы означает готовую поставку, а не пройденную нативную проверку.

Доступные базовые источники:

| source.type | Обязательные поля | Подготовка |
| --- | --- | --- |
| `files` | `directory`, `entrypoint` | Самодостаточные готовые файлы из подкаталога recipe; переносимые пути, UTF-8, до 100 файлов / 5 МиБ / 1 МиБ на файл. Символические и жёсткие ссылки, секретные файлы, выход за папку recipe и исходники TypeScript отклоняются. |
| `npm` | `package`, точная `version`, `entrypoint` | На площадке для каждой цели устанавливаются production-зависимости с `--ignore-scripts` и `--no-bin-links`. TS/TSX-точка входа компилируется esbuild в готовый JS. На клиенте npm и компилятор не нужны. `latest`, диапазоны версий и URL вместо имени npm-пакета запрещены. |
| `project` | `directory`, `entrypoint` | JS/TS-проект из подкаталога recipe компилируется esbuild в готовый JS. Скрипты package.json не запускаются; зависимости готовятся с отключёнными lifecycle hooks. |
| `repository` | `url`, полный `commit`, `entrypoint` | Публичный GitHub скачивается по закреплённому SHA: JS/TS проходит компилятор проекта, `neurocenter.tool.json` — адаптер готовой поставки. Необязательный `subdirectory` выбирает пакет монорепозитория. Архив проверяется до извлечения: до 256 МиБ сжатого / 1 ГиБ распакованного / 20 000 файлов, без ссылок и выхода за каталог. |
| `runtime` | `adapter`, `assets` по поддерживаемым целям | Готовое приложение и, для Python/Java/.NET, отдельный закреплённый runtime перепаковываются в автономный MCP. Компиляция и установка зависимостей не выполняются. |
| `release` | `assets` по целям платформ | Для каждого asset задаются HTTPS `url`, `sha256`, `format: "tar.gz"` или `"zip"`, `entrypoint` и необязательные `executables`. Проверенный релиз перепаковывается в тот же delivery-архив. |
| `prepared` | `adapter` | Проверенные встроенные адаптеры: `opencode-rag` (MCP), `opencode-rag-plugin` (плагин), `opencode-snip`, `filesystem`, `memory`, `sequential-thinking`, `project-context`, `git-context`. Произвольный путь к исполняемому адаптеру не принимается. |

Для `files` entrypoint — готовый `.js`, `.mjs` или `.cjs`: этот источник не компилирует TypeScript. Для исходного проекта используйте `project`. Для npm путь указывается относительно установленного пакета, например `dist/index.js`: готовый JS закрепляется как `node_modules/<package>/dist/index.js` без обёртки, поэтому CLI-проверки `process.argv[1]` сохраняют смысл. npm entrypoint `.ts` или `.tsx` проходит компиляцию на площадке в `entrypoint.mjs` или `entrypoint.cjs` с сохранением формата исходного модуля; клиент получает готовый JS. Пример npm-рецепта — `examples/npm-mcp.json`.

`project`, `repository` и npm с TS entrypoint собирают локальные статические импорты в JS-бандл. Production-зависимости остаются полным `node_modules`, включая их ресурсы и лицензии. Произвольные ресурсы самого проекта, которые код читает через `fs`, относительный `new URL(..., import.meta.url)` или вычисляемый `require`, автоматически не переносятся. Для таких расширений подготовьте самодостаточный каталог `files`, готовый npm с JS entrypoint или закреплённый `release` с ресурсами. Нативные зависимости и сложные runtime-ресурсы требуют подходящего адаптера и отдельной проверки запуска; успешная компиляция не означает, что этот сценарий уже проверен.

CommonJS-плагины с default фабрикой (`module.exports = async (...) => ...`) получают небольшой ESM-фасад автоматически. Это относится к `.cjs` и `.js` с явным ближайшим `package.json` типа `commonjs`; MCP сохраняет прямой CJS запуск и main guard. Именованные фабрики публикуйте как явные ESM exports. Неоднозначный `.js` без объявления формата не переписывается. Фасад и исходная точка входа записываются в provenance; исходники расширения при сборке не исполняются.

CLI-рецепт репозитория использует уже закреплённый полный SHA, например:

```json
{
  "schemaVersion": 1,
  "key": "fetch-mcp",
  "name": "MCP Fetch",
  "kind": "mcp",
  "description": "Получение веб-страниц через MCP.",
  "revision": "git-1ddb1a59cb09a2d38e759f2d7a97829680cbe514",
  "source": {
    "type": "repository",
    "url": "https://github.com/zcaceres/fetch-mcp",
    "commit": "1ddb1a59cb09a2d38e759f2d7a97829680cbe514",
    "entrypoint": "src/index.ts"
  }
}
```

GitHub-архив загружается один раз на сборку и проверяется по SHA-256 при повторном использовании для платформ. `repository.json` и provenance сохраняют URL, commit, подпапку и SHA исходного архива; лицензии корня и выбранного пакета включаются в комплект. Конфигурация npm из репозитория не используется.

Этот рецепт сохранён в `examples/repository-mcp.json`. Проверка без скачивания и записи: `npm run tools:build -- --recipe scripts/catalog-plugins/examples/repository-mcp.json --output output/fetch-mcp --dry-run`.

### Готовый MCP на Python, Java, .NET, Go, Rust или native

Автор добавляет **один `neurocenter.tool.json`** в корень пакета своего публичного GitHub-репозитория. Пользователь открывает **Каталог инструментов → Упаковать инструмент → Репозиторий GitHub**, вставляет ссылку и нажимает **Упаковать и добавить**. Форма показывает закреплённый commit, способ поставки и только платформы из манифеста. Это MCP; режим плагина OpenCode для такого рецепта недоступен. Репозиторий с сырыми `.py`, `.java`, `.cs`, Go или Rust без манифеста автоматически не компилируется.

Шаблоны ниже проходят проверку структуры. **Все URL `https://example.com/...` и SHA из повторяющихся цифр — заглушки**, а не существующие релизы. Перед реальной сборкой замените их публичными HTTPS-ссылками на готовые файлы и настоящими SHA-256 их байтов. Сборка по этим заглушкам не должна успешно завершаться; `--dry-run` не скачивает и не проверяет содержимое удалённых assets.

| Адаптер | Шаблон манифеста | Что подготовить автору |
| --- | --- | --- |
| `python` | [Python](examples/runtime/python/neurocenter.tool.json) | `.py` с готовыми зависимостями и переносимый Python со стандартной библиотекой и нужными native-модулями. |
| `java` | [Java](examples/runtime/java/neurocenter.tool.json) | Исполняемый `.jar` со всеми зависимостями и совместимый переносимый JRE. |
| `dotnet` | [.NET](examples/runtime/dotnet/neurocenter.tool.json) | Готовую `.dll`, `.deps.json`, `.runtimeconfig.json`, зависимости и совместимый .NET runtime. |
| `go` | [Go](examples/runtime/go/neurocenter.tool.json) | Готовый самодостаточный бинарник для указанной ОС/архитектуры/libc. |
| `rust` | [Rust](examples/runtime/rust/neurocenter.tool.json) | Готовый бинарник и необходимые ресурсы/библиотеки в рабочем переносимом layout. |
| `native` | [Native](examples/runtime/native/neurocenter.tool.json) | Другую готовую нативную MCP-программу с нужными ресурсами/библиотеками. |

Контракт манифеста: `schemaVersion: 1`, необязательные `name`, `description` и обязательный `source: {type: "runtime", adapter, assets}`. Размер UTF-8 JSON — до 64 КиБ. `key`, `revision`, `kind`, команды сборки, install hooks и произвольные поля в этот файл не добавляются. Это декларация репозитория, а не полный CLI recipe; оператор использует прежний `build.mjs`, где её `source` помещается в обычный recipe с `kind: "mcp"`.

Каждый ключ `assets` — одна реально подготовленная цель: `darwin-arm64`, `darwin-x64`, `linux-arm64-glibc`, `linux-x64-glibc`, `linux-arm64-musl`, `linux-x64-musl`, `win32-arm64` или `win32-x64`. Можно указать подмножество; отсутствующие платформы не достраиваются. Linux glibc/musl и разные архитектуры совместимыми автоматически не считаются. Для каждой цели задайте `app`; для `python`, `java`, `dotnet` дополнительно обязателен `runtime`. Для `go`, `rust`, `native` поле `runtime` запрещено.

Удалённый `app` или `runtime` содержит `url`, `sha256` из 64 строчных hex-символов, `format: "tar.gz" | "zip" | "file"` и `entrypoint`. Необязательный `executables` перечисляет дополнительные исполняемые файлы относительно этого asset. Главная программа/runtime получает право исполнения автоматически. Для `format: "file"` скачанные байты сохраняются под именем `entrypoint`; для архивов путь должен уже существовать внутри архива.

**Верхняя папка архива не удаляется (`strip` отсутствует).** Если JRE содержит `jre-21/bin/java`, укажите весь этот путь, а не `bin/java`. Для Python так же нужен фактический полный путь, например `python-runtime/bin/python3`; на Windows — настоящий `.exe`. `app.entrypoint` для managed-адаптеров заканчивается на `.py`, `.jar` или `.dll` соответственно. Shell-обёртки `.sh`, `.cmd`, `.ps1` не являются автономной точкой входа.

Вместо удалённого `app` можно включить уже подготовленную папку репозитория, например:

```json
"app": { "directory": "ready-app", "entrypoint": "server.py" }
```

`directory` считается от папки с `neurocenter.tool.json`, `entrypoint` — от `directory`. Скопируется весь готовый каталог с ресурсами; исходники зависимостей здесь не устанавливаются. `runtime` всегда задаётся удалённым asset, а не `directory`. Для Python зависимости должны импортироваться из включённого приложения или bundled runtime; пользовательские site-packages и `PYTHONPATH` не используются.

Приложение и runtime должны работать после переноса в другую папку и при чтении из неизменяемого кеша. Особенно проверьте Python/JRE: архив только с обычными файлами и папками, без символических/жёстких ссылок, специальных файлов и абсолютных путей. Распространённый архив с ссылками нужно заранее подготовить в таком виде, сохранив лицензии. Обновление системного Python, pip/npm, JDK/.NET SDK или изменение `PATH` на клиенте не выполняются. Все требуемые зависимости входят в готовую поставку.

Для monorepo в блоке **Ветка и подпапка** укажите папку, где лежит манифест. Поле **Файл запуска или рецепт** можно явно заполнить значением `neurocenter.tool.json`; путь к папке задаётся отдельно. API проверки: `GET /api/tool-builds/repository` с `url`, необязательными `ref` (ветка/тег/commit), `subdirectory`, `entrypoint`. При отправке `POST /api/tool-builds` используется обычный `source: {type: "repository", url, ref: "<полный commit из проверки>", entrypoint: "neurocenter.tool.json"}`; необязательный `subdirectory` также находится внутри `source`. Верхние поля запроса — `kind: "mcp"`, `name`, `description`, `requestKey`. `runtimeSource` и `manifestSha256` клиент не передаёт: сервер читает манифест заново на закреплённом commit.

Успешная проверка структуры или упаковка не доказывает запуск на целевой ОС. Автор отдельно проверяет настоящий MCP initialize/listTools, работу зависимостей, завершение процессов и требования подписи ОС. Публикация и установка сохраняют существующее одобрение точной версии; наличие манифеста его не обходит.

`config` MCP допускает `args`, `env`, необязательные `transport: "stdio"`, `command: "node"` и `extra.localConfiguration`. Builder сам задаёт entrypoint и runtimeArtifacts. У плагина допустим только `extra`; совместимость с конкретным API OpenCode проверяется отдельно. Секреты задаются ссылками `{env:ИМЯ}` или через локальный мастер MCP, а не значениями в общем recipe.

В output сохраняются архивы, descriptors, `ready.json`, снимок `recipe.json` и `provenance.json`. Для npm сохраняются отдельные `lock-<target>.json` с контрольными суммами. Они фиксируют реально разрешённые зависимости первой сборки; для повторной установки и публикации используйте уже готовый manifest, а не новое разрешение транзитивных версий. `runtimeChecked: false` явно отделяет успешную упаковку от запуска и нативных проверок. Отдельная диагностика через мост выполняется после установки.

Встроенный каталог использует этот же builder. `prepare.mjs` выбирает рецепты и объединяет результаты, без второго механизма упаковки:

```sh
node scripts/catalog-plugins/prepare.mjs --output output/catalog-next --only project-context,git-context --dry-run
node scripts/catalog-plugins/prepare.mjs --output output/catalog-next --only project-context,git-context
```

Результаты отдельного инструмента лежат в подкаталоге его key, общий manifest — `output/catalog-next/ready.json`. Поле `provenance.recipePath` указывает на сохранённый `recipe.json` относительно папки provenance и остаётся корректным после переноса поставки. Изменение адаптера получает новую ревизию `pack.N`, чтобы не заменять байты ранее опубликованной ревизии. Для OpenCodeRAG по умолчанию выбираются семь доступных целей; явно запрошенный Intel Mac отклоняется.

```sh
node --test scripts/catalog-plugins/test/build.test.mjs scripts/catalog-plugins/test/pack.test.mjs
```

## Импорт и публикация

`publish.mjs` импортирует уже собранные архивы в локальный dev-стек и публикует реальные MCP или плагины через административный API. Установку в пользовательский проект выполняет обычный план каталога и мост; публикация не запускает локальные задания установки.

```sh
node scripts/catalog-plugins/publish.mjs --manifest output/catalog-plugins/ready.json --dry-run
node scripts/catalog-plugins/publish.mjs --manifest output/catalog-plugins/ready.json
```

Сначала соберите `services/catalog-service`. Нужен Node.js 22 или новее с `util.parseEnv`. Значения окружения берутся из `.env`, `.env.local`, затем `process.env`; пароли и cookie не выводятся. В dev с отключённым SSO помощник открывает собственную сессию и закрывает её после публикации. Для существующей административной сессии передайте `--cookie-file` с содержимым заголовка `Cookie`. Production-вход через IdP помощник не выполняет.

Manifest имеет следующий контракт:

```json
{
  "schemaVersion": 1,
  "tools": [
    {
      "key": "example-plugin",
      "publication": {
        "name": "Example plugin",
        "kind": "plugin",
        "description": "Описание расширения",
        "origin": "npm:example-plugin",
        "revision": "1.2.3",
        "config": {
          "extra": {
            "runtimeArtifacts": ["Полный descriptor из descriptor.json"]
          }
        },
        "files": []
      },
      "artifacts": [
        { "archivePath": "example-plugin/runtime.tar.gz", "descriptorPath": "example-plugin/descriptor.json" }
      ]
    }
  ]
}
```

Строку в `runtimeArtifacts` заменяет объект descriptor существующего delivery-контракта: `target`, `sha256`, `compressedBytes`, `unpackedBytes`, `filesCount`, `entrypoint`, необязательный `executable`. Пути архивов считаются от каталога manifest. Для текстового самодостаточного плагина допустим `artifacts: []` с обычными `files` и `config.entrypoint`.

Все публикации и SHA архивов проверяются до первого HTTP-запроса или импорта. `--dry-run` выполняет только чтение. `key` и точная `publication.revision` задают постоянный ключ повторной отправки; при необходимости его можно сохранить явно в `tool.publicationKey`. Повтор с другими байтами под той же ревизией сервер отклонит. Новая ревизия уже существующей карточки публикуется через её редактирование с `expectedVersion`, а не созданием дубликата.

Готовый архив содержит зависимости целевой платформы; `npm install`, сборка исходников и внешние install-скрипты на компьютере пользователя не выполняются. Для production используйте `scripts/production/import-runtime-artifact.mjs` и административный API с действующей SSO-сессией.
