# Spec Delta

## Purpose

Позволяет каждому участнику команды использовать собственный ключ конкретного удалённого провайдера, сохраняя общий выбор модели и независимость доступа других пользователей.

## ADDED Requirements

### Requirement: Режим авторизации провайдера
Система SHALL применять настроенный администратором режим `none`, `optional` или `required` к конкретному удалённому подключению модели.

#### Scenario: API без ключа
- **WHEN** режим равен `none`, даже если пользователь ранее сохранил ключ
- **THEN** запрос не содержит Authorization.

#### Scenario: Необязательный и обязательный ключ
- **WHEN** персонального ключа нет
- **THEN** `optional` допускает анонимный запрос, а `required` показывает настройку личного доступа до отправки провайдеру.

### Requirement: Изоляция персональных ключей
Система MUST хранить ключ зашифрованным с привязкой к пользователю, провайдеру и ревизии. Ключ не возвращается через GET, журналы, экспорт, RAG или prompt.

#### Scenario: Два пользователя
- **WHEN** A и B обращаются к одной модели
- **THEN** каждый запрос использует только персональный ключ своего пользователя; отсутствие ключа B не подменяется ключом A, администратора или окружения.

#### Scenario: Изменение адреса
- **WHEN** администратор меняет URL или runtime провайдера
- **THEN** прежний персональный ключ не передаётся новому провайдеру.

### Requirement: Сохранение и отзыв личного доступа
Система SHALL разрешать аутентифицированному пользователю сохранять и удалять только собственный ключ через CAS и подтверждённую квитанцию. Удаление убирает ciphertext текущего личного ключа, сохраняя безопасную историю операции.

#### Scenario: Потерянный ответ
- **WHEN** ответ сохранения или удаления потерян, включая отзыв прав после COMMIT
- **THEN** прежний requestKey сохраняется; чтение квитанции и точный повтор не создают новую операцию.

#### Scenario: Конкурентное изменение
- **WHEN** credentialRevision или connectionRevision устарела
- **THEN** операция не заменяет свежий ключ, сообщает конфликт и сохраняет ввод пользователя.

### Requirement: Авторизация перед физической отправкой
Система MUST проверить точного пользователя, актуальный доступ, провайдера и отзыв ключа перед физической отправкой HTTP, сохраняя существующие квоты и запрет перенаправлений.

#### Scenario: Отзыв во время ожидания
- **WHEN** ключ или доступ отозваны, пока запрос ждёт rate limit или резерв квоты
- **THEN** провайдер не получает запрос; неиспользованный резерв освобождается по существующему контракту.

#### Scenario: Уже отправленный запрос
- **WHEN** отзыв происходит после физического начала запроса
- **THEN** принятый результат и учёт расхода сохраняются; повторного платного запроса нет.

### Requirement: Общая модель не содержит личный доступ
Система MUST сохранять общий model pin и embedding profile при ротации личного ключа. Личная ошибка авторизации одного пользователя не блокирует модель для другого.

#### Scenario: Ошибка ключа A
- **WHEN** провайдер отклоняет ключ A
- **THEN** ключ B и общая готовность модели не меняются.

### Requirement: История и независимые транспорты
Система SHALL сохранить прежние общие зашифрованные секреты без угаданного владельца и без использования в новых запросах. Отключение функции сохраняет разрешённые текущими правами сведения и восстановление. Локальный OpenCode auth и управляемый хостинг используют собственные маршруты.

#### Scenario: Старое подключение
- **WHEN** существующая модель имела общий ключ администратора
- **THEN** этот секрет остаётся сохранённым, а новый пользователь настраивает личный доступ.

#### Scenario: Функция выключена
- **WHEN** персональный удалённый доступ выключен
- **THEN** новые изменения и удалённые запросы закрыты; разрешённое чтение статуса и квитанций остаётся доступным.
