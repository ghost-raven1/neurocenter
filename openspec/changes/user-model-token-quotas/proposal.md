# Proposal

## Why

Общий лимит запросов модели ограничивает частоту всей команды, но не персональное потребление токенов. Нужен настраиваемый главным администратором бюджет человека для конкретной модели с честным учётом, понятным отказом и сохранением работы после потери подтверждения.

## What Changes

- Политика принадлежит normalized пользователю платформы и каноническому ID модели: суммарные входные и выходные токены, явно выбранный токенный период, включение и ревизия. Период не наследует ограничение request-rate1с–24ч или аналитические1/7/30дней.
- Перед фактической отправкой атомарно проверять фактический расход и активные оценочные резервы, включая резерв нового вызова. Не допускать новые запросы, когда бюджет для оценки исчерпан.
- После ответа учитывать reported usage ровно один раз. Возможное превышение последним ответом сохранять полностью, показывать пользователю и учитывать при следующем admission. Это выбранная пользователем семантика, не жёсткий billing ceiling.
- Переиспользовать существующий usage ledger, его UUID и приватную атрибуцию. Оценка, фактические токены и неизвестный исход различаются; ради восстановления учёта inference не повторяется.
- Настраивать политику через UI модели с выбором существующего пользователя, включая ещё не совершавшего вызовов. Ошибка сохраняет ввод; история, settlement и recovery доступны независимо от флага.
- Отсутствие provider output cap само по себе не блокирует выбранную модель: резерв остаётся оценкой с указанным основанием. Управляемые серверные вызовы и прямые локальные BYOK-вызовы имеют явную границу полномочий.

## Capabilities

### New Capabilities

- `user-model-token-quotas`: персональная политика канонической модели, оценочное резервирование, фактическое списание с видимым превышением и восстановление.

### Modified Capabilities

Нет. Основной capability inventory пуст; общий request-rate limit и существующий usage остаются самостоятельными контрактами.

## Impact

Политика и API в catalog-service, дополнение существующих ModelUsageService/Repository и физического admission, компактная frontend-фича рядом с настройками модели. Единственный основной usage ledger — `model_usage_calls`; отдельной конкурирующей таблицы попыток не создаётся. Нужны таблица политики, журнал её exact mutations и добавочные quota-поля существующего usage receipt; независимый physical-attempt journal допускается только при доказанной необходимости нескольких sends внутри одной observation.

Root координирует реестры, DI, фичафлаг и OpenAPI. Для готовящегося среза назначена миграция46 после существующих0–45. Ранее предложенный reset46 не зарегистрирован и не выпускался; его отдельный WIP при интеграции получит47 и повторную проверку схемы. Новый пакет/tokenizer, платные вызовы и изменение рабочей БД не требуются для контракта. Это отдельный WIP вне стабилизируемого релиза; production-реализация начинается после его release gate и назначения файлов.
