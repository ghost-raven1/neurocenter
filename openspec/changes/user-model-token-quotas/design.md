# Design

## Context

См. proposal.md. Существующий ModelUsageService создаёт `model_usage_calls.id` до inference, хранит canonical model ID, trusted actor/provenance, nullable input/output, worker/lease и агрегированный dispatchCount. При ошибке записи он повторяет receipt, сохраняя исходный ответ провайдера. ModelApiAdmission проверяет текущие права/флаги непосредственно перед физической отправкой, но activity progress пишется после её начала и может быть пропущен.

Подтверждённая пользователем семантика: запрещать **новые** вызовы по расходу и резерву; возможное превышение последним ответом учитывать и показывать. Прежний hard-ceiling вариант и обязательная bounded-adapter матрица больше не являются условиями реализации. Источники: `.run/user-model-token-quotas-20261028/{source-contract,ledger-seams-review,bounded-adapter-review}.md`; последний отчёт остаётся свидетельством отсутствия hard-bound, а не запретом мягкого admission.

## Goals / Non-Goals

Цель — один owner учёта и первый связный managed-server срез от MainAdmin политики до отказа, результата и восстановления. Оценка ограничивает admission и конкуренцию; она не доказывает максимальный счёт провайдера. Не нужны второй top-level attempt ledger, новый tokenizer, цены, календарный billing или управление прямыми внешними BYOK-вызовами.

## Decisions

1. **Политика и период.** Ключ — normalized platform email + canonical model ID. Отсутствующая политика означает ненастроенный конечный бюджет. Политика содержит tokenLimit, enabled, CAS revision и собственную положительную длительность `periodMs`; UI явно показывает длительность и начало учёта. Длительность хранится независимо от request-rate `windowMs`, поддерживает бюджеты длиннее суток и не наследует rate1с–24ч или аналитические1/7/30дней. ROOT утвердила default1сутки и настраиваемую положительную безопасную длительность до365суток; это отдельный token-policy validator, не копия rate-ограничения. Изменение pin, display name или ревизии политики не сбрасывает уже учитываемый расход. Начало учёта новой политики фиксируется явным серверным receipt; историческим unknown не приписывается выдуманный actual.

2. **Единственный ledger.** Расширить `model_usage_calls`, сохранив его UUID как identity попытки, existing actual input/output, attribution, worker/lease и историю. Нужны quota-state, reserved/debit amounts и компактные metadata: версия оценки, input/output estimate, политика/период, DB-time admission, model pin и settlement proof. Старые строки не переписываются. Таблица policy и её exact-write receipts являются настройкой, не вторым usage ledger. Для текущих обычных server adapters один observe уже соответствует одному physical send. Следующий физический retry получает новую связанную usage identity. Child attempts понадобятся только если реально сохраняется несколько sends внутри одного observe: scalar dispatchCount тогда не обеспечивает раздельный settlement; до такого изменения новая таблица не создаётся.

3. **Оценка вместо hard-cap.** Сервер строит версионированную input+output estimate из уже подготовленного запроса и существующих planning данных. Текстовая input-эвристика остаётся явно `estimate`; её нельзя выдавать за tokenizer или actual. Известный лимит/план ответа используется как основание output estimate; при его отсутствии применяется явная серверная оценка, без добавления неподдерживаемого wire-параметра и без запрета модели лишь из-за cap. Основание и неопределённость доступны в receipt. Первая реализация не расширяет протоколы провайдеров или adapterParameters ради hard-bound.

4. **Atomic check + reserve.** Единственная обязательная точка резерва — named physical admission, связанная с usage UUID. Не устанавливать новый reserve в общий beforeDispatch callback: тот вызывается несколько раз на runtime/admission/device polling. Под короткой транзакцией и nonblocking user+model lock читаются свежая policy и DB clock; разрешение требует `charged + activeReserved + heldUnknown + newEstimate <= tokenLimit`. Проверка и запись резерва неразделимы. HTTP inference, fresh-authority callbacks и вложенные pool checkouts не выполняются под бюджетным SQL-lock. После ожиданий и перед dispatch права/политика проверяются заново. Устаревшая identity или неизвестный COMMIT не разрешают send/new UUID; доказанно неотправленный резерв освобождается через CAS.

5. **Settlement и превышение.** Полный reported input+output заменяет резерв один раз в том же usage owner. Actual не обрезается до оценки или лимита. Полученный ответ сохраняется при overrun; UI показывает превышение и отказ следующей попытки по обновлённому балансу. Частичные actual и удержанный неизвестный debit различаются; admission не учитывает один и тот же остаток как полный reserve и полный charge одновременно. Минимальная консервативная оценка неизвестного итога не ниже уже известной части расхода. Изменение budget accounting не превращает оплаченный результат в повторный inference при сбое metadata.

6. **Неизвестность и поздний ACK.** Pending/dispatch/settled/unknown/released различаются в quota-state, а public usage status сохраняет прежнее значение. После dispatch отмена, истечение lease, некорректный ответ или потеря usage не означают бесплатный вызов. Active/unknown reserve не исчезает лишь на границе периода. При unknown settlement повторяется только идемпотентная запись/чтение существующего UUID. RAM writeback остаётся быстрым путём, но durable reserve переживает процесс и отражается как unknown до достоверного уточнения. Поздний usage обновляет тот же учёт с proof/CAS; не меняет cancelled job в success. Для асинхронного device-канала связь с durable call receipt обязательна, иначе его coverage не объявляется завершённой; отсутствие output cap не является причиной такой границы.

7. **UI, права и OFF.** MainAdmin выбирает пользователя через существующий `/api/platform/users`, не через usage facets; редактор принадлежит auth+model+target user. Write сохраняет exact body/key до POST, использует expectedRevision, read receipt и явный exact replay;404 не доказывает отсутствие принятия. Свежий403 очищает приватный view и не теряет неизвестный journal. Counters раздельны: actual, active reserve, unknown estimate и overrun; рядом объясняется оценочный admission, не billing ceiling. Root-owned флаг `user_model_token_quotas` defaultOFF выключает новые quota checks, но не обычный mandatory usage, settlement/history/recovery. При включении учитываются сохранённые authoritative факты, а не фальшивый reset. Прямой локальный BYOK вне managed API обозначается как неподконтрольный, без выдуманных токенов.

## Risks / Trade-offs

- Оценка может оказаться ниже фактического расхода → полный overrun остаётся видимым, следующий admission учитывает его; это принятая семантика.
- Консервативный unknown временно уменьшает доступный бюджет → UI показывает неизвестную часть и путь чтения/сверки, без time-only refund или платного повтора.
- Строки без прежнего quota metadata/асинхронные late receipts → не выполнять массовый backfill догадками; перед включением политики явно закрепить границу учёта и покрытые каналы.
- Необязательная activity metadata не является reservation proof → mandatory budget transitions отделены от best-effort progress, сохраняя pool/deadline изоляцию.

## Migration Plan

Root назначил миграцию46: зарегистрированная цепочка заканчивается45 и требует непрерывности. Предварительный reset46 из другого незавершённого worktree не является выпущенной миграцией; перед его интеграцией номер станет47 с новым контрактом и проверками. Исторические SQL0–45 не меняются. Additive schema: policy + exact policy-write receipts и quota-поля/indexes existing usage table. Прежние actual/history остаются неизменными, defaultquota-state nullable. Root отдельно согласует classification новых policy settings и usage fields в reset/retention; partial reset не должен случайно удалять настройку как рабочий журнал.

Сначала schema/verifier и флагOFF, затем API/ledger/admission/UI. Первое включение возможно только для явно проверенных managed путей; server text adapters дают минимальную связную вертикаль без нового ledger. Остальные managed пути получают ту же identity/settlement-связь до объявления их enforcement; они не выдаются за покрытые по одному наличию настройки. Rollback выключает новые quota checks, продолжает settlement принятых receipts и не удаляет столбцы/историю. Production rollout не входит в текущую source-only фазу.
