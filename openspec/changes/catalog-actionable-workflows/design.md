# Design

## Context

См. proposal.md. База аудита: main b81cd2aa, локальная ссылка origin/main совпадала (без нового fetch); мост пакета 0.9.28. Чужие untracked-файлы сохранены. Пассивный MCP 30.10.2026: Catalog live 200 / ready 503, bridge/frontend/flags/skills/RAG/gateway недоступны. Это не сведения о рабочей площадке на фотографиях.

Существуют publication preview с version/hash, durable build journal, отдельные редакторы RemoteConnectionModal/RemoteProviderAccess, импорт метаданных OpenCode и локальная форма провайдера. Основные разрывы — переходы между ними. Реальные причины и фото собраны в evidence.md.

## Goals / Non-Goals

**Goals:** переиспользовать действующих владельцев состояния и прав; сделать следующий шаг явным; доказать отсутствие повторной сборки/потери ввода. Очереди менять по независимым срезам.

**Non-Goals:** новая UI-библиотека, переименование таблиц и API, автоматическое обновление всех проектов, массовая передача ключей, расширение лимитов без бюджета, новая функция фотографий по присланным снимкам.

## Decisions

1. **Совпадение имени.** Узкий lookup точного имени без учёта регистра под существующими правами упаковщика. Результат — id/kind/archive, затем существующий preview и явное подтверждение version/hash. Общий поиск ILIKE не подходит: скрывает архив и допускает неточные совпадения. Серверная проверка create/CAS остаётся обязательной после клиентского preflight. Несовпадение типов не преобразует инструмент автоматически.

2. **Проблема → действие.** Сводка сопоставляет item.id с актуальным source plan. Переход открывает мастер нужного рецепта, существующий сохранённый запрос либо конкретную операцию. Открытие никогда не означает submit. Для неизвестного/устаревшего плана — объяснение и перечитывание; для архивной поставки — импорт. UI не предлагает повтор, пока исход прежнего запроса неизвестен.

3. **Общий каталог.** Сначала совместимая вкладка «Поставка» и переиспользование карточек/действий; затем устранение дублирующей страницы. /assets остаётся redirect с сохранением query и восстановления. Карточка отображает один объект, но отдельно источник, опубликованную редакцию, закрепление проекта и квитанцию компьютера. Права источников не расширяются из-за общего экрана. Готовый пакет → «Обновить в проекте»; только исходники → «Подготовить обновление»; ручной конфликт → просмотр изменений и подтверждение.

4. **Контекст шапки.** Извлечь выбор проекта из Store в фичу контекста с URL как общим источником выбранного id. Не создавать второй независимый store в Core. Компьютер/OpenCode/каталог проекта/операции/чат используют общие 48px высоту и отступы. Проверить embedded Store, прямой URL, reload, роль и смену проекта при открытом диалоге.

5. **Провайдеры.** На карточке явное действие «Провайдер и API-ключ» открывает существующие редакторы с местом исполнения. Участник может изменить личный доступ, администратор — общий endpoint. Объединение формы не объединяет права или хранилища. Из OpenCode сначала читаются только безопасные метаданные. Серверный импорт выбранного API-ключа — отдельный capability/flag и подтверждение точного получателя; OAuth не превращается в API-key. Локальный режим использует ключ на компьютере. Пока этот перенос не реализован, показывается честный ручной ввод, а не обещание импорта.

6. **OpenCode 2.** Сейчас shared AUTH_VERSION и native actual-PATH gate закреплены на 1.14.48. Добавить отдельный версионный adapter после изучения первичного контракта установленного CLI и независимой fixture V2. Не подменять константу диапазоном 2.x. Доработка продолжает bridge-first-local-setup: поправить текущий контракт read-only для иных версий и восстановить отсутствующий в tasks раздел V2 до реализации. Показывать безопасные причины inventory.issues по отдельности.

7. **Очереди.** Сначала server+bridge capability и две bounded полосы обычных/коротких управляющих операций. Короткие виды определяет серверный allowlist; допустимый начальный кандидат — read-only проверка версии CLI, только без конфликта с установкой CLI. Смена папки/глобальной конфигурации имеет device-wide fence; действия папки — binding/instance fence. Старые мосты работают serial. Уже существующие system-role lanes и MCP budget сохраняются.

8. **Сборки и импорты — следующие срезы.** PackageBuildService singleton child/activeBuild и global recovery всех RUNNING требуют job-owned lifecycle прежде чем добавить второй слот. Для import учитываются зависимости и публикация одной карточки. Capacity reservation на каждый job, exact cancellation, owner/nonce lease и CAS публикации обязательны. Параметры идут в существующий configurable-runtime-limits 5.1; длинные работы получают гарантированный бюджет, внутри полосы FIFO, между проектами bounded fairness.

9. **Архивы.** Ошибка на IMG_1259 — лимит извлечённых исходников, включая игнорируемые файлы, а не лимит готовой поставки. Сохранить защиту от распаковки большого архива. Для известного OpenCodeRAG вести в закреплённый рецепт, для готового runtime — импорт поставки. Изменение лимитов согласуется с валидатором публикации, транспортом и runtime policy, а не одной константой.

## Восстановление bundled-сборки, срез 1.5

Операция получает только безопасный `toolBuildSource` с id и revision из связанной глобальной сборки того же actor. Защищённый GET сборки возвращает ограниченную bundled-проекцию `recovery`: исходник, платформы, kind, name, description, tags и при обновлении id выбранной карточки. Исходные файлы, пути, agent config и прежние version/hash/согласие на публикацию не возвращаются. Миграция таблиц не нужна: данные уже сохранены в конфигурации сборки.

Ссылка `/assets?prepare=<sourceId>&recoverBuild=<buildId>` открывает существующий мастер и журнал. Чтение не вызывает POST. Другой незавершённый локальный запрос сохраняется; потеря ACK разрешается прежним requestKey. Явный повтор подтверждённой FAILED/CANCELLED сборки использует новый ключ, исходную revision и свежий publication preview/CAS. Если исходная revision больше недоступна, интерфейс объясняет причину без автоматической замены текущим рецептом. Старые и не-bundled операции сохраняют совместимый путь восстановления.

## Квитанция встроенного импорта, срез 1.4

Для встроенного импорта квитанция пересборки хранит отдельный `importId`; `operationId` сборки нормализуется в `tool-build-<UUID>`. Старые квитанции совместимы: raw UUID обычной сборки нормализуется при переходе, raw UUID строки `inline:` читается как id импорта. Путь `/assets?recoverImport=<UUID>` читает существующий GET импорта, не записывает новый intent и не перезаписывает другой локальный журнал. После открытия используются существующие retry/resolve/cancel по id задания. Неизвестный ответ координатора разрешается поиском по прежнему deterministic request key; недоступный lookup не считается разрешением создать второй импорт.

## Risks / Trade-offs

- Один общий экран смешивает права → доступ к поставкам и действиям проверяется отдельно от видимости каталога.
- Предварительная проверка имени устаревает → серверный create guard и CAS сохраняются; ввод остаётся после конфликта.
- Переход по ссылке обходит журнал → мастер сначала восстанавливает собственный scope, не начинает другую сборку поверх неопределённого запроса.
- Разные стадии обновления выглядят как успех установки → сообщение и кнопка называют только подтверждённый этап.
- Конкуренция повреждает общие файлы → блокировки ресурсов на обеих сторонах, проверка реальным PG/bridge до включения.
- Ключ может уйти неверному получателю → явный выбор исполнения/endpoint, собственные права и ревизия; секреты не входят в каталог и логи.

## Migration Plan

1. Узкие исправления упаковки и сводки под существующими флагами, unit/DOM/типы и независимое review. Отдельная browser-проверка на готовом стенде.
2. Общая навигация/терминология и шапка с совместимыми ссылками. Затем вход к настройке модели.
3. Версионная интеграция V2 и явное использование ключей — по отдельным проверкам native, прав и пользовательского результата.
4. Queue capability развёртывается server→bridge с выключенным новым флагом; старые workers сохраняют serial. Включение после PG/installed archive приёмки. Отключение прекращает новый admission, но даёт завершиться принятым lease.
5. Сборщик/импорты распараллеливаются отдельно после job-owned recovery. Данные/история не удаляются при откате.

## Явный перенос личного ключа, срез 2.5

Первый поддерживаемый маршрут ограничен сохранённой записью `openai.type=api` обычного OpenCode1.14.48 и личным доступом выбранной `remote-openai` модели с точным `https://api.openai.com/v1`. OAuth, ссылки на окружение и V2 accounts не преобразуются в API key. Фоновая синхронизация по-прежнему передаёт только метаданные.

Отдельные `open-opencode-personal-key`, capability `opencode-personal-key-v1` и выключенный по умолчанию `opencode_personal_key_transfer` используют существующий lifecycle глобальных заданий. Публичный запрос хранит только model/device/provider IDs, CAS revisions и request UUID. Actor берётся из серверного задания. Открытие окна — отдельная квитанция, не подтверждение сохранения ключа.

Приватная loopback-форма переиспользует session/CSRF/expiry/cleanup локального редактора. Она показывает сайт, фактический API origin, пользователя, модель, endpoint и ревизии. Подготовка читает только выбранную API-запись после свежей проверки CLI/owner; явное второе действие передаёт ключ напрямую device endpoint. HTTP допускается только для loopback, иначе нужен HTTPS; перенаправления, environment proxy и исходные тексты сетевых ошибок не используются. Ключ не попадает в DOM, website API, job payload/result или completion outbox.

Сервер переиспользует personal repository: AES-GCM, actor/provider fences, CAS и прежний request key. Дополнительный transaction guard держит device→job locks и проверяет свежие права/флаги/получателя до записи. Transfer provenance отделяет request hash от ручного сохранения; внутренний hash и provenance не выдаются через public transfer receipt или альтернативный manual receipt endpoint. Native intent хранит target, request UUID и файловый stat fingerprint, без ключа/его хеша. После lost ACK сначала читается прежняя квитанция; повтор использует прежний запрос и неизменный источник.

История читается при OFF. Для истёкшего открытого окна browser receipt возвращает серверный `canStartNew`, рассчитанный после exclusive job fence, который дожидается уже допущенной записи. Браузер не делает выводов по своим часам и не открывает новое окно автоматически. Параллельные изменения ключа остаются защищены CAS. Настоящий PostgreSQL, установленный мост, браузер и production требуют отдельных свидетельств.
