# Spec Delta

## Purpose

Проводить задачи проекта по BMAD/OpenSpec внутри Нейроцентра с сохраняемыми этапами и настоящими изменениями кода и проверками через локальный мост.

## ADDED Requirements

### Requirement: Versioned project workflow
Система SHALL позволять выбрать BMAD, OpenSpec или совместный режим BMAD → OpenSpec для задачи проекта и сохранять версии методик, этап, текст задачи, команды проверки, точную привязку и результат. Принятый запрос MUST использовать неизменяемый снимок этих входов. Локальные документы читаются на момент фактического запуска; интерфейс MUST сообщать эту границу, а результат SHALL сохранять наблюдаемые хеши изменений и итоговых артефактов.

#### Scenario: Start a project task
- **WHEN** администратор проекта запускает задачу с выбранной методикой
- **THEN** интерфейс показывает методику, этап и точный компьютер/папку исполнения

#### Scenario: Continue existing artifacts
- **WHEN** в привязанной папке уже есть документы и незавершённая задача методики
- **THEN** исполнитель продолжает текущий допустимый этап без перезаписи принятых требований и ручных изменений

#### Scenario: Local files change while queued
- **WHEN** после принятия запроса локальные документы изменились до начала исполнения
- **THEN** исполнитель использует текущие файлы выбранной папки, сохраняя прежние текст задачи, методику и команды; система не объявляет документы снимком на момент принятия запроса

#### Scenario: Combine methods
- **WHEN** выбран режим BMAD → OpenSpec
- **THEN** принятые требования и архитектура BMAD становятся входом изменения OpenSpec без второго PRD и двойной реализации

### Requirement: Untrusted or damaged knowledge
Система SHALL отличать необязательные знания Quirk от принятых требований. Повреждённое хранилище MUST NOT подменять требования, получать ложную отметку готовности или автоматически очищаться при запуске задачи.

#### Scenario: Damaged Quirk storage
- **WHEN** чтение Quirk не проходит проверку целостности
- **THEN** отказ виден, прежние данные сохраняются и доступно продолжение без неподтверждённого контекста либо явное устранение обязательной зависимости

### Requirement: Execute through the bound local bridge
Система SHALL выполнять работу с файлами и команды проверки только через авторизованный мост в точной привязке проекта. При отсутствии исполнителя или методики MUST быть видна причина и действие продолжения без ложного успеха.

#### Scenario: Real code and checks
- **WHEN** локальный исполнитель изменил код и выполнил проверки
- **THEN** результат содержит фактические изменения, команды и их исходы, различая успешные, неуспешные и невыполненные проверки

#### Scenario: Missing prerequisites
- **WHEN** мост недоступен либо локальный исполнитель не настроен
- **THEN** задача сохраняется, интерфейс объясняет следующий шаг, код не считается изменённым и проверки не получают PASS

### Requirement: Durable cancellation and replay
Система SHALL сохранять идентичность принятого задания и результат до подтверждения доставки. Повтор получения результата MUST NOT повторно запускать исполнителя при неизвестном исходе. Отмена MUST завершать принадлежащие заданию процессы.

#### Scenario: Lost acknowledgement
- **WHEN** после выполнения теряется подтверждение сервера
- **THEN** повтор возвращает сохранённую квитанцию без нового исполнения кода

#### Scenario: Cancel or lose authorization
- **WHEN** задание отменено, отозван доступ либо изменена привязка папки
- **THEN** исполнитель останавливает свои процессы и поздний результат не продолжает прежнюю задачу

### Requirement: Feature availability and history
Новый цикл SHALL управляться фичафлагом независимо от прав. При OFF система MUST сохранять историю, результаты, отмену и восстановление принятых заданий.

#### Scenario: Workflow disabled during execution
- **WHEN** администратор выключает функцию при незавершённом задании
- **THEN** новые задания недоступны, а разрешённые чтение результата и отмена остаются доступны
