# Design

## Context

См. proposal.md и три spec delta. Прежний мастер имеет четыре шага с повторным legacy-footer и статической строкой CLI в SetupProgress. BridgeConnection уже меняет общий selected device; отчёт содержит bridgeVersion, но не версию пользовательского OpenCode. BridgeSourcePanel различает доступную, импортированную и реально готовую поставку. Его build progress относится к подготовке пакета на площадке, не к обновлению компьютера.

Device jobs уже имеют device-global примеры choose-root/model scan, durable request aliases, claim, lease и состояние reconciling. Обычный worker/pause считает reconciling активной работой: обновляющий себя worker не сможет безопасно использовать этот путь без отдельной передачи исполнения. Существующий проектный provider engine требует project/binding/model pin и пишет bridge-private credential; он не является глобальным OpenCode auth owner.

## Goals / Non-Goals

**Goals:** сохранить действующих владельцев очереди/установщика, добавить фиксированные операции конкретного компьютера до выбора проекта, сделать видимые стадии соответствующими фактам исполнения.

**Non-Goals:** произвольный shell от браузера, скрытый платный inference, автоматический перенос локальных ключей на сервер, ослабление проектных ACL/binding, обновление неизвестного владельца процесса или удаление активного runtime.

## Decisions

1. Start остаётся единственным Ant Design owner для обычных, pairing и исторических ссылок. По уточнению пользователя «Старый мастер не нужен» legacy-компонент и его отдельные проектный шаг/карточки расширений удаляются без render fallback. В текущем четырёхшаговом мастере исторические `step=1`/`step=2`, pairing и add-computer intent ведут к основному этапу «Компьютер и папка»; `setup=1` сохраняет индексы основного мастера. Переходы сохраняют `p`, `connect`, `extension`, прочий query-контекст и hash; `setup=0` позволяет свернуть мастер, сохранив pairing-контекст, а основной переход удаляет obsolete `legacy`. Одна помощь возвращает к основному подключению. Удаление прежнего UI не доказывает будущую перестановку bridge-first из задачи 5.1. Основная шапка показывает выбранный компьютер, свежесть и сообщённую версию; детали проекта и инструментов находятся в своих шагах. Проверка папки сначала ведёт к выбору, затем к явной проверке готовности. Навигация не завершает job.
2. Добавить browser-safe shared contract для device-global software actions и public results. Каждый action — фиксированный тип, без command/path/secret из браузера. Admission, claim, dispatcher и completion проверяют одинаковые target/capability/flag/authority. Использовать existing bridge_jobs/request aliases/operation tracking; новые SQL таблицы для первого среза не нужны. Не менять исторические миграции.
3. CLI observation разрешает пользовательский executable в нормальном локальном контексте и запускает только `--version` через владельца ограниченного дочернего процесса. Результат: device/job identity, checkedAt, missing/failed/timed-out/installed и допустимая версия. В completion не передавать stdout/stderr: исключить случайный вывод конфигурации или секретов. Исчезновение связи даёт unknown, а не missing.
4. Установка CLI — fixedglobal `install-opencode-cli` с четырёхпольным UUID-запросом и capability `opencode-cli-install-v1`; оба действующих role имеют минимум 2. Сервер закрепляет `{buildId,target,version,sha256}`; `ComputerSetupSupplyApproval` проверяет её по каноническому Gateway supply. Без approval provider новая установка запрещена. Approval предшествует финальному SQL-снимку прав, lease и точного report source. Native использует только `bin/opencode-probe` 1.14.48 своего runtime, сверяет SHA и fixed version, публикует отсутствующий `~/.local/bin/opencode` атомарным link под install mutex. Ручной/более новый CLI сохраняется. Конфиги, auth и shell profile не меняются. Установленная версия и обычная PATH-команда проверяются отдельно; отсутствие `.local/bin` в PATH даёт `inspect-path`. Private journal до копирования закрепляет stage inode/parent; durable marker предшествует публикации. Recovery удаляет только свой stage, сохраняет опубликованный файл, возвращает unknown/reconcile после marker и не повторяет копирование. Потеря ACK перечитывает исходный UUID/outbox.
5. Версия установленного моста берётся из его heartbeat, готовая версия обновления — из совместимой проверенной install supply, а не просто available.version. Сравнение учитывает target/build и свежесть. Старый мост без новой команды получает единственный поддержанный путь первичного обновления в помощи; браузер не предполагает отсутствующую capability.
6. Автообновление использует внешний supervisor из проверенной стадии вне заменяемого runtime. До handoff обычный job держит lease. Специализированная транзакция блокирует device, проверяет отсутствие иной активной работы/MCP, переводит точный update job в reconciling и выдаёт ограниченный handoff permit; claim не пересекает эту передачу. Installer adapter узнаёт только этот точный permit и исключает только собственный handoff из pause count. Обычный pause/чужие jobs не ослабляются. Supervisor применяет существующий атомарный installer/stop/recovery протокол и пишет durable локальные стадии. Сервер завершает обновление по подтверждённому новому heartbeat/build, а не по запуску helper. Неизвестный исход сохраняет reconciling и исходный request key.
7. Новый global provider adapter до проекта читает реальные OpenCode config/auth и перечисляет все API/OAuth/auth-only providers. Он не использует ограничение project providerKinds и не требует модель каталога. Linux auth следует XDG_DATA_HOME. Локальная форма работает в существующей loopback/same-origin/CSRF/capability границе; сайт показывает выбранный компьютер и ожидает свежий безопасный статус. iframe и server key-transfer не включаются.
8. Изменение auth адресует выбранный provider ID, использует реальный pinned OpenCode auth owner и сохраняет остальные записи/неизвестные поля. Перед реализацией мутации отдельный native fixture закрепляет поведение pinned1.14.48 на API/OAuth/unknown fields/invalid auth и наблюдаемом внешнем изменении. При конфликте сохраняются исходные байты; пустой fallback запрещён. Никакой секрет или его производный отпечаток не возвращается на сайт.
9. Новые software/auth mutations и CLI inspection управляются `computer_setup` default true с зависимостью computer_connections и новой capability моста. Безопасный global provider READ — отдельное разрешённое действие при OFF: только метаданные текущего локального окружения, действующий owner и свежие ACL, без ключей и model calls. OPEN и каждое сохранение остаются gated `computer_setup` и `computer_connections`. Existing unified_project_setup управляет основным UI. OFF оставляет accepted jobs/status/history/cancel/recovery. Смена устройства/роли/сессии меняет async owner; чтение исходного результата не зависит от текущего открытого шага.
10. Новая навигация имеет шесть стадий и marker `setupFlow=bridge-first`, индексы `step=0..5`. Исторические connection/pairing/add-computer ссылки ведут к мосту; прежние явные agents/check `setup=1&step=2|3` — к новым стадиям 4|5. Переходы сохраняют проект, pairing, справку, hash и сворачивание. Этот versioned контракт заменяет четырёхшаговую адресацию из исторического решения 1. Header и Start используют общий owner. Известная квитанция установки не создаёт повторный автоматический inspection при навигации; явное «Проверить OpenCode» вызывает fixed inspection. Отказ чтения не восстанавливает private version из устаревшего bridge snapshot.

## Risks / Trade-offs

- Самообновление может остановить свой исполнитель → внешний supervisor, fenced handoff, новый heartbeat как критерий успеха; никаких force kill неизвестных процессов.
- Старый мост не умеет новый job → capability gate и один поддержанный первичный upgrade/reconnect через помощь.
- Локальный auth может редактировать другой процесс → контрактный fixture реального owner, проверка наблюдаемого изменения и отказ с сохранением; не обещать атомарность произвольных внешних писателей.
- Локальная форма открывается на выбранном компьютере → явно показывать target и ожидание; секрет не пересылать через центральный job.
- Наличие provider auth не доказывает ответ модели → отдельная явная проверка без автоматического платного вызова.

## Migration Plan

Поставить UI cleanup отдельно проверяемым коммитом. Затем shared/backend admission и bridge capability без включения неподдержанных действий на старом устройстве; проверить CLI observation и установку, global auth, supervisor update. После native/browser приёмки переставить основные этапы и актуализировать документацию. Отключение computer_setup прекращает новые admissions, сохраняя исходные квитанции и recovery. Проверки и выпуск 0.9.25 остаются в исходном checkout; эта ветка не меняет его кандидата.
