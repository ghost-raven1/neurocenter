# Design

## Context

См. proposal.md. В dev CLI профиль fast сейчас всё ещё выполняет asset selection в TTY, Native входит в общий набор пакетов, image/signing/runner проверщика обязательны. Root/Catalog/Gateway скачивают контракт ассетов из codeload того же внешнего репозитория. Действующий UI уже принимает архивы закреплённого источника и позволяет оставить веса невыбранных моделей отсутствующими.

RAG-сервис уже использует Nest/PostgreSQL без LanceDB/Ollama-плагина в runtime. Его публичная запись и seal требуют настоящих embeddings; keyword retrieval и UI загрузки документов отсутствуют. Nullable embedding не используется как обход semantic-контракта.

## Goals / Non-Goals

**Goals:** детерминированный базовый запуск, выборочная архивная доставка, полезный первый поиск на существующем стеке, сохранность принятой работы.

**Non-Goals:** полная автономная установка npm/ОС, замена выбранных embeddings, автоматический платный inference, произвольные недоверенные архивы, обновление upstream OpenCodeRAG и удаление повреждённого Quirk.

## Decisions

1. Переиспользовать fast как явный базовый профиль для install/build/up/watch. В нём нет asset selection/prefetch, Native npm/build/pack/apply и image build. Расширенную подготовку оставить явному существующему профилю. Существующие install outputs не удалять; общий список отслеживаемых процессов сохраняет владение прежним runner при down.
2. Включить минимальный runtime/CLI контракт ассетов в vendor с SOURCE/NOTICE и SHA-описью точного upstream commit e1255b4. Код совпадает с принятыми API Root/Catalog/Gateway; runtime dependencies отсутствуют. Обновить локальные dependencies/locks, Docker source paths и prepared-source closure. Удалённый пакет сохранял скрытую обязательную asset-зависимость; копирование всех descriptors/prompts/весов из upstream не требуется.
3. Разделить сохранение signing identity и подготовку executor. Базовый режим не создаёт и не заменяет ключи. Catalog получает явное runtime-состояние disabled/unconfigured для запрета новых публикаций даже при старом heartbeat. Исторические подписи и recovery не зависят от нового допуска. Явная полная подготовка сохраняет image digest/SDK/DB advisory проверки.
4. Первый архивный срез переиспользует доверенный source archive: полная небольшая metadata-история плюс blobs выбранных компонентов. Упаковка/помощь объясняет текущую границу всех заявленных платформ выбранного компонента. Standalone asset.json и произвольная новая metadata не выдаются за уже поддержанные; trustedPins, index evolution и stable ID остаются обязательными.
5. Текстовый корпус имеет отдельную ревизию и квитанции в существующем RAG/PostgreSQL owner. Catalog владеет свежей проектной авторизацией и идентичностью запроса; RAG владеет атомарной записью, бюджетом и текстовым поиском. Существующие semantic generation/profile/seal и общий бюджет не обходятся. PostgreSQL full-text/действующие зависимости обеспечивают первый режим без дополнительного сервиса.
6. Новый флаг текстового режима независим от model_hosting; существующий project_search остаётся семантическим. UI показывает загрузку и поиск как основной путь, модель/синхронизацию — как расширение. Контекст чата/агента хранит режим, ревизию и источники принятого поиска; переключение существующего semantic-профиля не выполняется молча.
7. Уточнённый контракт доставки: GitHub Releases недоступен пользователю и не становится новым обязательным каналом после переноса репозитория. Основной Git должен содержать проверенные текущие немодельные исходники/рецепты/metadata; веса hosting-моделей добавляются только явным импортом GGUF/архива. Ни fast, ни full, ни сохранённый выбор компонентов не должны автоматически скачивать веса. Полный перенос текущих компонентов, поддержка GGUF и удаление отдельного репозитория следуют отдельными проверяемыми срезами; минимальный vendor-контракт не выдаётся за их завершение.
8. Доступ к моделям сохраняет три маршрута: провайдеры OpenCode, remote API и установленный hosting. Общий проектный контекст с разрешёнными чатами, Quirk и знаниями нужен каждому маршруту; явный текстовый RAG этого изменения предоставляет только выбранный корпус/цитаты и не считается полной реализацией агрегатора.

## Risks / Trade-offs

- Существующий node_modules скрывает сетевую зависимость → холодный checkout, отдельные HOME/cache, блокировка asset-hosts и настоящий offline root npm ci.
- Старый verifier heartbeat показывает ложную готовность → явный runtime gate и тест принятой проверки при остановке/возобновлении.
- Отдельные тексты обходят лимиты rag_chunks → общий транзакционный бюджет, реальная PG-проверка конкурентной загрузки и отката.
- Потерянный ACK создаёт дубль → request key + hash байт + сохранённая квитанция; после commit повтор читает принятое состояние отдельно от нового допуска.
- Новый поиск меняет семантическую выдачу → отдельный явно показанный режим, неизменность существующего профиля и проверка reindex-инвариантов.

## Migration Plan

Поставлять проверенными независимыми коммитами: vendor → базовый профиль/executor gate → UI архивная приёмка → текстовый контракт и его миграция → текстовый UI/контекст. Новая миграция добавляет только свои таблицы/ограничения с проверкой существующей ledger/schema; старые миграции не редактируются. При выключении новых функций данные и квитанции сохраняются; после использования текстовых таблиц откат выполняется совместимым кодом либо согласованным восстановлением, не удалением строк.
