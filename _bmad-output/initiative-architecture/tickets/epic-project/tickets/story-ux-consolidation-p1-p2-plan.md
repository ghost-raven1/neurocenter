## Intent

**Problem:** UX-аудит (`docs/reports/model-connection-ux-audit-2026-11-13.md`, 194 строки, 19 форм/модалок/мастеров, 7 точек путаницы с file:line) дал план P0/P1/P2. **P0 (6 пунктов) — в работе** (worktree nc-ux-p0 + импорт-агент для P0-6-импортная-часть). **P1 (6) + P2 (4) — этот трекер**: консолидация, требующая продуктовых решений (8 открытых вопросов аудита §4), не запускаемых без них.

**P1 — консолидация (6):**
1. Единый 3-шаговый поток «подключить модель» на СУЩЕСТВУЮЩИХ модалках (не новые): подключение (RemoteConnectionModal) → ключ (ProviderAccessModal) → готовность (авто-check). Одна цепочка для всех 4-х точек входа (карточка/RAG/чекбокс/reindex-подтверждение).
2. Одно место для ключа: три «ключа» (общий legacy / личный / локальный OpenCode) в трёх местах → единая точка выбора (личный ключ = LocalKeyTransfer, существующий; legacy — миграция/отметка).
3. Персист выбора «Куда подключить модель» (сейчас локальный `useState`, теряется между вкладками, дублируется в 3 селекторах) → в проект/сессию.
4. Консолидация страницы устройства (OpenCodeModelSyncSettings): убрать дубль «настроить локальный провайдер» (глобальный `/start`-шаг vs project-scoped мастер — разные job kinds).
5. Убрать дубль подписей: 5 формулировок «подключить модель» → одна (словарь из P0-1).
6. После импорта → переход в «Мой доступ» (часть P0-6, импорт-агент; здесь — только если не закрыта P0-работой).

**P2 — глубокая перестройка (4):**
1. Панель «статус подключения» (агрегированный: TLS/ключ/имя-модели/готовность — один взгляд, а не 5 формулировок).
2. Глобальные vs проектные локальные провайдеры — разграничение (какой канонический — OQ аудита).
3. Авто-готовность на сервере (check по событию, не по поллингу UI).
4. (по остатку аудита §3 P2).

## Design Notes

- **Почему трекер, не отдельные тикеты:** P1/P2 — 10 пунктов, все из одного аудита, все требуют OQ-решений; один трекер = одна точка планирования, разбивается на под-задачи при старте каждой (по решению OQ). Не дублировать P0 (в работе).
- **Стык с P0:** P0-работа (nc-ux-p0 + импорт-агент) мержится ПЕРВОЙ; этот трекер стартует после, на чистом main. P0-6 (цепочка ключа) — частично здесь (P1-2), частично у импорт-агента (импортная часть).
- **Ядро + швы:** консолидация на существующих модалках (не новые); единый словарь/статус — helper (modelCatalogState.ts), не разбросанные константы.

## Open Questions (решения продуктовому владельцу — до старта каждой под-задачи)

1. **Перенос ключа с компьютера — дефолт после импорта?** (P1-2, P0-6). Рекомендация: да (LocalKeyTransfer = существующий механизм), opt-out флаг. Обоснование: импорт без ключа = мёртвый тупик; перенос уже есть, боль — discoverability.
2. **Глобальные vs проектные локальные провайдеры — какой канонический?** (P1-4, P2-2). Рекомендация: проектные (project-scoped мастер) как канон, глобальный `/start`-шаг — наboarding-only. Обоснование: проект = единица (эпик 8).
3. **Legacy-ключ — мигрировать или пометить?** (P1-2). Рекомендация: пометить (не мигрировать — данные провайдера, не наши). Обоснование: миграция чужих ключей = риск.
4. **Авто-готовность (P2-3) — по какому событию?** (check после save / после key-revoke / по расписанию). Рекомендация: после save + после key-revoke (event-driven), без расписания. Обоснование: поллинг UI = текущая боль; расписание = нагрузка на gateway.
5. **P2-1 панель статуса — где?** (карточка модели / отдельная страница / «Мой доступ»). Рекомендация: карточка модели (агрегированный блок). Обоснование: статус подключения = атрибут модели, не отдельная сущность.
6. **P2-4 (остаток аудита §3 P2) — скоуп уточнить при старте.**
7. **Персист выбора «Куда подключить» (P1-3) — в проект или в сессию?** Рекомендация: в проект (model set — атрибут проекта, FR-601..608). Обоснование: выбор цели — проектная настройка, не сессионная.
8. **Единый поток (P1-1) — 3 шага фиксированы или адаптивные (под authMode)?** Рекомендация: адаптивные (authMode none → 2 шага, без ключа). Обоснование: не все подключения требуют ключа.
