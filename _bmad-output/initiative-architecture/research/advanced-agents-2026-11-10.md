# Как сделать 5 дефолтных агентов Neurocenter самыми продвинутыми

**Задача (решение пользователя 2026-11-10).** Сделать 5 дефолтных агентов (Планировщик, Разработчик, Ревьюер, Тестировщик, Документатор) «самыми продвинутыми — полезнее и умнее». Дополнительное требование того же дня: «Агенты должны иметь способность и инструменты для анализа и решения задач и проблем».

**Ограничение.** Не менять файлы каталога и промпты. Только исследование + конкретные рекомендации.

**Важно про «умнее».** Все 5 актуальных промптов уже содержат сильные антигаллюцинационные правила («не объявляй фикстуру реальной ОС», «не утверждай, что сам выполнил проверку, которую только прочитал в отчёте», «сначала воспроизведи дефект»). Это хороший базис **честности**. Но «умнее» ≠ «честнее». Умность = **способность довести задачу до проверенного результата без человека**. Для этого нужны: (1) инструменты, которые агент *может фактически вызвать* (а не только прочитать про них), (2) обязательный verification-протокол, (3) контекст проекта (RAG/quirks/память), (4) формат вывода-контракт, который позволяет следующему агенту/человеку продолжить. Ниже — что именно добавить к каждому агенту и сквозные механизмы.

## 1. Текущее состояние

### 1.1. Контракт карточки агента (рантайм)

Что реально поддерживает рантайм (подтверждено в `services/shared/project-agents.cjs` и `docs/features/agent-method-workflows.md`):

- **Рантайм:** OpenCode **1.14.48** (V1-написание frontmatter: `permission.bash`, `mode`, `prompt`). Методики — **BMAD 6.12.4 + OpenSpec 1.15.0** (pinned, установлены в папке проекта, мост ничего не скачивает).
- **Поля карточки** (`DEFINITION_FIELDS`): `description` (≤1024), `prompt` (≤64KB), `mode` (`primary|subagent|all`), `permission` (обязательные) + **опциональные `model`, `temperature` (0–2), `topP` (0–1), `steps` (1–1000)**.
- **Permission-ключи** (`AGENT_PERMISSION_KEYS`, всего 15, а не 10): `read, edit, bash, glob, grep, list, task, external_directory, todowrite, question, webfetch, websearch, lsp, doom_loop, skill`. Значения — `allow|ask|deny` (плоская карта, без per-path/per-command паттернов на уровне карточки).
- **Inline delivery:** карточка рендерится в `.opencode/agents/nc-<slug>.md` (JSON-frontmatter + тело промпта). OpenCode перечитывает при следующем запуске.
- **selected-agent (FR-401 / agent-method):** браузер передаёт `workflow.agentId` + `expectedAgentsRevision`; сервер независимо получает assignment/model requirements + последнюю успешную `configure-project-agents` delivery; OpenCode server обязан загрузить именно этот native-агент (имя/mode/модель). **Важно:** «Отдельный набор skills/plugins/MCP и изоляция каждого агента этим расширением **не реализованы**» — skills/MCP сейчас на уровне **проекта**, не агента.

**Вывод по динамике:** эволюция шла по оси **честности/антигаллюцинации + привязки к системным ролям (context/system-assistance/learning)**. Оси **умности/решательности** (обязательный verification-протокол, machine-readable контракты, разрешённые инструменты для фактического выполнения) — **ещё не затронуты**. Это и есть зона роста.

### 1.4. Локальные эталоны «продвинутого агента» — извлечённые паттерны

**BMAD-агенты (Amelia/John/Winston/Mary/Sally/Sofia, `bmad-agent-*` SKILL.md).** Ключевой механизм — **протокол On Activation из 8 шагов**:
1. Resolve the Agent Block (merge `customize.toml`: base→team→user)
2. Execute Prepend Steps
3. **Adopt Persona** (полностью вжиться; персона несётся во все шаги сессии)
4. **Load Persistent Facts** (факты `file:`/verbatim несутся всю сессию)
5. **Load Config** (`resolve_config.py`: output_folder, active_initiative; если есть тикет — читать его целиком и работать от него)
6. Greet the User (иконка-префикс, напомнить про `bmad`)
7. Execute Append Steps
8. **Dispatch or Present the Menu** (коды/меню, **Stop and wait for input**; один короткий вопрос, не «confirmation ritual»)

Дополнительно: **test-first дисциплина** (red→green→refactor), **AC ID и file paths как «язык»**, **quality bar** («shipping verified code that meets every acceptance criterion»), **эскалация** («если skill не установлен — скажи и предложи установить»). Суть: агент = **персона + загруженные факты/конфиг + меню-диспетчер**, а не «системный промпт на абзац».

**Локальные OpenCode-subagent'ы (dossier-ko: backend/db/designer/devops/reviewer/tester).** Это самые близкие эталоны к нашему рантайму (тот же OpenCode). Паттерны:
- **Frontmatter:** `description`, `mode: subagent`, `model`, **`temperature` (reviewer 0.1, db 0.1, backend 0.2, tester 0.2, designer 0.5)**, **granular permission** (`edit: {"*": deny, "application/**": allow}`, `shell: {"*": ask, "mvn*": allow, "git*": allow}`).
- **Структура тела:** `# Роль` → `## Зона ответственности` (конкретные слои/файлы) → `## Скиллы (MCP-инструменты)` (нумерованный список *конкретных* вызовов: `search_semantic`, `get_file_skeleton`, `find_usages`, `recall_quirks`, `add_quirk`) → `## Архитектурные правила` / `## Правила` (конкретные инварианты) → `## Стиль` → `## Выход` (**format-контракт**: «Код (полные файлы), Изменения в pom.xml, Список затронутых модулей»).
- **Ревьюер:** приоритизация `CRITICAL → HIGH → MEDIUM → LOW`, **явный вердикт `APPROVED`/`CHANGES REQUESTED`**, формат `[file:line] issue → suggestion`, «Не ври».
- **Разделение анализ/решение:** db/reviewer — read-only (shell deny/ask, edit на узкие паттерны); backend/tester — edit на свои каталоги, bash на `mvn*`/`npm*` allow.

**Web-эталоны (Anthropic + практика 2025–2026).**
- **Anthropic, Building effective agents:** «workflows» (предсказуемо, для well-defined) vs «agents» (гибкость, модельное решение); агенту нужен **ground truth** от окружения на каждом шаге (результаты tool-вызовов, исполнение кода); автономность = выше стоимость и **компаунд-ошибки**.
- **Anthropic, Context engineering:** контекст = **конечный ресурс** (context rot — чем больше токенов, тем хуже recall); **just-in-time** подход — держать лёгкие идентификаторы (пути, запросы, ссылки) и подгружать данные в рантайме через инструменты; **note-taking** для персистентности.
- **Addy Osmani, Code Agent Orchestra:** «dedicated @reviewer teammate, auto-trigger on every task completion → lead sees only green-reviewed code»; оркестрация = in-process subagents/teams.
- **Agent self-review loop + Pre-completion checklists:** перед сдачей — **отдельный review-проход по своему diff** (`git diff` в скоупе изменений) + **чек-лист «что должно быть сделано до завершения»**.
- **Plan–Execute–Verify loop:** сгенерировал → запустил тесты → проанализировал падения → починил → перезапустил → показал финальный diff.

## 2. Паттерны продвинутых агентов (что реально работает)

Сводка механизмов с указанием, где они дают «умность/решательность» и как ложатся на наш рантайм.

| # | Механизм | Суть | Что даёт «умности» | Совместимость с рантаймом |
|---|---|---|---|---|
| P1 | **Verification-протокол (pre-completion checklist)** | Обязательный блок «что ДОЛЖНО быть проверено до заявления «сделано»» (запущенные команды + exit code, diff, тесты). Без этого — «сделано» не считается | Главная ось. Превращает «агент сказал что сделал» в «агент показал что сделал». Именно «проверяемый результат — верификация, а не «сделано»» (FR-304) | Только промпт (prompt-секция). Не требует кода |
| P2 | **Output-контракт (машинночитаемый формат вывода)** | Жёсткая структура ответа (роли/изменения/проверки/следующий шаг/вердикт). Следующий агент/человек продолжает по полям, а не по пересказу | Позволяет **оркестрацию** planner→developer→reviewer→tester (C5/R5) и провенанс (R9). «Следующий исполнитель получает принятые решения и артефакты, а не пересказ» | Только промпт. Опционально — markdown-секции с фиксированными заголовками |
| P3 | **Разрешённые инструменты для фактического выполнения** | `allow` на инструменты, без которых роль не может *выполнить* (тест-раннер, git-диагностика, read-only команды), а не только `ask` | **Решательность.** В автономном режиме (FR-401/agent-method) `ask` = стоп. Без разрешённого запуска тестов Тестировщик = «тестировщик на бумаге» | Меняется `permission` в карточке (плоская карта allow/ask/deny). Безопасно для read-only/диагностики; мутации остаются ask/deny |
| P4 | **Context-инъекция (RAG + quirks + memory)** | Обязательные шаги: `search_semantic` до чтения, `find_usages` перед правкой, `recall_quirks` при ошибке, `add_quirk` при решении; memory-граф между сессиями | Агент «знает» проект: не изобретает, а находит; помнит gotchas. just-in-time (Anthropic) — держит идентификаторы, подгружает через инструменты | MCP `mcp-opencode-rag` + `mcp-memory` + скиллы `neurocenter-project-context`/`project-learning` (уже в каталоге). Промпт обязан *требовать* вызовов |
| P5 | **Role-appropriate model/temperature/steps** | `temperature` под роль (reviewer/db 0.1, dev/tester 0.2, planner/doc 0.3), `steps` — потолок итераций | Детерминизм там, где нужен (review), креатив там, где нужен (plan), **ограничение doom-loop** (steps) | Поля `temperature`/`steps`/`model` **уже поддерживает карточка, но 5 дефолтных их НЕ используют** |
| P6 | **Workflow-шаги (нумерованный протокол)** | «Step 1…Step N» с явными stop-points (BMAD On Activation; plan-execute-verify) | Предсказуемость, воспроизводимость, проверяемость самого процесса; меньше «free-form» галлюцинаций | Только промпт |
| P7 | **Anti-patterns: запрет «ask only questions», симуляции вызова, «сделано по сообщению модели»** | Не задавать только вопросы; не симулировать tool-вызов текстом; не называть тест пройденным по одному сообщению | Уже частично есть в промптах — **усилить** до проверяемых инвариантов | Только промпт (уже есть, усилить) |
| P8 | **Эскалация/ограничения (HITL-гейты)** | Явный список «что требует поручения» (публикация/деплой/удаление данных/платный повтор); «потерянное подтверждение → выяснить исход, не повторять» | Безопасность + доверие; не «умнее», но **необходимый каркас**, внутри которого агент может быть агрессивным | Только промпт (уже есть, стандартизировать) |
| P9 | **Orchestrator–worker + auto-trigger reviewer** | Planner выдаёт план-контракт → Developer реализует → Reviewer auto-trigger на готовность → Tester верифицирует; lead видит только green-reviewed | Стратегический рычаг для C5 (реальный проект агент-командой end-to-end). «Агент-команда» — это и есть эпик 9 | Зависит от **эпика 9** (agent-team: FR-302/304/309/310). Сейчас — только output-контракты, которые это *подготовят* |
| P10 | **Persona + Persistent Facts + Menu-dispatch (BMAD)** | Персона несётся в сессию; persistent facts (file:/verbatim); меню-диспетчер с кодами | Улучшает UX и «узнаваемость» роли; persistent facts = контекст между раундами. **Опционально** для нас (у нас нет `customize.toml`-merge в рантайме) | Частично: persona/persistent facts — промптом; menu-dispatch — не поддерживается inline-delivery (нет интерактивного меню) — **не тащить** |

**Что НЕ тащить из эталонов:**
- BMAD `customize.toml` merge / `resolve_customization.py` — нет в рантайме (inline delivery, нет `_bmad/`-resolve).
- Menu-dispatch «Stop and wait for input» — интерактивные question/plan-переходы **запрещены** в agent-method-workflow («Интерактивные question/plan-переходы запрещены, как в неинтерактивном CLI»).
- Granular per-path/per-command permission (как в dossier-ko) — **не поддерживается** карточкой Neurocenter (только плоская allow/ask/deny). Можем только рекомендовать как *будущее расширение* схемы (эпик 9/12).

## 3. Целевая спецификация по каждому агенту

Легенда permission: `A`=allow, `a`=ask, `D`=deny. Ядро — 10 ключей из ТЗ (bash/edit/read/grep/glob/list/task/webfetch/websearch/external_directory/skill). Отмечу дополнительно `lsp` (диагностика) — ключ в схеме есть, но **проверить доступность в 1.14.48 перед использованием**.

### 3.1. Общие правила структуры промпта (для всех 5)

Каждый промпт = **6 секций** (порядок важен):
1. **Роль/цель** (1 строка: кто ты, какой наблюдаемый результат ты обязан дать).
2. **Workflow-шаги** (P6): нумерованные шаги с явными stop-points; «сначала контекст → затем действие → затем проверка».
3. **Правила качества** (инварианты роли: test-first, minimal code, read-only и т.д.).
4. **Verification-протокол** (P1): **обязательный** чек-лист «что должно быть проверено и каким свидетельством, до заявления «сделано»». Без завершённого протокола — результат не считается.
5. **Формат вывода** (P2): фиксированные заголовки-поля (контракт для следующего агента/человека).
6. **Ограничения/эскалации** (P8): явный список «что требует поручения» + «потерянное подтверждение → выяснить исход, не повторять автоматически» + «не симулируй вызов».

**Сквозные обязательные шаги (P4, P7)** — включить во все 5:
- Перед выводом о коде: `search_semantic(query)` → `get_file_skeleton(path)` → чтение конкретных строк (just-in-time, не «прочитать весь файл»).
- Перед правкой сигнатуры/полиморфного места: `find_usages(symbol)`.
- При ошибке/падении: `recall_quirks(query)`; при решении non-obvious проблемы: `add_quirk(content)`.
- Не объявляй контекст отсутствующим, пока не проверил фактические инструменты/RAG/индекс.
- Разделяй **факт / гипотеза / предложение** в каждом ответе.

### 3.2. Планировщик (agent-planner)

**(а) Структура промпта.**
- *Роль:* Цель пользователя → **исполнимый план** с проверяемым результатом. Не реализация.
- *Workflow:* (1) установи фактический контекст (проект, инструкции, RAG, переписка, инструменты) — выполни read-проверки; (2) найди затронутые модули через `search_semantic`/`find_usages`; (3) разбей на срезы с **владельцем-ролью** (developer/reviewer/tester/documenter) и **критерием проверки** у каждого среза; (4) зафиксируй существенные допущения и зависимости; (5) выведи план-контракт.
- *Правила качества:* не добавляй шаги для несуществующих требований; не мутируй файлы; учитывай обычный путь + сохранение ввода при ошибке + смену доступа + отмену + неизвестное подтверждение.
- *Verification-протокол:* план считается готовым, если **у каждого среза** есть: (i) наблюдаемый критерий проверки (команда/тест/сценарий), (ii) владелец-роль, (iii) указание, какие факты уже проверены, а какие — гипотезы; если план зависит от состояния индекса/модели/моста — сохранена ссылка на квитанцию system-assistance.
- *Формат вывода (контракт):*
  ```
  ## План
  - Срез 1: <что> | Владелец: <роль> | Проверка: <команда/тест/сценарий>
  ## Допущения (гипотезы)
  ## Проверенные факты (с источниками: путь:строка / квитанция)
  ## Пробелы доступа и путь продолжения
  ## Следующий шаг (кому и что)
  ```
- *Ограничения:* файлы/настройки не менять; мутирующие команды не запускать; публикация/деплой — только по поручению.

**(б) Рекомендуемый permission-профиль.**

| Ключ | Сейчас | Рекомендация | Обоснование |
|---|---|---|---|
| read / grep / glob / list | A | **A** (оставить) | анализ |
| skill | A | **A** (оставить) | neurocenter-project-context/system-assistance |
| **bash** | a | **a → A (read-only)** — см. ниже | решательность анализа |
| **edit** | D | **D (оставить)** — решение ниже | separation plan/execute |
| task | a | **a** (оставить) | делегирование spike — опционально, по поручению |
| webfetch / websearch | a | **a** (оставить) | публичные источники — по необходимости |
| external_directory | a | **a** (оставить) | безопасность |

**Ключевое решение по `edit: deny` (вопрос пользователя).** **Не снимать deny.** Обоснование: (1) separation plan/execute — это свойство **верификации** (FR-304 «верификация, а не «сделано»»): если Планировщик правит файлы, размывается граница план/исполнение и ломается цепочка planner→developer→reviewer (невозможно атрибутировать, кто что изменил); (2) встроенный `plan`-агент OpenCode делает ровно так же — «explores and plans without editing normal project files. It may write OpenCode plan files when asked»; (3) потребность «fix-прототип» правильнее покрывается **не** edit-правом Планировщика, а **(α)** делегированием `task` → Разработчик (Планировщик предлагает прототип-срез, Разработчик исполняет, Ревьюер верифицирует) либо **(β)** отдельным режимом «spike/прототип» (эпик 9). Поэтому решательность Планировщику даём **не правкой**, а **разрешённой read-only диагностикой** (bash).

**`bash: ask → allow (read-only).**** Чтобы «анализ = решение», Планировщик должен *фактически* прогонять диагностику, а не «читать про неё». Рекомендация: промпт-инвариант «запускай только read-only диагностические команды» + `bash: allow`, а мутации закрываются (а) тем, что edit: D, (б) тем, что в agent-method OpenCode получает `external_directory: deny`, (в) тем, что verification-протокол требует приводить exit code — мутирующая команда будет видна в квитанции. **Риск/альтернатива:** если команда хочет жёстче — оставить `bash: ask`, но тогда в автономном режиме (FR-401) Планировщик будет на каждом `git status`/`--dry-run` просить подтверждение и реально не «анализировать», а «предполагать». **Рекомендую `bash: allow` с промпт-инвариантом read-only** (это именно то, что просит требование «инструменты для анализа»).

**(в) Какие skills/MCP прицепить.**
- **Обязательно:** `skill-neurocenter-project-context` (RAG/файлы/переписка), `skill-neurocenter-system-assistance` (состояние индекса/модели/моста).
- **MCP:** `mcp-opencode-rag` (search_semantic/get_file_skeleton/find_usages — **основа анализа**), `mcp-memory` (читать persistent facts проекта).
- **Плагин (проектный, auto):** `plugin-git-context` (текущая ветка + список изменений — контекст плана), `plugin-project-context` (package manager + scripts).
- **После эпика 12:** `BMAD-METHOD` → скиллы `bmad-prd`/`bmad-architecture`/`bmad-product-brief` (если план требует brief/PRD/архитектуру) и **OpenSpec** (`openspec context`/`list`) для привязки плана к change. Обоснование: FR-308 обязывает BMAD→OpenSpec; Планировщик — точка, где рождается plan, который потом OpenSpec превращает в change.

**(г) Что НЕ менять.** `mode: primary`; `edit: deny`; inline delivery; контракт `permission` (плоская карта); запрет интерактивных question/plan-переходов в agent-method; «упоминание роли не заменяет вызов инструмента».

### 3.3. Разработчик (agent-developer)

**(а) Структура промпта.**
- *Роль:* Согласованное изменение → **проверенный результат** минимальным кодом в существующей архитектуре.
- *Workflow (test-first, как Amelia):* (1) воспроизведи текущее состояние: Git-статус, контракты, ближайшие тесты, `find_usages` на затрагиваемые символы; (2) **красный** — напиши/укажи тест, который ловит нужное поведение/дефект; (3) **зелёный** — минимальная правка; (4) **refactor** — без изменения поведения; (5) **запусти** затронутые тесты + сборку; (6) выведи квитанцию.
- *Правила качества:* minimal code, сохраняй чужие изменения/версии/данные; не симулируй вызов или результат текстом; найденный фрагмент ≠ доказательство текущего кода (проверь происхождение).
- *Verification-протокол:* «сделано» = **все** : затронутые тесты запущены с реальным exit code (0) и приведены; `find_usages` подтвердил отсутствие сломанных колл-сайтов; diff ограничен заявленными срезами; для существенного дефекта — воспроизведено ДО и исчезло ПОСЛЕ. Без этого — результат не считается.
- *Формат вывода (контракт):*
  ```
  ## Изменено (файлы, краткая суть)
  ## Проверено (запущенные команды + exit code, тесты pass/fail)
  ## Непроверенное (явно, если есть)
  ## Затронутые колл-сайты (find_usages)
  ## Следующий шаг (кому и что)
  ```
- *Ограничения/эскалации:* публикация/деплой/удаление пользовательских данных/внешние сообщения — только по поручению; платный повтор после неизвестного подтверждения — **не** автоматически; опыт — через `neurocenter-project-learning`, но новое знание не применять автоматически.

**(б) Рекомендуемый permission-профиль.**

| Ключ | Сейчас | Рекомендация | Обоснование |
|---|---|---|---|
| read/grep/glob/list | A | A | анализ |
| skill | A | A | context/system-assistance/learning |
| **edit** | a | **a** (оставить) — см. ниже | мутация = ask (HITL), но в автономном режиме — вопрос |
| **bash** | a | **A (test/build/git read-only) + ask на mutation** | решательность: должен запускать тесты/сборку |
| task | a | a | делегирование reviewer/tester — по поручению |
| webfetch/websearch | a | a | доки — по необходимости |
| external_directory | a | a | безопасность |

**Нюанс по edit/bash в автономном режиме.** Карточка поддерживает **только плоскую** allow/ask/deny (без per-path). Поэтому мы не можем сказать «edit allow только на src/**, bash allow только `mvn test*`» на уровне карточки (это умеет V2 `permissions[]` / dossier-ko, но **не** наш рантайм 1.14.48-карточка). Компромисс: `edit: ask` (HITL на каждую правку) + `bash: allow` с **промпт-инвариантом** «запускай только проверочные/сборочные команды (`<test-runner>`, `<build>`, `git status/diff/log/show`), мутирующие команды — только по явному поручению». Это даёт решательность (тесты/сборка идут без стопов) при сохранении HITL на правки. **Если эпик 9 расширит карточку до granular `permissions[]`** — перейти на `edit: {"*": ask, "<project-src>/**": allow}` и `bash: {"*": ask, "<test> *": allow, "<build> *": allow, "git *": allow}`.

**(в) Какие skills/MCP прицепить.**
- **Обязательно:** `skill-neurocenter-project-context`, `skill-neurocenter-system-assistance`, `skill-neurocenter-project-learning`.
- **MCP:** `mcp-opencode-rag` (search_semantic/find_usages — критично перед правкой), `mcp-filesystem` (точечные правки в пределах проекта), `mcp-sequential-thinking` (декомпозиция сложной правки — ветвление гипотез).
- **Скиллы по стеку (inline, из каталога):** `skill-nestjs-best-practices`, `skill-typescript-advanced-types`, `skill-vite`, `skill-supabase-postgres-best-practices` — прицепить **контекстно** (промпт: «применяй соответствующий стеку скилл»). Не все сразу — по проекту.
- **Плагин:** `plugin-git-context`, `plugin-project-context`.
- **После эпика 12:** **OpenSpec** `openspec-apply-change` (исполнение change — именно то, что делает developer в BMAD→OpenSpec) + BMAD `bmad-build`/`bmad-build-auto` (test-first build). Это ядро FR-308.

**(г) Что НЕ менять.** `mode: primary`; HITL на мутацию (edit: ask); запрет авто-повтора платного запроса; «не симулируй вызов»; границы публикация/деплой/удаление данных.

### 3.4. Ревьюер (agent-reviewer)

**(а) Структура промпта.**
- *Роль:* Конкретные дефекты изменения, влияющие на наблюдаемое поведение; отделить от предпочтений оформления. **Read-only.**
- *Workflow:* (1) **diff-скоупинг** — `git diff`/`git show` по изменению (что именно менять); (2) `search_semantic`/`find_usages` по контексту затронутых мест; (3) прогони read-only проверки (lint/типизация/тесты **без правок** — если разрешено); (4) для каждого подтверждённого замечания: **место (file:line) / условие возникновения / последствие / приоритет**; (5) выведи вердикт.
- *Правила качества:* не изобретать дефекты; «не утверждай, что сам выполнил проверку, которую только прочитал в отчёте» (усилить: если не запустил — так и напиши «проверка не запускалась»); проверь права/сохранность ввода и данных/принадлежность асинхронного результата/конкуренцию/отмену/повтор после неизвестного подтверждения.
- **Verification-протокол (новый):** каждый дефект = **подтверждённый** (есть место + условие + воспроизведение/логика) либо явно помечен «гипотеза». Формулировка по приоритетам.
- *Формат вывода (контракт, как в dossier-ko reviewer):*
  ```
  ## CRITICAL (fix before merge)
  - [file:line] <issue> → <suggestion>
  ## HIGH (should fix)
  ## MEDIUM (nice to have)
  ## Вердикт: APPROVED | CHANGES REQUESTED
  ## Не проверено (явно, если не запускал)
  ```
- *Ограничения:* read-only: не менять файлы/настройки/данные; не запускать мутирующие команды.

**(б) Рекомендуемый permission-профиль.**

| Ключ | Сейчас | Рекомендация | Обоснование |
|---|---|---|---|
| read/grep/glob/list | A | A | анализ |
| skill | A | A | context + code-review skill |
| **edit** | D | **D** (оставить) | read-only — ключевое свойство |
| **bash** | a | **A (read-only: git diff/log/show, lint, typecheck, тесты без правок)** | чтобы *фактически* проверять, а не читать чужие отчёты |
| task | a | a | — |
| webfetch/websearch | a | a | доки/уязвимости — по необходимости |
| external_directory | a | a | безопасность |

**`bash: ask → allow (read-only) — самое важное для Ревьюера.** Сейчас Ревьюер не может фактически запустить `git diff`/lint/тесты без подтверждения → он «ревьюит по отчётам». Это ровно тот anti-pattern, против которого сам же промпт предупреждает («не утверждай, что сам выполнил проверку, которую прочитал»). Дать `bash: allow` + промпт-инвариант «только read-only: `git diff/log/show/status`, `<lint>`, `<typecheck>`, тесты в режиме без правок». Это превращает Ревьюера из «читателя отчётов» в «проверяющего» — **самый большой прирост решательности на единицу effort** (меняется 1 permission + 1 строка промпта).

**(в) Какие skills/MCP прицепить.**
- **Обязательно:** `skill-neurocenter-project-context`, `skill-code-review-excellence` (системная проверка, приоритет замечаний, обратная связь — **прямое попадание**).
- **MCP:** `mcp-opencode-rag` (find_usages — влияние изменения; search_semantic — контекст).
- **Плагин:** `plugin-git-context` (diff-контекст).
- **После эпика 12:** **BMAD** `bmad-code-review` (несколько независимых ревьюеров параллельно, triage) + `alibaba/open-code-review` (CLI + Claude-plugin — внешний ревьюер). Обоснование: «dedicated reviewer, auto-trigger on completion» (Addy Osmani) — после эпика 12 Ревьюер получает реальные review-инструменты, а не только промпт.

**(г) Что НЕ менять.** `mode: subagent`; `edit: deny`; read-only; «не изобретать дефекты».

### 3.5. Тестировщик (agent-tester)

**(а) Структура промпта.**
- *Роль:* Требование → **различающие** проверки; довести подтверждённый отказ до **воспроизводимого** сценария.
- *Workflow:* (1) изучи текущий код/инструкции/существующие средства проверки (`search_semantic("test <ClassName>")`); (2) составь матрицу: основной путь + пустое состояние + отказы (отзыв доступа, смена контекста, отмена, потерянный ответ); (3) напиши проверки на **изолированных** фикстурах; (4) **запусти** (управляя порядком событий, не случайными задержками); (5) выведи фактический отчёт.
- *Правила качества:* различающие проверки (отличают «работает» от «не работает»); поведение/интеграция важнее зеркал реализации; рабочая БД/пользовательский индекс/реальные ключи — **не** тестовый стенд; каждый тест `given_when_then`.
- **Verification-протокол (новый):** «проверено» = **реально запущено** с фактическими `passed/failed/skipped/недоступные` + областью + ревизией. Завершение сессии ≠ успех теста. Тест не запущен → `not_run` (не «passed»).
- *Формат вывода (контракт — матрица покрытия, как в dossier-ko tester):*
  ```
  ## Матрица: unit | интеграция | браузер | нативная | CI | площадка
  ## Результат: passed=N failed=N skipped=N not_run=N (область, ревизия)
  ## Воспроизведённые отказы (сценарий + как повторить)
  ## Не покрыто (явно)
  ## Следующий запуск (конкретная команда для пробела)
  ```
- *Ограничения:* запускать только проверки в порученной области; реальная платная модель — только по разрешению; неизвестный исход — не повторять автоматически; «завершение сессии не доказывает успех теста».

**(б) Рекомендуемый permission-профиль.**

| Ключ | Сейчас | Рекомендация | Обоснование |
|---|---|---|---|
| read/grep/glob/list | A | A | анализ |
| skill | A | A | context/system-assistance/learning |
| **edit** | a | **a → A (только тестовые файлы)** — см. ниже | писать тесты |
| **bash** | a | **A (test-runners/build/git)** | **главное:** фактически запускать тесты |
| task | a | a | — |
| webfetch/websearch | a | a | — |
| external_directory | a | a | безопасность |

**Ключевое: `bash: ask → allow (test-runners)`.** Тестировщик, который не может **фактически запустить** тесты — не Тестировщик, а «автор тестов». В автономном режиме (FR-401/agent-method) `bash: ask` блокирует главную способность. Рекомендация: `bash: allow` + промпт-инвариант «запускай только проверочные команды (`<test-runner>`, сборка, `git status/diff`) в порученной области, мутирующие — по поручению». `edit: ask → allow` на тестовые файлы — **только** при расширении карточки до granular (эпик 9); сейчас (плоская карта) оставить `edit: ask` (HITL), т.к. нельзя сказать «edit allow только `**/*.test.*`».

**(в) Какие skills/MCP прицепить.**
- **Обязательно:** `skill-neurocenter-project-context`, `skill-neurocenter-system-assistance`, `skill-neurocenter-project-learning` (фиксировать воспроизведённые баги), `skill-playwright-best-practices` (E2E/негативные сценарии — **прямое попадание**), `skill-vitest` (если стек Vitest).
- **MCP:** `mcp-opencode-rag` (search_semantic по тестируемой логике/похожим тестам; find_usages для edge cases), `mcp-sequential-thinking` (декомпозиция матрицы проверок).
- **Плагин:** `plugin-git-context` (что менять → что регресс-тестить).
- **После эпика 12:** BMAD `bmad-qa-generate-e2e-tests` (e2e/API-тесты для готовых фич).

**(г) Что НЕ менять.** `mode: subagent`; изоляция фикстур; «не трогать реальные ключи/рабочие данные»; «не повторять неизвестный исход автоматически».

### 3.6. Документатор (agent-documenter)

**(а) Структура промпта.**
- *Роль:* Точные инструкции и документация = **подтверждённое** поведение через реальные команды/интерфейс/пути продолжения.
- *Workflow:* (1) изучи относящиеся исходники/настройки/существующую справку (`search_semantic`/`get_file_skeleton`); (2) привяжи документацию к **фактическому** коду/диффу (не к старому отчёту); (3) для каждого шага: зачем → как выполнить → какой результат → что при подтверждённом отказе; (4) **проверь** ссылки и примеры (запускаются/компилируются — если можно read-only); (5) выведи документ.
- *Правила качества:* сохраняй принятые названия; разделяй **реализованное / исторические свидетельства / планы**; примеры сохраняют scope/точные версии/доступ/смысл отмены-повтора; ключи/приватные сообщения/непроверенные команды — **не** в документацию.
- **Verification-протокол (новый):** каждый пример/команда = либо **проверен** (read-only запуск/компиляция) и помечен, либо явно «не проверен». Ссылки = либо валидны, либо помечены. «Не заявляй выполнение тестов/миграций/деплоя без свидетельств».
- *Формат вывода (контракт):*
  ```
  ## Документ: <зачем / как / результат / при отказе>
  ## Проверено (ссылки/примеры: валидны + как проверено)
  ## Не проверено (явно)
  ## Изменения (что/где/почему)
  ## Следующий шаг
  ```
- *Ограничения:* не включать секреты; не заявлять непроверенное как проверенное.

**(б) Рекомендуемый permission-профиль.**

| Ключ | Сейчас | Рекомендация | Обоснование |
|---|---|---|---|
| read/grep/glob/list | A | A | анализ |
| skill | A | A | context/system-assistance |
| **edit** | a | **a** (оставить) — HITL на правку доков | мутация доков — ask |
| **bash** | a | **A (read-only: git, lint/компиляция примеров, проверка ссылок)** | чтобы *проверять* примеры, а не утверждать |
| task | a | a | — |
| webfetch/websearch | a | a | проверка внешних ссылок/доков |
| external_directory | a | a | безопасность |

**`bash: ask → allow (read-only) + webfetch: allow.** Документатор, который не может проверить, что пример запускается и ссылка жива, будет «заявлять без свидетельств» — ровно тот anti-pattern, против которого промпт. `bash: allow` (read-only: проверка ссылок, компиляция примеров, `git`) + `webfetch: allow` (валидация внешних ссылок/доков) превращают Документатора в «проверяющего документацию».

**(в) Какие skills/MCP прицепить.**
- **Обязательно:** `skill-neurocenter-project-context`, `skill-neurocenter-system-assistance`.
- **MCP:** `mcp-opencode-rag` (search_semantic по существующим докам; get_file_skeleton), `mcp-fetch-mcp` (проверка внешних ссылок/доков — **прямое попадание**).
- **Плагин:** `plugin-project-context`, `plugin-git-context`.
- **По стеку (контекстно):** `skill-mcp-builder` (если документируем MCP), `skill-api-design-principles` (если API-доки).
- **После эпика 12:** `opencode-see-image` (анализ скриншотов/макетов для UI-доков) + `ui-ux-pro-max-skill` (дизайн-система в доках).

**(г) Что НЕ менять.** `mode: subagent`; «не включать секреты»; «разделяй реализованное/историческое/планы».

## 5. Сквозные механизмы

### 5.1. Оркестрация цикла planner → developer → reviewer → tester

**Цель (C5/R5):** реальный проект агент-командой end-to-end с провенансом.

**Как это собирается из секции 3.** Ключ — **output-контракты (P2)**, которые уже заданы выше:
1. **Planner** → `## План` (срезы + критерии проверки + владельцы-роли).
2. **Developer** берёт срезы из плана → реализует → `## Изменено / Проверено / Непроверенное / Следующий шаг`.
3. **Reviewer** (auto-trigger на «Developer: сделано») → берёт diff + квитанцию Developer → `## CRITICAL/HIGH/MEDIUM / Вердикт APPROVED|CHANGES REQUESTED`.
4. **Tester** → матрица покрытия + фактический `passed/failed/skipped/not_run`.
5. **Вердикт цикла:** green только если Reviewer=APPROVED **и** Tester=0 failed **и** все `not_run` обоснованы. Иначе — возврат на Developer (с конкретным CHANGES/failed).

**Состояние сейчас.** Каждый агент — отдельный **режим** (FR-401) в проектном чате. **Автоматического handoff-контакта и auto-trigger reviewer между режимами нет** — это и есть **эпик 9** (FR-302 «последовательный контекст и подключение агента агентом», FR-309 «деление контекста», FR-310 «вызов системного агента»). Поэтому **сейчас мы можем только подготовить контракты** (output-форматы, которые handoff *поймёт*), а сам цикл включится с эпиком 9.

**Что сделать сейчас (без эпика 9):** привести 5 output-контрактов к единой схеме (поля `Следующий шаг (кому и что)` и `Вердикт`) — это и есть «подготовка к C5». **Зависит от эпика 9:** оркестратор/auto-trigger, провенанс между агентами.

### 5.2. Контекст проекта (RAG-инъекция)

- **Сейчас:** MCP `mcp-opencode-rag` + `mcp-memory` + скиллы `neurocenter-project-context`/`system-assistance`/`project-learning` **уже в каталоге**. Но промпты **упоминают** скиллы, не **обязывая** RAG-decision tree.
- **Что сделать:** включить в каждый промпт **обязательный** порядок (P4): `search_semantic` → `get_file_skeleton` → чтение строк; `find_usages` перед правкой; `recall_quirks` при ошибке; `add_quirk` при решении. Это превращает RAG из «доступного инструмента» в «обязательный путь мышления» (just-in-time, Anthropic).
- **Эпик 8 (FR-311):** «семантический поиск агентов по четырём корпусам — актуальный код, публичные чаты, одобренные знания, опыт». Это расширит корпуса RAG, по которым агенты ищут — **усилит** нашу инъекцию после эпика 8.

### 5.3. HITL-гейты

Единый стандарт (P8) для всех 5 (сейчас разрознен по промптам):
- **Требует поручения:** публикация, деплой, удаление пользовательских данных, внешние сообщения, платный повтор после неизвестного подтверждения, мутирующие bash-команды.
- **Потерянное/неизвестное подтверждение:** сначала выяснить исход прежней операции (квитанция), **не** повторять автоматически.
- **Read-only по умолчанию:** анализ/ревью/доки не мутируют; мутация = ask/deny.
- **Автономный режим (FR-401/agent-method):** `ask` на критическом пути = стоп; поэтому разрешаем **только** read-only/проверочное на `allow`, мутацию держим на `ask` (в agent-method OpenCode дополнительно получает `external_directory: deny`).

### 5.4. Метрики «полезности» (как измерить, что агент стал умнее)

Привязать к success-метрикам PRD (R6 completion-rate, R8 тупики=0, R5 провенанс):

| Метрика | Как измерить | Целевой сдвиг |
|---|---|---|
| **Autonomy rate** — доля задач, доведённых до результата **без** подтверждения `ask` | лог tool-вызовов: count(ask) / count(total) по задаче | ↑ после `bash: allow` (read-only/test) |
| **Verification rate** — доля результатов с **фактическим** свидетельством (exit code/пройденный тест), а не «сделано» | доля квитанций с `## Проверено` + реальным exit code | ↑ после verification-протоколов |
| **Defect escape** — доля дефектов, найденных Reviewer/Test **до** пользователя | сравнение «нашёл агент» vs «нашёл человек постфактум» | ↑ после `bash: allow` у Reviewer/Tester |
| **Hallucination rate** — доля «заявлено, но не доказано» (проверка по отчёту, не запущено) | аудит: заявленные проверки vs фактически запущенные | ↓ после anti-pattern P7 |
| **Handoff success** — доля циклов planner→dev→review→test, завершённых green без человека (после ep9) | провенанс C5 | измеряемо после **эпика 9** |
| **Context hit rate** — доля задач, где агент нашёл ответ через RAG (`search_semantic`/`find_usages`) вместо «перевода» | лог RAG-вызовов | ↑ после обязательного RAG-пути |
| **Quirk learning** — число `add_quirk`, подтверждённых и переиспользованных `recall_quirks` | count в `mcp-memory`/project-learning | ↑ (накопительная умность между сессиями) |

**Минимальный набор для старта:** Autonomy rate + Verification rate + Hallucination rate — все три **измеряемы сейчас** (по логам tool-вызовов и квитанциям), без эпика 9. Это даёт «до/после» по каждому улучшению.

## 7. Резюме: 5 главных выводов (что даст наибольший прирост «умности»)

1. **Дать агентам инструменты, которые они МОГУТ реально вызвать, а не только прочитать про них.** Общий рычаг = `bash: allow` на read-only/проверочные команды (Reviewer, Tester, Developer, Documenter; Planner — read-only) + MCP RAG (`search_semantic`/`find_usages`/`get_file_skeleton`). Сейчас их главная способность на `ask` = в автономном режиме (FR-401/agent-method) это **тупик**. Это **T1, Low effort, наибольший прирост «решательности»**.

2. **Обязательный Verification-протокол (pre-completion checklist) во все 5.** Превращает «агент сказал, что сделал» в «агент показал: exit code, diff, пройденные тесты». Это прямая реализация FR-304 («проверяемый результат — верификация, а не «сделано»») и главный анти-галлюцинационный рычаг. **T2, Low effort.**

3. **Контекст проекта = обязательный RAG-путь + память (quirks/memory), а не «доступный инструмент».** just-in-time (Anthropic): `search_semantic`→`get_file_skeleton`→чтение строк; `find_usages` перед правкой; `recall_quirks` при ошибке; `add_quirk` при решении. Агент «знает» проект и **компаундит** опыт между сессиями. **T3, Low-Med effort.**

4. **Output-контракты (единая схема: Изменено/Проверено/Вердикт/Следующий шаг) — это то, что делает 5 агентов КОМАНДОЙ, а не 5 режимами.** Сейчас handoff-контракта нет (эпик 9).
