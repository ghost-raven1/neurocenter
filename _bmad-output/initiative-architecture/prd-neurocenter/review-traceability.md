**«Лимиты реально» (NFR-6): достаточно ли FR-902?** Посылка задачи устарела — FR-902 в актуальном PRD про добавление пользователей. Фактический носитель NFR-6 — **FR-1002** («Runtime-лимиты настраиваются главным админом и реально исполняются; у каждого quota-пого есть enforcement-точка»). Достаточность: **частично**. (а) FR-1002 покрывает admin-настраиваемую часть и дословно совпадает с правилом AD-D4 («quota-поле без enforcement-точки = фэйл») — хорошо. (б) NFR-6 шире FR-1002: «каждый **заявленный** лимит» включает и протокольные константы, которые admin не настраивает (10MiB вложений, 128KiB текста — AD-D4 их ратифицирует) (L-6). (в) FR-1002 не упоминает двухуровневую модель AD-1: ceiling — константа компиляции, админом **не** поднимается; «настраиваются админом» без оговорки о ceiling — неполная картина (L-6).

## 5. Сверка с 4 spine'ами (противоречия/расхождения, без дублей)

### H-2. C3/FR-803/UJ-5 ↔ AD-OP-4 + AD-D2: model-weights — главный найденный противоречие-резидуал
- AD-OP-4: бандл = PG + 4 тома + S3 + образы; **model-weights сознательно вне бандла** (задокументированный residual: «веса не входят в release-манифест… DR-restore требует доступ к model-registry (ollama pull) или ручную повторную загрузку GGUF»).
- PRD FR-803 перечисляет бандл «данные + тома + S3-объекты + образы релиза» — формально не противоречит, **но нигде не говорит, что веса не восстанавливаются**. C3 требует restore «на живых данных», UJ-5 — «вход/чтение/запись в проекте» после restore. Если живой проект использует hosted-модели (FR-602), после cross-host restore модельные операции (чат/агент/embedding) не работают до ручной повторной загрузки весов. **PRD-обещание (C1 GO, C3, UJ-5) не квалифицировано известным архитектурным residual'ом** — это риск именно для приёмочного решения.
- Также L-8: список «4 тома» в AD-OP-4 устарел относительно AD-D2 (новый volume `artifact-cache` — 5-й); явного решения «кэш в бандл / вне бандла» нет (производный → по аналогии с capacity должен быть явно вне).

### M-6. FR-601 (ручной GGUF-импорт) ↔ AD-D2 (model-weights: owner = ollama)
- FR-601: «веса добавляются **вручную из GGUF**… подготовка и активация — отдельные явные действия». FR-602: lifecycle «prepare/start/…(Ollama-runtime)».
- AD-D2: на volume `model-weights` **один owner — ollama**; «catalog-хидратация — только через ollama API (pull/manifest), прямой FS-запись из catalog запрещён». Формулировка AD-D2 описывает registry-pull; **механизм попадания локально загруженного GGUF в ollama в spine не специфицирован** (ollama `create` от локального файла? общий read-only путь? какой писатель кладёт GGUF?).
- Brownfield-подтверждение двойного писателя прямо в `compose.production.yml`: `model-weights:/root/.ollama` у ollama-сервиса И `model-weights:/data/models:rw` у catalog-service — то, что AD-D2 обязан исправить. До явной спецификации пути «GGUF → ollama» FR-601 остаётся продуктовым обещанием без согласованного с AD-D2 механизма.
- Совместимые точки (не противоречие): квота/retention импорта в FR-601 = AD-D4(5) (GGUF-лимиты ратифицированы) + runtime-limit-inventory (GgufImportService получает ggufPolicy — уже есть).

### FR-1002/FR-605 (лимиты) ↔ AD-D4 / AD-OP-6 / AD-1 — согласованы
- FR-1002 ↔ AD-D4: дословное совпадение правила (enforcement-точка). FR-605 ↔ AD-D4(2/3) + inventory (model-token-quotas, rate-limits, platform/project RAG quota — уже реализованы с CAS). Противоречий нет. AD-OP-9 из посылки — про npm-поставку; к лимитам правильный стык AD-OP-6 (container-level pids/mem/non-root — другой уровень, не дубль) и AD-1 (двухуровневая модель — см. L-6).

### C5/FR-3xx ↔ runtime-trust (MCP/агенты) — расхождение уровней абстракции (L-7)
- FR-303 (системные роли: настройка/диагностика/модели/мосты/доступы/данные/обновление/восстановление) ↔ AD-14 (system-role-mcp — явный контроллер gateway) — совпадает.
- FR-301 «агент — участник проекта» не разделяет **server-side системных агентов** (system-role-mcp, доверенный сервер) и **client-side агентов** (машинный bridge → mcp-host, недоверенная сторона, AD-1…4, 13). Spine'ы работают с двумя разными trust-моделями; PRD — с одним понятием. Не противоречие, но контракт не фиксирует границу.
- C5 «код → тесты» в FR-302 ↔ Out of Scope («arbitrary install/build hooks; автоматическая компиляция non-JS»): семантика «код» в цепочке не определена (L-3). «Подготовка выпуска» — конечное состояние цепочки, но сущность «релиз проекта» FR'ом не является.

### FR-401 / FR-101 (каталог проекта) ↔ AD-OP-1/AD-D2 — противоречий нет
Посылка «FR-401 = каталог проектов» устарела (FR-401 = чат). Фактическое покрытие: FR-101 «назначенный каталог… принадлежит проекту» + FR-102 + FR-2xx. Volume-модель AD-OP-1/AD-D2 (`projects` — write-owner catalog, rag-sync → ro) с продуктом не конфликтует; чат (FR-403) живёт в PG + S3 (chat-оригиналы) и входит в retention-каскад AD-D3 и бандл AD-OP-4 — консистентно.

### FR-203 (провенанс; посылка «FR-501») ↔ AD-OP-2 (supply-манифест) — согласованы
Release supply (bridge-dist-архивы, installers, vendor-контракт, SHA-опись) — тот же принцип «SHA + опись + manifest» как FR-203 для каталожных артефактов. Противоречий нет.

- FR-803 «RPO/RTO измерены» ↔ AD-OP-4 «первая измеренная репетиция = baseline, дальше политика в maintenance_settings» — согласовано.
- FR-1004 (ротация секретов с последствиями) ↔ AD-OP-4 (runbook на каждый секрет + запись последствий, стык AD-4: internal_token гасит билеты) — согласовано.
- **M-5. FR-603 ↔ Vision (импортозамещение).** Vision: «внешние LLM-API… недопустимы по требованиям к контуру». FR-603 одновременно в контракте: «OpenAI-совместимые API с приватными credentials» + «импорт моделей устройства (OpenCode/Codex)». ## 6. Brownfield-факты

1. **Какие limit-обёртки уже есть** (`runtime-limit-inventory.md`): общий редактор (текст + GGUF, `GgufImportService` + `ggufPolicy()`), per-model token quotas, model rate-limits, response-limits, RAG platform- и project-quota (enforced в DB), bridge-cache policy, backup-policy (RPO/RTO-поля). Т.е. FR-605 и квота импорта FR-601 в основном **уже реализованы**; реальный gap NFR-6 — `projects.quota` (подтверждено: `project-quota.ts` — 22 строки, только normalize с нулями, enforcement-кода нет; AD-D4: «ноль кода») и gateway artifact cache (tmpdir без квоты/eviction — AD-D2).
2. **MCP-пул (L-10): изменение поведения, а не фикс.** Подтверждено в коде: `services/api-gateway/src/features/mcp-host/host.ts:40` — `const MAX_HOSTS = Math.max(1, Number(process.env.NEUROCENTER_MCP_HOST_MAX || 4))`; `Number("abc") = NaN`, `Math.max(1, NaN) = NaN` → сравнение `size >= NaN` всегда false → **неограниченный пул** при мусоре в env (точка, зафиксированная AD-9). Сегодня де-факто лимит пула может не работать вовсе. Целевое состояние по AD-4: «глобальный пул (default 4) ограничен per-project/per-device квотами». Значит NFR-6/FR-1002 («у каждого quota-пого есть enforcement-точка») по пулу = **введение действующего ограничения**, сужающее текущее поведение, — PRD это не декларирует явно (покрывается только общей формулой NFR-6).
3. **FR-103 (полный каскад удаления)** vs brownfield: S29 = «частично» (только FK-cascade, RAG-БД остаётся) — AD-D3 фиксирует фикс (каскад + receipt). PRD-целевое состояние корректно; объём работ велик, но противоречий нет.
4. **FR-102 (шаблоны) — greenfield:** template-механизма в коде catalog-сервиса не найдено — C4 строится с нуля.
5. **UJ-5 статус «не принят» в PRD** соответствует brownfield (S24: «независимый cross-host restore не принят», H6-приёмки) — консистентно, завышения нет.
6. **Dual-writer model-weights** — подтверждён в compose (п. M-6 выше).

## 7. Вердикт

PRD **в целом traceable**: C1/C3/C4/C5 уперты в FR, UJ-2/UJ-4 покрыты плотно, NFR-2/4/5/6 связаны с FR, 6 P0-блокеров 1:1 совпадают с readiness-доком, brownfield-статусы не завышены. Контракт с 4 spine'ами в основном согласован (лимиты, DR-бандл, провенанс, supply).

Критичные разрывы — два, оба на линии приёмочного решения GO:
1. **H-1** — MCP-runtime (крупнейшая зона trust-архитектуры) не имеет ни одного FR; конечная точка UJ-3 висячая.
2. **H-2** — DR-обещания (C3/UJ-5) не квалифицированы residual'ом model-weights: «чтение/запись после restore» не гарантировано для модельных проектов.

Рекомендации: (а) добавить FR для MCP-канала (билеты/авторизация/отзыв) в FR-7xx; (б) в FR-803/UJ-5 явно вынести «model-weights восстанавливаются вне бандла: re-pull/загрузка GGUF по runbook — часть restore-SOP»; (в) FR для onboarding агента (C2); (г) зафиксировать состав «5 приоритетных сквозных проверок»; (д) FR на activity/usage-метрики; (е) закрыть Q6 перед фиксацией FR-603; (ж) в FR-601 указать механизм GGUF→ollama с учётом AD-D2; (з) поднять NFR-3 в FR (actionable-ошибки + recovery-пути).
