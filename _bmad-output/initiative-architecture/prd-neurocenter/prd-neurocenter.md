# Neurocenter — PRD

## Vision

**Одна строка.** Neurocenter — проектная среда, работающая **полностью в закрытом контуре (импортозамещение: локальный LLM, self-hosted-идентичность, локальная поставка инструментов)**, где команда людей и агентов ведёт проект от анализа до подготовки выпуска: каждый исполнитель — человек или агент — получает **принятые решения, исходные артефакты и результаты проверок, а не пересказ без происхождения**.

**Проблема.** Три связанные дыры:

1. **Импортозамещение (внешних зависимостей нет в принципе).** Команде нужны AI-возможности (агенты, модели, чат, проектные знания), работающие **без зарубежных внешних сервисов**: внешние LLM-API и SaaS-платформы агентов — недопустимы по требованиям к контуру и данным; внешние экосистемы инструментов — недоступны как поставка. Подкрепляющий аргумент (research 2026-11-05): внешние экосистемы агентов недоверены, в т.ч. как supply chain — 36.8% agent skills с уязвимостями, 824 malicious skills в ClawHub, zero-click RCE в рантаймах. Версионированный каталог под контролем оператора с SHA и квитанциями — **требование импортозамещения, а не nice-to-have**.
2. **Провенанс в командной работе.** Когда люди и агенты совместно ведут проект, следующий исполнитель не может доказать: какое решение принято, какой артефакт исходный, какая проверка пройдена. Без провенанса «команда агентов» вырождается в цепочку пересказов.
3. **Управляемость как инфраструктура.** Платформа в закрытом контуре обязана быть **восстановимой**: не «deployable air-gapped», а quiesced backup + restore на другом хосте с измеренными RPO/RTO.

**Центр тяжести.** Проект — единица продукта. Команда (люди + агенты), каталог, знания — **слои проекта**. [пользователь, 2026-11-05]

**Для кого.** Фаза 1 — наша команда (single-tenant, один оператор). Фаза 2 (в горизонте 12 мес) — команды организации; модель поставки (self-hosted) не меняется. [пользователь, 2026-11-05]

**Обязательства 12 месяцев** (что должно стать правдой; пользователь, 2026-11-05, все 5):

| # | Обязательство |
|---|---|
| C1 | **Закрытый пилот = GO**: 6 P0-блокеров закрыты приёмками: P0-SSO (IdP), P0-NAT (матрица установщиков), P0-S3 (cross-host DR), P0-UPD (обновление/восстановление), P0-RES (ресурсы/наблюдаемость), P0-MNT (maintenance); предпосылка — замороженный кандидат релиза (REL-01) |
| C2 | **Самонастройка участника**: новый человек или агент подключается и начинает работать за минуты без оператора (человека может добавить админ — это не вмешательство оператора) |
| C3 | **DR как инфраструктура**: cross-host restore пройден на живых данных, RPO/RTO измерены и задокументированы |
| C4 | **Проекты из шаблона**: создание проекта с предзаполненным каталогом, знаниями и правами |
| C5 | **Агент-команда end-to-end**: реальный проект проведён от анализа до подготовки выпуска с провенансом |

**Фазирование** [оценка пользователя, 2026-11-05]: старт со своей команды → небольшой релиз → дебаг/доработки → выход на команды организации. Оценка релизной фазы: **2–3 недели** («то, что здесь есть, сделано агентами за 2 недели») — оценка пользователя, не коммитмент PRD (источник — Addendum).

**Позиционирование.** Ниша «локальный LLM-рантайм + версионированный каталог + per-project RAG + device pairing/revocation + offline DR + single-host» не занята целиком (research 2026-11-05, addendum); **все найденные сопоставимые продукты — внешние**, в контексте импортозамещения они не являются рабочей альтернативой (требуют внешнего рантайма, облачных сервисов или закрытых лицензий). Table stakes (SSO/RBAC/audit/локальные LLM/MCP/air-gap) покрыты, кроме полноценного SSO (он же первый P0-блокер, P0-SSO). Дифференциаторы: каталог под контролем оператора, device lifecycle, offline quiesced restore, работа без внешних зависимостей в рантайме.

**Не цели (Out of Scope)** [подтверждено пользователем, 2026-11-05]:
- приватный Git/SSH/другие хостинги; произвольные install/build hooks; автоматическая компиляция non-JS репозиториев;
- автоматические письма-приглашения;
- HA/multi-replica, Kubernetes, Redis, микрофронты, отдельный build-сервис;
- multi-tenant SaaS, мобильный клиент;
- «тонкое устройство» (мост + исполнители без локального opencode-агента) — не целевое состояние: устройство = личный агент пользователя. [пользователь, 2026-11-05]

## Глоссарий

| Термин | Значение |
|---|---|
| **Проект** | Единица продукта: участники (люди/агенты), каталог, знания, чаты, устройства (FR-101) |
| **Каталог** | Версионированный набор инструментов (скиллы/MCP/плагины/модели/агенты) под контролем оператора; версии immutable (FR-2xx) |
| **Комплект** | Одобренный точный набор версий каталога с зависимостями, назначенный проекту (FR-202) |
| **Квитанция** | Сохраняемая проверяемая запись действия (установка/удаление/restore/провенанс); повтор idempotent (FR-702, FR-103, NFR-4) |
| **Знание** | Проектный опыт: опыт → гипотезы → проверка → кандидат → одобрение (FR-5xx) |
| **Артефакт** | Опубликованный объект с провенансом: версия + SHA + источник + время + издатель (FR-203) |
| **Snapshot/restore (quiesced)** | Снимок состояния проекта с SHA в остановленном состоянии; restore — на другом хосте или в новый проект (FR-104, FR-803) |
| **Retire** | Отзыв версии каталога или устройства: необратим; эффект — с момента следующей проверки (FR-204, FR-703) |
| **Pin** | Зафиксированная версия remote-подключения; смена pin → ре-верификация (FR-603) |
| **Мост** | Подключение устройства к серверу: pairing, привязка папки, канал в проект (FR-7xx) |
| **Карточка** | UI артефакта каталога: провенанс (версия + SHA + источник + издатель) + действия (FR-203) |
| **Версия** | Immutable-единица каталога (FR-202); версия модели/артефакта фиксируется pin (FR-603) |
| **Фаза** | Этап roadmap: Фаза 1 (своя команда, пилот) / Фаза 2 (команды организации); не путать с «релизной фазой» (2–3 недели — оценка времени, не этап roadmap) |
| **Билет (ticket)** | HMAC-допуск устройства для MCP-канала: TTL 24h, re-issue при reconnect (FR-705) |
| **fail-closed** | Отказ в сомнительном состоянии (без сессии/доступа), а не молчаливое прохождение (NFR-2, FR-901) |
| **Runbook** | Документированная процедура операционного действия (update/DR/ротация), NFR-5 |

## Пользователи и роли

| Роль | Что делает |
|---|---|
| **Главный админ** (платформа) | bootstrap первого админа, общий каталог, обслуживание, лимиты |
| **Админ проекта** | комплект проекта: одобряет версии/зависимости, назначает инструменты, одобряет знания |
| **Разработчик** | работает в проекте: публикует, устанавливает, добавляет опыт, предлагает гипотезы |
| **Наблюдатель** | read-only |
| **Оператор** (эксплуатация, **вне продукта** — не одна из 4 продуктовых ролей, в продукт не входит) | хост и стек, DR, секреты, обновление платформы — по runbook (NFR-5; FR-802–804, FR-1004), не через UI продукта |

**Важно:** команда ещё не видела продукт (стадия прототипа) — **закрытый пилот является первой пользовательской валидацией**. [пользователь, 2026-11-05]

## User Journeys

Зафиксированы из сценарных документов продукта (`publication-scenarios.md` S01–S29, `user-scenario-regression`); формат «протагонист → делает → чем заканчивается». Подтверждены (2026-11-05, пользователь).

- **UJ-1. Вход.** *Разработчик* → SSO/IdP → выбирает проект → **первая полезная операция** (чат с агентом проекта или открытие карточки инструмента). Неверный state/отказ IdP не создают сессию (→ FR-901).
- **UJ-2. Публикация.** *Разработчик/главный админ* → упаковка (npm/публичный GitHub/архив/ready-runtime) → **карточка + immutable-версия + SHA в каталоге** → *админ проекта* одобряет точный комплект → **назначение в проект с записью в аудит**.
- **UJ-3. Устройство.** *Разработчик* → установщик (SHA, архитектура) + pairing + привязка папки → one-click установка комплекта проекта → **сохраняемая квитанция** (повтор idempotent; прерванный setup продолжается с фактически незавершённого шага) → полезный MCP-вызов.
- **UJ-4. Обучение.** *Разработчик* → добавляет опыт → «построить гипотезы» → проверка → кандидат знания; *админ проекта* → **одобрение (только одобренная версия попадает в контекст проекта)** / отзыв / откат.
- **UJ-5. Восстановление.** *Оператор* → quiesced backup → доставка на независимый S3 → **restore чистого стека на другом хосте** (секреты — отдельно по runbook; веса моделей — re-pull/загрузка GGUF по restore-SOP) → вход/чтение/запись в проекте (статус сегодня: не принят — C1/C3).

## Требования

Приоритеты: **[P1]** — высокий приоритет, подтверждено пользователем; **[P2]** — приоритет открытый; без метки — базис контракта. P0-коды (P0-SSO и др.) — идентификаторы приёмных блокеров, не приоритеты FR.

### A. Проект (единица) — FR-1xx

- **FR-101.** Проект — единица работы: участники (люди и агенты), назначенный каталог, знания, чаты и привязанные устройства принадлежат проекту.
- **FR-102.** Проект создаётся из шаблона: предзаполненный каталог (агенты/скиллы/модели), знания, роли и права (обязательство C4). Lifecycle шаблона (создание, хранение, версионирование, правка) — главный админ.
- **FR-103.** Жизненный цикл проекта (создание → активен → архив) и удаление с полным каскадом (БД + файлы + S3-объекты + per-project RAG-БД) и квитанцией. Ручной retire RAG-БД (вне удаления проекта) — защищённый явный purge (retention/hold/preview/подтверждение); автоматический purge — только триггер удаления проекта.
- **FR-104.** Состояние проекта снимается (snapshot) с SHA (data-level — FR-801); два пути восстановления: restore в новый проект (с верификацией) и activate/rollback снимка (смена head внутри проекта, CAS-проверка перед сменой).

### B. Каталог и поставка — FR-2xx

- **FR-201.** Инструменты (скиллы/MCP/плагины/модели/агенты) упаковываются из доверенных источников (npm, публичный GitHub, архив, ready-runtime) с SHA-описью.
- **FR-202.** Версии каталога immutable; назначение в проект — только одобренный точный комплект с зависимостями.
- **FR-203.** У каждого опубликованного артефакта провенанс: версия, SHA, источник, время, издатель; проверяется из карточки (NFR-4).
- **FR-204.** Отзыв версии (retire, AD-16) — необратим: новые назначения не разрешаются, запуск в mcp-host и проверка билета (FR-705) не проходят; уже запущенные сессии гаснут при следующей проверке (окно ≤ TTL кэша); версия остаётся в каталоге (провенанс сохраняется); запись в аудит.

### C. Агенты — FR-3xx

- **FR-301.** Агент — участник проекта: имеет роль, контекст (одобренные знания), инструменты из каталога проекта (включая семантический поиск по коду, публичным чатам, знаниям и опыту — FR-311) и **доступ к публичным чатам проекта** (пользователь, 2026-11-05). Два типа: server-агенты (системные роли, доверенная сторона) и device-агенты (через мост, недоверенная сторона).
- **FR-302.** Агент-команда закрывает цепочку анализ → требования → архитектура → задачи → код → тесты → ревью → подготовка выпуска; следующий исполнитель получает принятые решения и исходные артефакты (C5). Последовательный контекст: следующий агент видит опубликованные ответы предыдущих (ID/автор/порядок/версия опубликованных сообщений) до своего вызова. Агент может подключить к задаче, которую решает, другого агента проекта: контекст задачи передаётся подключённому, подключение — с записью в аудит. [пользователь, 2026-11-05]
- **FR-303.** Системные роли покрывают вопросы самой системы: настройка (включая **конфигурации на компьютере** — пользователь, 2026-11-05), диагностика, модели, мосты, навыки/плагины/MCP, агенты/ассеты, доступы, данные (включая RAG/quirk), очереди, обновление, восстановление; координатор показывает владельца следующего действия (агент может вызвать системного агента и напрямую — FR-310); сводка — только после ответов нескольких уникальных агентов.
- **FR-304.** Результат работы агента в проекте проверяем: верификация (exit-code/покрытие), а не «сделано».
- **FR-305.** [P1] Агент запускается в фоне (не блокирует чат): задача → работа в полной среде → результат в проектный чат. Работает на сервере; рабочая среда агента — **opencode** (полная сессия: инструменты, терминал/файлы, скиллы, плагины, MCP); через мост — **настраиваемый доступ к компьютеру** (включая работу с opencode на компьютере). Контекст настраивается: проект (данные, одобренные знания, каталог), компьютер (через мост), web. [пользователь, 2026-11-05]
- **FR-306.** [P1] Плагины/скиллы/MCP opencode для агента — из одобренного каталога проекта (точный комплект, FR-202); подключение локальных расширений с устройства допускается **строго для тестирования возможностей** (экспериментальный режим: не входит в одобренный комплект, фиксируется в аудите). [пользователь, 2026-11-05]
- **FR-307.** [P1] Добавление агента в проект без оператора: роль, контекст (одобренные знания), инструменты из каталога, доступ к публичным чатам; первая полезная операция — за минуты (C2). [пользователь, 2026-11-05]
- **FR-308.** [P1] Работа всех исполняющих агентов (агент-команда FR-302 и фоновый агент FR-305) ведётся через методику **BMAD + OpenSpec**: закреплённые версии, скрытых обновлений и установки при отправке задачи нет. Обязательный режим для агент-команды — **BMAD → OpenSpec**: BMAD формирует или переиспользует brief/PRD/архитектуру, OpenSpec ведёт единственную реализацию с проверками; принятые документы переиспользуются, второй PRD и второй build-цикл не создаются. Устройство (личный агент, FR-701) — вне мандата. (Фича: `docs/features/agent-method-workflows.md`.) [пользователь, 2026-11-05]
- **FR-309.** [P1] Агенты могут делиться контекстом: с другими агентами проекта (состояние задачи, промежуточные результаты, решения; подключение из FR-302 — частный случай, с записью в аудит), с пользователем (личный диалог), с командой (публичные чаты/комнаты проекта, FR-402). Делёный контекст несёт провенанс (какой агент и что, версия; NFR-4); деление — только в комнаты, где у агента есть доступ (FR-301); приватный диалог не является каналом деления с командой (FR-403). [пользователь, 2026-11-05]
- **FR-310.** [P1] Любой агент проекта может вызвать агента с системной ролью (FR-303) в случае проблемы или для уточнения. Вызов — явный (случай: проблема/уточнение), с записью в аудит; ответ системного агента доступен вызвавшему в проектном диалоге. При отсутствии пути продвижения вызов системного агента — recovery-путь: тупиковые сценарии исключены (NFR-3). [пользователь, 2026-11-05]
- **FR-311.** [P1] У каждого агента проекта — семантический поиск по четырём корпусам: (1) актуальный код проекта, (2) публичные чаты/комнаты проекта (FR-402), (3) одобренные знания (FR-502), (4) опыт (записи цикла FR-501). «Актуальный» = индекс синхронизирован с изменениями (reindex/sync — FR-606); поиск по протухшему индексу — дефект. Результаты поиска несут провенанс: источник (файл + commit, сообщение + комната, версия записи знания/опыта; NFR-4). Граница: приватные диалоги и личный диалог с агентом не являются корпусом поиска (FR-403). [пользователь, 2026-11-05]

### D. Командный чат — FR-4xx

- **FR-401.** Личные и проектные диалоги; @агенты; группы агентов; явный запуск исследования. Режимы диалога: обычный @; совместная дискуссия людей+агентов; автономные раунды — запускаются явным сообщением пользователя в чате или запросом агентов (лимит раундов/бюджет, пауза/остановка/вмешательство, шаг, уже потребивший бюджет, не повторяется после перезапуска); режим сохраняется в диалоге. [пользователь, 2026-11-05]
- **FR-402.** Чат изолирован по проекту; публичные/приватные комнаты.
- **FR-403.** История чата — часть данных проекта (snapshot/DR покрывает). Приватный диалог не читается никем другим по ID, включая главного админа; usage приватных командных диалогов виден только участникам.
- **FR-404.** Вложения в чат: upload/extract/context/preview/remove; лимиты — 10MiB/файл, 5 файлов/сообщение, 50MiB/диалог; файл из чата не публикуется в каталог и не добавляется в проектный RAG.

### E. Обучение и знания — FR-5xx

- **FR-501.** Цикл: опыт → гипотезы → проверка → кандидат знания → одобрение/откат человеком. Политика подтверждений: порог — число независимых подтверждений (от 1 до N), настраивается админом проекта; повтор одного доказательства и несколько пересказов одной моделью не увеличивают счётчик независимых подтверждений; действующее человеческое одобрение активации сохраняется.
- **FR-502.** Только одобренная (человеком) версия знания попадает в контекст проекта.
- **FR-503.** Версии знания отзываемы и откатываемы с записью в аудит.
- **FR-504.** Точечный перенос опыта между проектами: явный выбор отдельных единиц опыта/знания (не bulk-копия всей базы) переносится между проектами с провенансом (источник — исходный проект); в целевом проекте единица проходит цикл FR-501 — до одобрения админом целевого проекта не попадает в контекст. [пользователь, 2026-11-05]

### F. Модели (свои модели, хостинг, подключения) — FR-6xx

- **FR-601.** Веса для хостинга добавляются вручную из GGUF или архива: SHA-256, строгая проверка формата (архитектура/тензоры/quant), квота и retention импорта; **подготовка и активация — отдельные явные действия**; автоматической загрузки весов нет; per-version runtime-теги.
- **FR-602.** Lifecycle подготовленной модели: prepare/start/check/stop/cancel/recovery с прогрессом и ресурсными лимитами (Ollama-runtime).
- **FR-603.** OpenAI- и Ollama-совместимые API (remote-openai/remote-ollama) с приватными шифрованными credentials и явной pin-верификацией (смена pin → ре-верификация). Credentials remote-провайдера — личные ключи пользователей (без общего admin fallback). Импорт моделей устройства (OpenCode/Codex) с credential consent; opt-in sync — с сохранением старого pin до успешной проверки.
- **FR-604.** Точный project model set с in-use guard (живой чат/агент/embedding) и снятием назначения.
- **FR-605.** Rate-limits/CAS/admission/queue/cancel — enforced model budget (NFR-6); usage-факты со скоупами own/project/all.
- **FR-606.** Проектная embedding-модель + reindex/sync; смена модели непустого индекса — только явная миграция или новый проект (автоматической конвертации векторов нет).
- **FR-607.** [P2] Контекст-окно каждой локальной модели; история/сравнение/откат системного промпта; разделение серверного и внешнего (OpenCode) потребления. Приоритет — открытый (agent-capability-audit, см. Addendum).
- **FR-608.** Capability модели (chat/text, vision, multimodal, embedding, **rerank** и прочие разновидности) — **открытое множество**: capability — часть карточки и точного указания модели; закрытый список capability платформой не заводится; «проверить модель» выполняет содержательную пробу заявленной capability (карточка ≠ работающая обработка). [пользователь, 2026-11-05: реранкеры и прочие разновидности]

### G. Устройства и мост — FR-7xx

- **FR-701.** Подключение устройства: установщик по ОС, pairing, привязка папки, one-click установка комплекта проекта (C2). Устройство — **личный агент пользователя (opencode) «одетый» проектом**; серверный фоновый агент (FR-305) — дополнение, а не замена. [пользователь, 2026-11-05]
- **FR-702.** Каждая установка — с квитанцией; повтор idempotent (не дублирует).
- **FR-703.** Lifecycle устройства: pairing → активен → отзыв (отвязка/деактивация); после отзыва доступ отклоняется в окне ≤ 1 минута (AD-4: TTL кэша 60s).
- **FR-704.** Устройство работает offline (кэш) и переподключается без потери данных.
- **FR-705.** [P1] Вызовы инструментов проекта устройством — через билет (HMAC, TTL 24h; re-issue при reconnect); авторизация — на соединение и на каждую операцию (привязка device↔project, активность, pin, версия не retired); отзыв устройства/версии — билет не переживает (окно ≤ TTL кэша); пул MCP-хостов — per-project/per-device квоты (NFR-6).
- **FR-706.** [P1] Комплект проекта декларирует поддерживаемые версии opencode; мост определяет фактическую версию на устройстве; несовместимая версия — без тихой установки: явная ошибка + actionable следующий шаг (обновить / совместимая версия) (NFR-3). [пользователь, 2026-11-05: «важна совместимость с разными версиями»]

### H. Данные и DR — FR-8xx

- **FR-801.** Данные проекта (БД, файлы, знания, чат) snapshot-ируются с SHA (проектные пути восстановления — FR-104).
- **FR-802.** Полный offline-бэкап (quiesced) по расписанию; доставка на независимый S3 с верификацией readback (C1).
- **FR-803.** Restore на другом хосте: бандл самодостаточен (данные + тома + S3-объекты + образы релиза — решение о поставке образов, 2026-11-05); **секреты и веса моделей (model weights) — вне бандла**: секреты — по runbook, веса — re-pull/повторная загрузка GGUF как часть restore-SOP (задокументированный residual). RPO/RTO измерены и задокументированы (C3).
- **FR-804.** Обновление платформы: репетиция (rehearsal) на копии данных до обновления; rollback = restore из pre-update копии (C1).

### I. Доступ — FR-9xx

- **FR-901.** SSO (настоящий IdP — **Blitz**, единственный в контракте) + 4 продуктовые роли; менее привилегированная роль ограничивает и интерфейс, и API (C1). Неверный state/отказ IdP не создают сессию (fail-closed).
- **FR-902.** Пользователи добавляются главным админом по почте (письма-приглашения — вне контракта).
- **FR-903.** Каждая админ-мутация — в транзакционном аудите (NFR-4).

### J. Обслуживание — FR-10xx

- **FR-1001.** Модуль обслуживания: feature flags, журнал операций, capacity, статус бэкапов; activity-факты (проекты/участники/устройства) для usage-метрик.
- **FR-1002.** Runtime-лимиты настраиваются главным админом и **реально исполняются** (у каждого quota-лимита есть enforcement-точка). Настраиваемость — поэтапная (скоуп и плановые срезы — `docs/runtime-limit-inventory.md`); часть лимитов — протокольные константы и ceiling компиляции (не настраиваются).
- **FR-1003.** Самодиагностика: health/readiness, видимость ошибок (error-store + admin UI), алерты. Каждая ошибка — actionable (указан следующий шаг); для каждого failure mode — recovery-путь (re-pairing, re-fetch, restore) (NFR-3).
- **FR-1004.** Секреты ротируемы с задокументированными последствиями.

## Сквозные NFR

- **NFR-1. Простота.** (Дыра: «переусложненный интерфейс».) Ядро сценариев доступно без чтения документации; прогрессивное раскрытие: сложность — опционально. Метрики — Success Metrics «Удобство и отзывы»: completion-rate задач пилота без помощи; число шагов ядра сценариев.
- **NFR-2. Надёжность и стабильность.** (Дыра: «общая нестабильность».) Нет молчаливых падений: crash-политика + запись ошибки; контролируемые отказы (fail-closed); видимость ошибки главному админу. Метрики — Success Metrics «Надёжность»: инциденты с потерей данных; MTTR.
- **NFR-3. Нет тупиковых сценариев.** (Дыра: «много тупиковых сценариев».) Каждая ошибка — actionable (следующий шаг указан); для каждого failure mode есть recovery-путь (re-pairing, re-fetch, restore). Метрики — Success Metrics «Удобство и отзывы»: тупики, найденные в пилоте, = 0 незакрытых.
- **NFR-4. Провенанс.** Артефакты/решения несут версию + SHA + квитанцию; admin-действия — в аудите (метрика — Success Metrics «Провенанс»). Counter: артефакт без провенанса = 0.
- **NFR-5. Эксплуатируемость.** Single-host compose; самодиагностика; операционные действия (update/DR/ротация) — по runbook.
- **NFR-6. Лимиты реально работают.** Каждый заявленный лимит (квота/бюджет) имеет enforcement-точку; «лимит, который не работает» — дефект.
