# Security Review — architecture-runtime-trust

- **Lens:** trust boundaries & fail-closed
- **Reviewer:** ad-hoc security reviewer (BMad architecture Reviewer Gate)
- **Дата:** 2026-11-05
- **Объект:** `architecture-runtime-trust.md` (spine, draft, AD-1..AD-11) + memlog
- **Код-срез (brownfield-состояние):** `services/api-gateway/src/features/mcp-host/`, `services/shared/runtime-limits.cjs`, `services/shared/runtime-artifacts.cjs`, `mcp/neurocenter-asset-sync/src/features/runtime-artifacts/`, `vendor/asset-contract/lib/asset.mjs`

## Verdict (общая оценка)

Парадигма «signed-contract pipeline» (ceiling-константа / админ-политика / подписанный дескриптор) выбрана правильно и в целом fail-closed: HMAC-билет без секрета в payload, точные равенства SHA/размеров, USTAR-only распаковка без ссылок, `O_NOFOLLOW`+`nlink===1`, whitelist платформ, fail-fast при отсутствии секрета. **Главные риски spine — не в выбранной модели, а в молчании AD о режимах отказа**: AD-4 не определяет поведение live-binding lookup при ошибке (самая вероятная точка fail-open), AD-2 не определяет случай «дескриптор без `limits`» (самая вероятная точка fail-open на клиенте), AD-1 откладывает сами значения ceiling при том, что текущий код имеет **неограниченный env-кранок** лимитов (fail-open транзитного состояния), а server-side кэш артефактов не имеет ни квоты, ни eviction, хотя AD-1 декларирует cacheBytes «во всех сервисах». Ни одно из этих мест не является ошибкой модели — все закрываются ужесточением формулировок AD или фиксацией residual.

## 2. Findings

### F1 — AD-4: не определено поведение live-binding lookup при отказе → вероятный fail-open (отзыв обходится при сбое инфраструктуры)
- **Severity: high**
- **Что:** AD-4 требует проверку device↔project «при соединении на канале (lookup с кэшем ≤ 60s)», но не говорит, что происходит, когда lookup **ошибается** (DB/каталог недоступны, таймаут) или когда кэш истёк и не обновился. Реализация «при ошибке — пропустить проверку» (самый частый паттерн «не ломаю доступность») = во время любого инфраструктурного инцидента **отзыв перестает работать вообще**, а билет живёт до TTL 30 дней.
- **Почему важно:** AD-4 — единственный механизм revocation (per-ticket denylist отложен). Его обход в момент сбоя превращает «revocable device» в декларацию — ровно то, что AD-4 заявляет как Prevents.
- **Предложение:** ужесточить AD-4 формулировкой: «lookup error (не 401/403 от каталога) → отклонить соединение (fail-closed, 503); кэш не используется за TTL (stale-while-error запрещён); 401/403 = отзыв (403)». Зафиксировать как residual: «задержка отзыва ≤ TTL кэша (30–60s)». Текущая реализация `host.ts:authorizeSession` уже fail-closed — закрепить её в правиле.

### F2 — AD-2: «десcriptor без `limits`» не определён → вероятный fail-open на клиенте (ceiling/env вместо политики)
- **Severity: high**
- **Что:** AD-2 фиксирует fail-closed только для значений **вне** `[1..ceiling]`. Случай **отсутствующего** поля `limits` не зафиксирован. Контракт 1.2.1 (byte-pinned) поля не имеет; текущий клиент берёт лимиты из env машины пользователя **без потолка** (`asset.mjs:10`, `limitValue` без cap). Естественная реализация «нет limits → контрактные константы/ceiling/env» = клиент применяет верхнюю границу или управляемое пользователем env = fail-open (ослабление guard окружением пользователя — ровно то, что AD-1 Prevents).
- **Почему важно:** это единственная граница, где security-параметры применяются на недоверенной машине пользователя; молчание правила = реализация выберет наименее безопасный из двух вариантов (ceiling), либо сломает все существующие ассеты (reject без limits), — и то и другое должно быть осознанным решением, а не побочным эффектом.
- **Предложение:** ужесточить AD-2: «`limits` — обязательное поле новой версии контракта; отсутствие поля = невалидный дескриптор (fail-closed на обеих сторонах); версия контракта, в которой `limits` обязательна, фиксируется в AD-2». Плюс миграционная заметка: как переиздаются/ре-пины ассеты без `limits` (иначе все установленные ассеты станут невалидными).

### F3 — AD-1: ceiling Deferred, а текущее состояние fail-open: env-кранок поднимает лимиты без ограничения
- **Severity: high**
- **Что:** (а) Конкретные значения ceiling отложены («подтвердить при реализации»), при этом **сегодня** `limitValue()` (`runtime-artifacts.cjs:28-35`) принимает из env любое положительное целое без верхней границы — оператор сервера (или пользователь машины на клиенте) может поднять лимиты до произвольного значения. «Ceiling — константа компиляции» существует пока только на бумаге. (б) Свойство «env — никогда выше дефолта» заявлено, но механизм принуждения (fail-fast при env > дефолт) не задан. (в) Транзитный дрейф уже виден в коде: admission в `connect` (`mcp-host.controller.ts:116`) проверяет `compressedBytes` против **литерала 2 GiB**, а `verifyHostedMcpTicket` (`ticket.ts:126`) — против `LIMITS.compressedBytes` (по умолчанию **256 MiB**, env) → билет, выданный для артефакта 1 GiB, проходит `connect` и получает 401 на канале. Два разных «ceiling» в двух местах — прямой симптом того, что AD-1 (единая константа) обязателен, а не опционален.
- **Почему важно:** до приземления AD-1 система fail-open по DoS-огибающей: env = неограниченный кранок. Отложенный ceiling (8 GiB unpacked / 16 GiB cache = ×4–×8 от текущих дефолтов) при этом — нерешённая DoS-огибающая сервера.
- **Предложение:** (1) ужесточить AD-1: «ceiling — константа, существующая с первого среза AD-1; env-bootstrap валидируется на старте: значение ≤ дефолт, иначе fail-fast»; (2) закрыть Deferred «значения ceiling» до реализации (не в момент реализации) — в этом обзоре или отдельным решением; (3) инвариант-тест: все admission-проверки читают потолок из единого shared-модуля, литералы запрещены (сверить: `controller.ts:116`, `ticket.ts:126`).

### F4 — AD-5: правила верны, но не покрывают слабый секрет, миграцию fallback-деплойментов и ротацию internal-token
- **Severity: medium**
- **Что:** (а) «Отсутствие секрета = fail-fast» зафиксировано; «слабый секрет = fail-fast» — нет (сейчас порог 16 символов проверяется не на старте, а на каждый issue/verify; 16 символов — слабый порог энтропии). (б) Текущий код содержит сам fallback, который AD-5 отменяет: `ticket.ts:52` `NEUROCENTER_MCP_HOST_SECRET || NEUROCENTER_INTERNAL_TOKEN`. После AD-5 все деплойменты, живущие на fallback, потеряют валидность всех активных билетов (смена HMAC-ключа) — это осознанное изменение поведения, не описанное в spine (deploy-note). (в) Residual «ротация host-secret гасит все билеты» зафиксирован; то же свойство у `NEUROCENTER_INTERNAL_TOKEN` (ротация = обрыв всех internal-вызовов gateway↔catalog) — не зафиксирован.
- **Почему важно:** AD-5 — backbone доверия «инternal-токен ≠ хост-ключ»; неопределённые хвосты (слабый ключ, миграция, ротация второго секрета) размывают границу trust-domain.
- **Предложение:** ужесточить AD-5: «отсутствие **или длина < 32 байт / не криптогенерированное значение** = fail-fast на старте (через config-модуль, AD-9)»; добавить в Deferred/Residual: «ротация NEUROCENTER_INTERNAL_TOKEN обрывает internal-каналы и гасит билеты (следствие fallback-эпохи, после AD-5 — только internal-каналы)»; deploy-note о сгорании билетов при первом деплое AD-5.

### F5 — Secrets lifecycle: нет правила «значение секрета не попадает в логи/отчёты/аудит/ответы»
- **Severity: medium**
- **Что:** AD-9 вводит «fail-fast с агрегированным отчётом на старте» — типичная реализация такого отчёта печатает **все** переменные со значениями, включая секреты. AD-5 не фиксирует хранение секрета (env only, не DB, не UI runtime-limits, не audit). Аудит runtime-limits покрывает политики, но конвенция «секреты не логируются» нигде не зафиксирована. Хорошо, что `neurocenter_bridge_status` явно «секрет подключения не возвращается» — но это локальное решение, не конвенция.
- **Почему важно:** утечка секрета через стартовый лог/агрегированный отчёт/отладочный дамп = обход всей модели AD-5 (форж билеты по HMAC-ключу, или internal-токен → полный internal-канал).
- **Предложение:** в Consistency Conventions добавить строку: «Значения секретных переменных (NEUROCENTER_MCP_HOST_SECRET, NEUROCENTER_INTERNAL_TOKEN и будущие) не печатаются ни в одном логе, агрегированном отчёте config-модуля, аудите или API-ответе; отчёты маскируют значения (только имя + факт присутствия/длина)»; в AD-9: «секретные переменные в схеме помечаются, их значения исключаются из валидационного отчёта».

### F6 — Residual (не зафиксирован): 30-дневный bearer-билет в URL + зазор mid-session revocation
- **Severity: medium**
- **Что:** Билет = bearer-токен в URL-пути `/api/mcp-host/m/:ticket` на TTL 30 дней (`HOSTED_MCP_TTL_MS`). (а) URL попадает в access-логи gateway, прокси, конфиг OpenCode на машине пользователя, историю инструментов — канал утечки bearer на 30 дней. (б) AD-4 проверяет привязку «при соединении»; установленная долгосессия не перепроверяется по правилу (текущий код перепроверяет **на каждый** request — строже, но spine этого не требует). (в) Утечка билета лечится только отвязкой устройства (granularity по device) или ротацией секрета (сжигает всё) — перепуск одного билета невозможен (denylist отложен).
- **Почему важно:** единственный residual в AD-4 — ротация секрета; эти три хвоста (URL-логирование, mid-session, 30-дневное окно) — не зафиксированы.
- **Предложение:** зафиксировать residual-блок в AD-4: «билет — 30-дневный bearer в URL: может попасть в логи промежуточных узлов; отзыв действует при следующем обращении к каналу (в реализации — на каждый request); окно утечки закрывается только отвязкой device или ротацией host-secret; TTL — контрактная константа, не выше 30 дней».

### F7 — DoS: server-side кэш артефактов без квоты и eviction, хотя AD-1 декларирует cacheBytes «во всех сервисах»
- **Severity: medium**
- **Что:** `artifact-cache.ts` раскрывает каждый `artifactSha256` в `NEUROCENTER_MCP_HOST_DIR/artifacts/<sha>` — **без** суммарной квоты, LRU или eviction (в клиенте есть квота cacheBytes + cleanup-политика + eviction; в сервере — ничего). Ограничен только процессный пул (`MAX_HOSTS`, env, дефолт 4) и размер одного артефакта (ceiling). Аутентифицированный пользователь с устройством может последовательно подключать разные одобренные пакеты → каждый материализует до ceiling unpacked (сегодня 1 GiB, рекомендованный ceiling 8 GiB) на диске gateway → disk-exhaustion. AD-11 advisor дополнительно может подталкивать админа к 16 GiB cache.
- **Почему важно:** AD-1 биндит `cacheBytes` «во всех сервисах», но ни AD, ни Deferred не определяют механизм server-side кэша — декларация без механизма = при реализации либо его не будет (DoS), либо будет ad-hoc (расхождение с AD-1).
- **Предложение:** ужесточить AD-1 (или новый AD): «server-side кэш артефактов gateway подчиняется той же квоте cacheBytes; при переполнении — LRU-eviction (или явная ошибка 503, если eviction запрещён); квота не превышается никогда». Альтернатива — зафиксировать residual с расчётом: `MAX_HOSTS × ceiling_unpacked` как верхний bound кэша.

### F8 — Транзитный дрейф: admission в `connect` (2 GiB литерал) ≠ verify (`LIMITS.compressedBytes`, дефолт 256 MiB) → билет, выданный на `connect`, может получить 401 на канале
- **Severity: medium**
- **Что:** `mcp-host.controller.ts:116` принимает `compressedBytes ≤ 2 GiB` (магический литерал), `ticket.ts:126` отклоняет `compressedBytes > LIMITS.compressedBytes` (дефолт 256 MiB, env `NEUROCENTER_RUNTIME_MAX_COMPRESSED_BYTES`). Артефакт 257 MiB–2 GiB: билет выпущен — канал отдаёт 401 «Соединение MCP истекло». Направление fail-closed (безопасно), но это функциональный слом + прямое доказательство дрейфа, который AD-1 должен убрать.
- **Предложение:** покрывается F3(3): единый shared-ceiling + запрет литералов + инвариант-тест «admission == verify bound».

### F9 — AD-3: связка claim↔descriptor зафиксирована только для `artifactSha256`; limits из хедеров каталога — доверие без правила
- **Severity: low**
- **Что:** `artifact-cache.ts:94-95`: если в claim нет `unpackedBytes`/`filesCount`, лимиты инспекции берутся из HTTP-хедеров каталога (`x-neurocenter-unpacked-bytes`, `x-neurocenter-files-count`) — т.е. из ответа доверенного, но **отдельного** сервиса в момент загрузки, а не из одобренного на момент публикации. Сегодня защита трёхслойная и fail-closed: NaN/не-integer отклоняются `normalizeRuntimeArtifacts`; глобальный guard `LIMITS.unpackedBytes + filesCount*1536 + 1MiB` в `inspectRuntimeArchive` независим от descriptor; точное равенство `total === descriptor.unpackedBytes` не даёт «надуть» лимит. Но spine об этом молчит, и более слабая реализация по AD-3 (проверка только sha256) допустима текстом.
- **Предложение:** ужесточить AD-3: «claim-лимиты (unpackedBytes/filesCount) привязаны к описи артефакта в каталоге; значения из ответа каталога при отсутствии в claim принимаются только при равенство с описью, иначе fail-closed».

### F10 — Литералы-границы вне spine: `ready()` жёстко 20000 файлов; entrypoint/name/ticket-length не зафиксированы в AD-1
- **Severity: low**
- **Что:** (а) `artifact-cache.ts:133` — `receipt.entries.length > 20000` → при рекомендованном ceiling filesCount = 200000 все легитимные крупные артефакты будут **fail-closed отклонены** при cache-hit (направление безопасное, но функциональный слом + ещё один дрейфующий литерал). (б) Границы `entrypoint ≤ 240`, `name ≤ 200`, `session-поля ≤ 200`, `ticket ≤ 2048` — security-relevant DoS-границы, живущие только в коде, не в spine.
- **Предложение:** F3(3) (единый источник границ) + в AD-1 или Consistency Conventions зафиксировать контрактные границы строк (entrypoint/name/session/ticket) как часть vendor-контракта.

### F11 — DoS-кранок вне реестра AD-1: `NEUROCENTER_MCP_HOST_MAX` (число процессов) env без ceiling
- **Severity: low**
- **Что:** `host.ts:40`: `Math.max(1, Number(process.env.NEUROCENTER_MCP_HOST_MAX || 4))` — env-кранок числа живых MCP-процессов без верхней границы и без валидации (мусор → NaN → 1, безопасно; большое число → принимается). Это часть DoS-огибающей сервера (каждый host = child-процесс + буферы транспорта 8 MiB), но не покрывается ни AD-1 (реестр = compressed/unpacked/files/cache), ни AD-9 явно.
- **Предложение:** включить «число хостов MCP» в реестр лимитов AD-1 (default + ceiling, например ceiling 32) или явно вывести из scope cceiling-заметкой; в любом случае — валидация в config-модуле (integer ≥ 1, ≤ ceiling, fail-fast).

### F12 — Не зафиксированный residual: internal-канал gateway→`operationRemote` как SSRF-вектор при компрометации каталога
- **Severity: low**
- **Что:** `operationRemote` (URL + произвольные заголовки) из claim приватных role-сессий запускает MCP-транSPORT gateway на **любой** URL: защиты есть (`redirect: 'error'`, точный pin URL на запрос, 8 MiB, 30s), но **нет allowlist хостов**. По trust-модели spine каталог — доверенная сторона, так что формально это out-of-scope; но компрометация каталога (internal-токен) даёт SSRF с gateway-хоста в internal-сеть/метаданные облака с произвольными заголовками.
- **Предложение:** зафиксировать residual: «operationRemote унаследует доверие к каталогу: компрометация каталога = SSRF с gateway; опционально — allowlist хостов operationRemote при реализации».

### F13 — Мелкие (информационные)
- **Severity: low.** (а) Сравнение `NEUROCENTER_INTERNAL_TOKEN` в `main.ts` нескольких сервисов — обычное `!==` (не constant-time); на высокоразрядном токене через HTTP практически неиспользуемо, но конвенция «HMAC/секреты — только `timingSafeEqual`» стоит зафиксировать (ticket уже использует правильно). (б) `ready()` пересчитывает SHA256 **всех** файлов кэшированного артефакта при каждом cache-hit (`artifact-cache.ts:141-143`) — CPU/IO-усиление на горячем пути при крупных ceiling (8 GiB / 200k файлов); bound-ограничено, но при реализации AD-1 с новым ceiling стоит оценить или кэшировать receipt-проверку. (c) AD-8 «базовая форма» деклараций — для security-значимых границ (типы/диапазоны) покрыто слабее, чем имена; усилить drift-тест на границы чисел в декларациях shared-модулей.

## 3. Residual risks: что зафиксировано, что нет

| Residual | Статус |
| --- | --- |
| Ротация `NEUROCENTER_MCP_HOST_SECRET` гасит все активные билеты | ✅ зафиксирован в AD-4 |
| Ротация `NEUROCENTER_INTERNAL_TOKEN` обрывает internal-каналы (и гасит билеты в эпоху fallback) | ❌ не зафиксирован → F4 |
| Билет — 30-дневный bearer в URL (логи узлов, утечка с машины) | ❌ не зафиксирован → F6 |
| Mid-session revocation: долгосессия не перепроверяется (в spine — «при соединении») | ❌ не зафиксирован → F6 |
| Задержка отзыва ≤ TTL кэша live-binding (30–60s) | ⚠️ только как Deferred («размер кэша»), не как residual → F1 |
| Per-ticket denylist отложен → утечка одного билета лечится только device-level | ⚠️ отложен, но последствия не зафиксированы как residual → F6 |
| OperationRemote = SSRF при компрометации каталога (trust-модель) | ❌ не зафиксирован → F12 |
| `process.report`-хрупкость (AD-7) | ✅ зафиксирован в Deferred |

## 4. Итоговые рекомендации (порядок)

1. **AD-4** — добавить fail-closed клаузулу lookup (error → 503, stale-while-error запрещён, 401/403 → 403) + residual задержки отзыва. *(F1, high)*
2. **AD-2** — `limits` обязательное поле новой версии контракта; отсутствие = невалидный дескриптор (fail-closed) + миграционная заметка для ассетов 1.2.1. *(F2, high)*
3. **AD-1** — ceiling существует с первого среза (закрыть Deferred до реализации); env-bootstrap валидируется ≤ дефолт (fail-fast); все admission-проверки — из единого shared-модуля, литералы запрещены (инвариант-тест: admission == verify bound). *(F3/F8, high/medium)*
4. **Новое правило или расширение AD-1** — server-side кэш артефактов: квота cacheBytes + LRU-eviction (или явный 503). *(F7, medium)*
5. **AD-5** — fail-fast также на слабый секрет (длина/энтропия); deploy-note о сгорании билетов; residual ротации internal-token. *(F4, medium)*
6. **Consistency Conventions** — строка «значения секретов не логируются/не в отчётах/аудите/ответах» + пометка секретных переменных в AD-9. *(F5, medium)*
7. **AD-4** — residual-блок: 30-дневный bearer в URL, окно утечки, TTL-константа. *(F6, medium)*
8. **AD-3** — привязка claim-лимитов (unpackedBytes/filesCount) к описи, а не только sha256. *(F9, low)*
9. Реестр лимитов AD-1 расширить: число хостов MCP (ceiling), контрактные строковые границы (entrypoint/name/session/ticket), литерал `20000` в `ready()` → на shared-константу. *(F10/F11, low)*
10. **Residual** — operationRemote/SSRF при компрометации каталога. *(F12, low)*

## 5. Что в spine сделано хорошо (не менять)

- Парадигма «ceiling — константа, админом не поднимается» — правильный DoS-страховочный слой.
- AD-3: verify против ceiling, а не текущей политики — осознанное и верное решение (админский слайдер не ломает выданные билеты).
- AD-7: unknown libc → throw (fail-closed) + whitelist TARGETS — реализовано ровно так.
- AD-5: отказ от fallback-цепочки секретов — правильный trust-domain split.
- AD-2: «значения вне [1..ceiling] — fail-closed» и запрет отдельного канала доставки лимитов.
- Текущий `inspectRuntimeArchive` (USTAR-only, без ссылок, точные равенства, TOCTOU-защита `ino/mtime/nlink`, global unpack guard) — reference-grade; AD-1/AD-3 должны сохранить эти свойства в правиле, а не только в коде.
