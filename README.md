# Neurocenter — Нейроцентр

Веб-каталог инструментов и знаний команды: проекты, скиллы, MCP-серверы, плагины OpenCode и локальный мост для работы с папками пользователя.

## Возможности

- Общий и проектный каталог, версии и зависимости инструментов.
- Вкладка «Модели»: добавление моделей Ollama, назначение проектам, запуск и проверка хостинга с прогрессом.
- Упаковка npm-пакетов, публичных Git-репозиториев, ZIP/TAR-архивов и подготовленных приложений разных runtime.
- Установка, настройка, диагностика и восстановление через локальный MCP-мост.
- Синхронизация проектных баз знаний LanceDB ↔ PostgreSQL/pgvector.
- Локальная модель эмбеддингов с отдельным API и весами внутри проекта.
- Локальная обработка изображений: описание, чтение надписей и ответы на вопросы.
- Роли, отзыв доступа, журнал операций и транзакционный аудит изменений.
- Флаги функций: отдельный сервис и управление хостингом моделей, сборкой инструментов и синхронизацией знаний в «Обслуживании».
- Полные резервные комплекты, расписание обслуживания, S3-доставка и контроль ресурсов.

Состояние: разработка и локальная приёмка. Production-допуск **NO-GO**: настоящий IdP, полная матрица клиентских платформ и независимое восстановление требуют отдельной проверки. Точные границы: [готовность](docs/implementation-readiness.md), [реализация](docs/current-implementation.md), [сценарии](docs/publication-scenarios.md).

## Быстрый старт

Нужны **Node.js 24**, npm и установленный Docker CLI/Engine; dev-скрипты рассчитаны на macOS/Linux. Node.js 24 нужен для локальной упаковки автономного моста. Compose устанавливается автоматически. Порт 5432 должен быть свободен.

```sh
git clone https://github.com/ghost-raven1/neurocenter.git
cd neurocenter
cp .env.example .env
node -e "require('node:fs').appendFileSync('.env','\nNEUROCENTER_INTERNAL_TOKEN='+require('node:crypto').randomBytes(32).toString('hex')+'\n')"
scripts/dev.sh install
scripts/dev.sh up
```

`install` сохраняет рабочий `docker compose` v2 или новее. Если плагина нет или он не поддерживает `up --wait`, скачивается закреплённый Compose 2.40.3 с проверкой SHA-256. Отдельная установка: `npm run compose:install`. Docker Engine устанавливается заранее; для `up` он должен быть запущен. [Платформы, повтор и восстановление при сбое](docs/compose-install.md).

Случайный внутренний ключ создаётся один раз в локальном `.env` и используется всеми сервисами; не публикуйте этот файл.

`feature-flags-service` запускается штатными dev/Compose-командами. Главный администратор переключает функции в «Обслуживании»; изменения защищены от конфликтующих сохранений и попадают в аудит. Значения хранятся в PostgreSQL и сохраняются при перезапуске. [Контракт и поведение при сбоях](docs/current-implementation.md#флаги-функций).

Интерфейс: <http://localhost:5173>. В шаблоне включён локальный вход `SSO_DISABLE=true`; для реального SSO задайте параметры своего IdP. Production-конфигурация проверяется отдельно и не допускает dev-авторизацию.

При нескольких Node задайте `NODE_BIN` абсолютным путём к Node 24+. Остановка `scripts/dev.sh down` сохраняет PostgreSQL и данные. Проверки: `npm run check` или `scripts/dev.sh check`; они собирают проект и останавливаются при первой ошибке.

Справка по командам: `scripts/dev.sh --help` (также работает `scripts/dev.sh up --help`). Установка, сборка и запуск показывают этапы и итог; `status` выводит готовность сервисов и адрес интерфейса, `tail` — последние 20 строк каждого лога. Подробный вывод npm и сборщиков сохраняется в терминале. Цвета включаются только в TTY; `NO_COLOR=1` отключает их явно.

Запуск привязан к каталогу проекта, даже если папка вызова была удалена или переименована. Готовность интерфейса включает компиляцию стилей Ant Design: ошибка Less не позволяет объявить фронт готовым по одному ответу HTML.

Повторный запуск распознаёт собственные процессы после переноса папки. При сбое показываются сервис, порт, код выхода и путь к его логу. Для сохранения существующей базы после переноса укажите прежнее имя Docker-проекта в `.env.local`: `COMPOSE_PROJECT_NAME=...` (имена видны в `docker compose ls`).

`scripts/dev.sh up` после сборки и готовности PostgreSQL синхронизирует встроенный каталог из закреплённого `scripts/catalog-plugins/catalog-release.json`. Готовые архивы скачиваются с GitHub Releases с проверкой SHA-256; повтор использует сохранённые файлы. Конфликтующая карточка сохраняется, остальные обновляются; при ошибке поставки приложение запускается с сохранённым каталогом и предупреждением с причиной и командой повтора. Это не подтверждает готовность всех инструментов.

Для нативного запуска после `git pull`: `npm run tools:sync` при работающем PostgreSQL; проверить манифест без изменения данных: `npm run tools:sync -- --dry-run` (CLI предварительно собирается). Для production Docker-стека: `npm run tools:sync -- --production --directory /srv/neurocenter/config --project-name neurocenter-production`. Этот режим использует БД, секреты и тома выбранного стека и манифест из его собранного образа; новый исходный код сначала проходит штатную [процедуру обновления](docs/production-update.md). История, проектные связи и установленные версии сохраняются; зависимости не переключаются на новую версию автоматически. [Механизм публикации](scripts/catalog-plugins/README.md#синхронизация-встроенного-каталога).

При потере или повреждении `.run/processes.json` команды `up` и `down` находят сервисы по команде Node и рабочему каталогу проекта. После остановки `up` проверяет освобождение портов; оставшийся конфликт отменяет запуск с указанием сервиса и порта.

Обе встроенные модели входят в поставку проекта: `qwen3-embedding:4b` и `qwen3-vl:2b-instruct`. При обычном `scripts/dev.sh up` их полный комплект автоматически размещается в `data/embedding/models/` **до остановки прежних сервисов**, затем запускается общий проектный runtime. Это 9 настоящих файлов моделей общим размером **4 427 274 223 байта**. В Git находятся [опись и SHA-256](scripts/models/bundle-release.json), lock-файлы и лицензии; большие бинарники поставляются частями из закреплённого [GitHub Release `models-2026-10-19.1`](https://github.com/ghost-raven1/neurocenter/releases/tag/models-2026-10-19.1).

Подготовить или проверить только файлы моделей, без запуска приложений:

```sh
npm run models:prepare
npm run models:verify
```

Повтор с полным проверенным каталогом не обращается за весами в сеть. Для переноса без повторного скачивания сохраните весь `data/embedding/models/`, затем выполните `models:verify`; образ runtime нужен отдельно. В production ту же поставку подготавливает `model-volume-init` в томе `model-weights` до запуска runtime.

### Обновление через Git вместе с моделями и инструментами

На каждом новом клоне один раз выполните из корня проекта (Node.js 24+, зависимости npm для загрузчика не требуются):

```sh
npm run assets:init
```

Команда подключает локальные Git-хуки и готовит закреплённые архивы моста, инструменты каталога и все модели из реестра. После этого обычный `git pull` или `git pull --rebase` автоматически подготавливает недостающие файлы с проверкой SHA-256. Теги работающих моделей и БД при загрузке не меняются. Хуки не переносятся самим Git; новая машина также требует `assets:init`. Прежние Git-хуки продолжают работать; отключить интеграцию: `npm run assets:hooks -- --uninstall`.

Для обновления с обязательной проверкой результата, включая повтор после оборванной загрузки или `pull` без новых коммитов:

```sh
npm run update
```

Это `git pull --ff-only` и проверка всей поставки; локальные изменения отслеживаемых файлов останавливают команду. Git-хук выполняется после слияния и не отменяет уже обновлённый код при ошибке скачивания. `update` в таком случае возвращает ошибку; повторная подготовка без Git: `npm run assets:sync`, проверка без сети и записи: `npm run assets:verify`. Только подключить хуки без скачивания: `npm run assets:hooks`.

`scripts/dev.sh up` повторяет подготовку поставки до сборки и остановки прежних процессов. Production обновляется по [штатной процедуре](docs/production-update.md): host-предзагрузка моделей монтируется в init-контейнер только для чтения и копируется с SHA-проверкой в отдельный том, поэтому повторная загрузка весов из сети не требуется. Для копии в томе нужно дополнительное место. Зависимости npm, Docker-образы, миграции и перезапуск применяются штатным запуском/развёртыванием, а не Git-хуком.

Состав поставки вычисляется из трёх release-описей, реестра моделей и всех его lock-файлов. Квитанция `.run/assets-ready.json` появляется после полной проверки; прежняя квитанция при отказе не означает готовность новой ревизии. `.env`, `.env.local` и окружение учитываются в этом порядке. `MODEL_STORAGE_PATH` / `EMBEDDING_DATA_DIR` задают каталог моделей (для native runtime — внутри проекта); `RUNTIME_ARTIFACT_DIR` — архивы инструментов. Общая блокировка исключает одновременную подготовку несколькими hooks/командами.

### Новые модели в поставке

Главный администратор открывает карточку модели → **Подготовить поставку** → **Скачать параметры**. Сохраните JSON в корне исходников на машине с загруженными весами в проектном хранилище. Команда из окна передаёт публичные параметры файлом; GitHub-токены в браузер не передаются.

```sh
# Сначала только упаковать и проверить локальный комплект:
npm run models:publish -- --recipe model-example.supply.json --release models-YYYY-MM-DD.N
# После проверки — публикация; подготовленные части используются повторно:
npm run models:publish -- --recipe model-example.supply.json --release models-YYYY-MM-DD.N --publish
```

Публикация требует настроенного `gh` с правом записи в `ghost-raven1/neurocenter`. Она создаёт draft, загружает полный комплект и проверяет серверные размеры/SHA, публикует Release и только затем обновляет `scripts/models/model-registry.json`, lock модели и `bundle-release.json`. Сбой загрузки допускает повтор с тем же release; другие файлы существующего release не перезаписываются. При конкурентном изменении описей checkout сохраняется для сверки. Сохраните изменённые реестр/lock/опись одним коммитом и отправьте его в Git **после** успешной публикации. Команда сама не делает commit/push.

Реестр поддерживает дополнительные модели и имена `namespace/model:tag`; сервер создаёт карточки с теми же ID и сохраняет пользовательские подписи и назначения. Несовместимое повторное использование ID останавливает обновление. Для весов, находящихся только в production Docker-томе, сначала нужен их операторский экспорт в host-каталог: сама команда публикации не читает том через Docker. Явный SHA в рецепте должен совпасть с локальным манифестом; `null` закрепляет SHA проверенной локальной версии.

### Переключение и возврат моделей

Новая поставка заменяет только ранее зарегистрированные теги, чей SHA точно совпадает с квитанцией. Все blobs проверяются до переключения; прежние файлы и описи сохраняются. Журнал позволяет восстановить согласованный набор после прерывания; runtime запускается после успешного завершения подготовки. Возврат предыдущей управляемой поставки без сети:

```sh
npm run models:prepare -- --rollback
```

При первом `assets:init` существующий полностью совпадающий комплект регистрируется автоматически. Если сервер пропустил эту регистрацию и сразу получил изменённые модели, подтвердите прежнюю поставку из истории Git:

```sh
npm run models:prepare -- --adopt-from-git ORIG_HEAD
npm run assets:sync
```

Вместо `ORIG_HEAD` можно указать SHA доступного commit-предка `HEAD` с прежней описью. Команда читает только Git-объекты и проверяет все фактические SHA прежнего комплекта; теги, пользовательские модели и checkout не перезаписывает. После rebase `ORIG_HEAD` может не быть предком — выберите подходящий commit явно. Для применения возврата согласуйте версию кода/реестра и перезапуск runtime; следующий запуск с новой описью снова активирует новую поставку.

API локального runtime — `http://127.0.0.1:11435`; глобальный Ollama не требуется. Содержательная проверка эмбеддингов и обработка изображения:

```sh
npm run embedding:check
npm run vision:check
npm run vision:describe -- ./image.png 'Что изображено на картинке?'
```

Отдельные команды `embedding:up` и `vision:up` сохраняют прежний сценарий: поднимают общий контейнер и при необходимости получают выбранную модель из реестра Ollama. Поставка обеих моделей через GitHub Release выполняется командами `models:*` и штатным запуском приложения. `vision:down` и `embedding:down` останавливают общий контейнер, сохраняя веса. [Эмбеддинги и OpenCodeRAG](docs/local-embedding.md), [обработка изображений](docs/local-vision.md).

В `bridge-dist/` хранятся исходники установщиков. `scripts/dev.sh build` и `up` готовят переносимый мост и автономные пакеты для текущей платформы и Linux x64 (glibc). Подготовка выполняется до остановки работающих сервисов. Повторная подготовка проверяет версию, отпечаток сборки и SHA-256 архивов и использует готовые пакеты без скачивания зависимостей и запуска сборщиков. Готовые бинарные архивы в Git не включены.

Отдельная подготовка на Node.js 24: `npm run bridge:prepare`. Выбор целей: `BRIDGE_RUNTIME_TARGETS=linux-x64 npm run bridge:prepare`. Linux x64/ARM64 glibc можно собрать через Docker; остальные отсутствующие пакеты готовятся на целевой ОС командой `node scripts/prepare-bridge-runtimes.mjs --targets=<цель>`. [Подготовка и нативная приёмка](docs/p0-external-acceptance.md).

Если мост уже установлен, на странице «Начало работы» → «Компьютер» выберите «Мост уже установлен» и выполните команду подключения. Повторное скачивание не требуется; установка и обновление доступны отдельно. [Подключение, продление доступа и ограничения](docs/bridge-upgrade-recovery.md#подключение-уже-установленного-моста).

Зеркало OpenCode для всех систем готовится командой `node scripts/prepare-opencode.mjs`: 12 пакетов для восьми системных целей, включая обычные и baseline-варианты x64. Архивы и SHA-256 сохраняются в `bridge-dist/opencode/`; повтор использует проверенные готовые файлы. [Подробности установки](docs/catalog-mvp.md#автономная-установка).

## Структура

| Каталог | Назначение |
| --- | --- |
| `frontend/` | React, TypeScript, Vite, Ant Design, Redux Toolkit, Less |
| `services/` | NestJS, PostgreSQL/JSONB, pgvector, Socket.IO |
| `mcp/neurocenter-asset-sync/` | Локальный MCP и worker |
| `scripts/catalog-plugins/` | Общая упаковка и публикация инструментов |
| `scripts/embedding/` | Запуск, проверка и закреплённая версия локальной модели |
| `scripts/vision/` | Закреплённая vision-модель и обработка изображений |
| `scripts/models/` | Опись поставки весов, подготовка и SHA-проверка, лицензии и общие команды моделей |
| `scripts/production/` | Настройка, обслуживание, backup/restore и обновление |
| `docs/` | Архитектура, контракты, runbooks и история проверок |
