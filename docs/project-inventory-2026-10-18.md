# Инструменты в проекте и локальные варианты — кандидат MCP 0.8.0

Статус: локальная приёмка кандидата **0.8.0** завершена в описанных ниже границах. Финальный полный прогон — **1412 Vitest без пропусков**, typecheck и сборки прошли; отдельно подтверждены настоящий worker, браузер, автономный macOS ARM64-архив и изолированная production-конфигурация после исправления согласия. Выпуск и production остаются **NO-GO**: семь других native-вариантов, настоящий Blitz/целевой сервер, внешний DR, нагрузка/soak и CI/deployment не приняты. [Предыдущий этап 0.7](reliable-installation-2026-10-17.md) сохранён отдельно; его результаты не суммируются с новым прогоном.

## Пользовательские сценарии

В проектном каталоге блок «На этом компьютере» разделён на вкладки **«Под управлением»** и **«Найдено в проекте»**. История прежних папок сохраняется отдельно от действующей установки. Смена папки, экземпляра, роли или устройства не перенаправляет открытую модалку в новый контекст.

### Найти и принять существующий инструмент

1. Выберите собственный online-компьютер и подтвердите экземпляр папки проекта. На вкладке «Найдено в проекте» явно запустите поиск.
2. Просмотрите найденные скиллы, MCP и плагины. Проверяются только выбранная папка проекта и её конфигурации OpenCode; личный глобальный профиль и другие проекты не сканируются. Код найденных инструментов не выполняется.
3. Для подходящей неуправляемой записи разработчик выбирает **конкретный инструмент и конкретную версию из проектного каталога**. Совпадение имени не назначает цель автоматически. Требуется действующее одобрение точного пакета и полного набора зависимостей.
4. MCP готовит отдельный preview принятия. После его проверки пользователь подтверждает принятие под управление. Допускается запись только квитанций и реестра владельцев; файлы инструмента и подключения OpenCode сохраняются побайтно. Неканоническое расположение объясняется пользователю; автоматического перемещения или переустановки нет.
5. После принятия повторите сверку файлов. Диагностика запуска остаётся отдельным действием с новым согласием.

Наблюдатель вправе искать и просматривать доступный ему проект, но не принимать записи под управление. Повреждённые, небезопасные, недоступные и неизвестные записи показываются с причиной. Неполный поиск нельзя использовать для принятия: пропущенные записи могли скрыть конфликт владения.

### Вернуть сохранённый локальный вариант

1. У действующей установки выберите **«Ещё → Сохранённые локальные варианты»**. Список доступен наблюдателю; подготовка и применение восстановления требуют разработчика. Сервер проверяет права и точное одобрение установленной версии.
2. Выберите подходящий вариант с датой и числом файлов. Записи другой установки/версии/экземпляра, неподтверждённые старые копии, повреждённые и общие зависимости не становятся автоматической целью восстановления.
3. Разработчик готовит первое полное сравнение выбранного варианта. Браузер показывает добавления/замены/удаления, размеры и SHA до/после. Полный diff открывается только на компьютере.
4. По умолчанию выбраны все показанные файлы. При необходимости снимите галочки и нажмите **«Подготовить выбранные изменения»**: создаётся новый preview с точным `restorePaths`. Первоначальный список сохраняется, поэтому исключённый файл можно вернуть в выбор. Пустой набор не отправляется. Пока новый план не совпадёт с текущим выбором, применение и просмотр старого diff заблокированы.
5. Проверьте новый preview только выбранных изменений и дайте **новое согласие**. Перед применением нынешнее состояние сохраняется в новую закрытую резервную копию. Восстанавливаются только доказанные файлы и собственные подключения инструмента, без полной замены конфигурации и метаданных управления.
6. Повторите сверку файлов. Ручные байты могут отличаться от одобренного пакета; версия в каталоге не меняется, старые успешные статусы больше не подтверждают текущее содержимое. Автоматического запуска после восстановления нет.

Выбор варианта не делает его одобренной версией. Смена галочек или новая подготовка сбрасывает согласие. Смена варианта, tuple установленной версии, устройства, роли, binding/instance или известного текущего состояния сбрасывает весь выбор. Если ответ содержит иной набор путей, вместо тихого частичного восстановления требуется новое полное сравнение.

Восстановление разрешается только в том же подтверждённом физическом экземпляре по marker v2 и закрытому реестру. Текущие квитанции и ledger должны подтверждать установленную версию, root/SET SHA и **точные refs всего набора**; совпадения имени или пути недостаточно. Происхождение резервного варианта связывается с этим instance и теми же refs. Проверяется владение физическими путями и собственными элементами JSONC; пересечение с чужой квитанцией, смена экземпляра или изменение общей зависимости, используемой другим владельцем, блокирует запись. Подтверждённый rename/transfer того же экземпляра может сохранить происхождение копии; отдельная копия с новым instance его не наследует. Старые копии без доказуемого происхождения остаются недоступными для автоматического возврата.

## Контракты и приватность

Протокол очереди остаётся **2**, новые пакеты — формат **4**; прежние форматы 2/3 продолжают читаться. Возможности 0.8 разделены на `project-inventory-v1` для поиска, `adopt-installation-v1` для принятия и `local-recovery-v1` для локальных вариантов. Они не вводят дополнительный gate для обычного выбора общей папки или RAG. Для каждого действия нужны собственное подключение и текущий подтверждённый binding/instance.

| Действие | Закреплённый контекст |
| --- | --- |
| `scan-project-inventory` | Устройство, серверный проект, `expectedBindingId`; результат — scan UUID/digest, instance, дата и срок 15 минут |
| `prepare-adopt-installation` | Inventory job, scan/candidate UUID, digest; точные asset/version, одобренные plan ID/revision и SHA всего набора |
| `apply-adopt-installation` | Подготовленный change plan ID/revision/digest и исходный tuple; отдельное подтверждение пользователя |
| `list-local-variants` | Точный установленный asset/version/root SHA, binding/instance; результат содержит только подходящие метаданные записей |
| `prepare-local-restore` | Установленный tuple и recovery UUID; необязательный явный `restorePaths`; новый план на текущем снимке выбранных файлов |
| `apply-local-restore` | Подготовленный change plan ID/revision/digest и исходный tuple; отдельная цель восстановления, отличная от ремонта одобренных файлов |

Поиск возвращает не более 200 записей, список вариантов — не более 100. Неполнота обозначается явно. Публичный результат поиска содержит относительные пути, тип, состояние и фиксированные коды причин; список вариантов — UUID, дату, число файлов и допустимость. Содержимое файлов, полные backup bytes, секреты и абсолютные пути не передаются в этих результатах.

Подготовки принятия и восстановления используют неизменённую публичную схему плана изменений 0.7: только операции, относительные имена, размеры, SHA и сроки. Полные исходные/резервные байты и HTML diff остаются в закрытом состоянии MCP. Миграция каталога **2 — `project-inventory-local-variants`** добавляет в `bridge_local_change_plans` назначение `purpose` (`repair` / `adopt` / `restore-local`) и `source_id`. Прежние строки получают `repair`; kind задания и purpose плана проверяются совместно. Применение другого вида не может потребить эту подготовку, даже при известном plan ID/digest. История миграций сохраняет имя и SHA SQL, а применение остаётся транзакционным под advisory lock. Это не автоматический downgrade всего стека.

Интерфейс повторно проверяет роль, online, загруженную очередь, текущие device/binding/instance, установленный tuple и сроки. Новый поиск обязателен после изменения файлов или метаданных проекта. Успешное принятие или восстановление аннулирует прежнюю сверку и диагностику; оно само не является результатом запуска.

### Браузер: выбранный возврат и принятие

Ремонт сохранил ручной вариант с двумя правками. Пользователь снял галочку, подготовил новое подмножество и отдельно подтвердил применение. Финальная проверка байтов доказала возврат **только выбранного файла**, исключённый ресурс остался неизменным; [browser-restore-files-final.json](../.run/installation-inventory-20261018/browser-restore-files-final.json). Повторная сверка честно показала `modified`, версия сохранилась **1**, запуск не объявлен проверенным; [снимок](../.run/installation-inventory-20261018/restored-modified-desktop.png).

Принятие потребовало явных ID/версии и одобрения; preview содержал только receipt и ledger. После применения у **трёх исходных файлов** — payload скилла, его ресурса и `opencode.json` — совпали SHA, inode и mtime; [browser-adopt-files.json](../.run/installation-inventory-20261018/browser-adopt-files.json). Повторный scan показал **три управляемые записи**; [снимок](../.run/installation-inventory-20261018/inventory-managed-desktop.png).

Найден и исправлен сброс галочки согласия при повторном polling/WS-объекте того же succeeded prepare. Результат принимается однократно для job ID и ожидаемого контекста; новая подготовка продолжает сбрасывать согласие. Добавлены **4 регрессии**, входящие в 373 frontend-теста; браузер подтвердил удержание согласия после обновлений статуса. Для modal restore применён тот же guard.

На ширине **390** документ имеет ширину **390**, диалог — **366**; горизонтального переполнения нет. Desktop проверен на 1280 × 900. Снимки: [выбор файлов](../.run/installation-inventory-20261018/restore-subset-mobile.png), [принятие](../.run/installation-inventory-20261018/adopt-preview-mobile.png). ### Артефакт, повтор тестов и cleanup

macOS ARM64-архив 0.8 содержит Node **24.22.0**, OpenCode **1.14.48**, build ID `521d76925dea25807ca4e0d4dd26c1e93428bdcfc87886eefa2dafde90627e18`, SHA256 `5cbf6f29868b88e715dfb0ad442bab116f99d9e6bd41b6261efad01925a8c1e0`; [metadata](../bridge-dist/runtime/neurocenter-asset-sync-darwin-arm64-0.8.0.tgz.json). Нативная приёмка относится к macOS ARM64; другие семь вариантов не приняты. Windows runtime probe остаётся `unsupported`; временный профиль не является песочницей ОС для одобренного кода.

Один промежуточный полный прогон был **неуспешным**: совмещённый тест binary/absence превысил пятисекундный deadline при параллельной Docker-нагрузке, cleanup затем получил `ENOTEMPTY`. Два независимых сценария разделены на отдельные `it` с собственными фикстурами; финальный MCP-прогон подтвердил **385/385** без пропусков. [Неуспешный лог сохранён](../.run/installation-inventory-20261018/check-before-fixture-split.log); это не нагрузочная приёмка и не основание скрывать первую ошибку. Финальный результат находится в `check-final.log` выше.

UI-фикстура использовала собственные проект, устройство и папки. `unmanage-skill` удаляла только локальную квитанцию и самостоятельный root собственного чистого скилла при пустой очереди, сохраняя MCP/остальные файлы. После проверки свои worker, устройство, проект и временные папки удалены; baseline совпал **точно**: [ui-cleanup.json](../.run/installation-inventory-20261018/ui-cleanup.json). Проверка dev-состояния подтвердила неизменность рабочих данных/RAG, идентичности и отчёта устройства, личного MCP/OpenCode; заданий **0**, шесть health — **200**: [dev-integrity.json](../.run/installation-inventory-20261018/dev-integrity.json).

Финальный production-стек `nc-production-verify-2bbbeaba` удалён вместе со своими контейнерами, volumes и сетью. Сохранены **24** проверочных image tags; прежние **18** имеют те же image ID, global prune не применялся. После cleanup свободно около **24,85 ГиБ**; [cleanup.json](../.run/installation-inventory-20261018/production-final/cleanup.json). Успешный тестовый стек с фиктивным Blitz не является развёртыванием на целевом сервере.
