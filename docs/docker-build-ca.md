# Docker за корпоративным HTTPS-прокси

`dev.sh install`, `build` и восстановление зависимостей при явной сборке выполняют `npm ci` с отдельными пустыми user/global конфигурациями, временным HOME и явным публичным registry. Глобальные `.npmrc`, scoped registry, `NPM_CONFIG_*`, `npm_config_*` и токены компьютера в установку не наследуются. Исходные файлы настроек сохраняются. Docker дополнительно исключает `.npmrc` на всех уровнях build context. Настроенные переменные HTTPS-прокси и доверенного публичного CA сохраняются.

После `install` образ проверщика снимков уже готов. `up`/`watch` выполняют только `docker image inspect` до подготовки ассетов, компиляции и PostgreSQL; отсутствующий образ даёт команду `scripts/dev.sh install` или `scripts/dev.sh build`. Ключи подписи при установке образа не создаются, PostgreSQL для неё не нужен. При старте ключи проверяются отдельно, с уже выбранным неизменяемым image ID. `up` также не выполняет общий `npm ci` и не устанавливает зависимости после ошибки локальной компиляции. Выбор профиля по-прежнему управляет ассетами и моделями; их загрузка отдельна от установки npm-зависимостей.

Сборка исполнителя снимков сохраняет HTTPS и по умолчанию проверяет сертификаты. Её переключатель описан ниже. Остальные команды установки сохраняют ранее согласованную политику `strict-ssl=false` / `NODE_TLS_REJECT_UNAUTHORIZED=0`. Предупреждение `(node:7)` обозначает PID процесса внутри контейнера, а не версию Node. Оно печатается при подготовке первого TLS-подключения и само по себе не означает остановку; последующей видимой строкой может стать лишь ответ сети или ошибка по таймауту. По запросу пользователя для `npm ci` исполнителя снимков добавлен command-scoped `NODE_NO_WARNINGS=1`: он скрывает предупреждения Node и унаследовавших эту настройку lifecycle-процессов, сохраняя stderr/код ошибки npm и диагностический HTTP-вывод. Это не runtime ENV образа и не устранение сетевой задержки. [Поведение параметра в Node](https://r2.nodejs.org/docs/latest-v24.x/api/cli.html#node_no_warnings1). Внешний Docker build имеет собственный бюджет, описанный ниже.

Ошибка npm `UNABLE_TO_GET_ISSUER_CERT_LOCALLY` означает отказ проверки цепочки сертификатов. В сборке исполнителя снимков проверка теперь включена по умолчанию (`SNAPSHOT_VERIFIER_TLS_VERIFY=1`). Для корпоративной сети нужен **публичный корневой/промежуточный CA в PEM**; приватный ключ и сертификат сервера npm вместо CA не подходят. По отдельному запросу можно явно выбрать `SNAPSHOT_VERIFIER_TLS_VERIFY=0` только на время этой сборки. HTTPS и проверка integrity npm сохраняются в обоих режимах; настройка не передаётся сервисам и игнорируется с готовым `SNAPSHOT_VERIFIER_IMAGE`.

Для локального запуска добавьте в `.env` путь к обычному файлу:

```dotenv
NEUROCENTER_BUILD_CA_FILE=/absolute/path/corporate-ca.pem
SNAPSHOT_VERIFIER_TLS_VERIFY=1
```

`scripts/dev.sh install` и `scripts/dev.sh build` передают этот CA сборке исполнителя снимков. `up` только проверяет уже готовый образ. Для остальных образов и production используйте:

```sh
export NEUROCENTER_BUILD_CA_FILE=/absolute/path/corporate-ca.pem
node scripts/docker-build.mjs compose build
node scripts/production/setup.mjs build --directory /srv/neurocenter/config
```

Путь может содержать пробелы; в shell заключите значение в кавычки. Если отдельная переменная не задана, используется явно установленный `NODE_EXTRA_CA_CERTS`. Поддерживаются PEM-пакеты до 1 МиБ/256 CA. Ссылки, файлы с приватными ключами, посторонним текстом и сертификатами без признака CA отклоняются до Docker.

Если корпоративный CA уже включён в обычный системный PEM-пакет Linux, можно указать существующий `/etc/ssl/certs/ca-certificates.crt`: все сертификаты в нём должны быть CA. Менять глобальные настройки Node/npm на компьютере не требуется.

Каждая сборка получает собственный публичный `ca-<UUID>.pem` в `docker/build-ca/` и `frontend/docker/build-ca/`. В образ копируется только выбранный файл под именем `extra.pem`; SHA-256 проверяется до включения доверия. Старый `extra.pem` исключён из Docker-контекста. Его наличие, тип и содержимое не блокируют повтор. После завершения удаляются только собственные неизменённые файлы текущего вызова. Параллельные и вложенные сборки, включая разные CA, используют независимые имена.

Без выбранного дополнительного CA Docker копирует пустой `.gitkeep`, а `extra.pem` внутри образа остаётся пустым. Ручная очистка старого `extra.pem` или `.run/docker-build-ca.lock` не требуется. Остатки уникальных публичных файлов после аварийного завершения не выбираются следующей сборкой.

Выбранный исходный CA по-прежнему проходит проверку обычного файла, содержимого и признака CA. `.npmrc`, `.env`, токены и приватные ключи не копируются. npm использует `https://registry.npmjs.org/`. Для verifier значения `strict-ssl` и `NODE_TLS_REJECT_UNAUTHORIZED` согласованно выбираются через `SNAPSHOT_VERIFIER_TLS_VERIFY`; по умолчанию проверка включена. Остальные Docker-этапы npm сохраняют `strict-ssl=false` и `NODE_TLS_REJECT_UNAUTHORIZED=0` для установки, сборки и prune. У обычных сервисов эта переменная не становится постоянной runtime-настройкой; прежняя отдельная настройка Gateway сохраняется.

Образ каталога также загружает PostgreSQL client через HTTPS curl/apt. Эти команды отключают проверку сертификата только на время загрузки: curl использует `--insecure`, каждый `apt-get` — `Acquire::https::Verify-Peer=false` и `Verify-Host=false`. Проверка подписей apt и `signed-by` сохраняются. Проверенный PEM-пакет по-прежнему разделяется на отдельные CA-сертификаты и добавляется к системным корням до загрузок; глобальный `apt.conf` не меняется.

Сборка работает с обычным Docker builder и BuildKit. При прямом `docker build` или `docker compose build` без обёртки используется пустой CA по умолчанию. Для передачи корпоративного CA используйте команды обёртки выше: они передают согласованные имя файла и SHA. Общая блокировка сборок и перезапись старого `extra.pem` больше не используются.

При `dev.sh install` / `dev.sh build` подготовка образа исполнителя снимков сразу печатает этап и лимит, затем каждые 15 секунд — прошедшее время, даже если Docker ничего не выводит. stdout/stderr Docker передаются сразу: объём скачанных слоёв виден, когда его сообщает сам Docker. Для BuildKit по умолчанию выбирается `BUILDKIT_PROGRESS=plain`; явно заданное значение сохраняется, legacy builder не получает неподдерживаемого CLI-флага.

`npm ci` в этом образе всегда показывает HTTP-события и вывод lifecycle-скриптов. Эти события сообщают о завершённых запросах, повторах и отказах; они не дают достоверного общего процента или числа уже скачанных байт npm. Периодическая строка отражает только ожидание Docker. Уведомление о новой версии npm отключено через `--update-notifier=false`, остальные ошибки и код выхода сохраняются. Остановка по лимиту или Ctrl+C дожидается завершения собственного Docker CLI; это не подтверждение остановки задания Docker daemon.

Если сборка исполнителя снимков останавливается примерно через 10 минут, проверьте итоговую причину: `ETIMEDOUT` означает лимит ожидания Docker в dev CLI. По умолчанию он равен 600 секундам. Для медленной первой загрузки можно явно выбрать от 1 до 3600 секунд в `.env` или на один запуск:

```sh
SNAPSHOT_VERIFIER_BUILD_TIMEOUT_SECONDS=1800 ./scripts/dev.sh build
```

Параметр относится только к подготовке образа, в окружение сервисов не передаётся. При выбранном `SNAPSHOT_VERIFIER_IMAGE` сборка пропускается. Ошибка указывает таймаут, код выхода, сигнал или код отказа запуска Docker; прежние сервисы до успешной подготовки не останавливаются. Предупреждение `NODE_TLS_REJECT_UNAUTHORIZED=0` само по себе не означает отказ npm.

Для остановки после этого предупреждения включите диагностический режим на один запуск:

```sh
SNAPSHOT_VERIFIER_NPM_DIAGNOSTICS=1 ./scripts/dev.sh build
./scripts/dev.sh up --profile=fast
```

Допустимы только `0` и `1`, по умолчанию `0`. Диагностика включает verbose-вывод и отключает запись debug-логов npm; HTTP/lifecycle-вывод доступен и без неё. Сетевая политика одинакова в обоих режимах: `maxsockets=1` (одно соединение на origin; все текущие архивы verifier используют registry.npmjs.org), `fetch-timeout=120000`, `fetch-retries=1`, задержка повтора от 2000 до 5000 мс. Один повтор означает не более двух попыток запроса; обычно для единственного повтора применяется минимальная задержка 2 с. Прежний диагностический лимит 30 с без повторов убран после подтверждённого FETCH_ERROR/network timeout на Linux.

Это не общий лимит установки или lifecycle-скрипта: всю сборку по-прежнему ограничивает отдельный Docker-таймаут, по умолчанию600 с. При нескольких последовательных сетевых отказах общий лимит может наступить раньше завершения всех повторов. Последняя строка с предупреждением ещё не определяет источник задержки; HTTP-вывод может появиться лишь после ответа или отказа запроса. После попытки смотрите строки `npm http` и `npm error`. Настройка используется только при сборке образа и не передаётся сервисам; с `SNAPSHOT_VERIFIER_IMAGE` она не применяется.

`npm http cache ... (cache hit)` не подтверждает, что архив уже прочитан: npm/pacote печатает сообщение при открытии потока кэша, затем может обнаружить отсутствие данных и начать сетевой fetch ([исходник](https://github.com/npm/pacote/blob/main/lib/fetcher.js)). Это воспроизведено на пустом временном кэше. Ориентируйтесь на последующие `fetch GET 200`, ошибки и итог установки. Сам по себе `PONG` тоже не проверяет загрузку всех архивов.

Сборка исполнителя явно передаёт заданные `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY` и их варианты в нижнем регистре через `--build-arg NAME`. Значения берутся из окружения Docker CLI и не добавляются в аргументы команды. Явно пустое значение также передаётся; для отсутствующих переменных остаются настройки Docker client. Это не настраивает сеть самого Docker daemon и не подтверждает доступность registry из контейнера.

Этот механизм передаёт публичные CA **внутрь Node-образов**. Ошибка скачивания базового образа самим Docker требует настройки доверенного CA у Docker daemon администратором сервера. Недоступность GitHub и истечение сетевого таймаута — отдельные причины, добавление CA их не устраняет.

При полностью закрытом GitHub сборка самого Catalog также не сможет получить закреплённую npm-зависимость `@neurocenter/asset-contract` с `codeload.github.com`. Исполнитель снимков использует отдельный `scripts/snapshots/verifier/package-lock.json`: LanceDB 0.29.0, Apache Arrow 18.1.0 и их зависимости с прежними версиями и integrity Catalog. Ему не нужны Nest, esbuild или asset-contract; все его архивы берутся из npm registry. В закрытом окружении заранее собирайте образы для архитектуры рабочего сервера на машине с доступом к источникам и переносите их через `docker image save` / `docker image load`. Для native dev заранее загруженный исполнитель снимков можно выбрать через `SNAPSHOT_VERIFIER_IMAGE`; тогда `dev.sh up` проверяет существующий образ и не пересобирает его. Каталог ассетов после подготовки работает независимо от GitHub в [автономном режиме](assets.md#работа-без-доступа-к-github).

Если npm пишет `attempt ... failed with EAI_AGAIN`, это временный отказ разрешения имени ([getaddrinfo](https://man7.org/linux/man-pages/man3/getaddrinfo.3.html)). На шаге npm ci кэшированные пакеты могут проходить сразу, тогда как отсутствующие архивы требуют сетевых запросов и повторяются до ошибки либо общего лимита. Отключение проверки сертификатов не исправляет этот этап. По URL npm нельзя установить, отказало имя registry или настроенного прокси.

Для Linux сравните `getent ahosts registry.npmjs.org` на хосте с тем же запросом в уже скачанном базовом образе; из корня Neurocenter:

```sh
docker run --rm --pull=never \
  "$(sed -n '1s/^FROM //p' services/catalog-service/snapshot-verifier.Dockerfile)" \
  getent ahosts registry.npmjs.org
```

Команда не загружает образ и не меняет настройки daemon. Если образ не найден, это отсутствие локального образа, а не результат DNS-проверки. Успех на хосте не доказывает успех в контейнере; runtime-контейнер также не доказывает настройки отдельного BuildKit builder. [Docker описывает отдельные DNS-настройки контейнеров](https://docs.docker.com/engine/network/#dns-services). При корпоративном прокси отдельно проверьте его hostname без вывода пароля/токенов. Публичные DNS-серверы, изменение daemon.json и network=host не применяются автоматически. После выбора DNS/маршрута нужен повтор именно упавшей сборки с загрузкой не кэшированного пакета.

Если обычный контейнер не разрешает имя, а повтор с `docker run --network=host` возвращает адреса, можно явно выбрать сеть хоста для RUN-этапов сборки verifier:

```sh
SNAPSHOT_VERIFIER_BUILD_NETWORK=host SNAPSHOT_VERIFIER_NPM_DIAGNOSTICS=1 ./scripts/dev.sh build
./scripts/dev.sh up --profile=fast
```

Перед сборкой CLI показывает фактически выбранные `network`, `npm-diagnostics`, `timeout` и имена явно заданных proxy-переменных. Значения proxy и пароли не печатаются; для отсутствующих переменных могут действовать настройки Docker client. Внутри Docker отдельный шаг печатает фактическое значение `npm-diagnostics`: строка инструкции `ARG ...=0` сама по себе показывает значение по умолчанию и не доказывает, что диагностика выключена.

После успешного DNS можно отдельно проверить HTTPS/npm в уже скачанном образе:

```sh
docker run --rm --pull=never --network=host "$(sed -n '1s/^FROM //p' services/catalog-service/snapshot-verifier.Dockerfile)" npm ping --registry=https://registry.npmjs.org/ --strict-ssl=false --fetch-timeout=15000 --fetch-retries=0 --update-notifier=false --loglevel=http
```

`PONG` подтверждает ответ registry на этот запрос. Загрузка архивов, доступ к другим источникам и полный `npm ci` проверяются отдельно. Успешное скачивание ссылки в браузере тоже не подтверждает сеть npm: браузер может применять собственный proxy/PAC или DNS.

`SNAPSHOT_VERIFIER_BUILD_NETWORK` принимает только `default` или `host`; без настройки дополнительный Docker-флаг не передаётся. `host` добавляет `--network=host` только к сборке исполнителя снимков. Этапы RUN используют сеть Docker-хоста; для удалённого daemon это другой компьютер, для Docker Desktop — его среда виртуализации. Настройка не передаётся сервисам/runner, не действует с готовым `SNAPSHOT_VERIFIER_IMAGE` и не меняет daemon.json, прокси, TLS или настройки остальных сборок. Неизвестное значение отклоняется до БД и подготовки ключей.

[Docker build network](https://docs.docker.com/reference/cli/docker/buildx/build/#network) применяется к RUN. Если BuildKit запрещает `network.host`, нужен builder, где этот режим разрешён; CLI не включает дополнительные entitlements, не меняет builder и не повторяет сборку в другой сети автоматически. Отказ остаётся видимым. Успех DNS с host network — основание для этого явного повтора, но не доказательство успешного npm ci; B26 закрывается после проверки полной сборки на целевом Linux.

Если итоговая ошибка содержит `EAI_AGAIN` и `hostname registry.npmjs.org`, при успешном DNS хоста можно явно передать один свежий IPv4 в build-контейнер. Это обходит повторные DNS-запросы только к registry, сохраняя имя HTTPS/SNI:

```sh
registry_ipv4="$(getent ahostsv4 registry.npmjs.org | awk 'NR==1 {print $1}')"
SNAPSHOT_VERIFIER_REGISTRY_IPV4="$registry_ipv4" SNAPSHOT_VERIFIER_TLS_VERIFY=1 SNAPSHOT_VERIFIER_BUILD_NETWORK=host SNAPSHOT_VERIFIER_NPM_DIAGNOSTICS=1 ./scripts/dev.sh build
./scripts/dev.sh up --profile=fast
```

CLI проверяет `SNAPSHOT_VERIFIER_REGISTRY_IPV4` до БД, ключей и Docker: нужен ровно один IPv4. Пустой ответ `getent` также отклоняется — сначала восстановите DNS самого хоста. Адрес не зашит в исходники; получайте его заново перед повтором, не переносите адрес из чужого скриншота. [Docker --add-host](https://docs.docker.com/reference/cli/docker/buildx/build/#add-host) задаёт запись hosts только для этой сборки; daemon.json, DNS хоста, настройки прокси и остальные образы не меняются. Переменная исключена из runtime; с готовым образом она игнорируется. Это не исправляет DNS самого прокси или другие имена при redirect. Наличие адреса ещё не гарантирует TCP/HTTPS-доступ к нему; после этого нужна полная сборка на целевом Linux. Удалять все образы и node_modules ради EAI_AGAIN не требуется.

Проверки: `node --test --test-concurrency=1 scripts/test/docker-build-ca.test.mjs scripts/test/docker-build-ca-lifecycle.test.mjs`. Новый набор: 32 PASS и один явный Docker-skip. Отдельно `DOCKER_BUILD_CA_TEST=1` дал 16/16 в основном файле: настоящие legacy/BuildKit сборки на уже доступном закреплённом Node-образе, без npm-загрузок. Проверены выбранный CA, неверный SHA, отсутствие CA и исключение старого пустого/приватного `extra.pem` из контекста. Эти16 пересекаются с основным набором и к32 не прибавляются. Полная сборка приложения и корпоративный Linux этим не приняты. Квитанции: `.run/docker-ca-isolation-20261022/{final,real-docker}/receipt.json`, `compose-receipt.json`.

Основание: [CA в Docker](https://docs.docker.com/engine/network/ca-certs/), [NODE_EXTRA_CA_CERTS в Node.js](https://nodejs.org/docs/latest-v24.x/api/cli.html#node_extra_ca_certsfile).
