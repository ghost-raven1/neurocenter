# Единый источник ассетов

Текущие metadata, агенты, скиллы, рецепты, исходники адаптеров и точные locks хранятся в основном Git, в `catalog-source/`. Файл `services/shared/bundled-catalog.lock.json` закрепляет SHA-256 описи и vendored source closures. Внешний репозиторий ассетов и GitHub Releases для запуска не требуются. Runtime-архивы и веса моделей в Git не включены.

Опись приложения имеет явную content identity `app-bundled / sha256:<index SHA>`. Это не Git commit. Прежние Git commit/SHA и неизменённые JSON описей сохранены отдельно для чтения старых квитанций и архивов; прежние бинарные поколения не включены в рабочую поставку.

## Формат и версии

Descriptor `schemaVersion: 1` содержит стабильный `id`, `kind`, версию, происхождение, лицензию, совместимость, карточку и доставку. Зависимость закрепляет ID, версию и SHA descriptor. SHA считается по фактическим байтам файла, включая завершающий перевод строки. Изменённые байты требуют новой версии.

Индекс сохраняет опубликованные версии; одна версия каждого ID отмечена `current`. Выбор ID импортирует текущую версию, а зависимости разрешаются по точным версиям. Исторические версии нельзя удалить или незаметно заменить при обновлении индекса.

Локальная ZIP-загрузка использует `source.type: archive` с SHA-256 и числом байтов исходного архива. Runtime artifact может не иметь URL: тогда его байты обязаны уже находиться в проверенном серверном SHA-кэше. Отсутствующий локальный blob даёт ошибку до сетевых загрузок; адрес GitHub не выдумывается. Публикация реального транспорта создаёт новую source-версию и сохраняет нативные package pins.

Общий пакет `@neurocenter/asset-contract` проверяет source envelope у producer и importer. Нативные toolpkg, skillpkg, model bundle и bridge release остаются форматами установки своих runtime; отдельного альтернативного source-формата у них нет. Агент имеет собственный `kind: agent` с промптом и настройками OpenCode, доставляемыми inline; [общий шаблон и настройки проекта](agents-opencode-2026-10-21.md) версионируются отдельно. Проверка envelope не заменяет проверку нативного пакета перед записью.

## Импорт и установка

1. Главный администратор открывает **Ассеты** и обновляет описания. Это действие не скачивает бинарные файлы и не меняет карточки.
2. Готовые агенты и скиллы добавляются с точными зависимостями. Для MCP/плагина в разделе **Исходники текущей версии** выберите **Подготовить пакет** или **Подготовить обновление**. Рецепт и его application revision закрепляются до постановки в существующую очередь упаковщика. Обновление прежней карточки требует подтверждения свежей редакции и source ownership; native ID сохраняется.
3. Платформенная сборка получает обычные зависимости из npm по точному lock, проверяет архив и реальный запуск в изолированной ОС. Только успешная публикация создаёт новую редакцию каталога. Метка «пакет этой версии опубликован» требует успешного задания с точной revision и совпадающего текущего head. Наличие исходников или произвольный импорт архива этого не доказывает.
4. Повтор запроса с тем же ключом продолжает ту же операцию. Прогресс хранится на сервере; закрытие страницы не означает отмену.
5. Конфликт с локальной правкой карточки требует явного решения. SHA состояния проверяется повторно перед применением решения.
6. Проект получает точную версию карточки и пакета. Добавление существующего назначения не переключает версию; обновление назначения выполняется отдельно с проверкой ожидаемого pin.
7. Установка на компьютер использует мост и API Gateway. Клиент получает проверенные файлы с адреса Нейроцентра. Версия проекта и квитанция выбранной папки сравниваются отдельно; обновление каталога само не подтверждает локальную установку.

Импорт нескольких сервисов может закончиться частично. В таком случае операция показывает фактические результаты по ассетам и допускает повтор; общего обещания транзакции между PostgreSQL и файловым хранилищем скиллов нет.

## Упаковка скилла и локальные ассеты

В каталоге откройте **Упаковать инструмент → Исходники** и выберите папку, файлы либо ZIP/TAR/TGZ. Единственный `SKILL.md` определяется на любой глубине вложенных папок. Если инструкций несколько, выберите нужный путь. Ресурсы `scripts/`, `references/` и `assets/` сохраняют пути относительно выбранного `SKILL.md`; соседние скиллы не становятся его ресурсами. GitHub поддерживает закреплённый commit и выбор подпапки.

Инструкция содержит YAML frontmatter с техническим `name` или `slug` и описанием. Название карточки и описание можно уточнить в форме. Исполняемый файл и выбор платформы для скилла не нужны. `SKILL.md` должен быть UTF-8; бинарные ресурсы передаются существующим `encoding: base64`. Лимиты исходников: 100 файлов, 1 МиБ на файл, 5 МиБ суммарно; ресурсы выбранного скилла — до 4 МиБ. Небезопасные пути, ссылки за пределы скилла и отсутствующие файлы локальных Markdown-ссылок отклоняются.

Результат — обычный `kind: skill` с inline-доставкой в общем контракте. Для локальных файлов provenance сохраняет SHA детерминированного JSON-снимка исходников, включая бинарные ресурсы. `asset.json` и поставку можно скачать, проверить штатным CLI и импортировать повторно. Потерянное подтверждение публикации восстанавливается по сохранённому намерению; чужой ручной скилл с тем же slug не перезаписывается.

Раздел **Ассеты** показывает **Упакованные на этой площадке** отдельно от описей внешнего репозитория. Они уже находятся в общем каталоге, поэтому повторный импорт из GitHub не требуется. Поиск, переход в каталог, редактирование, архивирование и восстановление используют текущую нативную карточку. **Обновить список** перечитывает сервер; **Перечитать поставку** проверяет исходники текущей версии приложения. Недоступность GitHub не скрывает сохранённые локальные упаковки.

Сквозная проверка использует отдельный PostgreSQL на случайном порту и временные корни хранилища. После сборки Catalog и skills-service запустите `node --test scripts/test/skill-packaging-http.test.mjs` с `SKILL_PACKAGING_TEST_ADMIN_URL`, указывающим на disposable PostgreSQL, а не рабочий порт 5432. Проверка проходит через настоящий Gateway, сервисы, экспорт поставки, назначения проекта и установщик моста.

## Предзагрузка и запуск

Корневые зависимости устанавливаются через `npm ci --ignore-scripts` на Node.js 24+. Команды не меняют БД, карточки, назначения или теги работающих моделей:

```sh
npm run assets:sync -- --metadata-only
npm run assets:sync -- --asset skill-code-review-excellence
npm run assets:sync -- --without-models
npm run assets:verify -- --without-models
```

`assets:verify` работает без сети и записи: текущие описи читаются из Git, архивы — из проверенного кэша. Отчёт различает готовые inline-инструкции и `prepare-required` / `explicit-model-archive` / `application-bridge-archive`. Обычная синхронизация не скачивает веса. Неполный требуемый кэш возвращает ошибку. `--without-models` не скрывает зависимость выбранного инструмента от модели: такой набор нужно выбрать явно.

## Работа без доступа к GitHub

Поставку можно переносить вместе с проектом или хранить отдельной папкой на рабочем сервере. Формат тот же: закреплённые описи и SHA-файлы, без перепаковки. Большие файлы не нужно коммитить в Git.

### Загрузка архива через интерфейс

Главный администратор открывает **Ассеты → Импортировать архив**, выбирает ZIP, TAR или TAR.GZ и загружает его. Принимаются архив репозитория `neurocenter-assets` (включая обёртку GitHub Download ZIP) и архив подготовленной автономной папки. Размер архива и распакованного содержимого ограничен 8 ГиБ, число записей — 10 000. Ссылки, небезопасные пути, повреждённые файлы и несовпадения SHA отклоняются до принятия описи.

Архив можно перетащить в зону загрузки или выбрать кнопкой. Такие же зоны есть в упаковщике исходников, архиве MCP и ресурсах скилла. Однофайловые загрузчики отклоняют несколько файлов целиком; ресурсы скилла принимают набор файлов. Папку выбирайте отдельной кнопкой, чтобы сохранить структуру путей.

Обычный архив GitHub содержит описания и рецепты, но не файлы из Releases. Скиллы и агенты с inline-доставкой можно добавить сразу; карточки с отсутствующими файлами или зависимостями показывают, сколько файлов нужно доставить, и недоступны для выбора. Загрузка архива сама не добавляет карточки в общий каталог: после проверки выберите доступные ассеты и нажмите обычную кнопку добавления.

Для полной поставки подготовьте папку командами ниже и упакуйте её **вместе со скрытыми подпапками**:

```sh
tar -czf neurocenter-assets-offline.tar.gz -C ./offline-assets .
```

Импорт из архива использует только локальные файлы, даже на сервере с доступом к GitHub. Этот режим сохраняется при перезагрузке страницы и повторе задания. Для текущей поставки **Перечитать поставку** возвращает опись приложения; уже созданные задания сохраняют свой exact source и режим доставки. Пользовательские публичные GitHub feeds остаются отдельным явно настроенным источником. Наличие файлов проверяется быстро по безопасному пути и размеру, а перед фактическим импортом повторно проверяется полный SHA.

Индекс архива должен соответствовать закреплённому в приложении источнику либо точной описи, ранее проверенной этим сервером. Имя ZIP и имя верхней папки не подтверждают Git commit. Для неизвестной новой версии обновите приложение до соответствующего выпуска или заранее проверьте источник на сервере с доступом к GitHub. Архив с неизвестным индексом не заменяет действующую опись.

### Подготовка и перенос папки

На машине с доступом к источнику подготовьте папку для **той же версии проекта**:

```sh
npm run assets:sync -- --offline-ready --without-models --artifacts-directory ./offline-assets
npm run assets:verify -- --offline-ready --without-models --artifacts-directory ./offline-assets
```

Для выборочной поставки замените `--without-models` повторяемыми `--asset <id>`. `--offline-ready` сохраняет все небольшие закреплённые описания, включая исторические версии и рецепты. Бинарные файлы скачиваются только для выбранных ассетов и их точных зависимостей. Уберите `--without-models`, если нужны все текущие ассеты вместе с весами моделей. `--metadata-only` не подтверждает готовность бинарных файлов.

Перенесите `offline-assets/` на рабочий сервер. Сохраните скрытые подпапки `.asset-source-metadata` и `.asset-source-blobs`, обычные файлы без ссылок; процесс Catalog должен иметь доступ на чтение и запись. Локальные сборки и импорт используют эту папку как рабочее хранилище, поэтому монтировать её только для чтения нельзя.

Для нового dev-окружения Docker добавьте override:

```sh
OFFLINE_ASSETS_DIR=/absolute/path/offline-assets docker compose -f docker-compose.yml -f compose.offline-assets.yml up -d
```

Override заменяет dev-volume хранилища указанной папкой. Для уже работающего окружения сначала сохраните и перенесите в неё существующие SHA-файлы: карточки в БД могут ссылаться на прежнее хранилище. Production сохраняет штатный named volume с мониторингом ёмкости; этот bind-override для него не предназначен. Автономный режим production требует предварительно заполненного штатного volume.

Для native dev задайте в `.env.local`:

```dotenv
ASSET_SOURCE_MODE=offline
RUNTIME_ARTIFACT_DIR=/absolute/path/offline-assets
```

В **Ассетах** нажмите **Перечитать поставку**, выберите нужные карточки и добавьте их в каталог. Предзагрузка сама не создаёт карточки и не активирует модели. Неполная поставка возвращает ошибку до сетевой загрузки; повреждённые SHA-файлы не используются. Повторное чтение не допускает подмены уже опубликованной истории источника. При обновлении переносите проверенную поставку и соответствующий checkout с новым `bundled-catalog.lock.json` и папкой `catalog-source/`, затем пересоберите и перезапустите Catalog: lock читается при запуске сервиса. В контейнерах используйте образ соответствующего релиза.

На шаге **Компьютер** открытие и обновление статуса читают сохранённое состояние сервера. Для прежнего default asset-источника проверка сети выключена: API возвращает `sourceReady:false / archiveRequired:true` до явной поставки текущего архива моста. Пользовательские GitHub feeds проверяются по отдельному действию. В режиме `offline` она скрыта; `/api/bridge-source/check` проверяет локальное состояние без обращения к GitHub и не объявляет сохранённую upstream-версию новой. Подготовленный мост и его архивы выдаются через API Gateway после обычного импорта ассета моста.

Режим относится к источнику ассетов и моста. Для установки npm-зависимостей и сборки проект явно задаёт `strict-ssl=false`, включая дочерние сборщики и Docker-этапы; загрузчики установщиков используют ту же политику. HTTP 502 от registry или прокси остаётся отдельным сетевым отказом: отключение проверки сертификата не меняет HTTP-ответ сервера. Получение базовых Docker-образов самим daemon и внешние API инструментов имеют собственные сетевые настройки. [Параметры сборки и CA](docker-build-ca.md).

`dev.sh install/build/up/watch` по умолчанию использует `fast`: без выбора/предзагрузки ассетов, упаковки Native и обязательного проверщика снимков. Поведение одинаково с TTY и без него. Компоненты добавляются архивом через «Ассеты». Явный `up --profile standard` предзагружает текущие ассеты без моделей, `full` — текущие metadata и заранее подготовленный общий runtime; предварительно выполните `install --profile standard`. Ни один профиль не импортирует карточки и не активирует веса автоматически. Установка npm-зависимостей и Docker-образов может требовать сеть при любом профиле.

Git-хуки `assets:init` и `npm run update` проверяют только описания. Production setup/update также не наполняет каталог и не переключает модели. Пустой каталог и пустой model runtime являются допустимыми начальными состояниями.

## Хранилище и восстановление

В `RUNTIME_ARTIFACT_DIR` находятся `.asset-source-blobs/<sha>.blob` и `.asset-source-metadata/<sha>.json`. Каждый файл проверяется по SHA и размеру; повреждённый существующий файл не принимается как готовый и не заменяется посторонними байтами. Предзагрузка использует тот же layout, что и серверный импорт.

Квитанция `.run/assets-ready.json` содержит конкретные версии, commit источника, SHA индекса и режим проверки. Квитанция metadata-only или частичного набора не подтверждает готовность всех бинарников. Она также не подтверждает успешную установку на компьютер или inference модели.

Для восстановления сохраняйте дамп каталога, хранилище скиллов, приватную конфигурацию моделей и проверенный blob-кэш. Одних строк карточек недостаточно для изолированного восстановления. Закреплённые версии можно восстановить из того же источника, пока соответствующие release-файлы доступны; пользовательские модели и частные источники требуют собственной копии. [Общий порядок восстановления](production-recovery.md).

## Удаление и миграция

Главный администратор выбирает последствия удаления после просмотра связанных проектов. Удаление только из общего каталога сохраняет версии, историю и закреплённые назначения. Удаление назначений — отдельное явно выбранное последствие; используемая активным RAG-индексом модель защищена от незаметного отключения.

Старые карточки сохраняются как локальные данные без выдуманного provenance нового источника. Старое назначение без записанной версии имеет состояние незавершённой миграции; оно не превращается в автоматическое следование текущей версии. Фактически установленная на компьютере версия учитывается отдельно.

Gateway выдаёт установщик моста для импортированного выпуска и проверенные архивы именно этого выпуска. Отсутствующий импорт или blob возвращает ошибку; старый локальный архив не является резервным источником. Producer `bridge:prepare` создаёт новый descriptor и нативные архивы; уже экспортированные версия, сборка и набор платформ неизменяемы.

## Подтверждение нового producer в Git

При изменении подготовленных adapters, helpers, dependency locks или другого файла из retained producer maintainer сначала проверяет изменение, затем выполняет на Node24 `node scripts/assets/catalog-source-pin.mjs --write`. Вместе коммитятся `catalog-source/producer.json`, обновлённая опись и `services/shared/bundled-catalog.lock.json`. Проверка `--check` не пишет файлы и выявляет забытый pin. Пользовательское `git pull`/`npm run update` не переподписывает изменённый producer автоматически. Отказ этой проверки сохраняет историю и отмену принятых заданий; новые source recipes не объявляются готовыми.
