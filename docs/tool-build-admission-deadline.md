# Приём сборки и отмена при SQL-блокировке

B13 расширяет локальную приёмку упаковщика до приёма задания и барьера публикации. Все собственные транзакции `PackageBuildRepository` устанавливают ограничения сразу после `BEGIN`: максимум 5 секунд на получение одной блокировки и 30 секунд на один SQL-запрос. Меньшие ненулевые настройки сессии сохраняются независимо; после COMMIT/ROLLBACK возвращаются прежние значения. Публикация продолжает использовать тот же ограничивающий helper.

В PostgreSQL лимит блокировки применяется отдельно к каждой попытке её получения. Последовательное ожидание нескольких блокировок может занять больше пяти секунд в одном запросе; его ограничивает `statement_timeout`. Это не общий срок HTTP-запроса, транзакции или сборки. [Семантика PostgreSQL 16](https://www.postgresql.org/docs/16/runtime-config-client.html).

## Продолжение в интерфейсе

- SQL `55P03`/`57014` из ограничиваемой транзакции репозитория при приёме или отмене возвращается как безопасный 503: «Сервер не подтвердил результат запроса. Проверьте его состояние или повторите сохранённый запрос». Первичная ошибка остаётся внутренней причиной; SQL-текст не попадает в ответ. Проверенные 403/409 сохраняют свой смысл. Предварительные проверки доступа и SQL до этой транзакции находятся вне данного mapper.
- При неизвестном результате создания сохраняются точное тело, UUID, uploadId и основа CAS. Автоматическое восстановление выполняет только поиск результата. После ограниченной проверки доступны явные повторная проверка и отправка того же сохранённого запроса. Повторного автоматического POST нет.
- При неподтверждённой отмене сохраняется намерение DELETE, в том числе после reload. Отмена остаётся доступной; система не показывает `CANCELLED` и не позволяет забыть ещё неизвестный результат. После освобождения очереди повторяется прежняя отмена. Подтверждённая отмена оставляет tombstone, который запрещает поздний POST с тем же UUID.
- При внешней блокировке строки задания нельзя подтвердить запись `FAILED`. Worker освобождает владение после ограниченного отказа; строка может оставаться `RUNNING` без барьера и native-публикации. После освобождения строки восстановление фиксирует прерывание, сохраняет исходники и продолжает очередь. Новая сборка после подтверждённого конечного результата требует явного действия и нового UUID.

Изменение исправляет существующий сценарий `tool_builds`; нового бизнес-флага нет. Прежние проверки прав, истории, отмены и восстановления при выключенном флаге сохраняются.

## Локальные свидетельства 23 октября 2026 года

На старом кандидате подтверждены пять SQL-ожиданий с настройками `0/0` дольше восьми секунд: READY upload, asset-lock новой версии, граф зависимостей, общая очередь и строка задания до барьера. Три здоровых контроля и продолжение очереди после unlock прошли. Это исторический причинный RED, а не доказательство бесконечного ожидания на рабочей площадке.

Исправленный кандидат принят отдельно: **8/8**, без ошибок очистки. Сверены 176 реальных SQL-трасс и 1082 неизменных хеша. Проверены:

- Безопасный 503, точный UUID, отсутствие дубликатов, отмена до создания задания и повтор той же отмены после освобождения общей очереди.
- Настоящий timeout записи `FAILED` при удерживаемой строке, освобождённый lease, `RUNNING`/пустой барьер/native404 до unlock; затем реальное восстановление в `FAILED` и успешная следующая сборка skill.
- Сохранность READY-байтов, исходника skill и прежних карточек/версий/происхождения, новые запросы с тем же uploadId, меньшие лимиты 100/200 мс и восстановление GUC на соответствующей сессии.

Первый кандидат дал 6/8 из-за двух неверных ожиданий QA: DELETE также ограниченно отказывает при внешнем queue-lock, а 14 секунд не покрывают последовательные lock waits. Его квитанции сохранены. Стенд исправлен без изменения production и без замены реальной SQL-ошибки искусственным timeout. Исторический baseline, первый кандидат и окончательные восемь случаев не суммируются.

Целевые проверки: API 11/11, репозиторий и прежние транзакционные регрессии 84/84, frontend 98/98, guards профиля 41/41; строгий TypeScript Catalog прошёл. После независимого ревью усилен oracle двух frontend-тестов, затем изменённый файл повторён 52/52. Эти пересекающиеся наборы не прибавляются к общему счётчику.

Общий unit-safe прогон всех восьми пакетов: **8695 pass / 0 fail / 53 skip**, 631/631 выбранных файлов, 78 исключены. AST: строки **69,29% (22751/32834)**, функции 62,56%, ветви 66,02%, выражения 64,71%; `complete:false`. Измерение выполнено на чистом `3bbbd221`, `sourceChangedDuringRun:false`. Все 2568 хешей инвентаризации совпали. Это не near-100 всех модулей workspace.

Все восемь пакетов собраны из отдельного снимка; 1304 текущих файла `src/shared` совпали с кандидатом. Восемь собственных БД удалены, native Node завершён, отдельный PostgreSQL штатно остановлен; PID/порт/pidfile проверены независимо. Основная БД и пользовательский мост не менялись.

Квитанции сохранены локально: `.run/build-admission-deadlines-20261023/verification-receipt.json`, native `.run/build-admission-reliability-20261023/candidate-wi56Eb/receipt.json`, очистка `.run/build-admission-reliability-20261023/fixed-b13-0d3792a9-783e-4748-88aa-0e85ffd7934f/native-cleanup-receipt.json`, общий отчёт `.run/coverage/build-admission-final-20261023/manifest.json`.

## Граница приёмки

Проверены compiled-методы контроллера и сервиса внутри процесса, настоящий PostgreSQL и native-журнал Skills на macOS ARM64. Gateway HTTP/middleware, браузер, настоящий MCP/JS-сборщик с установкой после отмены, обычный OpenCode, другие ОС, CI и production этим срезом не приняты. Полный упаковщик B10 и восемь цепочек стабильного MVP остаются отдельной приёмкой.
