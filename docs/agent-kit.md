# Neurocenter Agent Kit 0.1.2

Общий workflow Neurocenter: цель и критерии готовности → исследование → минимальная реализация и регресс → независимое ревью → проверенный результат. Правила интерфейса действуют во всех изменяемых сценариях продукта. Простая правка не требует полного ритуала большого проекта.

Канонический исходник — `.opencode/skills/neurocenter-task-flow`. OpenCode использует его непосредственно в этом проекте; Codex получает копию в локальный каталог skills. Общие инструкции написаны самостоятельно под текущую работу; [Everything Claude Code / ECC](https://github.com/affaan-m/ECC) использован как образец организации набора, его hooks и полный каталог не импортировались.

| Среда | Размещение | Вызов |
| --- | --- | --- |
| OpenCode, этот проект | `.opencode/skills`, `.opencode/agents`, `.opencode/commands` | `/neurocenter-task <задача>`; роли `neurocenter-explorer`, `neurocenter-reviewer` |
| Codex, этот компьютер | `~/.codex/skills/neurocenter-task-flow`; совместимые роли в `~/.codex/agents` | `$neurocenter-task-flow <задача>` |

Набор содержит **64 роли**, у каждой отдельный профильный skill, и один общий `neurocenter-task-flow`: всего **65 skills**. Восемь групп по восемь ролей: продукт, frontend, backend, модели/агенты, знания/хранение, поставка, качество и эксплуатация. [Полный каталог](../.opencode/skills/neurocenter-task-flow/references/catalog.md) связывает каждую роль с её входом, результатом, проверками и границами. Общий профиль Neurocenter загружается по необходимости.

Подробные инструкции роли загружаются для выбранной задачи. Наличие 64 ролей не означает их одновременный запуск: действует текущий лимит параллельности. Установщик skills не меняет модели, провайдеры, MCP, hooks, учётные данные и права запуска. MCP подключаются отдельно по запросу пользователя. Проверку типов и тесты выполняют существующие инструменты проекта. Роли исследования/ревью используют доступное read-only чтение и просмотр diff; необходимые тесты и сборки выполняет основной агент.

## Обновление набора

Исходные определения находятся в восьми JSON-файлах `scripts/agent-kit/roles/`; общие инструкции редактируются непосредственно в `neurocenter-task-flow`. Адаптеры и профильные skills формируются одной командой:

```sh
node scripts/agent-kit/generate.mjs
node scripts/agent-kit/generate.mjs --check
```

Генератор сохраняет SHA в manifest и отклоняет замену вручную изменённого сгенерированного файла. Управляемые файлы и manifest с символическими или жёсткими ссылками отклоняются до первой записи, чтобы обновление не затронуло связанный посторонний файл. Установщик Codex сначала проверяет весь план и целостность исходников. Существующий изменённый пользовательский файл не перезаписывается; повтор одинаковой установки не меняет файлы.

При переименовании роли `obsolete` показывает прежние управляемые пути. Генератор удаляет только свои generated outputs, установщик — только пути из прежней ownership receipt, если их SHA не изменился. Уже отсутствующие файлы снимаются с учёта; изменённые файлы и ссылки дают конфликт до записи. Ручные соседние файлы сохраняются, очищаются только пустые каталоги старых skills. Обновлённая receipt содержит текущий набор без бессрочного накопления старых ролей.

Локальный `NEUROCENTER_AGENT_KIT_RETIRE=0` блокирует применение плана с `obsolete` до любых записей, а план и `--check` остаются доступны. Допустимы только `0`/`1`, по умолчанию `1`. Проверка всего плана защищает от уже наблюдаемых конфликтов; многофайловое обновление не является атомарной файловой транзакцией против внешнего редактора.

```sh
node scripts/agent-kit/install-codex.mjs          # показать план
node scripts/agent-kit/install-codex.mjs --apply  # установить или обновить свои файлы
node scripts/agent-kit/install-codex.mjs --check  # проверить установленную копию
```

Путь Codex берётся из `CODEX_HOME`, иначе используется `~/.codex`. В проекте OpenCode читает размещённые файлы непосредственно, установка npm для самого kit не нужна.

### Диагностика набора

```sh
npm run agent-kit:check
npm run agent-kit:doctor
```

`agent-kit:check` проверяет актуальность сгенерированных файлов и manifest без записи. Полный `npm run check` начинает с этого допуска до сборок; ограниченные `--package`/`--step` сохраняют выбранную область.

`npm run check -- --tooling` объединяет этот допуск с явным набором локальных agent-kit/MCP/check/coverage-тестов и сохраняет обычный отчёт v3. Продуктовые сборки и Compose в этот режим не входят. [Область и отключение](developer-tools.md#проверить-инструментарий).

`doctor` раздельно проверяет исходники набора и установленную копию с ownership receipt. Отсутствующие файлы, ручные изменения и устаревшие адаптеры дают ненулевой exit; файлы и конфигурация не меняются. Без наблюдения клиента итог `unverified` с exit 0: наличие файлов не подтверждает загруженные роли или tools.

В исходниках `repository.obsolete` перечисляет устаревшие generated outputs. Ручная правка устаревшего файла отображается как отдельный конфликт владения в проекте или установленной копии; содержимое prompt в ответ диагностики не попадает. Для просмотра действий установки используй её режим плана без `--apply`.

Для сравнения фактически видимого каталога передай каждое имя через `--observed-tool <имя>`, например `npm run agent-kit:doctor -- --observed-tool workspace_status --observed-tool services_health`. Передавай весь список только сервера `neurocenter-dev`, без префикса клиента. Неполный список покажет отсутствующие инструменты. `observedClient.evidence` остаётся `caller-supplied`: doctor не опрашивает активный чат и не заменяет его наблюдение отдельным SDK-подключением. Совпадение tools не доказывает загрузку или качество ролей.

## MCP для разработки Neurocenter

Исполняемый цикл воспроизведения, точечного покрытия и отдельной сборки описан в [инструментах разработки](developer-tools.md).

`neurocenter-dev` — отдельный локальный stdio-сервер `scripts/dev-mcp/server.mjs`. Он использует уже установленные зависимости моста; при старте не загружает пакеты и не требует работающего API. Его область — checkout, в котором расположен сам сервер. Конфигурация MCP хранится отдельно от устанавливаемых skills.

| Инструмент | Результат |
| --- | --- |
| `workspace_status` | Git-состояние, версии восьми пакетов, версия MCP и его включённый каталог; сами проверки не запускаются |
| `services_health` | Ограниченные запросы к фиксированным локальным endpoints, HTTP-результат и проверка ожидаемого ответа |
| `service_logs` | До 100 строк / 32 КиБ стандартного журнала выбранного сервиса с маскированием распространённых секретов |
| `verification_summary` | Сводка выбранного coverage manifest, check report или isolated-build receipt; область, пропуски и пределы проверки исходников сохраняются отдельно |
| `coverage_gaps` | Цели для регресса выбранного unit-пакета: функции/ветви без исполнения, отсутствующие исходники и исключения; отдельные SHA manifest/gaps и состояние исходников |
| `check_plan` | План существующих проверок для явно выбранных пакетов и шагов, команды и отсутствующие npm test; без запуска или записи |

Сервер не принимает произвольные команды, URL или пути. Он не подключается к БД, не управляет сервисами и не выполняет операции моста над пользовательскими проектами. Используется стандартный `.run/logs`; внешний `LOGDIR` автоматически не читается. Ответ health подтверждает только выбранный probe, а не полную готовность БД или пользовательского сценария. Журналы и отчёты остаются недоверенными данными.

Версия диагностического сервера — `0.3.4`; стандартный каталог содержит шесть инструментов. Локальный флаг `NEUROCENTER_DEV_MCP_CHECK_PLAN=0` скрывает и запрещает `check_plan`, сохраняя чтение ранее полученных свидетельств. Допустимы `0` и `1`, по умолчанию включён; изменение требует нового процесса MCP. Doctor учитывает тот же флаг в окружении своей команды. Флаг не требует API или изменения продуктовых настроек. Подробные форматы и ограничения — в [инструментах разработки](developer-tools.md).

В 0.3.0 `services_health` различает liveness, пассивную readiness и принадлежность listener; `verification_summary` принимает check v3 с before/after SHA и cleanup, сохраняя legacy/v2. Все шесть ответов получили выходные схемы и серверную проверку. `NEUROCENTER_DEV_MCP_SERVICE_DETAILS=0` отключает добавленную readiness/OS inspection, `NEUROCENTER_DEV_MCP_OUTPUT_SCHEMAS=0` — новые выходные контракты. Сохраняются отдельные ограничения: готовность процесса не устанавливает версию работающего кода, а сохранённый SHA не сравнивается с текущими байтами самим MCP.

Исправление 0.3.1 сохраняет Node/Vitest counters, включая TODO и доступный cancelled, при чтении check, coverage и retained merge. Неизвестные прежние счётчики остаются `null`; пропуски, TODO и отсутствие нужных сведений не дают полной приёмки. План check привязан к прочитанным manifest/discovery bytes. Генератор дополнительно запрещает имя роли `task-flow`, занятое общим workflow. Checkpoint каждой задачи хранится по отдельному пути. Эти изменения не обновляют автоматически каталог уже открытого чата.

В 0.3.2 `service_logs.details` добавляет время наблюдения/изменения и размеры проверенного чтения. Связь append-журнала с текущим процессом явно остаётся `unknown`; метки внутри текста её не подтверждают. Существующий `NEUROCENTER_DEV_MCP_SERVICE_DETAILS=0` сохраняет прежний ответ без details. Новая tooling-selection читается `verification_summary` отдельно от восьми продуктовых пакетов.

В 0.3.3 полный хвост журнала с завершающим переводом строки больше не помечается как обрезанный. `truncated: true` означает пропуск строк или ограничение байтов.

В 0.3.4 `verification_summary` проверяет новый coverage lifecycle и читает ранние отказы/отмену без выдуманных метрик. Схемы ответа сохраняют совместимость с прежними отчётами; доступность нового процесса в текущем клиенте проверяется отдельно.

## Как проверить обнаружение

В новой сессии Codex вызови `$neurocenter-task-flow` или конкретный `$neurocenter-react-developer` и попроси назвать загруженный файл. Для независимого машинного контроля `skills/list` должен вернуть 65 имён `neurocenter-*`, включённые записи и ожидаемые пути без ошибок. Сравнение SHA установленного набора с manifest дополнительно подтверждает версию файлов.

Обнаружение skill, загрузка роли и качество её работы — разные проверки. На установленной CLI Codex 0.146.0 изолированная проверка вернула все 65 skills, показала все 64 роли в схеме `spawn_agent` и действительно запустила `neurocenter-reviewer`. Запрос дочернего агента содержал точные инструкции установленной роли; ожидание вернуло контрольный ответ. Ответы обеспечивал локальный синтетический стенд: внешних и платных запросов не было. Это проверяет механизм загрузки и запуска, но не качество решений настоящей модели.

Пользовательские роли зависят от версии клиента; наличие TOML-файла не доказывает, что конкретный клиент его загрузил. Сам skill сохраняет workflow и при отсутствии native custom roles. Существующие настройки и skills сохраняются; одноимённые изменённые файлы требуют разбора конфликта перед обновлением.

Проверки: формат skill и TOML/YAML, разрешение внутренних ссылок, независимые сценарии применения. Это не гарантия роста качества модели: оценивай набор по тому, сокращает ли он забытые требования, ручные шаги, повторные дефекты и неподтверждённые заявления о готовности. Новые правила добавляй по наблюдаемой причине, а не для объёма.
