# Production: безопасные резервные копии

17 октября 2026 года. Продолжение [этапа квот](production-stage-3-2026-10-17.md). HTTP-копии теперь имеют общий бюджет, ограниченную параллельность и публикацию полного файла; отказы не запускают очистку старых копий. **Промышленный допуск остаётся NO-GO**: это часть PR-05, а не защита всего диска и не независимая резервная инфраструктура.

## Что изменилось

- Проектные и системные копии сериализуются одной файловой блокировкой в `BACKUP_DIR`. Второй запрос получает 409 с понятным действием; после аварии блокировка не снимается по возрасту файла. Она действует между процессами, использующими один локальный том, и не является распределённой блокировкой нескольких хостов.
- Поток `pg_dump -Fc` пишет в эксклюзивный `.dump.partial` с правами 0600. Проверяются успешное завершение процесса и заголовок `PGDMP`, выполняется fsync; только затем файл получает окончательное имя без замены существующего. Если системная операция включает несколько БД, все дампы сначала завершаются. Это не общая транзакция разных БД — для согласованного полного комплекта есть операторский DR.
- Установлены бюджет всех файлов корня, лимит одного дампа и резерв свободного диска. Считаются вложенные, неучтённые и частичные файлы; ссылки/специальные файлы отклоняются. Каждая порция проверяется до записи, содержимое целиком в память не загружается.
- Сначала подтверждается запись новой копии в каталоге, затем удерживаются пять последних файлов своего формата. Новая копия защищена от удаления при переводе часов назад. Из метаданных удаляются только имена реально очищенных файлов; неподходящие/старые форматы не удаляются автоматически и продолжают занимать бюджет.
- Потеря подтверждения БД возвращает 503 `BACKUP_CONFIRMATION_FAILED`: новый опубликованный файл **сохраняется для проверки**, старые копии остаются. Запись могла завершиться после потери ответа; повтор без проверки способен создать ещё одну копию. Отказ очистки после подтверждения возвращает успешный результат с предупреждением.
- Переполнение лимита, `ENOSPC` и `EDQUOT` дают 507 без stderr, SQL и реквизитов PostgreSQL в ответе. Сбой процесса не объявляется успешной копией. Основная операция имеет deadline 20 секунд; поиск проектной БД — пять секунд. Остановка/cleanup могут занять дополнительное время. Для большой БД остаётся операторский CLI; фоновых пользовательских backup-заданий пока нет.
- SIGTERM отменяет поток и ожидает cleanup до закрытия каталога. Каждый `pg_dump` имеет уникальный `PGAPPNAME`; отменяется только его сессия в своей БД и под своей ролью. Права superuser для этого не добавлялись. Поведение сверено с [правилами сигналов PostgreSQL](https://www.postgresql.org/docs/16/functions-admin.html#FUNCTIONS-ADMIN-SIGNAL) и проверено на работающей БД.
- DR до остановки приложений проверяет API-mutex; файловый помощник не переносит комплект с lock или `.dump.partial`. При штатном отказе полный комплект не публикуется, приложения возвращаются в работу.

Настройки по умолчанию: **64 ГиБ суммарно / 16 ГиБ на дамп / 1 ГиБ резерва**. Они задаются положительными целыми байтами через `backupMaxTotalBytes`, `backupMaxFileBytes`, `backupMinFreeBytes` в закрытом JSON для `configure`; соответствующие env описаны в [настройке production](production-setup.md). Ноль не отключает защиту. Уже сохранённые файлы не удаляются ради уменьшенного лимита, а для следующего дампа нужно место до retention.

Разбор аварийной блокировки и неопределённого подтверждения описан в [runbook](production-recovery.md#лимиты-и-прерванные-копии-из-панели). Новые каталоги создаются с правами 0700, прежние права автоматически не переписываются. Без явного `BACKUP_DIR` системные и проектные функции используют `data/backups` от cwd; старый `~/lancedb-backups` самостоятельно не переносится.

## Интерфейс

Ant Design сохранён. Вкладка проекта проверяет форму ответа и соответствие проекта до сообщения об успехе. При ошибке обновления остаётся последний полученный список с предупреждением; первая ошибка показывает недоступность вместо ложного «копий нет». Backend также возвращает 503 при EACCES/EIO и других ошибках проверки хранилища; только отсутствующий файл после очистки пропускается. Повтор восстанавливает список без перезагрузки. Двойное создание защищено, запоздалый ответ списка не заменяет более новый, вкладка изолирована ключом проекта. Ошибки создания и предупреждения очистки показаны отдельно. Дата содержит время до секунд, чтобы различать копии за один день.

Ручной проход CUA выполнен на **временном проекте** локального стенда: создание, занятый mutex, ошибка чтения с сохранённой копией, первая ошибка чтения, повтор после восстановления сети, дата/время и ширина 1280/390. Сетевой отказ задавался только для URL списка этого проекта; блокировка снята, viewport reset выполнен. Проект, его БД, запись реестра и файлы удалены; исходная навигация восстановлена. На реальном Mac установка, обновление клиента и выбор папки не запускались.

HTTPS проверяет общий mutex системных/проектных действий, 507 по размеру файла и свободному месту, общий бюджет с неучтёнными файлами, неопределённое подтверждение, удержание пяти файлов и совпадающих записей, системную дату backup и 503 при ошибке файловой системы с возвратом списка после ремонта. Для проверки отмены отдельная тестовая PG-сессия держит реальную табличную блокировку; ожидающий `pg_dump` прерывается SIGTERM каталога. Затем проверяются отсутствие его PG-сессии/partial/lock, старые байты и список после перезапуска. Роль копирования не имеет superuser. Модульные проверки отдельно покрывают deadline и предупреждения об отказе очистки файлов/метаданных.

ENOSPC-тест использует настоящий маленький tmpfs, FileHandle/write и ошибку ядра: внешний писатель занимает оставшееся место между `statfs` и записью. Только источник байтов дампа подменён фикстурой; настоящий `pg_dump` проверен отдельно через HTTPS и восстановление. Файловая система Mac не заполнялась. После освобождения места подтверждены новая запись и удаление блокировки. Такая проверка не моделирует потерю питания или повреждение физического накопителя.

Финальная DR-фикстура: **пять БД, восемь файлов, 104 035 байт**. Backup с возвратом сервисов — **27,014 с**, restore данных — **15,154 с**, готовность приложений с новым тестовым входом — **48,097 с**. Образы уже были на хосте; это малый Linux ARM64 стенд, не измерение RTO на рабочем объёме. Тестовый TLS/Blitz не заменяет корпоративный IdP.

При `dev up` архив MCP перепакован: байты tar/gzip отличаются от архива неизменённого gateway-образа, содержимое всех 34 файлов одинаково. SHA256 обоих архивов записаны отдельно; побайтовое совпадение архивов не заявляется. Это не обновление кода MCP или установленного Mac-клиента.

Совокупный реестр — **329 уникальных сценарных/конфигурационных проверок**: 313 + 3 Node + 9 HTTPS + 2 DR + 2 ENOSPC; Vitest, повторные прогоны и ручные наблюдения в эту сумму не добавляются.
