# OAuth, права, MCP и администратор

## 1. Разделение ответственности

OAuth-провайдер выдаёт токен, предназначенный нашему API. OIDC используется для идентификации пользователя; стабильный субъект — пара `issuer + sub`, а не email. Проверяется подпись/JWKS либо introspection, issuer, audience, срок, разрешённый алгоритм и OAuth scopes.

Внешний сервис прав отвечает, может ли этот субъект выполнить действие над конкретным project, collection, snapshot или skill. Scopes токена ограничивают класс операций, но не заменяют проверку доступа к объекту.

API вызывает сервис прав под собственной служебной идентичностью и передаёт проверенный субъект и контекст. Входящий пользовательский access token не пересылается в другой сервис с иной audience. Рабочие процессы также имеют отдельные service identities.

## 2. Вход локального клиента и панели

Локальный MCP работает через stdio. OAuth здесь нужен для его HTTPS-запросов к backend, а не для локального канала OpenCode → MCP. Клиент заранее регистрируется как public native application, использует Authorization Code + PKCE S256, браузер и loopback callback, проверяет state и ожидаемый issuer. Refresh token хранится в macOS Keychain либо системном credential store другой ОС; конфиг содержит только ссылку на профиль входа.

Нужно предусмотреть обновление токена, logout и отзыв сессии, а также работу без refresh token, если провайдер его не выдаёт. Токены и подписанные S3 URL не выводятся в модель, tool results, диагностику или аудит.

Для админки предлагается BFF внутри NestJS API: OAuth/OIDC-вход, серверная сессия, cookie HttpOnly + Secure + SameSite и защита от CSRF для изменений. Доступ администратора подтверждается внешним сервисом прав; cookies панели не авторизуют сторонние MCP-клиенты.

Если включается удалённый MCP, он публикует Protected Resource Metadata, обнаружение authorization server и корректные 401/403 challenges. Для OAuth используются audience/resource binding и PKCE. Базовая версия спецификации для проектирования — 2026-07-28; совместимость выбранного OpenCode/MCP SDK проверяется до разработки. Pre-registration подходит для контролируемого корпоративного клиента; нельзя требовать только Dynamic Client Registration. [MCP Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), [защита OAuth в MCP](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations).

## 3. Предлагаемый контракт сервиса прав

Имена действий ниже — контракт нашего приложения, который ещё нужно сопоставить с API внешнего сервиса.

Запрос решения содержит проверенный субъект, action, тип и ID ресурса, project/collection context и request ID. Ответ содержит allow/deny, decision ID, policy revision и срок применимости. Нужны пакетная проверка и получение доступных scope/resource ID для фильтрации каталога. Иначе поиск будет создавать по отдельному RPC на каждый результат.

Чтение может кэшировать решение до 30 секунд с ключом субъект + действие + ресурс + revision. Инвалидация идёт через события от сервиса прав, если они доступны. Неистёкший allow может обслужить чтение и очередное окно download URL даже при временном сбое сервиса прав; после его TTL новая выдача блокируется. Для открытия новой transfer session, загрузки на сервер, принятия проверенного кандидата, активации, rollback и удаления требуется свежая проверка; ошибка сервиса прав блокирует изменение. Это сознательное окно отзыва до 30 секунд для чтения, дополнительно к сроку уже выданных URL.

Локальный config и интерфейс не являются границей прав. Каждая HTTP/MCP операция, список, поиск, выдача разрешения на передачу и финализация проверяются на backend.

## 4. Действия

| Действие | Что разрешает |
| --- | --- |
| `project.read` | Увидеть разрешённый проект и его метаданные |
| `image.download` | Скачать выбранный проверенный снимок без изменения серверной текущей версии |
| `image.sync.pull` | Синхронизировать управляемую локальную копию с выбранным серверным снимком или профилем |
| `image.publish` | Загрузить и предложить новую версию проектной базы |
| `image.head.update` | Сделать проверенную версию текущей, включая rollback |
| `image.delete` | Пометить снимок к удалению с учётом retention и зависимостей |
| `skill.read` | Скачать разрешённую версию скилла |
| `skill.sync` | Обновить управляемый локальный комплект скиллов |
| `skill.publish` | Опубликовать версию в указанную коллекцию |
| `skill.collection.manage` | Управлять составом и текущими версиями коллекции |
| `project.profile.manage` | Менять закреплённые версии образа и скиллов профиля проекта |
| `platform.admin` | Пользоваться административными функциями в пределах разрешённых действий |
| `audit.read`, `quota.manage` | Читать соответствующий аудит и управлять квотами |

Для sync pull требуются `image.download` и `image.sync.pull`. Загрузка и принятие кандидата требуют `image.publish` у автора. Отдельная активация уже проверенного кандидата или rollback требуют `image.head.update` у выполняющего действие пользователя; этому пользователю не нужен publish, а исходный upload lease уже не используется. Автоматическая публикация с немедленной активацией требует у её инициатора обоих действий. В аудите отдельно сохраняются автор версии и субъект активации.

Выпуск согласованного профиля образа и скиллов требует `project.profile.manage`, прав чтения закрепляемых скиллов и `image.head.update`, если операция также меняет head. При установке профиля получатель проходит проверки доступа ко всем его ресурсам. Профиль не передаёт полномочия своего автора читателям. Административное принятие кандидата допустимо, но не является обязательным шагом каждого релиза.

Права на общую коллекцию не дают прав на проектную и наоборот. Пользователь с доступом к проекту не получает автоматически содержимое всех общих коллекций.

Примерные роли формируются **во внешнем сервисе**: reader, sync user, project publisher, catalog maintainer, administrator. Роль администратора должна явно выдавать нужные действия; API не превращает локальный флаг `isAdmin` в обход внешнего deny.

## 5. Ограничения отзыва доступа

Проверка права предшествует выдаче signed URL на конкретный объект/операцию. Рекомендуемый срок начала запроса — 5 минут; новые URL выдаются небольшими окнами после актуальной проверки. Сессия передачи может жить дольше, но не содержит долгоживущего разрешения на весь bucket.

Уже выданный S3 URL остаётся bearer capability до истечения срока, а начатая передача может продолжиться и после него. URL также может повторно использоваться: это не одноразовый билет. Для versioned staging нужно учитывать повторные PUT и закреплять конкретные objectVersionId; бюджет reservation сам по себе не ограничивает физические записи. [Семантика S3 presigned URL](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html).

Отзыв права не забирает уже скачанные локальные файлы. Для требования немедленно обрывать доступ нужен отдельный Transfer Gateway, который авторизует каждый запрос/чанк и умеет прерывать активные потоки. Его вычисления и трафик следует отдельно заложить в размер инфраструктуры.

Обычный reader после скачивания физически способен изменять свои локальные файлы. Сервис гарантирует запрет неразрешённой синхронизации через API и публикации в общее хранилище; запрет любых локальных изменений потребовал бы управляемого устройства и отдельного контроля ОС.

## 6. MCP-инструменты

Названия — проект контракта, не существующие команды.

| Инструмент | Вход и результат | Право |
| --- | --- | --- |
| `projects_list` | Разрешённые project ID, head ID/revision и активный profile ID/revision | project.read |
| `image_status` | Установленная и серверная версия, размеры, локальный dirty state | project.read |
| `image_download` | project + snapshot; возвращает operation ID, затем локальный путь | image.download |
| `image_sync_pull` | project + ожидаемая локальная версия; состояние синхронизации | image.download + image.sync.pull |
| `image_publish` | project + expectedHeadId/revision + локальный snapshot; кандидат и operation ID | image.publish |
| `image_activate` | project + verified snapshot + expectedHeadId/revision | image.head.update |
| `project_release` | Новый профиль с точными версиями + expectedProfileId/revision; при смене head также expectedHeadId/revision | project.profile.manage + skill.read; image.head.update при смене head |
| `project_sync` | Закреплённый profile ID + expected local lock; подготовка и установка образа и скиллов | image.download + image.sync.pull + skill.read + skill.sync |
| `skills_list` / `skills_search` | Только разрешённые коллекции, версии и описания | skill.read |
| `skill_download` | skill + version + выбранное место сохранения | skill.read |
| `skills_sync` | project profile + expected local lock; установка закреплённого комплекта | skill.read + skill.sync |
| `skill_publish` | collection + skill + expectedVersionId/revision + Markdown; новая текущая версия | skill.publish |
| `operation_status` / `operation_cancel` | Состояние своей либо отдельно разрешённой операции | Доступ к операции и соответствующему ресурсу |
| `lance_query` | Локальный read-only поиск с лимитом результата | Локальная политика инструмента |

Большая передача всегда асинхронна. Tool result содержит progress, количество байтов, ID и понятную ошибку; raw базы, S3 URL и credentials в него не входят. Отмена останавливает локальную передачу, запрещает дальнейшую финализацию серверной сессии и освобождает резервы после безопасной очистки. После успешной активации cancel возвращает уже завершённое состояние; отменить опубликованный релиз можно отдельным разрешённым rollback, а не отменой старой операции.

`skill.publish` включает создание и продвижение новой версии конкретного скилла. `skill.collection.manage` нужен для управления составом коллекции и перемещения её head на уже существующую версию, включая rollback. Публикация скилла не обновляет закреплённые профили автоматически. Контракты расширения MCP-пакетов и плагинов вынесены в [extensions.md](extensions.md).

В config локального MCP нужны URL API, OAuth profile/client ID, разрешённые project ID, локальный storage root, выбранная версия формата, предел параллельных передач и кэш-квота. Доверенные endpoints задаются конфигурацией, а не текстом модели. Нельзя принимать произвольный S3 endpoint или объектный ключ от LLM.

OpenCode permissions управляют вызовом инструмента агентом и дополняют серверные ACL. По умолчанию публикацию и замену лучше скрыть от обычного агента, разрешив их в предназначенном для этого режиме. Существующая конфигурация OpenCode в репозитории этим проектом не меняется.

## 7. Панель администратора

UI на Ant Design **4.x**, без неявной замены на 5/6. Версию React и финальный patch AntD 4 фиксировать после проверки совместимости; основной стек и major библиотеки уже выбраны пользователем. [Документация Ant Design 4](https://4x.ant.design/docs/react/introduce).

Предусмотрены экраны:

- проекты: текущий образ, физический и логический объём, квота, активные операции;
- версии: автор, parent, состав таблиц, совместимость, результат проверки, активация и rollback;
- общие и проектные скиллы: версии, закрепления в проектах, конфликт имён;
- передачи и проверки: очередь, прогресс, ошибки, повтор и отмена;
- аудит: субъект, действие, ресурс, результат и решение сервиса прав;
- обслуживание: retention, состояние backup/restore и ограничения хранения.

Экран доступа показывает решения внешнего сервиса и ведёт в его интерфейс. Изменять разрешения из нашей панели можно только через явно предоставленный административный API этого сервиса; отдельный локальный реестр ACL не создаётся.

Каждое административное действие проходит тот же backend authorization layer. Интерфейс скрывает недоступные действия, но это только удобство отображения. Права публикации общей коллекции, проектных образов и управления инфраструктурой могут принадлежать разным администраторам.
