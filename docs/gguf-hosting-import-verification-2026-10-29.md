# Проверка импорта и активации GGUF — 2026-10-29

Рабочая копия: `openapi-contract-repair/neurocenter`, исходный HEAD `fe9f3841a6308f6364b9ac87c061e9dd4fd29626` плюс незакоммиченные изменения. Git, основные БД, установленные daemon и пользовательские веса исполнитель этого среза не менял.

## Поведение

- Главный администратор создаёт квитанцию через `POST /api/models/gguf-imports`, передаёт один файл через `PUT /:id/content`, проверяет `GET /:id` или `GET /requests/:key` и принимает его через `POST /:id/accept`.
- `GET /api/models/gguf-imports/limits` возвращает текущую типизированную политику. Приёмка сохраняет снимок пятнадцати настроек. Изменение политики применяется к новым импортам; чтение, отмена и точный повтор квитанции сохраняются при OFF и недоступности текущего provider настроек.
- Данные передаются с backpressure; сервер вычисляет SHA-256. Parser читает ограниченный заголовок, проверяет GGUF v2/v3 little-endian, обязательную архитектуру, размеры/смещения тензоров и пересечения. Split, adapter, projector, неподдерживаемые quant-типы и некорректные границы отклоняются.
- Отдельная таблица загрузок и UUID-файлы не используют 256 МиБ механизм исходников инструментов. Перед READY/ACCEPTED проверяются действующие права, epoch, квота и свободное место. Stream lease и запросы статуса/отмены используют отдельные пулы.
- Приёмка создаёт одну существующую карточку `IModel`: `source: custom`, `runtime: ollama`, фактический `fileImport`, `manifestSha256: null`. Это ещё не свидетельство работающего inference.
- Явный запуск хостинга использует Ollama **0.35.1**, HEAD/POST blob и files-only create. Нет pull/from, пользовательского template, автоматической установки или сетевой загрузки весов.
- Намерение `RESERVED → CREATE_SENT → CREATED` хранится отдельно. После неоднозначного ответа CREATE выполняется только сверка manifest и tags; второй CREATE не отправляется. Для закрепления требуется один model layer с точными SHA/размером исходного файла, согласованный manifest digest и проверка настоящего ответа модели существующим Ollama client.
- GGUF SHA и manifest SHA остаются разными идентификаторами. Существующие manifest-based aliases и legacy hosting сохраняют прежнее поведение. Экспорт model bundle из raw GGUF этим срезом не объявляется реализованным.

## Выявленные и закрытые дефекты

- Двойной резерв места перед READY: контролируемый RED вернул 507 при достаточном остатке. Теперь выполняется свежая проверка физического остатка без второго резервирования уже записанного файла.
- Исчерпание общего пула stream leases: отдельный пул сохраняет доступность статуса и отмены. PG-проверка использовала четыре потока при двух control connections.
- Runtime leases также вынесены из пула ModelsService. PG-проверка использовала пять одновременно удерживаемых provider операций при двух control connections.
- Readiness пропускала CHECK и UNIQUE(upload_id): контракт дополнен фактами PostgreSQL. Каждый обязательный CHECK и этот UNIQUE удалялись внутри откатываемой транзакции; readiness отвергала повреждение.
- Возврат Promise проверки без await отпускал lease до завершения reconciliation и приводил к unhandled rejection. Окончательный PG-прогон проверяет удержание lease и не содержит unhandled ошибок.
- Node HTTP requestTimeout по умолчанию сокращал срок больших загрузок. Controlled HTTP воспроизводит ранний 408, затем успешный GGUF 200; обычные и некорректные маршруты сохраняют прежний deadline, GGUF соблюдает собственный сохранённый timeout.
- Q8_1: pinned Ollama определяет 36 байт на блок из 32 значений. RED с валидными 36 байтами зафиксирован в `20261029T101105Z-q8-layout-red.log`, SHA `d14a79d79e24c94a44d469a899629016c2810f9ead648c5936f3a8362c13c307`; GREEN дополнительно отвергает обрезанные 35 байт.
- Имя файла ограничивается 240 UTF-8 байтами; OpenAPI не подменяет байтовую границу `maxLength`. RED для многобайтного имени: `20261029T101255Z-filename-bytes-red.log`, SHA `468b64f1d91d43dbeb958cb07ce391e09ff1c14c0832fa95b24f0da54358d5eb`.

Ранние отчёты на системном Node 20.19.5 сохранены как история исследования; они заменены окончательным прогоном выше и не используются как доказательство Node 24.

## Границы доказательств

В этой квитанции нет приёмки установленного Ollama daemon с явно выбранными реальными весами, browser-flow, CI, применения на основной площадке или полного измерения покрытия. Provider-тесты выполняли реальные HTTP-запросы только к собственному loopback fixture и использовали небольшие искусственные GGUF/manifest файлы. Сохранение `fileImport`, успешный CREATE и capability probe — отдельные этапы; READY импорта не подменяет итоговую готовность модели.

Ollama не предоставляет атомарный CAS для внешних писателей alias. Код сверяет наблюдаемые manifest/tags и отказывается от неожиданной подмены; исключить действия привилегированного стороннего процесса одной блокировкой PostgreSQL нельзя.
