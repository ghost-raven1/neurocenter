# Файлы чата в Ceph RGW / S3

Оригиналы вложений хранятся в объектном хранилище через S3 API. PostgreSQL содержит личные диалоги, извлечённый текст, метаданные, SHA-256, точную ссылку на объект и очередь удаления. Байты новых файлов в PostgreSQL не записываются. Ссылки на бакеты и ключи S3 браузеру не выдаются.

Используются два отдельных приватных бакета:

- `CHAT_S3_PROJECT_BUCKET` — файлы личных диалогов, привязанных к проекту;
- `CHAT_S3_PERSONAL_BUCKET` — личные диалоги из общего каталога.

Проектный бакет не делает переписку общей: права по-прежнему проверяются по владельцу диалога и текущему доступу к проекту. Ключ объекта включает хеш проекта, хеш владельца, UUID диалога и случайный UUID объекта. Имена файлов, email и названия проектов в ключах отсутствуют.

## Подключение Ceph

Настройки получает только `catalog-service`:

```dotenv
CHAT_S3_ENDPOINT=https://s3.example.test
CHAT_S3_REGION=us-east-1
CHAT_S3_PROJECT_BUCKET=neurocenter-chat-projects
CHAT_S3_PERSONAL_BUCKET=neurocenter-chat-personal
CHAT_S3_ACCESS_KEY_FILE=/run/secrets/chat_s3_access_key
CHAT_S3_SECRET_KEY_FILE=/run/secrets/chat_s3_secret_key
```

Файлы с ключами должны быть закрытыми, без перевода строки внутри значения. Не задавайте одновременно переменную с ключом и её вариант `_FILE`. В production нужен HTTPS с доверенным сертификатом; отключение проверки TLS не предусмотрено.

Для Compose добавьте `-f compose.chat-storage.yml` к основному файлу и задайте `CHAT_S3_ACCESS_KEY_PATH` / `CHAT_S3_SECRET_KEY_PATH` — пути к файлам на хосте. Overlay монтирует их только в Catalog. В `.env` для такого запуска не задавайте контейнерные переменные `_FILE` глобально.

Учётной записи нужны операции чтения/записи/удаления объектов и их версий, перечисления версий, проверки бакета, политики и ACL. Если бакеты заранее созданы оператором, разрешение создания бакета не требуется. Приложение проверяет приватность существующих бакетов; публичную политику или ACL оно не исправляет автоматически, а отклоняет подключение.

Подписанная проверка policy/ACL повторяется после PUT и чтения обратно, перед публикацией ссылки на новое вложение; анонимный HEAD служит дополнительной проверкой. Если RGW не позволяет прочитать настройки доступа, приватность считается неподтверждённой и операция отклоняется. Проверка не отключается для совместимости с неподготовленным бакетом.

Целевое хранилище — [Ceph Object Gateway с S3 API](https://docs.ceph.com/en/tentacle/radosgw/). Интеграционные тесты используют локальный MinIO; это проверка S3-пути, а не подтверждение конкретного Ceph-кластера.

## Локальная разработка

Без внешних `CHAT_S3_*` команда `dev.sh up` запускает отдельное S3-хранилище на `127.0.0.1:19010`. Образ закреплён digest, данные находятся в отдельном Docker volume. Доступ из сети и консоль администратора не публикуются. Изменить локальный порт можно через `CHAT_DEV_S3_PORT`.

Ключи создаются один раз в `.run/chat-storage/access-key` и `secret-key` с правами `0600`. Повторный запуск использует те же файлы и volume. Если ключи потеряны при существующем volume, запуск останавливается и просит восстановить их; новые ключи поверх существующей поставки не создаются. Хранилище проверяется до остановки предыдущих процессов приложения.

Адрес хранилища и имена бакетов входят в его идентичность. Простая смена переменных не переносит объекты между локальным S3 и Ceph: существующие ссылки отклоняются при несовпадении конфигурации. Перед таким переносом нужна отдельная согласованная миграция объектов и ссылок; сохраните исходное хранилище до проверки переноса.

## Перенос существующих вложений

Миграция БД 15 переносит прежние `bytea` в отдельную очередь обновления и удаляет колонку байтов из рабочей таблицы вложений. Во время запуска Catalog переносит каждый файл в S3, читает обратно, сверяет размер и SHA-256 и только после успешного коммита ссылки удаляет запись очереди. Перезапуск продолжает перенос. Рабочий путь чтения не использует очередь как запасное файловое хранилище.

При непустой очереди и недоступном S3 запуск не объявляет перенос завершённым: исходные данные остаются в очереди. Пустая новая установка может работать с текстовым чатом без S3; загрузка файлов сообщает, что нужно подключить хранилище.

## Запись, удаление и восстановление

До загрузки объекта создаётся durable intent в БД. После успешной загрузки и проверки ссылка привязывается к вложению транзакционно. Ошибка записи БД, отмена и потерянный ответ S3 оставляют отслеживаемый intent для уборки.

Удаление неиспользованного вложения, диалога или проекта ставит объект в очередь удаления. При недоступном Ceph задача повторяется с задержкой; удаление объектов не блокирует открытие остальных диалогов. Для бакетов с versioning чтение использует сохранённый version ID; уборка удаляет версии только принадлежащего операции случайного ключа. Tombstone сохраняется и периодически проверяется снова, чтобы поздний PUT после потери ответа не стал бесхозным объектом.

**Резервная копия PostgreSQL не содержит оригиналы вложений, уже размещённых в S3.** Неперенесённые legacy-байты ещё сохраняются в очереди `model_chat_attachment_transfers` до успешного коммита ссылки. Для восстановления нужны согласованные данные БД и оба S3-бакета с используемыми версиями объектов. Настройте резервное копирование/репликацию Ceph отдельно. Versioning и очередь удаления сами по себе не заменяют резервную копию. Существующая процедура резервирования проектных снимков не архивирует бакеты вложений чата автоматически.

Текущие ограничения загрузки: 10 МиБ на файл, 100 КиБ извлечённого текста, 100 страниц PDF, пять файлов в сообщении, 50 МиБ и 100 загрузок на диалог. Это ограничения обработки вложений; они не определяют число сообщений или окно модели.
