# Внешние полные копии через S3

Операторский транспорт для уже созданного согласованного комплекта neurocenter-recovery-v2. Он не запускает pg_dump, не останавливает приложения и не превращает локальный каталог в независимую копию. Полный исходный комплект создаётся по [процедуре recovery](production-recovery.md). Расписание и допустимая пауза относятся к созданию этого комплекта; передача в S3 выполняется после возврата приложений в работу.

**Приёмка на независимом S3 и восстановление на другом физическом хосте ещё не выполнены.** Локальные автоматические проверки используют имитацию S3. Поле crossHostRestoreVerified: false сохраняется и после успешной доставки или скачивания. Успешный SHA readback подтверждает переданные байты на момент чтения, но не работоспособность приложения после потери исходной площадки.

## Конфигурация оператора

Реквизиты передаются только процессу CLI через закрытое окружение на сервере. Не помещайте их в frontend, репозиторий, audit payload, публичный JSON расписания или shell history с реальными значениями.

| Переменная | Значение |
| --- | --- |
| EXTERNAL_BACKUP_S3_ENDPOINT | HTTPS origin S3, например https://objects.example.org; без пути, query и реквизитов |
| EXTERNAL_BACKUP_S3_REGION | Регион подписи SigV4 |
| EXTERNAL_BACKUP_S3_BUCKET | Уже созданный закрытый bucket |
| EXTERNAL_BACKUP_S3_ACCESS_KEY_ID | Ключ с правами чтения и условной записи объектов выбранного bucket/prefix |
| EXTERNAL_BACKUP_S3_SECRET_ACCESS_KEY | Секрет ключа |
| EXTERNAL_BACKUP_S3_SESSION_TOKEN | Необязательный временный session token |
| EXTERNAL_BACKUP_S3_STORAGE_ID | Несекретный постоянный идентификатор независимого хранилища |
| EXTERNAL_BACKUP_S3_INDEPENDENT | true после проверки оператором отдельного хоста/дисков/администрирования |

Оператор проверяет, что bucket не использует контейнеры, диски, ключи шифрования и единственную учётную запись исходного сервера как общий отказный домен. URL и строка INDEPENDENT=true не доказывают эту независимость. Поле квитанции independence: operator-declared отражает её источник.

HTTP, file:, IP literals, localhost, .local, .localhost, .internal и origin с путём запрещены. DNS каждого нового соединения также проверяется на loopback, link-local, multicast и адреса интерфейсов текущей машины. Частная подсеть на другой машине допускается; её независимость проверяет оператор. Используются стандартная проверка цепочки TLS и имени хоста, SigV4, запрет redirect и timeout. Внутренний удостоверяющий центр можно добавить штатным NODE_EXTRA_CA_CERTS; отключать TLS-проверку нельзя.

Хранилище должно поддерживать S3 path-style, SigV4, PUT с If-None-Match: * и немедленное чтение записанного объекта. Redirect на другой регион не выполняется: задайте правильный endpoint. Автоматическое создание bucket, изменение политик, внешнее шифрование и удаление объектов не выполняются. Настройте шифрование хранилища и ограниченные сервисные права отдельно.

## Доставка

После полного локального backup сохраните SHA256 описи из его квитанции в независимом закрытом месте. Выберите уникальный backup ID:

~~~sh
node scripts/production/external-backup.mjs upload \
  --source /mnt/neurocenter-backups/backup-id \
  --backup-id backup-20261018-001 \
  --expect-sha256 SHA256_ИЗ_ЛОКАЛЬНОЙ_КВИТАНЦИИ
~~~

До первого PUT штатный verifier проверяет весь исходный комплект. Каждый файл передаётся блоками до 32 МиБ; это позволяет передавать дампы больше предела одного S3 PUT без загрузки целого файла в память. Формат объектов фиксирован как neurocenter-external-v1/backup-id/data/SHA256-относительного-пути/номер-блока. Пустые файлы и каталоги описаны в описи и восстанавливаются из неё. После каждого PUT выполняется GET и проверка SHA256 реальных байтов; затем проверяется SHA всего файла и повторно весь исходный комплект.

manifest.json записывается последним и также читается обратно с проверкой SHA. Успех выдаётся только после всех проверок. Квитанция содержит storage ID, backup ID, SHA описи, даты исходной копии и внешней проверки, размеры и число файлов; секреты отсутствуют. Для возраста внешней копии используйте createdAt, для давности последней проверки — verifiedAt; это разные показатели. Сохраните квитанцию вне исходного хоста.

Условная запись не заменяет существующий объект. После разрыва повторите команду с прежними backup ID и SHA: существующие блоки повторно читаются и сверяются, повреждённые или конфликтующие байты останавливают операцию. Изменённый локальный источник требует нового полного backup и нового ID. Автоматически повторяются только временные сетевые ошибки и HTTP 408/409/429/500/502/503/504: всего до четырёх попыток с паузами 250/500/1000 мс на отдельное обращение. Ошибки TLS, доступа и SHA не повторяются. Одно обращение ограничено двумя минутами и 30 секундами отсутствия сетевой активности.

Частичные объекты после неудачи остаются для безопасного повтора. Отсутствие опубликованной описи означает незавершённую доставку. Предыдущие копии и частичные объекты не удаляются автоматически. Retention нужно отдельно настроить на стороне хранилища с учётом последней проверенной полной копии; нельзя удалять отдельные блоки живого комплекта.

## Получение полного комплекта и проверка восстановления

На целевой машине нужны только доступ к S3, сохранённый отдельно SHA описи и этот транспорт. Для получения данных исходные контейнеры и volumes не требуются. Родитель каталога назначения должен существовать с правами 700, само назначение должно отсутствовать:

~~~sh
node scripts/production/external-backup.mjs download \
  --destination /srv/private-recovery/backup-20261018-001 \
  --backup-id backup-20261018-001 \
  --expect-sha256 SHA256_ИЗ_СОХРАНЁННОЙ_КВИТАНЦИИ
~~~

Сначала проверяются SHA, формат и безопасные пути описи. Файлы собираются в закрытом временном каталоге с проверкой SHA каждого полного файла; штатный verifier проверяет точный комплект. После успеха каталог получает окончательное имя. При ошибке временный каталог удаляется, существующее назначение не перезаписывается. Родитель с правами 700 должен быть выделен этому оператору: не запускайте посторонних писателей в нём параллельно.

Далее выполняется recovery.mjs verify, а затем restore в новый пустой Compose-проект по основному runbook. Для реальной проверки нужны отдельно сохранённые TLS/SSO/PG-секреты, production-конфигурация и точные образы приложений/PostgreSQL. Они **не входят** в существующий recovery-v2 и этим транспортом не добавляются. Файлы конфигурации внутри четырёх серверных томов передаются как обычные файлы. Закрытый системный конфиг и образы должны иметь собственную независимую процедуру хранения и проверки получения.

Критерий промышленного завершения: на другом хосте получить комплект и секреты/образы при недоступном исходном сервере, восстановить все БД и тома, выполнить настоящий вход, чтение и запись, сверить настройки и измерить фактические RPO/RTO на рабочем объёме. Отдельно сохранить host identity, image digests, backup ID/SHA, время и прикладные результаты. Доставка с SHA и локальный download сами по себе этот критерий не закрывают.

## Локальная проверка реализации

~~~sh
node --test scripts/test/external-backup.test.mjs
~~~

Проверяются полная доставка/сборка, русские имена, пустые файлы, несколько блоков большого файла, повтор после обрыва, реальный SHA readback вместо доверия метаданным, повреждения, безопасные пути, существующее назначение, лимиты повторов, TLS-настройка и отказ redirect. Эти проверки не являются подключением к настоящему S3, тестом корпоративного сертификата или репетицией аварии другой площадки.

Контракт транспорта сверяется с официальными описаниями [SigV4](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sig-v4-header-based-auth.html) и [условной записи S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html).
