# Одобрение точных версий и безопасный повтор установки

Продолжение [этапа ресурсов скиллов](pilot-implementation-2026-10-17.md). Масштаб пилота и цели RPO/RTO задаются оператором площадки. Этот этап закрывает одобрение конкретного кода и его передачу в очередь. Полный граф зависимостей, проверка запуска и production-приёмка ещё не завершены.

## Изменение поведения

Выбор инструмента в проектный каталог больше не разрешает автоматически все его будущие версии. Разработчик готовит план для конкретной версии, администратор проекта проверяет состав и одобряет конкретный SHA-256. Главный администратор также проходит этот шаг. Это правило действует и для собственных проектных скиллов, которые разработчик может редактировать.

Одобренный пакет устанавливается одним нажатием. Для новой или отозванной версии открывается просмотр инструкции, текста скриптов, состава файлов, конфигурации и манифеста. Бинарные файлы показаны размером и SHA-256. Администратор может управлять разрешением без подключённого компьютера через кнопку «Разрешение версии».

Открытая модалка получает изменения по WebSocket и перечитывает тот же план через GET. Чужое одобрение показывает отдельную кнопку установки; оно не запускает её автоматически. Смена пользователя, роли, проекта или устройства закрывает старый контекст. Запоздавшие ответы не отправляют задание в другой проект и не перезаписывают более новую ревизию.

## Контракт сервера

- `POST /api/device-install-plans` — подготовка `{projectId, assetKind, assetId, version}`. Нужен разработчик этого проекта. Сервер проверяет каталог и сохраняет неизменяемый пакет в PostgreSQL.
- `GET /api/device-install-plans/:id` — чтение конкретного плана участником соответствующего проекта.
- `POST /api/device-install-plans/:id/approve` и `/revoke` — решение администратора проекта с `{expectedManifest, expectedRevision}`. Решение и событие аудита фиксируются одной транзакцией.
- Создание задания `install` требует `planId` и `planRevision`. Пакет берётся из сохранённого снимка; текущий head каталога не пересобирается. Проверки статуса, ревизии, проекта, типа, ID, версии и SHA повторяются при получении задания мостом и перед записью.

Таблица `device_install_plans` содержит пакет JSONB, идентичность инструмента, хэш, статус, ревизию и автора решения. Создание схемы идемпотентно; старые проектные каталоги и собственные скиллы не получают автоматических одобрений. Просмотренные файлы не попадают в аудит: там остаются идентификаторы, хэш и изменение статуса.

Начальные состояния: `pending/0`, `approved/1`, `revoked/2`, повторное одобрение — `approved/3`. Поэтому отзыв с последующим одобрением не возобновляет старую очередь. Новая установка может безопасно заменить ещё не полученное задание того же плана со старой ревизией; выполняющееся задание и состояние сверки не подменяются.

Повтор неуспешной установки сохраняет исходный план, ревизию и SHA. Удаление и повторное создание пути скилла больше не подменяет код при retry. Поколение публикации скилла входит в новый манифест. Снимок одобренной версии остаётся самостоятельным объектом: удаление карточки не заменяет явный отзыв разрешения. Удаление проекта удаляет его планы по внешнему ключу.

Отзыв останавливает ожидающие и ещё не авторизованные действия. Уже начавшаяся локальная файловая транзакция завершается или откатывается по журналу. Отзыв не удаляет установленные файлы и не запрещает их безопасное удаление по прежней квитанции.

## Дополнительные исправления

- Все новые пакеты используют формат 4 с канонизацией без зависимости от языка ОС. Старые форматы 2/3 остаются доступными для проверки и удаления прежних установок. Это закрывает также случай ASCII-путей с `I/i` на турецкой локали.
- Успех установки/удаления требует результата с исходными `projectId`, `assetId`, `version`, `manifest` и `bindingId`. Путь обновления прогресса больше не позволяет обойти атомарное подтверждение. Повреждённое описание пакета возвращает конфликт вместо 500.
- MCP 0.4.1 создаёт короткое временное имя в том же каталоге. Длинный допустимый UTF-8 путь ресурса больше не превращается в слишком длинный временный basename при атомарной записи.

## Границы этого этапа

Непустые `mcp/plugins` в требованиях скилла останавливают подготовку плана с понятной ошибкой. Без разрешённого графа зависимостей сервер не выдаёт частичную установку за готовый комплект. Локальная внешняя команда MCP без включённого Node-пакета также блокируется: команда `npx ...@latest` не закрепляет исполняемые байты. Поддерживаются включённый Node-пакет с точкой входа и одобренная конфигурация удалённого MCP. Удалённый URL закрепляет настройку подключения, а не код внешнего сервера.

Само копирование скилла не устанавливает зависимости его скриптов. Успешная запись файлов по-прежнему имеет `readiness: unverified`: загрузка OpenCode, OAuth, секреты, сторонние импорты и работоспособность инструментов проверяются следующим этапом.

Не завершены: полный закреплённый граф и общие зависимости, реальная инвентаризация и замена клона по тому же пути, общие версионированные миграции и rollback, внешние автоматические копии и оповещения, непривилегированные контейнеры, настоящие Blitz/сервер, Git/CI, остальные нативные платформы, нагрузка и суточный прогон. Откат на сервер до проверки одобрений не является допустимым production-rollback.
