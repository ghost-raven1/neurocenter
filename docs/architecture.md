# Архитектура и границы компонентов

## 1. Что означает образ

Образ — переносимый, согласованный снимок одной логической базы LanceDB проекта. Внутри базы может быть несколько таблиц. Снимок включает данные, манифесты, файлы удалений и необходимые индексы; это не только набор векторов и не Docker-образ.

Lance версионирует таблицы, а их манифесты ссылаются на физические файлы снимка. Поэтому нельзя считать обычное копирование активно изменяемого каталога гарантированно согласованным экспортом. Общую точку фиксации нескольких таблиц обеспечивает наш локальный клиент: останавливает управляемые записи и фоновые перестроения, фиксирует версии таблиц и делает согласованную копию. [Формат Lance](https://docs.lancedb.com/lance), [версии LanceDB](https://docs.lancedb.com/tables/versioning).

## 2. Компоненты

| Компонент | Ответственность | Хранит |
| --- | --- | --- |
| OpenCode | Вызывает MCP-инструменты; работает с установленными скиллами | Конфигурацию проекта, разрешения вызовов инструментов |
| Локальный MCP и агент передачи | Локальный поиск, экспорт, докачка, проверка хешей, установка, обращение к API | Локальную LanceDB, состояние операций, идентификаторы установленных версий |
| API / Catalog Service, NestJS + TS | OAuth resource server, каталог, политики, квоты, управление публикацией, API админки | Метаданные через PostgreSQL |
| Artifact Worker | Проверка снимков и Markdown, хеширование, продвижение объектов, очистка, индексирование каталога | Ограниченный временный каталог и кэш |
| PostgreSQL + pgvector | Метаданные, текущие версии, задания, аудит, outbox, поиск по разрешённому каталогу | Реляционные данные, небольшие JSONB-описания и embeddings |
| MinIO / S3 | Передача и долговечное хранение бинарных объектов | Чанки снимков, манифесты, версии скиллов, staging |
| OAuth/OIDC-провайдер | Вход, выпуск и отзыв токенов | Учётные записи и OAuth-сессии |
| Внешний сервис прав | Решения по субъекту, действию и ресурсу | Роли и разрешения; источник истины для ACL |
| Панель администратора | Каталог проектов, версии, задания, квоты, аудит и восстановление | Только клиентское состояние; бизнес-данные — в API |

На старте достаточно двух независимо масштабируемых серверных приложений: API и Worker. В API модули разделяются по фичам: identity, authorization, projects, images, skills, transfers, admin, audit. Отдельный микросервис на каждую сущность не нужен.

Worker имеет свои очереди и лимиты для проверки больших баз и небольших скиллов. Ошибка или тяжёлая проверка LanceDB не блокирует HTTP API. Библиотека LanceDB запускается в выделенном процессе проверки с read-only доступом к снимку, без сети и пользовательских скриптов, с лимитами CPU, RAM и времени; язык адаптера выбирается по проверенному SDK, с фиксированными версиями.

## 3. Пути данных

**Управление:** OpenCode → локальный MCP → HTTPS API → PostgreSQL / сервис прав. В ответах передаются идентификаторы, статусы, размеры и описания.

**Файлы:** локальный агент → HTTPS S3 endpoint → MinIO. API выдаёт краткоживущие разрешения на конкретные операции и объекты. Закрытые S3 credentials остаются на сервере.

**Локальный поиск:** OpenCode → локальный MCP → локальная LanceDB. Запросы по содержимому локальной базы не создают серверную vector-search нагрузку.

**Поиск каталога:** MCP или админка → API → PostgreSQL/pgvector. Поиск идёт по разрешённым скиллам, названиям, описаниям и тегам образов. Полное дублирование LanceDB в pgvector в эту архитектуру не входит.

## 4. Модель версий

- На проект приходится один image store и одна текущая версия `head`; историю сохраняют отдельные immutable snapshot versions.
- Версия имеет UUID, родительскую версию, время, автора, размеры, хеш манифеста и совместимость SDK/формата.
- Чанки адресуются SHA-256. Дедупликация ограничена одним проектом; между проектами нет проверки наличия чужих хешей.
- Манифест описывает относительные пути, размеры файлов, порядок чанков, хеш каждого файла и закреплённые версии всех Lance-таблиц.
- Подпись манифеста покрывает его каноническое представление. Ключ подписи сервиса хранится в KMS/secret manager; клиент знает допустимые публичные ключи.
- Проектный release profile закрепляет snapshot ID и список точных версий скиллов. Он позволяет воспроизвести комплект даже после обновления общего каталога. У проекта есть `active_profile_id` и монотонная `profile_revision`.
- Перемещение `head` требует пары `expectedHeadId + expectedHeadRevision` и выполняется одной транзакцией PostgreSQL. Даже rollback увеличивает revision: возврат к прежнему ID не делает устаревший запрос актуальным.
- Rollback выбирает уже проверенную версию и создаёт аудируемое событие перемещения `head`; старые объекты не переписываются.

Рабочая нагрузка возникает после релиза: один издатель готовит новый образ, сервер проверяет его один раз, затем участники проекта скачивают недостающие данные и обновлённые скиллы. Для общего релиза атомарно меняются `head` и активный профиль с точными версиями. Клиент закрепляет один profile ID на всю установку. Отдельная активация образа или обновление общего скилла не меняют уже выпущенный профиль; API явно показывает различие между head и образом закреплённого релиза.

LanceDB сохраняет изменённые данные по версиям, но индексирование и compaction тоже меняют версии. Экономия нашей доставки зависит от реально сохранившихся одинаковых файлов/чанков; это не гарантированный процент сжатия. [Версионирование LanceDB](https://docs.lancedb.com/tables/versioning).

## 5. Физическая организация MinIO

Используются отдельные приватные buckets с отдельными политиками доступа.

| Bucket / префикс | Содержимое и правило |
| --- | --- |
| `image-blobs/projects/<projectId>/<sha256>` | Неизменяемые проверенные чанки; записывает только Worker |
| `image-manifests/projects/<projectId>/<snapshotId>` | Подписанный полный манифест снимка |
| `skill-blobs/collections/<collectionId>/<sha256>` | Точный UTF-8 Markdown и связанные метаданные версии |
| `staging/uploads/<uploadId>/...` | Временные загрузки; versioning обязателен для фиксации проверяемого object version |
| Отдельное backup-хранилище | Независимая копия объектов и PostgreSQL; не та же группа дисков |

Текущая версия не определяется по имени `latest` в S3. Источник истины — транзакционная ссылка в PostgreSQL. Object versioning staging решает гонку повторного PUT, а версии образов — прикладная модель; это разные механизмы.

Транспортный размер чанка — до 64 МиБ. Большие файлы делятся, маленькие сохраняются без дополнения до 64 МиБ. Манифест восстанавливает исходное дерево Lance. Чанки — транспортный формат нашего сервиса, а не изменение Lance.

Не хранить постоянно второй полный архив каждой версии. Если нужен единый архив для ручного скачивания, формировать его отдельным заданием по запросу, с TTL и отдельной квотой; его объём и трафик добавляются к расчёту.

## 6. Локальное хранение и установка

Для каждого проекта клиент разделяет проверенные версии, временную загрузку, текущую ссылку и рабочую копию издателя.

| Область | Назначение |
| --- | --- |
| `versions/<snapshotId>/` | Проверенный каталог LanceDB; обычный режим — только чтение |
| `staging/<operationId>/` | Незавершённые загрузки с журналом успешно проверенных чанков |
| `CURRENT` | Маленький файл с ID текущей версии; заменяется атомарно в пределах одного filesystem |
| `workspace/` | Отдельная изменяемая копия для пользователя с правом публикации |
| `release-lock` | Установленный snapshot, версии скиллов, хеши, формат и версия клиента |

Новая версия скачивается в staging, проверяется и открывается LanceDB SDK. Затем staging переводится в каталог версий и атомарно меняется `CURRENT`. MCP закрывает или переключает свои подключения; старые читатели остаются на закреплённой версии до завершения. Изменять открытый каталог «на месте» запрещено клиентским протоколом.

Hardlink допустим между неизменяемыми кэшами. Изменяемая `workspace` использует filesystem clone/reflink с Copy-on-Write или полную копию; writable hardlink к проверенному снимку недопустим.

Бюджет локального диска: старый снимок + новый материализованный снимок + недостающие транспортные чанки + отдельная workspace издателя. Освобождение чанков по мере сборки, hardlink неизменённых файлов и Copy-on-Write могут снизить расход, но не входят в гарантированный бюджет. Проверка свободного места учитывает выбранный способ сборки и фактические размеры.

Ручные записи сторонних процессов в исходную LanceDB не контролируются MCP. Если издатель не может остановить таких писателей, он должен предоставить отдельно подготовленный согласованный экспорт; копирование живого каталога не публикуется как проверенный снимок.

## 7. Общие и проектные скиллы

Общий каталог — общая **авторизованная** коллекция, а не публичный bucket. Проектная коллекция привязана к одному проекту. Обе содержат свои скиллы и immutable версии.

Markdown хранится в S3 целиком. PostgreSQL содержит slug, описание, владельца, статус, текущую версию и ссылки; pgvector — embeddings фрагментов. Идентификатор модели embeddings и размерность сохраняются вместе с индексом. Историю Markdown не нужно целиком индексировать: по умолчанию индексируются только актуальные разрешённые версии.

Общий скилл можно закрепить в профиле проекта без копирования всего каталога. Проектная версия с тем же slug становится override только после явного выбора в профиле. При конфликте имён клиент не полагается на неявный порядок обнаружения OpenCode.

«Скачать» сохраняет Markdown в выбранный каталог и не обязано включать его в работу агента. «Установить» материализует согласованный набор в проектные `.opencode/skills/<slug>/SKILL.md`. Даже общий скилл по умолчанию устанавливается в конкретный проект; установка в глобальный профиль пользователя — отдельное явное действие. OpenCode ожидает YAML frontmatter с `name` и `description`, причём имя совпадает с каталогом. [Официальный формат Agent Skills](https://opencode.ai/docs/skills/).

Файлы пользователя без записи в release-lock автоматически не перезаписываются. При локальных изменениях установка возвращает конфликт. Публикация проверяет UTF-8, frontmatter, slug, размер и разрешённые относительные ссылки. Загрузка скилла не запускает его скрипты и не выдаёт ему серверные полномочия.

## 8. Интерфейсы и события

Локальный MCP — обязательная часть: удалённый сервер не имеет доступа к файловой системе пользователя. Он выполняет передачу через API и остаётся единственным ответственным за локальную установку.

Удалённый MCP поверх Streamable HTTP можно добавить как адаптер в API для иных MCP-клиентов. Он возвращает каталог и управляет серверными заданиями; для скачивания на пользовательский диск всё равно нужен локальный агент. Его OAuth-клиент не передаёт токены автоматически локальному stdio-серверу. [Локальные и удалённые MCP в OpenCode](https://opencode.ai/docs/mcp-servers/).

Начальная очередь — долговечные задания в PostgreSQL с lease, fencing token и захватом через `SKIP LOCKED`. Outbox записывается в той же транзакции, что и публикация. Это позволяет отправлять события и повторять задания после сбоя без обязательного Redis или брокера на старте.

Socket.io служит уведомлениям админки о прогрессе и смене версии. Истина — задания и каталог в PostgreSQL; при потере соединения клиент перечитывает состояние. Для двух API-реплик нужен реальный межрепличный adapter: начальный вариант — `@socket.io/postgres-adapter`. При сохранении HTTP long-polling балансировщик обеспечивает cookie session affinity; WebSocket-only режим может обходиться без неё, но лишается fallback. Авторизованные rooms не дают доступа к чужим операциям. [Несколько узлов Socket.IO](https://socket.io/docs/v4/using-multiple-nodes/), [Postgres adapter](https://socket.io/docs/v4/postgres-adapter/).

Adapter и слушатель outbox имеют отдельные постоянные подключения к PostgreSQL напрямую или через session pool. `LISTEN` нельзя вести через PgBouncer transaction pooling. NOTIFY лишь будит обработчик; пропущенные события восстанавливаются из outbox и каталога. Замена adapter на Redis возможна при измеренной необходимости. [Режимы PgBouncer](https://www.pgbouncer.org/features.html).

Каталог MCP-пакетов и плагинов предусмотрен как отдельное расширение того же хранения и доставки; его границы описаны в [extensions.md](extensions.md).
