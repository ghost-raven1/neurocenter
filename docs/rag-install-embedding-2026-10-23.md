# OpenCodeRAG: установка, подключение и индекс — 23 октября 2026

На фото готова удалённая embedding-модель `qwen3-embedding-4b`, размерность 2560, но добавление в проект заблокировано сообщением «Выберите проверенную установку OpenCodeRAG». Это сообщение относится к установке на выбранном компьютере, а не к проверке API модели. Точный отказ установки на рабочем Linux пока не получен; локальные проверки ниже не заменяют его диагностику.

## Исправленные переходы

1. После успешного `install` сервер атомарно ставит `inspect-installation` для поддерживаемого OpenCodeRAG. Ранее установка возвращала `unverified`, а отдельная сверка сама не запускалась: список допустимых установок оставался пустым. Для комплекта MCP/плагин проверки идут последовательно; одновременно активен один дочерний запрос. Повтор ACK не создаёт дубль. Отмена проверки останавливает продолжение; завершённый неуспешный результат оставляет понятную ошибку и позволяет проверить следующий пакет комплекта.
2. Сверка закреплена за исходными владельцем, ролью, проектом, устройством, binding/instance и точными байтами пакета. Права и возможности моста проверяются при получении и перед чтением файлов. Отключение бизнес-функции сохраняет разрешённую сверку уже принятой установки. Сервер не запускает модель или индексацию без пользовательского подтверждения.
3. Интерфейс различает отсутствующие компьютер, подходящий мост, привязку папки и установку; предлагает следующее действие. Пока точная установка сверяется, показывает ожидание и переход к ходу проверки, без предложения переустановки. Устаревший выбранный пакет сохраняется как недоступный, а другую проверенную установку можно выбрать даже при единственном оставшемся варианте. Неявной подмены компьютера или пакета нет. Режим серверной базы явно объясняет, что он не индексирует файлы на компьютере.
4. Явное перестроение кандидата больше не читает разрешение от прежней версии пакета до применения нового профиля. При обновлении прежний grant был корректно недействителен, но эта проверка обрывала подготовку нового индекса. В `pack.10` кандидат получает строго проверенные alias модели, размерность и приватное loopback-подключение в памяти. Обычный запуск MCP/плагина сохраняет прежние строгие проверки grant. Прежний индекс и приватный профиль сохраняются до проверенного переключения.

Runtime находится в приватном кэше моста, а связанная папка содержит подключение в `opencode.json`. Проверять установку следует по точному подключению, исполняемому файлу, installation receipt и результату сверки. Исходники плагина не обязаны копироваться в проект.

## Проверки

- Причинный серверный RED: реальное завершение установки в собственном PostgreSQL сохраняло `succeeded`, но не создавало дочернюю сверку. Исправленный код создаёт ровно одну. Новые 6 unit и 12 PostgreSQL-проверок прошли без пропусков; отдельно 334 связанных регрессии в 18 файлах и TypeScript прошли. Проверены потерянный COMMIT ACK, rollback дочерней записи/журнала, повтор и конкуренция ACK, свежие права/привязка/instance, отмена и предел 100 активных заданий.
- Frontend: целевые 55 проверок входят в окончательный полный прогон 3828/3828 в 302 файлах; пропусков нет, TypeScript прошёл. Причинные RED воспроизвели отсутствие действия восстановления, недоступный выбор единственной альтернативы и ложное предложение установки во время сверки. Ранний браузерный срез подтвердил 14 утверждений в четырёх цепочках настоящих компонентов React/Ant Design при подменённых данных bridge/auth/hosting/socket. Переполнение пустого состояния на 390 px найдено и исправлено; это fixture-приёмка UI, а не браузерный проход работающей площадки.
- Причинный native RED воспроизвёл отказ кандидата после обновления при старом grant. Исправленный адаптер выполнил 10 проверок с настоящей LanceDB и локальным тестовым embedding API, включая 2560 измерений; 19 HTTP-вызовов ушли только в этот fixture. Старые данные размерности 3 и приватный профиль сохранились. Отдельно прошли 115 Node-тестов без пропусков.
- Собраны MCP `2.4.4-mcp.pack.10` и плагин `2.4.4-plugin.pack.10` для `darwin-arm64` и `linux-x64-glibc`. Все четыре архива прошли общую проверку manifest, исходников, состава и SHA. Оба Mac-архива установлены настоящим TS-кодом моста в отдельные папки, без HTTP: `inspect-installation` вернул `checked/synced`, ручные provider/agent/MCP/plugin-настройки сохранены, точные launcher/file URL и runtime-файлы подтверждены.

Локальные протоколы находятся в `.run/rag-install-inspection-20261023/`, `.run/rag-install-embedding-20261023/` и `.run/rag-install-embedding-flow-20261023/`. Эти файлы не входят в Git. Проверка файлов не подтверждает запуск в OpenCode или готовность индекса. Linux-исполнение, реальный API рабочей модели и применение на рабочей площадке не проверены.

## Доставка исправленных пакетов

Изменения рецептов сами по себе не обновляют установленные карточки. Обычный `dev.sh up` сохраняет каталог, а prefetch читает закреплённый `services/shared/asset-source.lock.json`. `dev.sh install` обновляет поставку моста. Существующий доверенный источник не переключается на локальные recipe-архивы автоматически.

Для воспроизводимой подготовки нужных платформ:

```sh
node scripts/catalog-plugins/prepare.mjs \
  --output .run/rag-pack10 \
  --only opencode-rag,opencode-rag-plugin \
  --targets darwin-arm64,linux-x64-glibc
```

После запуска площадки оператор может проверить и импортировать каждый подготовленный `assets/<id>/<build-sha>/asset.json` штатным издателем:

```sh
node scripts/catalog-plugins/publish.mjs \
  --asset /absolute/path/to/asset.json \
  --base-url http://localhost:5173 \
  --dry-run
```

`--dry-run` проверяет метаданные без сети и публикации. Для фактического импорта используют тот же файл и адрес работающей площадки без `--dry-run`; при требовании входа передают `--cookie-file` с приватным файлом сессии главного администратора. Ключи и cookies не помещают в историю shell.

Этот импорт создаёт отдельную карточку публикации и не обновляет прежнюю карточку pack.9 или её назначения. После импорта нужно явно выбрать новую карточку в проекте, одобрить план её установки и дождаться автоматической сверки. Обновление существующей карточки — отдельный поддержанный сценарий публикации сборки с выбранной целью в UI. Новый произвольный архив не станет доверенным для импорта из «Ассетов» только потому, что он собран локально: публичная поставка требует отдельной публикации источника и обновления доверенного pin.

В этом срезе выполнен только dry-run обеих карточек. Живой каталог, установленный пользовательский мост, PostgreSQL площадки, S3 и пользовательские папки не менялись.

## Пользовательский путь

Связать папку → установить OpenCodeRAG → дождаться сверки файлов → выбрать проверенную установку и модель → подтвердить перестроение → дождаться проверенного индекса и синхронизации → перезапустить открытую сессию OpenCode. Для старой установки сверку можно запустить действием «Проверить файлы» в блоке «На этом компьютере». Пошаговая инструкция доступна в Markdown-статье [«Модели»](../services/catalog-service/content/help/models.md).
