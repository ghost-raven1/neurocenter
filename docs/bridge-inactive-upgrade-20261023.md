# Обновление моста с недействующим подключением — 23 октября

Исправление от 23 октября 2026 года для цепочки 3 стабильного MVP. Установка моста могла останавливаться на `--prepare-upgrade` с сообщением «MCP не подключён или доступ отозван», а последующее снятие паузы повторяло тот же отказ.

## Поведение

- Если прежний worker отсутствует или его PID уже завершился, установщик пропускает подготовительный запрос к API. Перед публикацией он повторно проверяет снимок блокировки, чтобы не заменить файлы появившегося worker.
- Сохранённый ключ разрешает только паузу и возобновление собственной очереди, даже после отзыва подключения, истечения срока или потери роли. Gateway сохраняет Bearer и внутреннюю авторизацию; Catalog проверяет текущий хеш ключа под блокировкой строки до COMMIT. Роль, срок, отзыв и ключ не изменяются. Остальные команды сохраняют обычную авторизацию.
- Пауза сериализована с выдачей заданий и сменой ключа. Учитываются `running`, `reconciling` и ошибки с неподтверждённым завершением после отзыва. Непустой промежуточный `result` не считается завершением.
- Живой процесс останавливается только после подтверждённой пустой очереди и проверки владельца ОС и установленного entry. При активном или неподтверждённом задании прежние файлы и процесс сохраняются. Потерянный ответ о паузе требует компенсации, а не разрешения замены.
- `dev.sh install` не вызывает `finish-upgrade` после подтверждённого `paused:false`. Подтверждённая пауза и неизвестный ответ сохраняют прежнее завершение и компенсацию.

Это восстановление существующего подключения: отдельный флаг не добавлен. Выключение `computer_connections` продолжает запрещать создание новой пары, сохраняя восстановительные pause/resume. Это проверено Gateway HTTP-тестами; отдельной native-матрицы переключения флагов нет.

Для применения нужно обновить код и перезапустить API Gateway и Catalog на площадке, затем повторить установку через `/start`. Протокол совместим с CLI 0.9.18. Проверка связности API, которая нужна для подтверждения нового подключения, остаётся частью подключения.

## Открытая приёмка

Native worker здесь — собственный idle-процесс, а connect ACK управляется фикстурой. Реальные рабочие задания, подтверждение в браузере, корпоративный Linux, Windows, CI и production этим не приняты. Пользовательский мост и основная БД не менялись. Собственная БД удалена, PostgreSQL и тестовые процессы завершены, порт закрыт.

Уже заменённый или отсутствующий серверный ключ не получает восстановительных прав. Для живого процесса с потерянной идентичностью и исторических неподтверждённых заданий нужен отдельный безопасный сценарий восстановления с доказательством завершения локальной работы. Этот остаток B01 не закрыт; автоматического обхода защиты активной записи нет.
