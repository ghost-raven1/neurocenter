# Каталог Нейроцентра: принятые решения

Решения Алексея от 16 октября 2026 года. Этот документ уточняет прежний проект хранилища образов: первый результат — каталог инструментов с установкой на компьютеры сотрудников. Состояние реализации и проверки фиксируется отдельно; описанный контракт не означает, что все его части уже готовы.

## Проекты и локальные пути

У серверного проекта постоянный ID. Название проекта — подпись для человека, а не имя каталога или базы данных.

На каждом компьютере локальный агент хранит свою привязку `serverUrl + projectId → localPath`. У двух сотрудников один проект может лежать в разных общих папках, иметь разные имена и разные пути. Перемещение папки меняет привязку этого устройства; серверный ID сохраняется. Git remote может подсказать соответствие, но не назначает его автоматически.

В интерфейсе пользователь один раз указывает общую папку с проектами, выбирает локальную папку и связывает её с разрешённым серверным проектом. Установку выполняет локальный агент. Backend не пишет на диск пользователя и не принимает его путь за путь на сервере. Браузер самостоятельно не имеет необходимого доступа к произвольным каталогам.

Локальная база знаний остаётся LanceDB. На сервере каждому проекту соответствует отдельная PostgreSQL-база знаний и отдельная история её резервных копий. Общая служебная PostgreSQL-база содержит пользователей, каталог, проектные назначения, версии, операции и аудит. Учётные данные PostgreSQL остаются на сервере.

Старый проект immutable LanceDB/S3-снимков из `architecture.md` и `sync-and-data.md` не является обязательным объёмом первого каталога. Его CAS, манифесты и протокол больших снимков нельзя выдавать за уже реализованные функции. Обычный `pg_dump` базы знаний также не является полным снимком локальной LanceDB с её индексами и служебными файлами.

## Пользователи и роли

Пользователи добавляются по нормализованной электронной почте. Добавление записи и отправка письма — разные операции; автоматическая почтовая рассылка на первом этапе не требуется. Для корпоративного входа почта берётся из доверенного SSO-профиля, а роли — из назначений Нейроцентра. Само наличие SSO-сессии не делает пользователя администратором.

| Роль | Область | Действия |
| --- | --- | --- |
| Наблюдатель | Назначенные проекты | Просмотр проектного каталога и разрешённых данных |
| Разработчик | Назначенные проекты | Работа с проектными материалами, установка разрешённых инструментов в локальную привязанную папку |
| Админ проекта | Только свои проекты | Выбор из общего каталога, управление составом проектного каталога и участниками, настройки проекта |
| Главный админ | Вся система | Пользователи, назначения администраторов, общий каталог, обслуживание и резервные копии |

Админ проекта назначает разработчиков и наблюдателей внутри своих проектов. Назначение другого администратора проекта и системного администратора оставлено главному админу. Если это правило потребуется изменить, оно меняется одновременно в API, интерфейсе и проверках.

Шапка показывает активную роль даже при единственном назначении. При нескольких доступных ролях появляется переключатель. Сервер проверяет, что роль действительно назначена; смена роли ограничивает права, не расширяя проектную область. Отсутствие участия в проекте означает отсутствие доступа, а не автоматическую роль наблюдателя.

Доступ проверяется для каждого действия, списка, скачивания, установки и прямого URL. Общий каталог доступен админам проектов для выбора инструментов. Остальные участники видят только проектный каталог. Нельзя получить чужие файлы, базу или историю, подставив другой ID.

## Как хранить и раздавать инструменты

Для локального запуска достаточно PostgreSQL и постоянного каталога `data/registry`. PostgreSQL хранит карточки и неизменяемые версии, привязки к проектам, варианты платформ, хеши и аудит. Файлы архивов хранятся на диске площадки по хешу. В дальнейшем файловый адаптер можно заменить MinIO/S3 без смены ID и контрактов.

Папка с архивами не публикуется целиком через nginx. API проверяет доступ к версии перед скачиванием. Служебные установочные архивы OpenCode и локального агента доступны в отдельном разделе площадки. Нативные бинарники разных ОС не смешиваются с пользовательским каталогом.

| Тип | Что публикуется | Как активируется локально |
| --- | --- | --- |
| Скилл | `SKILL.md` с `name`, `description` и ресурсами; архив при наличии нескольких файлов | `.opencode/skills/<slug>/SKILL.md` и ресурсы |
| Плагин OpenCode | Готовый JS/ESM, ресурсы и включённые зависимости | Проектная запись или загрузочный файл в `.opencode/plugins/`; вступает в силу после перезапуска |
| Локальный MCP | Готовый исполняемый пакет, entrypoint, ресурсы, runtime и зависимости | Команда stdio в проектной конфигурации OpenCode |
| Удалённый MCP | Профиль подключения, transport, адрес и схема авторизации | Подключение к отдельно работающему серверу; его секреты не входят в пакет |

Локальный MCP запускается на компьютере сотрудника. Это необходимо для доступа к проектным файлам и локальной LanceDB. Удалённый MCP подходит для общих серверных ресурсов, но не заменяет локальный агент. Загруженные пользователями MCP и плагины не запускаются внутри API каталога.

### Формат версии пакета

У версии есть постоянный ID, технический slug, понятное название и описание, вид, версия, автор, происхождение и совместимость. Манифест перечисляет файлы с UTF-8 или бинарным форматом, размерами и SHA-256, entrypoint, runtime и точные зависимости. Для нативного кода указываются ОС, архитектура и libc. Секретов, пользовательских путей и API-ключей в архиве нет.

Чистый JS-пакет может быть общим для нескольких систем после проверки. Пакеты с нативными модулями имеют отдельные варианты: macOS Intel/ARM, Linux x64/ARM и glibc/musl, Windows x64/ARM. WSL получает Linux-вариант. Копия `node_modules` с Mac не подходит для Linux или Windows.

### Публикация

1. Главный админ публикует исходники или подготовленный архив с манифестом.
2. Отдельный процесс сборки фиксирует зависимости и собирает нужные платформенные варианты. Сборка пользовательского кода не выполняется HTTP-обработчиком API.
3. Проверяются комплектность, пути, размер распаковки, хеши, запуск и совместимость. Версия после публикации не переписывается.
4. Админ проекта выбирает конкретную версию из общего каталога. Обновление общего инструмента не должно незаметно подменять выбранную проектом версию.

### Установка

1. Пользователь выбирает разрешённый инструмент своего проекта.
2. Сервер проверяет роль, проект, версию и устройство, выдаёт ограниченное разрешение на установку.
3. Агент скачивает готовый вариант с площадки и проверяет манифест, хеши, платформу и локальную привязку.
4. Файлы готовятся во временном каталоге. Изменённые пользователем или неуправляемые файлы не перезаписываются автоматически.
5. Агент активирует подготовленные файлы и аккуратно дополняет JSON/JSONC. Предыдущее состояние сохраняется для восстановления.
6. Интерфейс получает реальный результат. При ошибке нельзя показывать «Установлено».

Установка может занять время на скачивание. «В один клик» означает одно явное действие с понятным прогрессом и результатом. Она не означает скрытый запуск сборки или отсутствие проверки прав.

## Автономная установка

Пользовательские компьютеры скачивают всё с этой площадки: OpenCode, локальный агент, нужный runtime и варианты зависимостей. npm, GitHub и корпоративное зеркало могут использоваться при подготовке пакетов администратором, но не становятся обязательными источниками на компьютере сотрудника.

Основное имя установщика — `install_opencode.sh`; Windows PowerShell получает `install_opencode.ps1`. Bash-вариант поддерживает macOS, Linux/WSL и Git Bash. Версии и настройки берутся из подготовленного комплекта, действующие ключи и пользовательская конфигурация сохраняются.

Подготовка OpenCode на площадке:

```sh
node scripts/prepare-opencode.mjs
```

Скрипт сохраняет все 12 платформенных пакетов с SHA-256 в `bridge-dist/opencode`: восемь системных целей и дополнительные x64-сборки для процессоров с AVX2. В зеркале есть обычные и baseline-варианты macOS/Windows/Linux x64, включая Linux musl, а также ARM64 для macOS/Windows/Linux glibc и musl. Автоматические установщики и runtime probe выбирают baseline для x64, чтобы поддерживать процессоры без AVX2. Полная матрица и закреплённая версия находятся в `scripts/opencode-platforms.mjs` и соответствуют [платформенным зависимостям официального выпуска](https://registry.npmjs.org/opencode-ai/1.14.48).

Версия по умолчанию — 1.14.48; другая задаётся `OPENCODE_VERSION`. Источник администратора меняется через `OPENCODE_REGISTRY`. Повтор использует готовые архивы с корректной SHA-256; нативное выполнение других ОС эта подготовка не проверяет. Наличие установщика не означает наличие всех его архивов: отсутствие пакета даёт понятную ошибку.

Локальная проверка 19 октября 2026: подготовлены 12/12 настоящих архивов; каждый сверен с npm integrity (SHA-512), локальной SHA-256 и полями name/version/os/cpu внутри пакета. Повтор использовал кэш для всех 12. Нативная приёмка Linux и Windows остаётся отдельной проверкой.

## Очерёдность и приёмка

1. RBAC и пользователи: только назначенные роли; отсутствие доступа к чужому проекту через API и прямые URL; отзыв доступа без повторного входа.
2. Локальный агент и привязки: один серверный ID работает с разными папками у разных пользователей; установка действительно меняет локальную папку.
3. Версии и доставка: проект закрепляет версии; готовые пакеты устанавливаются без внешних registry; сохранность пользовательской конфигурации проверена.
4. Отдельные PostgreSQL-базы и бэкапы: изоляция данных проектов, независимый дамп и проверка восстановления на отдельной БД.
5. Завершение интерфейса: все страницы, роли, пустые состояния, ошибки, клавиатура и мобильная ширина проверяются в браузере.

Ни отдельный успешный typecheck, ни доступный HTTP health не подтверждают весь пользовательский сценарий. Нативные платформы, реальный SSO, установка на другой компьютер и восстановление резервной копии проверяются отдельно.

## Текущее состояние до завершения локального агента

- Назначения пользователей по почте, выбор назначенной активной роли, проектные ограничения списков/API и защита внутренних сервисов реализованы. Прямое обращение к внутреннему API и выбор неназначенной роли проверены отказом 403.
- Полный комплект из 12 пакетов OpenCode 1.14.48 подготовлен на площадке для восьми системных целей, включая обычные и baseline-варианты x64. Bash-сценарии установки проверены изолированными тестами; наличие Windows-архива и PowerShell-скрипта не заменяет нативный тест Windows.
- Локальный агент, привязки пользовательских путей, закрепление архивных версий и автономная доставка всех зависимостей инструментов ещё требуют реализации. Старую запись файлов сервером нельзя считать выполнением этого сценария.
