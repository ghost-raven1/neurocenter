# Обновление сервера и моста

Получение кода и артефактов: один раз `npm run assets:init`, затем `git pull` с автоматической предзагрузкой либо `npm run update` с обязательной проверкой результата и ненулевым кодом при отказе. Предзагрузка проверяет описи/SHA моста, инструментов и моделей; БД и теги runtime не меняются. Hook не может отменить уже выполненный merge. [Подготовка и публикация поставки](../README.md#обновление-через-git-вместе-с-моделями-и-инструментами).

Ассеты импортируются отдельно от развёртывания. Обновление сохраняет карточки, версии и назначения; оно не загружает веса и не переключает теги моделей. Доставку нового ассета главный администратор запускает в панели после выбора и проверки источника. [Единый формат и кэш](assets.md).

Процедура проверена модульными тестами и отдельной настоящей Docker-репетицией на синтетической копии. Это не свидетельство промышленного обновления: копия рабочего набора, независимый restore на другом хосте и нативные клиентские платформы остаются условиями допуска. Модульные проверки используют подставленные адаптеры; production-update-stack.mjs запускает только собственные изолированные стеки.

С добавлением `feature-flags-service` текущий набор содержит семь приложений. Обычный update требует одинаковую топологию и полный набор точных образов; план прежнего стека из шести приложений будет отклонён до паузы. Для перехода сохраните согласованную копию и точный прежний checkout/образы, отрепетируйте отдельный переход топологии на копии данных, затем переключайте трафик после проверки. Старые комплекты восстанавливаются прежним инструментом и его точными образами. Автоматический переход 6 → 7 этим изменением не принят.

## Сервер: подготовка

Для работы нужен Node.js 24, доступ оператора к Docker, закрытый production-каталог с правами 700 и его исходные секреты. Образы нового и прежнего выпусков должны уже находиться на хосте. Обновление PostgreSQL, изменение секретов, доменов, томов и параметров этим оркестратором отклоняются.

Используйте отдельное окно обслуживания: завершите задания MCP, остановите внешние записи в PostgreSQL и не запускайте одновременно configure/up, ротацию секретов или ручные Docker-команды. Общая daemon-блокировка защищает штатные setup/backup/restore/update. Произвольная команда оператора может обойти её.

Перед production проведите репетицию на новом Compose-проекте из согласованной копии. Проверьте сохранение настроек, повтор команды, сбой миграции и восстановление исходного комплекта в ещё один новый проект. Сохраните машинные журналы, версии, точные image ID, время и результат. Нельзя создавать успешную квитанцию по одному unit-прогону.

План JSON имеет формат:

~~~json
{
  "format": "neurocenter-update-v1",
  "id": "release-20261018",
  "sourceRelease": "old-release",
  "targetRelease": "new-release",
  "sourceImages": {
    "frontend": "sha256:<64 hex>",
    "api-gateway": "sha256:<64 hex>",
    "oauth2-bridge": "sha256:<64 hex>",
    "rag-sync-service": "sha256:<64 hex>",
    "skills-service": "sha256:<64 hex>",
    "catalog-service": "sha256:<64 hex>",
    "feature-flags-service": "sha256:<64 hex>"
  },
  "targetImages": {
    "frontend": "sha256:<64 hex>",
    "api-gateway": "sha256:<64 hex>",
    "oauth2-bridge": "sha256:<64 hex>",
    "rag-sync-service": "sha256:<64 hex>",
    "skills-service": "sha256:<64 hex>",
    "catalog-service": "sha256:<64 hex>",
    "feature-flags-service": "sha256:<64 hex>"
  },
  "postgresImage": "sha256:<64 hex>",
  "catalogMigrations": [
    {"version": 0, "name": "catalog-complete-baseline", "checksum": "<SHA256 SQL>"}
  ],
  "migrationCompatibility": "restore-required",
  "rollback": "restore-new-project",
  "rehearsalSha256": "<SHA256 файла успешной репетиции>",
  "maxPauseMs": 900000
}
~~~

Все значения из примера заменяются фактическими. Неизвестная совместимость не допускается. Для совместимого изменения укажите reviewed-значение backward-compatible; оба варианта используют восстановление согласованного комплекта для возврата. Полный массив `catalogMigrations` берётся командой `node /app/dist/database/migrate.cli.js manifest` из точного нового каталожного образа: сейчас это версии **0–6**, а не одна строка из примера. Preflight сверяет массив с образом. История должна быть точным префиксом; отдельно разрешено принятие прежнего непрерывного префикса 1–5 без baseline 0, с сохранением старых SHA и времени применения. Физическая схема проверяется CLI соответствующих сервисов; семантику преобразований и восстановление подтверждает репетиция.

После выпуска SQL baseline 0 и принятия схемы 6, включая импортируемые SQL-модули и структурный контракт, неизменяемы так же, как исторические 1–5. Следующее изменение требует новой миграции и нового контракта проверки; редактировать прежние определения для обхода несовпадения SHA нельзя.

Файл репетиции содержит format=neurocenter-update-rehearsal-v1, те же sourceImages/targetImages/postgresImage и булевы passed, copyOfData, settingsPreserved, repeatSafe, restoreVerified. Все пять признаков должны стать true только после соответствующих проверок. Его SHA256 хранится в плане. План и отчёт — обычные отдельные файлы 600 в приватном каталоге.

## Проверка и запуск

~~~bash
node scripts/production/update.mjs preflight \
  --directory /private/neurocenter-production \
  --project-name neurocenter-production \
  --plan /private/release-plan.json \
  --rehearsal /private/rehearsal.json

node scripts/production/update.mjs apply \
  --directory /private/neurocenter-production \
  --project-name neurocenter-production \
  --plan /private/release-plan.json \
  --rehearsal /private/rehearsal.json \
  --backup-destination /private/backups/before-release-20261018
~~~

Для операторских Compose-дополнений передавайте --compose-file /absolute/override.yml; повторять параметр разрешено. Каталог предварительной копии новый, его родитель существует и имеет права 700. Место для копии проверяется отдельно. Локальная предварительная копия не становится внешней.

Preflight проверяет имена выпусков, точные локальные образы, здоровые исходные контейнеры, неизменность Compose-настроек и историю миграций. Для описи запускаются временные контейнеры точных образов без сети и секретов; для `check` — временные контейнеры каталога, флагов и RAG с read-only root filesystem и read-only транзакциями БД. Приложения не запускаются, DDL и копирование данных не выполняются. История каталога также читается штатным nc_owner через docker exec/psql.

Для ключей удалённых моделей preflight также сопоставляет несекретную identity `model_credential_key` с keyId сохранённых подключений. Секреты и ciphertext не читаются. Если новый ключ ещё не настроен и в каталоге нет зашифрованных credentials, `apply` первично создаёт закрытый постоянный ключ до паузы. При утрате или несовпадении требуется исходный ключ из независимой копии конфигурации; автоматической ротации нет. Identity фиксируется в квитанции и повторно проверяется после копирования и при повторе успешного обновления.

Apply повторяет preflight под общей блокировкой, приостанавливает приложения, делает согласованный резервный комплект и проверяет SHA-256 всех файлов копии. Затем последовательно выполняет `migrate` точными образами catalog-service → feature-flags-service → rag-sync-service и требует ready-квитанции до запуска приложений. CLI RAG обрабатывает базовую БД; проектные БД мигрируются перед доступом, без перебора и неявного присвоения маркеров сохранённым БД. Приложения запускаются с заранее проверенными image ID через приватное Compose-дополнение; сборка и pull во время apply запрещены. После readiness меняется только `NEUROCENTER_RELEASE` существующего `.env`, исходный файл сохраняется отдельно. Capacity-collector при его наличии обновляется тем же catalog-service image ID. Каталог ассетов и runtime моделей эта процедура не заполняет.

Карточки, provenance, версии и назначения входят в дамп каталога. Blob-кэш и веса нужно резервировать отдельно либо обеспечить доступ к точным файлам источника по SHA. До обновления сохраните пользовательские и частные веса, которые нельзя воспроизвести из публичного источника. Проверка readiness сервисов не заменяет inference и проверку индексов проектов.

Квитанции в <production>/updates/<id>.json сохраняют фазы, точный план, SHA/путь копии, исходный env-хэш и несекретную identity ключа моделей. Рядом сохраняются <id>.env.before и <id>.compose.json. Успешный повтор того же плана только проверяет результат; копия и миграции повторно не запускаются. Изменённый план с тем же ID и незавершённая операция требуют разбирательства. Не удаляйте квитанцию, чтобы заставить команду повториться.

maxPauseMs включает остановку приложений, копию, SHA-проверку и запуск нового выпуска. Выборочный импорт ассетов и установка моделей выполняются отдельно; обновление не скачивает и не активирует их автоматически. При исчерпании бюджета новые этапы не начинают; команды ограничены оставшимся временем. Перед возвратом ошибки команда дожидается завершения/удаления файлового помощника и очистки partial-каталога. На обычном backup исходные приложения возвращаются в finally. Очистка и безопасный запуск после ошибки могут выйти за бюджет; это не гарантия времени восстановления при отказе Docker/ОС.

Файловый помощник резервного копирования получает собственное имя и метку. Таймаут Docker CLI сопровождается остановкой и удалением именно своего контейнера до возврата ошибки. Если Docker не подтверждает очистку, общая блокировка обслуживания сохраняется; сначала проверьте названный контейнер и завершение его работы. Освобождать блокировку при неизвестном состоянии писателя нельзя.

## Ошибка и восстановление

Если ошибка возникла до передачи управления обновлению, backup возвращает исходные приложения. Если запуск нового выпуска уже начался, оркестратор останавливает приложения и оставляет PostgreSQL и согласованную копию. При stopFailed в квитанции оператор должен проверить фактическое состояние контейнеров. Образы прежней версии автоматически не запускаются на изменённых данных.

Восстановите комплект в новый проект с исходными образами и исходной конфигурацией. Подготовьте отдельный каталог восстановления с сохранённым .env.before, прежними секретами и TLS. Имя целевого проекта и тома новые. Старый повреждённый проект сохраняется для диагностики.

~~~bash
node scripts/production/recovery.mjs verify \
  --source /private/backups/before-release-20261018 \
  --expect-sha256 <sha256-из-квитанции>

node scripts/production/recovery.mjs restore \
  --directory /private/neurocenter-restored \
  --project-name neurocenter-restored-20261018 \
  --source /private/backups/before-release-20261018 \
  --expect-sha256 <sha256-из-квитанции>
~~~

Restore требует те же семь image ID и образ PostgreSQL, что были при копировании, и отказывает для существующих контейнеров/томов. Приложения после restore остановлены. После проверки восстановленных данных разрешите запуск по [инструкции восстановления](production-recovery.md), проверьте реальный Blitz, роли, MCP и настройки, затем переключайте трафик. Повреждённый проект не удаляйте до принятия результата.

## Мост

Установщик обновляет только архив своей ОС/архитектуры/libc. До установки сохраните SHA256/metadata выбранного архива и приватную копию JSON/JSONC OpenCode, профиля подключения, привязок и локальных installation journal. Дождитесь окончания задач моста и закройте диагностику; проверьте завершение дочерних процессов. Эти файлы могут содержать секреты и остаются на компьютере пользователя.

Используйте установщик с доверенной HTTPS-площадки, показанный в разделе «Начало». Он проверяет SHA, встроенный Node и архитектуру, сохраняет прежнюю программу, запрещает downgrade и сохраняет регистрацию/подключение при повторе. После установки сопоставьте buildId, runtimeVersion, protocolVersion и archive SHA с принятым комплектом; проверьте папки, параметры, runtime и повтор подключения. Не включайте --reconnect без необходимости: обычный повтор сохраняет устройство.

Несовместимую прежнюю программу установщик автоматически не возвращает. После неудачи регистрации сохраняются отдельная прежняя версия и сообщение об ошибке; применяйте восстановление согласованной программы + локального профиля/конфига, проверенное на этой ОС. Одного копирования старого исполняемого файла недостаточно. Нельзя отключать Gatekeeper/SmartScreen/политику PowerShell ради приёмки. Подпись, нативная установка и завершение дочерних процессов для семи целей ещё не приняты; [матрица внешней приёмки](p0-external-acceptance.md).

Если Docker не подтверждает остановку файлового помощника, partial-каталог сохраняется: удалять его до проверки контейнера нельзя. Исходные приложения всё равно пытаются вернуть; такой случай требует оператора и не считается успешной копией.


## Локальная репетиция 18 октября 2026

Исторический сценарий `production-update-stack.mjs` прошёл **12/12** проверок: verify-20261018-v09-final → p0-20261018-final-6e31. Шесть исходных и целевых image ID сохранялись в локальном `.run/p0-20261018/update/update-stack.json`; этот артефакт отсутствует в текущем checkout. Последующее изменение final2 для показа nextRunAt в эту репетицию не входило. [Текущий harness](../scripts/test/production-update-stack.mjs) требует новой приёмки точных образов.

Сначала создан собственный source на прежних образах: синтетические проект/JSONB-плагин/права, настоящие RAG-строки через RagDb, политика обслуживания с ревизией 7, её аудит, Markdown, серверный файл, сохранённая копия и продуктовый runtime-архив. Его проверенный комплект восстановлен в новый manual-проект. Переключение на новые образы, повтор и рестарт catalog/RAG сохранили SHA всех публичных таблиц и файлов; runtime-архив заново прочитан продуктовым сервисом. Возврат проверен восстановлением исходного комплекта в ещё один новый проект с прежними образами. Только после этих действий создан SHA-отчёт успешной репетиции; production-gate не ослаблялся.

Затем неизменённый updateProduction обновил исходный синтетический source, создал собственную предварительную копию и изменил только метку релиза в .env. Повтор не создавал копии и не менял данные или историю миграций. Ошибочная SHA-квитанция отклонена настоящим preflight.

Измерения для **3 БД, 4 файловых томов, 7 файлов и 79 755 байт**: исходная копия с возвратом приложений 36,011 с; restore данных manual-проекта 26,682 с; смена образов на копии 33,773 с; обратный restore данных 15,525 с; полный оркестрированный update 34,890 с, включая предварительную копию 3,442 с. Это малый локальный стенд, не гарантия RTO рабочего объёма.

По историческому отчёту все три собственных проекта удалены вместе с их томами; глобальный prune не применялся. Реальные данные development/production не использовались. Настоящий Blitz и вход пользователя в этом сценарии не проверялись: realBlitz=false и authenticatedSmoke=false. Локальный `.run/p0-20261018/update/update-cleanup.json` в текущем checkout отсутствует.

Для повтора исторической репетиции ниже нужен checkout до добавления сервиса флагов (например, `e926d08`) и перечисленные прежние образы. Текущий harness требует семь приложений и новый прогон.

Повторить на хосте с уже собранными прежними и новыми образами:

~~~bash
NEUROCENTER_UPDATE_SOURCE_RELEASE=verify-20261018-v09-final \
NEUROCENTER_UPDATE_TARGET_RELEASE=p0-20261018-final-6e31 \
NEUROCENTER_TEST_EVIDENCE=.run/p0-20261018/update \
node scripts/test/production-update-stack.mjs
~~~

Harness не собирает и не скачивает образы, не использует исходные рабочие контейнеры/диски, не публикует порты и держит активным не более одного набора из семи приложений. Каждая проверка запускается на точных выбранных образах; новый tag требует отдельного прогона.
