# Системные агентные роли: ответственность и развитие

Пользователь уточнил: речь об агентных системных ролях. Документ предлагает поведение продукта; новые роли и полномочия им не включаются. Основание — текущий `main` `c7d05ee`, `system-role.definitions.ts`, `system-role.service.ts`, `system-role.targets.ts`, `system-role.apply.ts` и аудит связей модулей.

## Результат для пользователя

Пользователь описывает нужный результат, получает проверенное состояние и понятное следующее действие. Агент помогает довести действие до подтверждённого результата: выбранная модель ответила, пакет установлен, индекс пригоден к поиску, одобренное знание попало в нужный контекст. Сохранённая настройка, доставленные файлы и реально работающая возможность показываются отдельными фактами.

Системная роль — версионированный рабочий процесс. Она использует права текущего пользователя и не становится ролью доступа «Главный админ» или «Админ проекта». Сервер, локальный мост и доменные сервисы продолжают владеть своими операциями и данными.

## Что уже реализовано

Есть четыре определения: AI-админ, Автоконфигуратор, Индексатор, Упаковщик. Общий `SystemRoleService` хранит запуски, снимок контекста, точную модель/pin и результат. Он умеет диагностику и предложения; выбранные изменения применяют владельцы через CAS, с квитанцией и проверяемым откатом.

Контекст выбирается явно. Доступны типизированные безопасные измерения; приватный текст редактируемых настроек маскируется. Модель не имеет shell, произвольной сети, credentials или mutation tools. Упаковщик в этом интерфейсе сейчас консультирует; настоящий build/publish находится в `PackageBuildService`. Индексатор объясняет состояние, а sync/reindex/restore выполняются другими мастерами.

Существующий бюджет фиксирован: два вызова модели, четыре измерения, четыре цели, 64 КиБ контекста, 16 КиБ результата и две минуты. Второй вызов предназначен для исправления JSON, а не скрытого повтора неизвестного платного запроса. Эти пределы исполнения ещё не являются проектными квотами.

Главный продуктовый пробел: объяснение агента и исполнение мастером связаны слабо. Пользователю приходится переносить выбранные проект, модель, устройство и причину действия между экранами. Сначала стоит связать существующие четыре роли с действующими исполнителями, затем добавлять роли с отдельным результатом.

## Предлагаемый состав

| Роль | Полезный результат | Контекст по умолчанию | Действия через действующего владельца | Граница |
| --- | --- | --- | --- | --- |
| AI-администратор | Находит причину сбоя цепочки и доводит выбранное восстановление до повторной проверки | Готовность зависимостей, состояния операций, безопасная сводка своего устройства, pins/версии | Проверка подключения модели/моста; подготовка плана восстановления; передача точной задачи профильной роли | Не выдаёт liveness за готовность, не перезапускает всё по одной ошибке и не получает прямой Docker socket |
| Автоконфигуратор | Согласованная конфигурация проекта и агентов, которая реально применена к выбранной среде | Явно выбранные настройки, текущие версии, назначения и совместимость | Подготовить/сравнить конфигурацию; применить версию через Agents/Models/Skills; получить квитанцию доставки и отдельное испытание | Не меняет модель, права, зависимости и личные ключи через текстовый prompt |
| Упаковщик | Доверенный источник превращён в опубликованный, установленный и проверенный пакет | Закреплённый источник, рецепт, target, предыдущие версии, безопасный build report | `PackageBuildService` создаёт/отменяет build; каталог публикует; мост устанавливает; runtime probe проверяет конкретный target | Нельзя объявлять установку по build success или запускать непроверенный исходник произвольной командой |
| Индексатор | Актуальный проверенный индекс с совместимым embedding-профилем и полезным поиском | Профиль/dimension/model pin, source digest, scan completeness, generation, sync/reindex receipts | Подготовить sync/reindex/snapshot/restore; показать последствия замены; выполнить выбранный план через RAG/мост; проверить retrieval | Неполный scan не удаляет baseline; receipt уже совершённого COMMIT отличается от разрешения новой записи |
| Куратор знаний — новая роль | Подтверждённый опыт становится одобренным знанием и доставляется в нужные контексты | Выбранные reported experiences, quirks с provenance, версии гипотез/проверок, одобренный learning context | Предложить объединение дублей/проверку; после одобрения — learning overlay и управляемая Memory projection/cleanup | Не импортирует личный граф Memory целиком; не одобряет сам себя; не превращает уверенность quirk в доказательство |
| Контролёр качества — новая роль | Показывает, какие пользовательские цепочки доказаны и какие блокируют выпуск | Версия исходников, матрица модулей/связей, coverage denominator, структурированные отчёты проверок | Запросить разрешённый фиксированный профиль проверки; сопоставить артефакты; сформировать конкретный defect/release gate | Не исполняет команды из ответа модели; unit/build/HTTP/ОС/CI/production остаются разными свидетельствами |

Отдельный «диспетчер всего» пока не нужен: маршрутизацию по владельцу может выполнять AI-админ с явной передачей контекста. Отдельные «синхронизатор», «восстановитель» и «обучатель» сейчас дублировали бы Индексатор и Куратор знаний. Если появятся независимые операции и полномочия, их можно выделить по фактической необходимости.

## Общий контракт роли

Паспорт роли должен содержать стабильный ID, версию определения, понятное назначение, поддерживаемую область (площадка/проект/компьютер), доступные измерения, типы целей и разрешённые действия владельцев. Доступный context и действия вычисляет сервер с текущими ACL и флагами. Нельзя выдавать полномочия только по имени роли, prompt или списку tools от модели.

Разделяются три шага:

1. **Измерить.** Детерминированные bounded probes дают факт с источником, временем и областью. Отсутствие данных явно обозначается. Модель объясняет уже собранные факты и может предложить следующий разрешённый probe.
2. **Подготовить.** Доменный владелец создаёт план с точными ID/pins/revisions, последствиями, бюджетом, сроком действия и recovery path. Модель предлагает выбор и объяснение, но не конструирует доверенный grant.
3. **Применить и проверить.** Пользователь видит конкретное действие; исполнитель перепроверяет права/план, делает допустимую операцию, сохраняет durable receipt и проверяет полезный результат. Отмена, неопределённый исход и откат имеют собственные состояния.

Для сообщения «Почему Codex не работает?» AI-админ сначала проверяет цепочку аккаунт → доверенный connector → устройство/binding → импорт → назначение → ответ модели. Если отсутствует пакет, Упаковщик получает точный pinned source и target. После установки Автоконфигуратор выполняет подготовленный import/assignment, затем отдельный тест отвечает через тот же transport. Закрытие setup wizard не подтверждает работу модели.

## Передача между ролями и сервисами

Роль передаёт структурированное поручение существующему владельцу: `actionId`, actor, project scope, target IDs/pins, input digest, request key, expected revisions и deadline. Бизнес-операция не запускается через скопированный в чат URL или shell-команду. Дедлайн и отмена проходят через Gateway, сервис, очередь и мост; наблюдение результата не создаёт новое исполнение.

Для передачи другому агенту сохраняются родительский run, выбранные ссылки на контекст и ожидаемый тип результата. Получатель снова проверяет текущие права и совместимость. В сообщение не переносятся ENV, credentials, полная рабочая папка и скрытая история. При смене проекта/устройства прежний план становится stale.

Если известен durable receipt уже совершённого действия, его можно восстановить без повторного эффекта. Если неизвестно, была ли отправка/COMMIT, показывается uncertain и проверяется точный receipt. Необратимый вызов модели не повторяется автоматически. Новое исполнение требует текущего допуска, а выключенный флаг сохраняет разрешённые историю, отмену и восстановление.

## Настройка через интерфейс

В карточке системного агента показываются назначение, область, модель, доступные подключения, бюджет и последние проверки. Контекст и полномочия раскрываются подробностями; обязательного редактирования JSON нет. Неподключённый инструмент предлагает конкретный переход настройки с сохранённым планом и возвратом к исходной задаче.

Для каждой задачи видно: что проверено, что предложено, что выполняется, где нужен выбор пользователя, что уже сохранено и как продолжить после отказа. История содержит структурированную хронологию и ссылки на исходные операции. Текст «готово» выводится из квитанции владельца и результата проверки.

Идентичность встроенной роли остаётся серверной. Разрешённые проектные настройки (модель, язык/стиль ответа, рабочие предпочтения, бюджет в границах политики) можно версионировать в UI. Изменение пользовательского описания роли не добавляет tools, сетевые адреса или права. Пакеты скиллов и проектные overrides сохраняют своё происхождение и точные версии.

## Квоты и самообучение

Роли должны использовать общий проектный ledger/reservation, предложенный в `project-quotas-design-2026-10-24.md`. У запроса есть logical operation, attempt, purpose и исходный период. Оплаченный либо неизвестный результат учитывается отдельно от admission; отсутствие provider usage не изображается точным числом токенов/денег. Системная диагностика без проекта требует явно выделенного системного бюджета.

Лимиты роли (например, максимум шагов и длительность) ограничивают один run. Проектные квоты ограничивают совокупное потребление. Оба уровня проверяются сервером перед новым эффектом; история и cleanup не должны становиться недоступными из-за исчерпанной квоты.

Успешный run может предложить reported experience с привязкой к версии исходников/пакета и receipt. Куратор предлагает гипотезу и проверку, человек одобряет версию знания. Только одобренный контекст поступает в агентные запросы и Memory; снятие одобрения запускает управляемую очистку принадлежащих проекции наблюдений. Перенос workspace обязан переносить журнал владения, сохраняя ручные наблюдения.

## Проверки до расширения полномочий

| Проверка | Наблюдаемый результат |
| --- | --- |
| Empty/offline состояние | Агент называет недостающую зависимость и даёт продолжение; unavailable не становится healthy |
| Подмена инструкций в логах, RAG, quirk или файле | Внешние данные не меняют role/tool policy; provenance сохраняется |
| Отзыв роли/флага/назначения между prepare и execute | Новый эффект не начинается; уже совершённый receipt доступен в разрешённой области |
| Смена версии модели, источника, binding или контекста | Старый план не применим; ввод и понятное действие повторной подготовки сохранены |
| Потеря dispatch/COMMIT/ACK, SIGKILL | Нет скрытого платного повтора; exact receipt и owned journal восстанавливаются |
| Избыточный контекст или квота | Отказ до нового вызова с фактическим пределом и следующим действием |
| Два запуска/вкладки, полный production pool | Request keys/CAS сохраняют один эффект; собственная очередь не истощает вложенные обращения |
| Частичное применение нескольких целей | Каждая квитанция видна; откат касается только действительно применённой и всё ещё совпадающей версии |
| UI → системный агент → owner API → мост/провайдер | Отдельно проверены admission, исполнение и полезный результат; журнал умеет штатную отмену |

Модельные evaluations проверяют качество объяснения и соблюдение формата на фиксированном наборе фактов. API/SQL/ОС тесты доказывают полномочия, данные и побочные эффекты независимо от ответа модели. Изменение prompt/model pin требует нового model evaluation; оно не заменяет регресс исполнителей.

## Порядок развития

1. Закрыть замечания module audit: deadline, S3 bootstrap, RAG authorization, Memory ownership, операции/cancellation/pool и административный retry. Это фундамент для действующих ролей.
2. Проверить настоящие цепочки четырёх существующих ролей, включая отмену из общего журнала и провайдер Codex. Согласовать интерфейсное «сохранено/выполнено/проверено».
3. Добавить версионированные планы передачи AI-админ → профильный агент → действующий сервис; начать с одного полного сценария «подключить и проверить модель».
4. Куратор знаний появляется после принятой живой цепочки quirks → reported experience → approval → overlay/Memory → revoke cleanup. Контролёр качества — после server-owned проверяющего профиля и проверяемого denominator.

Новые роли/действия получают отдельные флаги по существующей политике. В этой итерации документ определяет направление; исполнение новых роль-действий и численные проектные квоты остаются отдельной реализацией и приёмкой.
