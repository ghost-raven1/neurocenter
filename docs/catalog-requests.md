# Заявки по каталогу

В каталоге есть вкладка «Заявки»: добавить новый плагин, MCP, скилл или модель, запросить обновление либо сообщить о проблеме. Заявка относится к общему каталогу или конкретному проекту.

Автор указывает тип обращения, тип ассета, название и описание. Ссылка на источник необязательна. Для обновления и сообщения о проблеме нужно выбрать существующую карточку. Подача заявки не загружает и не запускает её источник.

Автор видит свои доступные заявки. Главный админ видит все; админ проекта также видит и обрабатывает заявки своего проекта. Доступ проверяется по текущим назначениям: после отзыва участия сведения проекта больше не выдаются. Заявки удалённого проекта сохраняют исходную область и историю, а не превращаются в заявки общего каталога.

Порядок обработки:

1. «Новая» — автор может исправить заявку или отменить её; администратор берёт её в работу.
2. «В работе» — администратор выполняет изменение через обычные инструменты каталога, запрашивает уточнение или отклоняет заявку.
3. «Нужно уточнение» — автор исправляет данные и отправляет заявку повторно либо отменяет её.
4. «Выполнена» — администратор оставляет результат; для добавления и обновления связывает заявку с реально существующей карточкой нужного типа и области.
5. «Отклонена» и «Отменена» завершают обработку. Причина отклонения и запрос уточнения обязательны.

Карточка заявки содержит историю изменений и решений. Если связанный ассет впоследствии удалён, сохранённое название и версия остаются в истории, а доступность карточки проверяется отдельно.

Одновременные изменения проверяются по ревизии: устаревшая форма получает 409 и требует обновления. Автор сравнивает актуальную заявку со своим сохранённым черновиком и явно выбирает новую ревизию перед сохранением. Если заявку уже взяли в работу или завершили, черновик остаётся доступным для копирования, а повторное сохранение блокируется. Повтор одного и того же запроса с прежним `requestKey` не создаёт дубликат; использование ключа для другого изменения возвращает конфликт. Проверка текущих прав выполняется и при повторе.

HTTP API находится под `/api/catalog-requests`, параметры и ответы доступны в [Swagger](http://localhost:5173/api/docs). Таблицы заявки, истории и квитанций создаются нумерованной миграцией каталога; запуск не наполняет их демонстрационными данными.

## Проверка

Обычный `npm run check` включает проверки форм, доступа, аудита, параметров, Gateway и контракта Swagger. Сборка Gateway должна выполняться после изменения контроллеров: отдельный тест проверяет типы и фильтры в готовом `dist/docs/openapi.json`.

База и HTTP-приёмка проверяются отдельно: `scripts/test/catalog-requests-database.mjs` требует `REQUESTS_QA_ADMIN_URL`, а `scripts/test/catalog-requests-acceptance.mjs --execute` — закрытый JSON-файл `{ "adminUrl": "…" }` в `REQUESTS_QA_CONNECTION`. Это подключение к отдельному одноразовому PostgreSQL на `127.0.0.1`, к базе `postgres`, на порту, отличном от 5432. Сценарии создают и удаляют собственные базы; рабочее подключение использовать нельзя. HTTP-приёмка использует настоящие Catalog AppModule и Gateway, синтетические OAuth-аккаунты и локальные метаданные скиллов. Внешние OAuth-провайдер и установка ассетов в этот сценарий не входят.
