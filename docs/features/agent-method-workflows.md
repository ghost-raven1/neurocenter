# BMAD и OpenSpec через локальный мост

Проектная задача исполняется на выбранном компьютере в подтверждённой папке. Нейроцентр сохраняет методику, точную версию, задачу, команды проверки и идентичность привязки в `bridge_jobs`. Наличие кнопки и доступность модели сами по себе не означают готовность локального исполнения.

Неизменяемый вход принятого задания — текст задачи, методика, команды и target. Документы локального проекта читаются и хешируются при фактическом запуске. Их изменения во время ожидания очереди будут использованы исполнителем; снимка файлов на момент серверного принятия нет. UI показывает эту границу. Утверждение ревизии локальных документов до admission требует отдельного протокола подготовки и остаётся следующей задачей.

## Подготовка компьютера

Нужен мост с возможностью `agent-method-workflow-v1`; текущий исполнитель поддерживает macOS и Linux. Windows возвращает явное отсутствие поддержанного жизненного цикла процессов. Требуется OpenCode **1.14.48**: сначала используется движок штатного runtime моста, затем проверенный `opencode` из PATH. Другая версия не подставляется молча.

Выбранная методика должна уже существовать в связанной папке. Исполнитель ничего не скачивает и автоматически не запускает установщик:

- **BMAD 6.12.4:** `bmad --version` сообщает закреплённую версию; `_bmad/_config/manifest.yaml` содержит `installation.version: 6.12.4`; присутствуют `_bmad/scripts/render_skill.py`, `uv` и официальные проектные skills `bmad-help`, `bmad-spec`, `bmad-build-auto`, `bmad-code-review`.
- **OpenSpec 1.15.0:** `openspec --version` сообщает закреплённую версию; есть `openspec/config.yaml`; `openspec context --json` и `openspec list --json` успешно читают проект. Нужны официальные проектные skills `openspec-propose`, `openspec-apply-change`, `openspec-verify-change`, `openspec-archive-change`.
- **BMAD → OpenSpec:** закреплённая комбинация `bmad-6.12.4+openspec-1.15.0`; требуются обе методики и их проектные корни. BMAD используется для недостающих brief/PRD/архитектуры, затем одна реализация выполняется через OpenSpec. Принятые документы BMAD переиспользуются; второй BMAD build-цикл не запускается. Для планирования нужны `bmad-help`, `bmad-product-brief`, `bmad-prd`, `bmad-architecture`, затем четыре OpenSpec workflow выше.

Проектные skills читаются из `.opencode/skills/<имя>/SKILL.md` или `.agents/skills/<имя>/SKILL.md`. Устанавливайте методику штатным установщиком соответствующей версии в выбранную папку. Существующие документы и store OpenSpec требуют проверки перед переинициализацией; Нейроцентр не пересоздаёт их автоматически. Для BMAD требуется полный модуль BMM с workflow реализации и проверки, не только роль аналитика. При отсутствии любого условия задача получает `needs_setup` и действие `setup-method` или `setup-runtime`.

OpenSpec core-профиль может не включать verify workflow: установите его официальным способом вместе с остальными workflow до запуска полного цикла. Исполнитель сейчас принимает только OpenSpec root, совпадающий с привязанной папкой; внешний store и корень предка требуют отдельной настройки, а не создания второго локального root. Некорректный inline-конфиг OpenCode блокирует запуск; корректные `provider`, `model` и прочие параметры сохраняются, запрет внешних каталогов добавляется поверх существующих разрешений.

До любого старта OpenCode проверяются существующая конфигурация RAG и весь Quirk JSONL через read-only reader. Битый JSON, незавершённая строка, дубликаты, некорректный UTF-8, ошибка чтения или небезопасный источник дают `QUIRK_STORAGE_INVALID` / `inspect-workspace`; coding runtime не стартует. Хранилище не открывается через LanceDB, baseline не удаляется, не пересоздаётся и не «чинится» автоматически. Здоровые атомарные добавления Quirk перепроверяются целиком; они не превращают знания в принятые требования. Такая проверка JSONL не является приёмкой исправности всех нативных индексов LanceDB.

## Выполнение и результат

Сначала мост проверяет текущие device/site/project/binding/instance и серверную авторизацию. Затем читает реальные установленные workflow-инструкции и запускает собственный OpenCode HTTP-сервер в папке проекта. Сервер слушает случайный loopback-порт, защищён одноразовым паролем и входит в принадлежащее заданию дерево процессов. Мост создаёт отдельную сессию и ждёт завершённый ответ ассистента: HTTP200, частичный ответ, tool-call или ошибка модели сами по себе не дают успешного результата. Интерактивные question/plan-переходы запрещены, как в неинтерактивном CLI. Существующие документы задают продолжение текущего этапа. OpenSpec дополнительно проверяется настоящим `openspec validate --all --strict --no-interactive`. После завершения coding runtime мост самостоятельно запускает явно выбранные команды проверки через argv без shell-интерполяции.

В результате сохраняются относительные пути и SHA-256 изменённых файлов, артефактов методики и настоящие exit code/signal выбранных проверок. Сравнение выполняется относительно фактических байтов до запуска: уже существовавший dirty diff не объявляется работой нового задания. Сырые stdout/stderr, инструкции, личные ключи и локальные абсолютные пути в результат не передаются. Отсутствие изменённых файлов не доказывает отсутствие изменений в игнорируемых Git файлах: опись ограничена tracked и non-ignored файлами.

Проверки без фактического запуска получают `not_run`; ненулевой exit получает `failed`. `succeeded` допустим только после успешных выбранных проверок и завершения runtime. Сохранение method prompt без запуска coding runtime не является выполнением этого цикла.

Дополнительно проверяется окончание самой методики. Для OpenSpec нужен изменённый этим запуском change с завершёнными задачами и фактическим `instructions apply --json` в состоянии `all_done`, либо настоящий архив с завершёнными tasks, proposal и spec. Старый документ или новый proposal без выполненных задач не дают PASS. Для BMAD требуется изменённый артефакт `status: done` с `Auto Run Result` и `Review Triage Log`, без незавершённых задач. В комбинированном режиме вместо BMAD build/review-артефакта проверяются принятые planning-документы BMAD и завершение OpenSpec.

## Закреплённый проектный исполнитель

Дополнительный режим `project_agent_workflows` использует capability `agent-method-selected-agent-v1` моста0.9.23. Browser передаёт только `workflow.agentId` и `workflow.expectedAgentsRevision`. Сервер независимо получает актуальные assignment/model requirements и последнюю успешную configure-project-agents delivery для точного actor/device/project/binding/instance.

Приватный snapshot включает identity выбранного агента, ревизию, desired/compiled manifests, SHA native-файла, configurationJobId, поддержанный mode и approved safe model mapping. Он проверяется повторно внутри final enqueue и успешной completion транзакции, перед claim и при authorize. Изменение revision, archive/enabled/mode, модели или новой delivery не подтверждает прежний профиль. Публичные job/result metadata содержат только identity/hash; prompt и provider endpoint в результат не копируются.

Мост проверяет bridge-private committed proof, текущий файл, namespace и model metadata без чтения auth.json. Собственный OpenCode server до model POST должен действительно загрузить выбранные native имя, mode и модель. Запрос передаёт явные agent/model; финальный ответ обязан относиться к ним же. Несоответствие даёт `SELECTED_AGENT_NOT_READY` / `setup-agent` с сохранением доступных измеренных фактов. Авторизация и локальные проверки продолжаются во время исполнения.

Прежний protocol v1 без optional agent сохраняет исходную нормализацию и обработку квитанций. Старые API-клиенты могут явно использовать прежний режим при включённой базовой функции; выбранный агент не превращается в прежний режим автоматически. Отдельный набор skills/plugins/MCP и изоляция каждого агента этим расширением не реализуются.

## Отмена и восстановление

До разрешения исполняемому процессу стартовать сохраняется приватная квитанция с владельцем процесса. Группа и её известные потомки прекращаются при отмене, отзыве доступа, смене привязки, остановке worker или истечении срока. Авторизация и привязка проверяются перед шагами и повторно во время исполнения.

Завершённый результат записывается до ACK. Потеря ACK повторяет доставку той же квитанции. Если после перезапуска найден только маркер начатого выполнения, состояние становится `unknown`: повторного исполнения нет. Проверьте локальную папку и создайте новый явный запрос после выяснения результата. Ручные изменения не откатываются через `git reset`, `clean` или `restore`.

При остановке после частичного изменения мост пытается отдельно измерить результат read-only, только если исходные привязка и права ещё действуют. При отзыве доступа или смене папки такой обзор не выполняется; предыдущие измеренные факты сохраняются, а отсутствие новых данных не объявляется отсутствием изменений. Восстановление сохраняет уже записанные patch-факты и пройденные проверки, даже если crash случился до общей финальной квитанции.

## Границы

- Локальный срок — максимум 15 минут, включая подготовку, код и проверки; меньший срок запроса имеет приоритет.
- Один процесс — до 1 МиБ суммарного stdout/stderr; внутренние логи coding-сервера и его HTTP-ответ ограничены отдельно 1 МиБ каждый. Они не возвращаются серверу Нейроцентра. Обзор — до 20 000 Git-файлов, 512 МиБ суммарно и 8 МиБ на файл. Квитанция — до 64 изменённых файлов и 64 артефактов. Превышение даёт явный отказ наблюдения.
- OpenCode получает запрет `external_directory` для своих инструментов. Рабочая папка и этот запрет **не являются ОС-песочницей**. Coding runtime и выбранные команды — доверенное локальное выполнение с правами пользователя.
- Локальный provider/auth OpenCode остаётся на компьютере. Подготовка не вызывает модель. Сам явный запуск реального coding runtime может расходовать доступ выбранного локально провайдера; автоматического платного повтора после неизвестного результата нет.
- Отключение фичафлага запрещает новые задания; разрешённые история, отмена и получение сохранённых результатов остаются доступны.

Проверка harmless runtime fixture подтверждает реальные файловые изменения, argv-команды, отмену процессов и восстановление ACK. Она не подтверждает качество реальной модели, прохождение ею всех решений BMAD/OpenSpec, все клиентские ОС, CI или production.
