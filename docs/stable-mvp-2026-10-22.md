# Объём стабильного MVP

Решение от 22 октября 2026 года: восемь обязательных сквозных цепочек. Это граница приёмки, а не утверждение об их полной готовности. Обратная синхронизация LanceDB и базовый упаковщик обязательны по запросу пользователя. Реализация продолжает существующие восемь пакетов workspace; новые сервисы для MVP не нужны.

| № | Цепочка | Результат, который нужно принять целиком |
| --- | --- | --- |
| 1 | Первый запуск и управление | Запуск, вход, администратор, роли/участники, настройки через UI, фичафлаги, диагностика и восстановление после ошибки |
| 2 | Проект и локальная папка | Создать проект, назначить участника, выбрать компьютер, связать нужную папку; два компьютера могут иметь разные локальные пути |
| 3 | Мост | Установка с площадки или из доставленного архива, подтверждение подключения, повтор/обновление/переход между площадками с сохранением настроек и ключей |
| 4 | Каталог и установка | Импорт доверенной поставки, закрепление версии за проектом, установка на связанный компьютер, изменение/удаление и восстановление после отказа |
| 5 | Модели | Администратор подключает OpenAI-совместимый API, проверяет модель, назначает проекту; ключ приватный, ошибки/квоты понятны, повтор не создаёт скрытый оплачиваемый запрос |
| 6 | Чат в шапке | Оверлей, модель и группа агентов, отправка/остановка/повтор, история после reload, смена проекта и отзыв доступа без чужих данных |
| 7 | LanceDB → сервер → LanceDB | Полный проверенный снимок проекта, поиск, обратная загрузка в связанную папку с совместимой embedding-моделью; проверка generation/hash/count, отмена, конкурентное изменение и восстановление после прерывания |
| 8 | Базовый упаковщик | Исходник или архив → проверка структуры/конфигурации и зависимостей → пакет с версией и SHA → публикация → каталог → установка и восстановление прежней версии |

Упаковщик принимается с ошибками зависимостей, отменой, повтором после сбоя и сохранностью предыдущей опубликованной версии. Разработка произвольных новых runtime и универсальных сборочных языков в эту цепочку не входит. Поддерживаемые виды и платформы определяются реальными проверенными рецептами, а не наличием пункта в форме.

Аудит текущих исходников упаковщика оставляет три открытых пункта: пользовательской отмены ещё нет (форма только скрывает задание); изменённый исходник под прежним именем не имеет явного CAS-пути новой версии и конфликтует на поздней публикации; builder наследует CA, но теряет proxy-окружение сервера. Это проверенные ограничения кода, без новой сквозной проверки в реальном окружении. Их нельзя отмечать закрытыми по зелёным тестам соседнего установщика моста. Минимальная приёмка требует настоящего маленького JS-пакета через очередь/публикацию и его установки отдельным worker; существующие независимые fixture-пакеты эту связь не доказывают.

Обратная загрузка сейчас имеет семантику проверенной замены индекса, не объединения строк. В интерфейсе требуется явное подтверждение того, что несинхронизированные локальные данные не объединяются. Транзакционная previous-папка обеспечивает rollback при сбое и удаляется после успешного commit; это не постоянная пользовательская резервная копия. Нельзя считать сохранность всех несинхронизированных данных принятой только по успешному restore. Повторный полный roundtrip и восстановление после прерывания входят в приёмку отдельно.

На новом компьютере сначала настраивается проверенный локальный embedding-профиль через существующее подключение модели. Одного совпадения размерности недостаточно. Неполный или пустой серверный снимок текущий restore отклоняет, сохраняя локальный индекс; обратное применение пустого снимка/удалений отдельным подтверждённым действием ещё не реализовано. Ошибка до commit требует повторной загрузки, а durable-журнал восстанавливает уже начатое переключение без скачивания.

## Управление и поставка

Бизнес-операции используют существующие флаги; состав и зависимости задают `services/shared/feature-flag-catalog.json` и `feature-policy.cjs`. Для упаковщика обязателен `tool_builds`, для прямой синхронизации — `rag_sync`, для поиска — `project_search`. Чат модели и группы имеет отдельные `model_chat`/`group_chat`; карточки агентов — `agents`. Нельзя выключать `model_hosting` только потому, что используется внешний API: у него есть серверные зависимости inference. Изменять defaults или включённые флаги площадки этим документом не требуется.

Отключение бизнес-функции не должно лишать пользователя истории, отмены, удаления и восстановления. Поэтому `restore-rag` входит в recovery-allowlist и остаётся доступен при выключенном `rag_sync`, сохраняя проверки прав и binding. Общий системный backup остаётся операционным требованием; его UI использует `project_backups`, поэтому этот флаг нельзя исключать из MVP механически. Вложения чата и локальные runtime пока не имеют отдельных флагов: это открытый вопрос детализации управления, а не выполненное требование «каждая фича отдельно».

Для работы без внешнего registry администратор заранее доставляет доверенные карточки, архивы и runtime для нужной платформы. Недоступный внешний каталог не должен блокировать запуск площадки; при отсутствии локальных пакетов интерфейс честно показывает отсутствие поставки и путь её добавления. Проверенная chat-модель не заменяет отдельно выбранную и проверенную embedding-модель.

## Условия приёмки

Каждая строка проверяется в реальном UI и через свой worker/API, с ролями и прямым URL, пустым состоянием, offline, отменой, повтором, reload и отзывом доступа там, где применимо. Неверный вход отклоняется до изменения пользовательских данных. Временный отказ показывает причину и доступное следующее действие; сохранность данных важнее фиктивного успеха.

Локальные unit/fixture-тесты, сборка и health не заменяют нативные целевые ОС, корпоративную сеть/CA, реальный IdP, внешнее S3/Ceph и восстановление на другом хосте. Near-100 покрытие всех модулей остаётся отдельной целью: последний полный safe-срез до исправления SQLite queue имел 7506 pass / 1 fail / 53 skip, покрытие строк 64,88% по настроенному AST-знаменателю. Частные зелёные срезы не превращают этот общий результат в зелёный; новый полный запуск фиксируется отдельно.

Стабильный MVP объявляется только после закрытия этих восьми цепочек и их обязательных восстановительных сценариев. Остальные пользовательские требования сохраняются в бэклоге; уменьшение объёма MVP не означает удаления существующих возможностей.
