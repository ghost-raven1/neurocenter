# Надёжная установка через MCP — 17 октября 2026

Подготовлен MCP **0.2.0, протокол 2**. Закрыты критические обходы защиты, потеря результата при сетевом сбое, дубликаты из вкладок и потеря истории при обычном переподключении. Автономный комплект для **macOS ARM64** устанавливается без системных Node/npm. Универсальную готовность произвольного скилла, MCP или плагина обещать пока нельзя: оставшиеся сценарии перечислены ниже.

Исходные воспроизведения сохранены в [аудите до исправлений](one-click-installation-audit-2026-10-17.md). Этот документ описывает последующую реализацию и отдельный новый прогон. Production-развёртывание и настоящий Blitz не выполнялись.

## Что изменено

| Сценарий | Реализация |
| --- | --- |
| Старая команда пишет мимо разрешений/квитанции | `install_asset` и `install_plugin_bundle` больше не зарегистрированы; опасный обработчик и остатки сборки удалены. Отрицательная проверка выполнена через настоящий stdio MCP. Уже установленный старый клиент необходимо обновить: сервер не может удалить его локальные инструменты |
| Файлы записаны, но финальный запрос потерян | Результат сохраняется в личном каталоге `completions` до отправки. Повторяется только подтверждение; файлы не переписываются |
| Сервер сохранил результат, ответ потерян | `/jobs/:id/complete` принимает тот же результат идемпотентно. Статус задания и операция фиксируются одной транзакцией |
| Истекла аренда, результат ещё неизвестен | Задание переходит в `reconciling`. Для файлов проверяются устройство, аренда, пакет, версия, манифест и привязка папки. Подтверждённый откат или отказ до записи завершается ошибкой; простой сетевой сбой не считается откатом |
| Потерян отчёт выбора папки, привязки или RAG | Сохраняемый результат тоже сверяется после аренды. Проверяется исходное задание и выбранная папка/ID проекта; ошибка доставки не блокирует локальную очередь навсегда. UI показывает сверку и не предлагает второе действие поверх неё |
| Процесс остановлен после фиксации файлов | В журнале сохранены ID задания и результат. Новый worker завершает архивирование и доставляет подтверждение без повторной записи |
| Ошибка до начала файловой транзакции, затем обрыв | Сохраняется подтверждение `unchanged` с исходной идентичностью задания. После истечения аренды оно снимает неопределённость; несуществующий откат не изображается выполненным |
| Две вкладки создают разные ключи запроса | Lock строки устройства объединяет одинаковую незавершённую установку. Другая версия или противоположное действие получает 409 |
| Два worker запрашивают задания | Выдача сериализована на устройстве; одновременно выдаётся одно действующее задание |
| Большая очередь/длинная история | Предел — 100 незавершённых действий на устройство, далее 429. Ожидание более суток отменяется явно. Активные записи не вытесняются последними 100 завершёнными |
| Поздний отчёт старой версии | Текущая установка определяется порядком начала выполнения, а не временем доставки отчёта |
| Папка изменена после постановки задания | Задание закрепляет отпечаток конкретной привязки. Сервер и worker проверяют его перед записью. История для другой папки отмечается отдельно; удаление в новой папке блокируется |
| Истёк 30-дневный ключ | Владелец подтверждает продление с доказательством прежнего ключа; сохраняются ID и история. Секрет ротируется, старый перестаёт действовать |
| Потерян ответ подключения | Будущий ключ предварительно сохраняется на компьютере; сервер хранит только хэш. Повтор ответа протокола 2 возвращает тот же ID без секрета |
| Два одновременных продления | Сравнение прежнего хэша не позволяет второй паре заменить уже обновлённый ключ |
| Повтор установки самого моста | Используется действующее подключение; существующий JSON/JSONC сохраняется. Для явной смены назначенной роли есть переподключение |
| Обновление worker | Пауза выдачи заданий, ожидание активной операции, проверка собственного PID/команды и мягкая остановка. Чужие процессы не завершаются |
| Старый клиент/сломанный отчёт | Сервер и UI проверяют протокол и возможности. Повреждённый heartbeat отклоняется; новые задания, включая выбор папки и RAG, требуют протокол 2 |
| Нет Node/npm на компьютере | Готовый архив включает Node.js 24.22.0, зависимости и лицензию runtime. Установщик проверяет SHA256 и архитектуру, сохраняет предыдущий клиент и восстанавливает его при ошибке регистрации |
| Нет нативной LanceDB | RAG загружается отдельно от основных MCP-инструментов. Неподдерживаемая RAG отображается явно и не ломает загрузку всего моста. macOS Intel с текущей LanceDB требует отдельного решения |
| Пользователь не понимает следующий шаг | Команда обновления раскрывается автоматически, ручной код спрятан в резервный шаг. Модалка инструмента объясняет недоступную установку. Доставка файлов показана отдельно от непроверенного запуска в OpenCode |

Журналы и подтверждения записываются атомарно через временный файл; на POSIX используются `fsync` файла и родительского каталога. Это усиливает сохранность, но не заменяет испытание отключением питания и нативную проверку Windows ACL/файловой системы.

Для них проверен синтаксис; их полный live-проход заново не выполнялся. Свежие сквозные доказательства этого этапа — отдельные worker/PostgreSQL и HTTPS-наборы выше.

## Как собрать автономную раздачу

1. На целевой ОС/архитектуре использовать официальный Node.js 24 и npm для **сборки**.
2. Собрать MCP: `npm run build --prefix mcp/neurocenter-asset-sync`.
3. Выполнить `node scripts/package-bridge-runtime.mjs`. Скрипт ставит production-зависимости по lock-файлу в свою временную папку, проверяет нативную LanceDB, включает Node/лицензию, отклоняет ссылки и публикует `.tgz`, `.sha256`, `.json` в `bridge-dist/runtime`.
4. Выполнить `node scripts/test/bridge-runtime-smoke.mjs`; для Bash-платформ — `node scripts/test/bridge-native-installer.mjs`. Для Windows нужен отдельный реальный PowerShell-прогон.
5. Пересобрать gateway с этой раздачей и проверить доставку через HTTPS. Не выдавать подставной `uname` или запуск через эмуляцию за нативный тест.

Сейчас в раздаче есть `neurocenter-asset-sync-darwin-arm64-0.2.0.tgz` — около 84 МиБ. Контрольная сумма и `buildId` опубликованы рядом. SHA256 защищает целостность доставки с доверенной HTTPS-площадки; это не подпись издателя и не sandbox стороннего кода. Пользовательский установщик не обращается к npm-реестру.

## Что ещё не закрыто

1. **Работоспособность установленного инструмента в OpenCode.** Нужны отдельные состояния запуска/входа/готовности, MCP handshake с таймаутом, проверка загрузки плагина и явный внешний OAuth. Сейчас честно подтверждается доставка файлов; установленный пакет автоматически не исполняется ради проверки.
2. **Составной скилл и зависимости.** Доставляется один SKILL.md. `scripts/references/assets`, закреплённый граф MCP/плагинов, циклы/конфликты, общие зависимости, транзакция набора и историческая доставка старого Markdown требуют следующей реализации. Связи в метаданных не означают установку зависимостей.
3. **Инвентаризация, ремонт и несколько копий проекта.** История команд не сверяет постоянно реальные файлы. Нужны понятные diff/восстановление после ручных правок и backup, обнаружение замены папки на том же пути, выбор нескольких клонов и безопасное принятие ручной установки. Изменение пути уже защищено, но эти сценарии шире.
4. **Сложная потеря идентичности и результата.** Продление с сохранённым ключом реализовано. Потеря всех локальных credentials, перенос между OS-профилями, отозванное устройство и его зависшие операции требуют явной процедуры сверки. Отчёты прежних устройств сохраняются отдельно и предупреждают пользователя; автоматически чужой истории они не присваивают. Прерывание выбора папки/RAG до сохранения локального подтверждения и старые журналы без ID задания также могут требовать ручного восстановления; атомарного журнала полного RAG-переноса нет.
5. **Управление уже работающим кодом.** Остановка внешнего MCP/плагина при удалении, отзыв/карантин версии, доверие издателю и политика привилегий ещё не реализованы. Удаление файлов требует перезапуска OpenCode.
6. **Матрица ОС и отказов.** Готовый runtime нативно принят только на macOS ARM64. Windows, Linux GNU/musl, Intel Mac, native picker, сетевые диски, реальные потери питания и заполнение диска на каждой фазе требуют своих стендов. Пользовательские установки и привязки папок этим прогоном не изменялись.
7. **Production.** Реальные Blitz/TLS/первый адрес администратора, внешний backup, RPO/RTO, общий механизм миграций, аудит чувствительных действий, метрики/alerts и нагрузка остаются условиями допуска. [Общая оценка production](production-readiness-2026-10-17.md) сохраняет NO-GO.

Следующий приоритет разработки — проверяемый план состава установки и доставка ресурсов скилла, затем проверка запуска в поддерживаемом OpenCode и ремонт по инвентаризации. Остальные платформы принимаются на реальных целевых системах.
