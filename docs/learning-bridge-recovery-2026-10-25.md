# Восстановление запросов самообучения через мост

Сбор кварков OpenCodeRAG и синхронизация принятых знаний с MCP Memory сохраняют исходный запрос перед отправкой. Закрытие модального окна, обновление списка установок или потеря ответа не разрешают создать новый запрос поверх неподтверждённого.

## Пользовательский сценарий

После повторного открытия окно читает состояние исходного запроса. «Проверить отправку» выполняет только GET. Если сервер пока не находит ключ, пользователь может повторить проверку или явно отправить исходный запрос с прежним ключом и неизменным содержимым. Автоматической повторной отправки нет.

Исходная установка остаётся выбранной, даже если её больше нет в свежем списке. Полученное по точному ключу задание отображается перед общей историей: ограничение списка последними 100 завершёнными заданиями не скрывает его.

Проверка, просмотр результата и доступная пользователю отмена работают при выключенном флаге новых операций. Очистка отозванных записей Memory сохраняет существующее исключение. Отказ одной из этих функций не блокирует остальные чаты и агенты.

## Контракт чтения

`GET /api/device-jobs/requests/:requestKey` возвращает:

```ts
{ requestKey: string; requestFingerprint: string | null; job: PublicDeviceJob }
```

- `400`: некорректный ключ.
- `403`: текущая активная роль больше недоступна или сессия не допускается к маршруту.
- `404`: ключ отсутствует, принадлежит другому пользователю или его проект/компьютер недоступен текущему пользователю.
- `200`: точный alias запроса и существующее публичное представление задания.

Каталог заново проверяет текущие права. Даже главный администратор не получает чужой приватный запрос через этот маршрут. Учётные данные устройства не допускаются. Ответы шлюза, включая ошибки авторизации и `404`, имеют `Cache-Control: no-store`.

Чтение не продлевает lease, не запускает expiry, не меняет задания, не вызывает модель и не создаёт операций. Fingerprint берётся из точного alias, а не исходного задания: несколько ключей установки могут ссылаться на одно задание. Для legacy hash непригодного формата возвращается `null`; клиент не считает такой ответ подтверждением полного исходного запроса.

Клиент сверяет fingerprint, ключ, проект, компьютер, вид операции, установку, версию, manifest и привязку папки. Fingerprint соответствует существующему SHA-256 контракта `DeviceJobs.create`: исходная роль и отсортированные поля запроса, включая режим Memory, ревизию знаний и конфигурационные ревизии RAG.

## Состояние браузера и неизвестный исход

В `sessionStorage` текущей вкладки сохраняются только исходные метаданные запроса и fingerprint, с областью пользователя, проекта и вида операции. Тексты Memory, кварки, значения конфигурации и credentials туда не попадают. Это восстановление в браузерной сессии, а не перенос незавершённых намерений между компьютерами.

Изменение роли или имени проекта не теряет исходный ключ. Асинхронные ответы дополнительно проверяют полный текущий контекст авторизации и поколение компонента. Повторная отправка требует исходной роли и актуального разрешения операции. Изменившаяся сохранённая запись не может быть затёрта поздним ответом.

Первый однозначный отказ POST с `400/403/409` освобождает не принятый запрос. После неизвестного исхода и при повторной отправке такой ответ не доказывает отсутствие ранее принятого задания: исходный запрос сохраняется. Недоступное хранилище блокирует новую отправку с объяснением. Ошибка очистки хранилища после завершения также сохраняет запрет на замену исходного намерения.

## Проверки

Node 24.22.0, последовательные запуски с одним worker:

- Frontend: **66/66**, четыре файла `project-learning-{api,memory-ui,quirks-ui,quirks-actions}.test.ts`. Реальные React StrictMode lifecycle, deferred ACK, переоткрытие, смена пользователя/роли, storage errors, точная проверка полного запроса и восстановление при выключенных флагах.
- Catalog: **45/45**, `device-job-receipt`, `device-job-requests`, `device-job-access`, `device-job-feature-flags`. Из них десять новых HTTP-сценариев exact receipt.
- Gateway: **39/39**, `device-job-receipt-proxy` и `proxy-service-http`. Из них семь новых HTTP-сценариев маршрута, авторизации, отключённых флагов и запрета кэширования.
- Отдельный принадлежащий проверке PostgreSQL 16: **10/10**, `device-job-receipt-postgres`. Настоящий COMMIT с потерянным ACK, alias вне последних 100 заданий, текущие права, приватность, несовпадающие fingerprints, неизменность БД при чтении. Контейнер, том и временные credentials удалены после проверки отсутствия клиентов и тестовых баз.
- Браузер: реальные компоненты Memory и Quirks с синтетическими API. Для каждой операции один POST и одно принятое задание после потери ACK и переоткрытия; дальнейшие проверки выполняют GET. Отмена Memory доступна при выключенном флаге.

Проверка PostgreSQL покрывает цепочку `enqueue → receipt → client`; полное admission через `DeviceJobs.create`, реальная доставка в установленный MCP Memory/OpenCodeRAG, платные модели, CI и остальные сценарии проекта этим набором не подтверждаются. Для WebCrypto нужен HTTPS или localhost. Это целевой регресс, не измерение общего покрытия репозитория.
