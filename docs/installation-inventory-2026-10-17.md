# История папок и сверка установленного — 17 октября 2026

Кандидат MCP **0.6.0** продолжает [закреплённые комплекты 0.5.0](dependency-sets-2026-10-17.md). История установки учитывает папку проекта; отдельная команда сверяет известную установку с серверным пакетом. Production и пилот с рабочими данными остаются **NO-GO**.

## Привязка и история

Запись определяется устройством, постоянным ID проекта, `bindingId`, типом и ID инструмента. Переход A → B → A сохраняет версии обеих папок. Удаление в A не скрывает B. Позднее подтверждение старой операции не вытесняет новую установку; повторная установка того же SHA сбрасывает предшествующую сверку своей папки.

Новые запросы удаления и сверки обязаны передавать `expectedBindingId`; интерфейс передаёт его также при установке. Совпадение версии и SHA не разрешает устаревшей вкладке удалить установку другой папки. Повтор задания сохраняет исходную привязку. Старый интерфейс без этого поля получает 409 с предложением обновить сведения. Уже сохранённые задания продолжают использовать собственный закреплённый payload.

Имя папки берётся только из действующего отчёта устройства с тем же binding ID. Историческая строка показывает сокращённый идентификатор; прежний путь не угадывается по текущей папке. Записи без binding ID видны как прежняя история, но не становятся автоматической целью удаления или сверки. Перепривязка не присваивает их новой папке.

## Проверка файлов

Кнопка «Проверить файлы» создаёт `inspect-installation`. Нужны собственное подключённое устройство, текущая привязка, назначение в проекте и capability `installation-inspection-v1`. Наблюдатель может проверять доступный ему проект; установка и удаление по-прежнему требуют уровня разработчика. Поддержка комплектов `install-set-v1` и поддержка сверки проверяются раздельно.

Сервер передаёт неизменяемый пакет последней успешной установки данной папки. Локальная сверка сравнивает с ним квитанцию, реестр владельцев, байты файлов и управляемую запись JSONC OpenCode. Согласованная подмена файла и локальной квитанции не подменяет серверный эталон. Для обычных файлов действуют ограничения размера; симлинки, FIFO, повреждённые метаданные и изменение снимка дают явный отказ или неопределённый результат. Неизвестный прежний абсолютный путь Node не считается подтверждённым runtime.

Сама функция сверки только читает: не импортирует инструмент, не запускает subprocess, не обращается в сеть, не создаёт lock, не ремонтирует журнал и не меняет файлы. Занятый проект даёт `busy`. Worker сохраняет результат в собственную очередь подтверждений и передаёт его серверу. Обычное восстановление прерванных установок при запуске worker остаётся отдельной фоновой операцией **до** выдачи нового задания; read-only гарантия относится к функции и ветке сверки, а не ко всей жизни worker.

При смене привязки во время чтения worker сверяет идентичность результата с исходным заданием. Несовпадение превращается в обезличенный отказ с исходной identity; чужая привязка не попадает в очередь неподтверждаемых результатов.

Сервер принимает только фиксированную схему: identity пакета и папки, дату, `checked/busy`, `synced/modified/missing/unknown`, список из 20 допустимых кодов и `readiness: unverified`. Пути, содержимое файлов, конфигурация, значения секретов и произвольные поля не входят в результат. Оба способа завершения задания, `/complete` и terminal `/progress`, используют одну валидацию; промежуточный прогресс также не сохраняет произвольный результат или текст проверки.

Последняя корректная сверка читается из сохранённых заданий по полному ключу установки, версии, SHA и времени установки. Она остаётся видна после сотни последующих операций. Поздний старый отчёт её не заменяет; повреждённый сохранённый JSON не показывается как успешный.

Интерфейс различает текущую, историческую и прежнюю запись без папки. Показывает дату, занятость, ручные изменения, отсутствующие файлы и необходимость обновления MCP. Даже статус «Файлы сверены» сопровождается «Запуск в OpenCode не проверен». Ошибка сверки не заменяет сообщение удаления. Перед подтверждением удаления повторно проверяется выбранная папка.

## Границы и следующие этапы

- Сверяются известные серверу установки. Поиска произвольных инструментов на всём диске и автоматического присвоения найденных файлов нет.
- Новый клон по **тому же пути** пока не имеет отдельной локальной идентичности: binding ID зависит от сервера, проекта и realpath. Нужны идентичность экземпляра, явное подтверждение переноса и миграция прежних записей. История A/B этого не решает.
- Проверка запуска OpenCode, загрузки плагина, внешнего MCP, секретов и OAuth остаётся следующим самостоятельным этапом.
- Полная нативная матрица клиентов, настоящий Blitz и публичный сервер, независимое восстановление с согласованными RPO/RTO, общий процесс миграций и отката, нагрузка и длительный прогон ещё не приняты. В checkout отсутствует `.git`: публикация, CI и deployment не подтверждаются локальной сборкой.

### Сбой окружения и восстановление

Первая production-сборка **не дошла до тестов**: `rag-sync-service` не смог зафиксировать слой Docker (`failed to commit snapshot`, `input/output error`). На macOS APFS закончился свободный диск; логи Docker также содержали `ENOSPC`, а гостевой диск VM — ошибки блочного I/O. Подтверждения remount-readonly нет. Docker daemon перестал отвечать, PostgreSQL и зависимые readiness давали 503. Этот прогон не засчитан; его лог и диагностика сохранены.

После запроса пользователя на очистку образов Docker восстановлен: штатный restart завершился таймаутом, зависшие процессы Docker завершены, Desktop запущен заново; затем поднята прежняя `neurocenter-postgres-1`. Удалены **124 неиспользуемых проверочных тега Neurocenter / 83 image ID** без `--force`, после проверки образов всех существующих контейнеров. Проверено сохранение ID контейнеров и имён томов. Текущие шесть образов `verify-20261017-inventory` оставлены. После освобождения блоков на host доступно около 32 ГиБ. Глобальный prune не использовался.

Также удалены четыре устаревших сгенерированных runtime-архива 0.2.0/0.3.0/0.4.0/0.4.1 (около 350 МБ) и скачанный архив toolchain Node (около 53 МБ). SHA/метаданные прежних runtime, готовые архивы 0.5.0/0.6.0 и исполняемый Node сохранены.

В production-harness добавлена предварительная проверка минимум 6 ГиБ доступных процессу байтов на host до создания фикстуры и запуска Docker. Она остановила запуск при дефиците места до обращения к Docker; зарезервированные блоки не засчитываются. Это запас, а не бронирование места и не проверка отдельного лимита Docker VM. Команды Docker получили таймаут: 20 минут для build, 3 минуты для остальных действий. Границы проверки диска покрыты двумя новыми Node-тестами. После очистки финальная сборка и все 54 сценария прошли.
