# Диагностическое испытание проектного агента

Испытание запускается пользователем отдельной кнопкой и относится только к `server_chat` — чату Нейроцентра. Оно не включает агента, не блокирует обычный чат при неудаче и не подтверждает выполнение в OpenCode. Доставка управляемых файлов OpenCode остаётся отдельным статусом.

Сервер использует сохранённый эффективный промпт и параметры агента, точную назначенную модель проекта и её pin. Закреплённую модель нельзя заменить в запросе. Если агент наследует модель чата, пользователь явно выбирает модель только для этого испытания. Выключенного агента можно испытать до включения; удалённый или архивный агент недоступен.

## Что подтверждает результат

- `prompt_sent`: получен ответ на запрос с сохранённым системным промптом. `promptSha256` — SHA-256 его фактически отправленных UTF-8 байтов. Это **не доказательство послушания промпту**.
- `model_response`: модель выполнила короткое арифметическое задание и вернула свежий идентификатор попытки в точном JSON-формате. Это диагностический контракт, не оценка общего качества.
- `project_search`: только при выбранном режиме поиска. Модель запросила разрешённый инструмент; сервер действительно выполнил embedding и чтение текущего закреплённого индекса. Следующий ответ подтвердил фактические ID найденных источников либо пустой результат. Наличие подходящих документов и качество поиска этот статус не гарантирует.

Без инструментов успешное испытание допустимо. Для поиска требуется явно заданное `permission.read: allow` или `ask`; при `ask` пользователь передаёт `toolConsent: true` в неизменяемом запросе. Отсутствующее разрешение и `deny` не разрешают поиск. Произвольные shell, запись файлов, внешние MCP и inference через нативный OpenCode не выполняются. Approved learning в контекст этого диагностического задания не добавляется.

Пределы одной попытки: до двух chat-вызовов с максимумом 256 выходных токенов каждый; меньший настроенный `maxOutputTokens` соблюдается и в запросе, и в резерве контекста. Разрешены один embedding-вызов для выбранного поиска и суммарно до 8 КиБ текста ответов. Работа ограничена сигналом 90 секунд; lease — 100 секунд. Транзакции результата имеют локальные `lock_timeout=1s` и `statement_timeout=3s`. Контекст проверяется по известному окну модели без обрезки промпта; неизвестное окно не подменяется выдуманным значением.

## API и права

Все маршруты требуют текущую рабочую роль проекта, минимум «Разработчик», и человеческую сессию. Результаты и отмена доступны только владельцу попытки; главный администратор не получает доступ к чужим результатам по своей роли.

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/projects/:projectId/agents/readiness` | Общая загрузка метаданных и последней собственной попытки каждого агента; без inference. |
| `POST /api/projects/:projectId/agents/:agentId/readiness-trials` | Явный запуск; ответ `202` с сохранённой попыткой. |
| `GET /api/projects/:projectId/agents/:agentId/readiness-trials/:trialId` | Чтение собственной попытки, включая сохранённый результат. |
| `POST /api/projects/:projectId/agents/:agentId/readiness-trials/:trialId/cancel` | Отмена с `{expectedRevision}`; устаревшая ревизия даёт `409`. |

Тело запуска: `{requestId, expectedRevision, expectedAgentPin, modelId, expectedModelPin, tool, toolConsent?}`. `tool` — `none` или `project_search`; `requestId` — UUID. `expectedRevision` проверяет актуальность полного набора назначений только при создании. Неизменяемый snapshot хранит выбранного агента, промпт, параметры, модель и при необходимости индекс. Изменение другого агента не делает прошлый результат устаревшим.

Состояния: `queued`, `running`, `succeeded`, `failed`, `cancelled`, `interrupted`. Receipt существует уже в очереди, но проверки имеют `not_run`. Только успешно выполненные проверки получают `passed`. `current`, `staleReason` и `canCancel` вычисляет сервер. После изменения соответствующего промпта, модели или выбранного индекса прежний результат сохраняется как исторический и не становится новым подтверждением.

## Повторы, флаги и восстановление

Exact replay того же `requestId` и тела возвращает сохранённую попытку без нового вызова модели. Изменённое тело с тем же ключом даёт `409`. Новый запуск после `failed`/`interrupted` требует нового ключа. Одновременные собственные попытки одного агента сериализуются.

Маршруты испытаний намеренно освобождены от общего stateless feature gate: иначе потерянный ответ о запуске нельзя было бы безопасно перечитать повтором после выключения функции. Stateful сервис проверяет `agents`, `model_chat`, `group_chat`, `model_hosting` перед новой попыткой и каждым новым вызовом; выбранный поиск дополнительно требует `project_search`, включая проверку непосредственно перед RAG-запросом. Чтение и отмена остаются доступными при выключенных флагах. Уже полученный оплаченный ответ не отбрасывается только из-за выключения флага; свежие ACL, pins и отмена всё равно проверяются перед фиксацией.

Каждый вызов проходит существующий журнал использования: chat — `verification`, embedding — `project-search`, с общим `operationId` попытки. Неизвестное количество токенов остаётся `null`, не нулём. Receipt usage суммирует только chat-вызовы; embedding записывается отдельно в журнале.

Миграция каталога 20 создаёт owner-scoped таблицу попыток с неизменяемым source/request и terminal receipt. Исторические миграции не переписываются. Просроченный lease становится `interrupted`; рестарт не повторяет оплаченные действия автоматически. При блокировке БД отмена или terminal write завершается ошибкой, сохраняя существующий lease для последующего восстановления, а не выдавая ложное подтверждение отмены.

## Проверка реализации

Общий целевой backend-прогон двух функций: **215/215**, 0 пропусков, все 11 запланированных файлов выполнены. Он включает 56 миграционных проверок, learning, групповой чат, исследование и реальные Nest HTTP-маршруты. Результат сохранён отдельно в `.run/agent-readiness/frozen-final/`.

После добавления отрицательных сценариев отдельный прогон испытаний: **104/104**, 0 пропусков. В области `src/agent-readiness` покрыты 100% строк и функций, 97,89% ветвей; это не покрытие всего проекта. Source-хеши до и после совпадают; отчёт — `.run/agent-readiness/branch-coverage/`. Эти прогоны пересекаются, их количества не складываются.

Frontend после повторного независимого ревью: **184/184**, 0 пропусков, TypeScript и build проходят; узкий trial-срез — 100% строк и функций, 93,42% ветвей. Проверены сохранение точного повтора при отмене другой попытки и возврат к режиму без инструмента, если выбранный поиск стал недоступен. Квитанция исходников и результатов — `.run/coverage/agent-readiness-frontend-p2/`.

Браузер 857×789 на собственном QA: metadata и открытие окна не вызывают модель; явный success, сохранение после reload, отмена выполняющейся попытки и failed-контроль дают соответствующие состояния. Три явных запуска сделали три provider-вызова. Nest, SQL, ACL, pins и ledger настоящие; provider, сессия и списки проекта — контролируемые фикстуры. Socket.io, native OpenCode и RAG search этим браузерным стендом не проверялись; основной сервер не использовался как upstream. Скриншоты сохранены в `.run/agent-readiness/browser/`.

Проверены max-one pool, owner isolation, CAS/idempotency, отзыв роли и смена pins во время ответа, отмена после выключения флага, реальные SQL-блокировки, меньший настроенный бюджет ответа, строгий тип режима инструмента и сохранность данных при переходе 19→20. Provider inference и RAG-ответы контролируются фикстурами; это не приёмка платного провайдера или нативного OpenCode.

Локальная схема 19 обновлена до 20 после свежей копии и репетиции восстановления на отдельной QA PostgreSQL. До запуска сервисов совпали проекции прежних данных всех 101 таблицы. После запуска отдельно проверены identity процессов, реестр, readiness, исходники, runtime-хеши и снимки. Различия старых таблиц ограничились служебными отметками активности, регистрацией verifier и временем проверки очистки загрузок. Локальное обновление не подтверждает production-развёртывание или внешнее аварийное восстановление.
