# Готовность установки в один клик — 17 октября 2026

**Исторический аудит до исправлений.** Ниже сохранены исходные воспроизведения. После него подготовлены MCP 0.2.0/протокол 2, удаление старых команд записи, восстановление подтверждений, переподключение без потери ID, защита очереди/привязки и автономный macOS ARM64-пакет. Актуальные результаты — [доработка установки](installation-hardening-2026-10-17.md). Установленный у пользователя старый MCP автоматически не обновлялся; универсальная готовность произвольного инструмента по-прежнему не подтверждена.

**Решение: NO-GO для обещания «любой скилл, MCP или плагин готов к работе одним нажатием».** Основной путь через очередь умеет доставлять поддерживаемые готовые текстовые пакеты. Он пока не подтверждает работоспособность инструмента в OpenCode. В том же MCP остаётся старый путь записи с более слабыми гарантиями; его проблемы воспроизведены через настоящий MCP-протокол.

Это аудит текущей реализации, а не отчёт об исправлении найденных проблем. Код приложения, установленный на Mac мост, пользовательские конфигурации и привязки в этой проверке не менялись. Созданы этот отчёт и диагностические артефакты в `.run/install-readiness-20261017/`.

## Блокеры и ограничения

### 1. Старый инструмент MCP обходит гарантии нового установщика

`src/index.ts:219` по-прежнему публикует `install_asset`. Его обработчик принимает произвольный `targetPath` и пишет напрямую, без подключения устройства, привязки проекта, серверной проверки роли, квитанции и общего журнала изменений. Это доступный инструмент локального MCP; браузерный Store использует другой путь через очередь. Наблюдения не означают наличие анонимной HTTP-записи с сайта.

Через настоящий `tools/call` на временном проекте воспроизведены четыре случая:

1. У неподключённого MCP установка заменяет существующий SKILL.md с ручными изменениями.
2. Имя плагина с компонентами `..` создаёт файл вне переданного проекта, в пределах собственной тестовой папки.
3. Удаление скилла рекурсивно удаляет его папку вместе с посторонней личной заметкой.
4. Невалидный JSON конфигурации принимается за пустой объект и заменяется новой конфигурацией.

Основание: `mcp/neurocenter-asset-sync/src/tools/install-asset.ts:36,54,65,69,77,94`. Второй старый инструмент, `install_plugin_bundle` (`src/index.ts:247`, `src/tools/bundle.ts:246`), также имеет отдельную реализацию записи и удаления без квитанций; это установлено чтением кода, его отдельный сквозной вызов здесь не проверялся.

**Что делать первым:** закрыть старые изменяющие инструменты либо перевести их на тот же контракт задания с projectId, разрешённым пакетом, привязкой, проверкой прав и квитанцией. Нельзя оставить их альтернативным способом обойти защиту ручных файлов. Проверить и доставку обновлённого MCP уже подключённым компьютерам.

### 2. Успешная доставка не подтверждает готовность инструмента

Новый установщик заканчивает после `commitChanges`, возвращает количество файлов и пояснение о следующем запуске OpenCode. Worker записывает `succeeded`; модалка показывает «Установка завершена» и «Установлено».

В диагностике корректный по манифесту MCP-пакет с программой, немедленно завершающейся с ошибкой, успешно установлен в файлы. Отдельный запуск этой программы завершается с кодом 1. Это подтверждает отсутствие проверки запуска, а не ошибку проверки SHA-256.

Основание: `bridge/installer.ts:255–268`, `bridge/worker.ts:205–218`, `frontend/src/modules/Store/storeDetails.ts:27–47`.

**Нужно для целевого UX:** различать доставку, необходимость перезапуска/входа, проверку запуска, готовность и неисправность. Для MCP подтверждать handshake и доступность инструментов с таймаутом; для плагина — загрузку в поддерживаемом OpenCode. При отсутствии подтверждения показывать непроверенное состояние. Для внешнего OAuth сохранять явный шаг входа пользователя. Не объявлять произвольный плагин рабочим только потому, что его файл записан.

### 3. После записи файлов возможен противоречивый серверный статус

Воспроизведение: worker успешно записывает скилл; финальный запрос `succeeded` теряется **до сохранения сервером**; обработчик ошибки отправляет `failed`. Файлы остаются установленными, серверный статус — ошибка. Если запрос дошёл, но потерялся только ответ, поведение может отличаться; этот случай нельзя смешивать с воспроизведённым.

Основание: `bridge/worker.ts:205–227`. Серверный список установок выводится из успешных заданий (`devices/device-installations.ts:11–14`), а heartbeat не сверяет локальные квитанции. Поэтому такая установка не попадает в список. При неуспешном обновлении в списке может сохраняться прежняя успешно зарегистрированная версия. Ручное удаление или изменение локальных файлов тоже не отражается в списке до следующей операции.

Повтор через новый установщик умеет сверять локальные файлы; это полезная защита, но пользователю приходится инициировать восстановление состояния.

**Нужно:** сохранять локальный результат с идентификатором задания до отправки подтверждения, повторять доставку результата без повторной записи и сверять квитанции при восстановлении связи. Отдельно обрабатывать истёкшую аренду и свежие права; не превращать неизвестный результат в подтверждённое отсутствие установки.

### 4. Скилл не является полностью доставляемым пакетом с зависимостями

Сервер формирует один SKILL.md. Списки MCP/плагинов сохраняются в метаданных и манифесте, но не разрешаются в устанавливаемые пакеты. Диагностика подтверждает: скилл с отсутствующими MCP и плагином успешно записан без их установки.

Основание: `devices/device-artifacts.ts:66–75`, `bridge/worker.ts:203–211`. Модалка честно поясняет, что список связей не проверяет установку на компьютере (`StoreDetailsModal.tsx:154–156`).

Не поддержаны доставка дополнительных ресурсов скилла (`scripts`, `references`, `assets`), план установки зависимостей, согласование их версий, конфликты, циклы и восстановление частично установленного набора. У MCP/плагинов допустим готовый текстовый пакет, но нет общей сборки исходников, установки его произвольных зависимостей и доставки пользовательских бинарных ресурсов. Это заявленные ограничения формата, а не «всё проверено».

**Нужно:** сначала проверяемый план состава установки и недостающих настроек. Для поддерживаемых пакетов — закреплённые версии зависимостей, установка и проверка результата всего набора. Неподдерживаемые форматы должны иметь понятную причину до нажатия кнопки.

### 5. Полностью автономная установка моста и совместимость клиентов не готовы

`bridge-dist/install.sh:6–25` и `install.ps1:5–17` требуют установленный Node.js/npm и выполняют `npm ci`. Поэтому требование установки всех компонентов только с площадки, без внешнего реестра зависимостей, пока не выполнено. Установщик OpenCode и установщик моста — разные продукты; отсутствие `npm install -g opencode-ai` не устраняет зависимость самого моста от npm.

Heartbeat содержит платформу, корень и привязки, но не версию сборки моста, архитектуру, версию протокола и список возможностей (`bridge/workspace.ts:190–200`). Сервер не может заранее отличить совместимого клиента от старого. Работающий worker защищён PID-lock; проверка безопасного обновления и замены уже работающего worker не выполнена.

**Нужно:** проверяемые артефакты для заявленных ОС/архитектур с закреплённым runtime и зависимостями, отчёт версии/возможностей, проверка совместимости до постановки задания и управляемое обновление клиента. Приёмку проводить на настоящих поддерживаемых ОС, включая native LanceDB и выбор папки.

### 6. Есть дополнительные границы восстановления и версий

- У MCP/плагинов доставка закреплена на сохранённую версию пакета. Для скилла `DeviceArtifacts` читает текущую Markdown-версию и возвращает конфликт при запросе другой (`device-artifacts.ts:56`). Полноценная установка старой версии скилла не готова; повтор старого задания после изменения head тоже может требовать выбора актуальной версии.
- При ручных правках новый путь безопасно отказывает, но нет завершённого пользовательского сценария сравнения, сохранения своего варианта и последующего ремонта установки.
- Удаление проекта или отзыв доступа не удаляют ранее записанные локальные файлы. Нет автоматического безопасного сценария очистки осиротевших установок; наличие файлов не должно трактоваться как продолжающее действовать серверное разрешение.
- Журнал обеспечивает восстановление после проверенных прерываний процесса. Это не доказательство восстановления после потери питания, полного диска во всех фазах или аварии во время самого восстановления. В частности, документация уже допускает ручную проверку `recovery.lock`.

## Текущий компьютер и порядок доработок

Для установки недостаточно online-компьютера: пользователь должен выбрать общую папку и подтвердить привязку проекта. Неизвестная папка не подставляется автоматически; отсутствие привязки объясняется в интерфейсе.

Порядок работ:

1. Закрыть старые изменяющие MCP-инструменты и добавить отрицательные регрессии для четырёх воспроизведённых случаев. Доставить исправленный клиент.
2. Закрыть неопределённый результат после локальной записи: устойчивое подтверждение, сверка квитанций и проверка реального состояния.
3. Сделать единый план установки и понятные состояния: записано, нужны настройки/вход/перезапуск, проверяется, готово, требует исправления. Проверять поддержку и запуск.
4. Поддержать согласованный формат ресурсов и зависимостей; затем исторические версии скиллов и ремонт конфликтов без потери пользовательских файлов.
5. Подготовить автономные клиентские артефакты и версионированный протокол; провести реальные тесты ОС, обновления клиента, отказов сети/диска и загрузки в OpenCode.

Приёмочный критерий: после однократного подключения компьютера и выбора папки пользователь запускает установку разрешённого пакета одной кнопкой, видит недостающие настройки, получает подтверждённый результат в поддерживаемом OpenCode и может безопасно повторить, обновить, восстановить или удалить установку. До выполнения этих условий обещание универсальной готовности преждевременно.

## Внешний контракт

Формат скиллов, обнаружение и ограничения полей сверены с [официальной документацией Agent Skills](https://opencode.ai/docs/skills/). Загрузка локальных плагинов и механизм их зависимостей описаны в [документации Plugins](https://opencode.ai/docs/plugins/); конфигурация и авторизация внешних MCP — в [документации MCP servers](https://opencode.ai/docs/mcp-servers/). Эти документы помогают определить проверяемый контракт, но не заменяют приёмку закреплённой в проекте версии OpenCode 1.14.48. Автоматическая установка зависимостей скилла не следует из наличия в нашем SKILL.md списков `mcp`/`plugins`.
