## Связанная цепочка проекта, каталога и локального моста

В проекте `prj-a844b42e-c753-4ea1-9cec-b14ddb1bdb84` через обычный UI подтверждён отдельный QA-мост, выбран компьютер, проверена папка и подтверждена привязка `990e561c04e8a96b227d00f8bce2bd7e93a0974be3b3a04cf95194776955a125`. Использован собственный профиль, архив моста 0.9.25 и встроенный runtime; личный профиль оператора не менялся.

Нативное окно выбора общей папки действительно открылось. Mac был заблокирован, окно истекло через штатные две минуты; UI показал ошибку и возможность повтора. Отмена недоступна для этой операции — открытый пробел сценария. Общая папка затем задана поддерживаемой CLI-командой только в своём профиле; это предусловие, а не успешный выбор папки через GUI. ## Воспроизведённые и исправленные дефекты

1. Ссылка установки из настроек открывала прежний трёхшаговый мастер. Настройки, восстановление pairing и переход из провайдера используют общий построитель основного мастера. По уточнению пользователя прежний UI и его fallback удалены: исторические `step`, `legacy`, `connect` и `addComputer` ссылки открывают только основной мастер. Истёкший код удаляется при восстановлении; проект, `extension` и hash сохраняются. Проверены фактические переходы, помощь, сворачивание, повторное открытие и обновлённая статья справки. Выключенный флаг оставляет основной интерфейс состояния и восстановления; этот вариант подтверждён компонентными проверками.
2. Каталог только чат-моделей требовал компьютер для OpenCodeRAG. Выбор назначения эмбеддингов теперь показывается при наличии соответствующих моделей. Реальный UI проверен до и после появления embedding-карточки; неподдерживаемый embedding-провайдер не запускался.
3. Настройка провайдера с подтверждённым пустым списком компьютеров заканчивалась предупреждением и двумя неактивными действиями. Администратор получает «Подключить компьютер». Фактический клик открыл основной четырёхшаговый мастер и сохранил проект. При непрочитанном списке и без прав это действие не предлагается.

Для новых дефектов сначала сохранены падающие регрессии: 2 для лишнего RAG-блока и 1 для отсутствующего продолжения. После удаления старого мастера: 7 затронутых frontend-наборов, **79/79 PASS**, пропусков нет; production TypeScript `--noEmit` PASS. После последней правки справки отдельно повторены **8/8 PASS** проверок инструкций. Это частные проверки, не новый полный релизный прогон; два результата не складываются, поскольку пересекаются. Регрессии ModelCatalog проверялись отдельно до удаления старого мастера.

Кандидаты применены к копии frontend без перезапуска сервисов с отдельными записями исходных и конечных хешей. Основной checkout и установленный личный мост не изменялись во время тестов.

## Отказы окружения и ограничения

Первый запуск остановлен из-за неверного формата тестового ключа шифрования. После исправления окружения подключение модели принято через UI. Это не дефект хранения ключей приложения.

Второй запуск завершился после `PROCESS_INSPECTION_FAILED/ETIMEDOUT` в контроллере QA: глобальная проверка процессов имела таймаут 1 с и период 25 мс. Сырые FAIL и журналы сохранены. Отдельный контроллер восстановления использует проверку только собственной группы, ограничение 5 с и период 250 мс; режим UNKNOWN остаётся запрещающим. Подняты те же сервисы на той же собственной базе, данные проверены через UI. Общий production-контроллер не менялся.

При совместной работе браузеров наблюдались временные 503 проверки входа и таймауты PostgreSQL-подключений. После восстановления доступности наблюдались 17 idle-подключений при `max_connections=100`, открытых транзакций не было. Этот поздний снимок не объясняет историческую причину. Сбой сохранён как **неразобранная проблема доступности**, а не закрыт увеличением таймаутов или перезапуском. Полной стабильности под нагрузкой этот проход не доказывает.

Dev HMR после восстановления перезагрузил открытую форму скилла. До reload введённое оставалось в форме с явной ошибкой сохранения; сохранение из той же формы после reload не подтверждено. Последующее ручное восстановление ввода и сохранение v2 подтверждены отдельно.

Текст плана стенда предполагал Docker-путь резервного копирования, но фактическое окружение не передало `DEV_POSTGRES_CONTAINER` и не содержало `pg_dump` в PATH. Фактический запрос вернул 503 без запуска дампа. Наличие контейнера само по себе не считается готовностью резервного копирования.
