# Восстановление сообщения и совместимость ядра RAG

Готовый срез выделен из `main` `3f8c2ef3`: сохранять неподтверждённое сообщение при сбое отправки и разрешать управляемое ядро совместимого прежнего RAG-пакета по возможности ядра. Изменены семь файлов реализации и тестов; миграций нет.

## Поведение

До исправления отправка очищала поле ввода, а неподтверждённое сообщение оставалось только в памяти компонента. После отказа и обновления страницы PDF возвращался в черновик, текст терялся. Теперь ограниченный журнал сохраняет пользовательский ввод и прежний requestId по владельцу, модели, проекту и диалогу. История с совпадающим подтверждением удаляет журнал. Автоматической повторной отправки нет; локальное хранилище не становится источником ответов или прав.

У прежнего одобренного OpenCodeRAG есть фиксированный совместимый ABI, описанный через `localUi`, без нового поля `ragCore`. Сервер ошибочно требовал UI-возможность клиента для операции ядра. Теперь операции ядра требуют `hosted-rag-core-v1`, затем прежнюю строгую проверку ABI. Некорректный явный `ragCore` не получает fallback. Для операций интерфейса остаётся отдельная UI-возможность. Проверки текущих прав, привязки, экземпляра папки, одобрения, версии, манифеста и модели сохранены.

## Проверки

- На выделенной ветке поверх `main`: frontend **137/137**, backend **51/51**, оба TypeScript-check прошли. Все процессы проверок завершены, личные профили не использовались, зависимостей из сети не скачивали. Backend 51 состоит из первоначальных 44 и отдельно выполненных семи inspection-проверок: ошибочный несуществующий третий фильтр первого запуска не выдан за выполненный тест.
- Production-сборка frontend (`tsc && vite build`) прошла на `e1eeadfd` с cached Node.js 24.22.0 без загрузки зависимостей; артефакты созданы только в отдельной папке `.run` этой ветки. Сборка предупредила о JS-чанке больше 500 КБ; production runtime этим не проверен.
- Причинные RED → GREEN и независимое чтение исправлений сохранены. Новые production-файлы и тесты побайтово совпадают с проверенным кандидатом C `0f7db83a`; сам C также содержит отдельную разработку квот.
- В реальном desktop UI C сообщение с PDF пережило разрыв отправки и обычное обновление страницы. До явного повтора нет turn POST. Явный повтор дал 201; после следующего обновления у восстановленного запроса ровно одно сообщение и один ответ, без локального failed-дубликата; прежняя переписка сохранена.
- Отдельно сервер фактически сохранил PDF, а ответ был оборван. Независимое чтение собственной БД до повтора подтвердило один attachment. Повтор из UI использовал тот же requestId и вернул тот же attachment ID. Удаление вложения до отправки дало пустой `attachmentIds`; после обновления удалённый файл не вернулся.
- Через UI фактический мост установил одобренный RAG, локальная форма сохранила параметры, stdio-диагностика нашла пять инструментов. После исправления запущена настоящая индексация: два фрагмента, размерность 8, полная синхронизация с сервером. Public receipt, поколение, SHA снимка и реальные строки сервера согласованы.
- Инструмент агента действительно вызвал `rag_search`; результат содержит контрольный текст из `README.md:1–6`, оценку сходства и точные generation/snapshot. Вопрос не содержал сам контрольный текст. API модели и эмбеддингов — собственная синтетическая зависимость; качество настоящей модели не оценивалось.

В общей приёмке синхронизация и поиск остаются частичными: независимо не выполнена полная сверка локальных строк, векторов и digest с сервером; протокольный провайдер передал инструменту точный контрольный текст как query. Реальный поиск и происхождение результата подтверждены, качество семантического поиска — нет. Эти ограничения не выданы за два полных PASS.

Первичный machine-readable ledger C: `output/playwright/recovery-c-20261028/case-ledger.json` в исходном рабочем checkout `bridge-first-local-setup`. Raw входят в ignored output; пути в текущей машине сохранены в handoff. Локальный результат не заменяет CI, другие ОС, системное окно заблокированного Mac или production.

Стенд C повторно использует только собственные PostgreSQL/Minio volumes и ключи. До запуска сверены четыре БД, ключи 175 таблиц и байты S3 с проверенным экспортом B. Это reuse, а не выполненный dump-restore. Исторические отказы и неизвестные исходы A/B сохранены отдельно. Общая приёмка всего приложения продолжается.
