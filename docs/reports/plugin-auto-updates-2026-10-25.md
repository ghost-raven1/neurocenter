# Автообновление установленных плагинов — 25 октября 2026

Реализован личный opt-in для обычного установленного `kind=plugin`, ограниченный владельцем, проектом, компьютером, текущей привязкой папки и ID плагина. После включения проверяется **точная версия, закреплённая и одобренная админом проекта**. Публикация нового head в общем каталоге сама не меняет pin, одобрение или установленную версию. Это первый согласованный режим; автоматический выбор любой будущей catalog latest не реализован.

## Пользовательский путь

В текущей строке установленного плагина доступна кнопка «Автообновление». Закрытая кнопка не запрашивает приватную политику. В окне видны режим, результат последней проверки и последнее задание. Включение требует актуальных прав разработчика и рабочего подключения моста; `plugin_auto_updates` зависит от `tool_installation`.

1. Владелец явно включает режим для выбранной установки.
2. Появление новой catalog version даёт статус ожидания выбора и одобрения админом проекта.
3. Админ выбирает exact version/SHA проекта и одобряет обычный план установки.
4. Планировщик через существующий `DeviceJobs.create` ставит обычное `install` на выбранный компьютер. Существующие проверки назначения, manifest, зависимостей, привязки, одобрения и возможностей моста сохраняются.
5. Обычные квитанции моста отражают успех или отказ. Завершённый отказ не повторяется автоматически. «Проверить сейчас» — явное повторное решение с актуальной ревизией.

Проверка назначения выполняется каждый час; scheduler просматривает due-политики раз в минуту. Offline даёт ожидание подключения. Изменение конфигурации, схемы локальной настройки, зависимостей или готового комплекта требует ручного плана. Supply управляемого Codex-коннектора исключён: используется его мастер провайдера.

Выключение режима и флага сохраняет историю, доступную отмену и восстановление обычного установщика. Выключение политики останавливает будущую постановку; принятое задание отменяется отдельно через существующую операцию. Уже принятое задание продолжает подчиняться текущим правам и обычному флагу установки.

## Контракты восстановления

- Политика имеет неизменяемый tuple, CAS revision и ключ изменения режима; точный повтор не создаёт второй audit event.
- Scheduler использует PostgreSQL lease и `SKIP LOCKED`. До отправки сохраняются полный ограниченный `JobInput` и **исходная роль запроса** `pending_role`.
- Общая функция `deviceJobRequestHash` совпадает с прежним hash обычной очереди. Рестарт и неизвестный ACK сначала сверяют `bridge_job_requests`, сохраняя key.
- Admission держит policy `FOR SHARE` в той же транзакции, что принимает задание; disable/recheck держит `FOR UPDATE`. Выключение не пересекает приём нового задания.
- Явный recheck может сбросить unadmitted request только после подтверждённого отсутствия receipt под этим lock либо после известного terminal receipt. Поздний worker со старым lease отклоняется.
- `actor_role` остаётся текущей ролью политики; `pending_role` сохраняет идентичность уже отправленного запроса. Смена роли между неизвестным ACK, выключением и повторным включением не меняет hash старой квитанции. Новые effects проверяют действующие назначения.
- Проверка authorizer выполняется после ожидания policy lock. Чтение устройства и истории установки использует тот же borrowed client: нет вложенного ожидания ещё одного client из удерживаемого store pool.
- UI сохраняет неизвестный save для точного повтора; поздние read/save/cancel не применяются после смены пользователя, роли, папки или закрытия окна.

Миграция **41** добавляет только метаданные политики. Физический контракт измерен на выделенном PostgreSQL **16.14**, порт **59820**: **39 фактов**. Проверены ledger **0..41**, неизменность прежних checksums и физических фактов, текущий readiness и отказ readiness после удаления identity guard. Каждая fixture-база имела собственный UUID и удалена; рабочий PostgreSQL 5432 не использовался.

## Проверки

- Catalog: **95/95** в семи выбранных файлах, `--maxWorkers=1`: новая политика/валидация, существующие request receipts, очередь/права, планы/графы, совместимость, feature gate.
- PostgreSQL: **12/12**, собственная база. Основной путь использует реальные `PluginRepository.create/update`, `ProjectAssetRepository`, `AccessDb`, `InstallPlans.prepare/decide`, scheduler, `DeviceJobs.create/claim/authorize`, `completeDeviceJob` и чтение `DeviceInstallations`. После fixture success установлена версия 2, новый job ровно один. Store pool ограничен **одним** client.
- PostgreSQL конкуренция: CAS/replay, concurrent claim, disable до admission, disable ждёт уже admitted queue transaction, потерянный ACK/restart, explicit recheck/старый lease, immutable tuple, fresh authorizer после lock, **исходная роль A → disable B → enable B**. Последний сценарий сначала воспроизвёл 409 и после исправления прошёл.
- React + настоящий Ant Design + jsdom: **7/7** — закрытый control, понятная область каталога, exact retry при неизвестном ACK, accepted save при ошибке внешнего refresh callback, feature OFF с disable/cancel, поздние save/cancel при смене actor, смена папки.
- Catalog и frontend: `tsc --noEmit` завершились с кодом 0.
- Обычный установщик: **45/45** существующих `installation-files-safety.test.ts` и `install-set-installer.test.ts` на временных macOS-папках. Проверены ручные изменения, сохранение пользовательского opencode.jsonc, связанные зависимости, восстановление журнала и откат после ENOSPC. Пользовательские установки не изменялись.

Измерение: `scripts/test/plugin-auto-updates-measure-contract.mjs --write-contract`, затем отдельный запуск `--verify-all`. Обе команды требуют `PLUGIN_AUTO_UPDATE_TEST_ADMIN_URL` с явно выделенным loopback non-default PostgreSQL. Локальные квитанции: `.run/plugin-auto-update-verification/{schema,ledger}-receipt.json`.

## Ограничения и последующая приёмка

Это выбранные проверки функции, а не полный регресс продукта и не процент покрытия. Реальная установка пользовательского плагина, обновление рабочего моста, установленный архив, браузерная приёмка приложения, CI и production в этой ветке не выполнялись. Нет внешних скачиваний и запросов платного inference. PostgreSQL completion использует контролируемый bridge receipt; файловые fixture-проверки установщика — отдельное свидетельство.

После интеграции: проверить окно в текущем приложении, повторить readiness с последующими миграциями и включить в общий регресс parent-задачи. Future-version trust policy и автоматическое продвижение project pin требуют отдельного продуктового решения; не считаются выполненными этой функцией.
