# Причина отказа системного агента — 26 октября 2026

Фото пользовательского Linux показывает сохранённую диагностику и отказ координатора с **0/5 зарезервированных шагов модели**. Прежний общий текст не позволял отличить отклонённый контекст, права, изменение версии или недоступность зависимости. Причина старой ошибки не сохранялась отдельно, поэтому восстановить её из этой квитанции нельзя. Предыдущее фото с 1/5 описывает другой запуск; резервирование само по себе не доказывает отправку запроса, ответ или оплату.

## Изменение

`SystemRoleService.fail` сохраняет безопасное объяснение, этап и актуальное число резервирований из заблокированной строки операции. Статусы HTTP и точные известные сообщения приложения преобразуются в фиксированные категории с действием для пользователя. Произвольные тела/сообщения провайдера, пути, токены и stack не публикуются. Неизвестная причина явно остаётся неизвестной.

Отмена, специальный таймаут планирования и запрет записи после терминального состояния/смены lease сохранены. Новых повторов, обращений к модели, настроек, флагов, миграций и изменений лимитов нет. Старые записи остаются со старым текстом; новое объяснение появляется при следующем самостоятельно подтверждённом запуске после обновления сервиса.

## Причинная проверка до резервирования

Настоящий `SystemRoleRunner` с управляемыми зависимостями воспроизводит один возможный вариант отказа: `contextWindow=4096`, отсутствующий `maxOutputTokens`, системный резерв ответа 4096. Оценка сообщений вместе с резервом превышает окно, даже для «Привет»; диагностика сохранена, `reserveCall` и `infer` не вызваны. Контроль с явно заданными `contextWindow=8192`, `maxOutputTokens=1024` завершает четыре вызова заглушки, каждый с тем же пределом 1024. Продукт автоматически настройки не меняет.

Это гипотеза для пользовательского запуска: реальные настройки модели, причина ошибки и работа Linux не подтверждены. Общий счётчик 0/5 также совместим с другими отказами до резервирования.

- Новый тест сохранения ошибки через настоящий `SystemRoleService.fail`: RED **21 FAIL / 8 PASS**, GREEN **30/30** после добавления контроля отсутствующей строки. Проверены известные/неизвестные ошибки, приватность, актуальный этап/счётчик, другая lease, терминальные состояния и отсутствие вызовов inference.
- Шесть связанных backend-наборов: **124/124** без пропусков — failure, service, coordinator, policy, RAG context, guidance. Среди них публичный scheduler/receipt, прежний таймаут и два контроля контекстного окна.

- Изолированная сборка `catalog-service`: PASS; квитанция `198f4fd1-1d92-41de-964b-b032feca7b92` подтвердила `sourceCurrent`, `liveOutputsUnchanged`, `dependencyLinksUnchanged`, `candidateInputsUnchanged`.
