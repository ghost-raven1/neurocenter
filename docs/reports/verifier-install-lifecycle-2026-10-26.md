# Подготовка зависимостей отделена от запуска — 26 октября 2026

Пользователь спросил, зачем dev.sh up скачивает зависимости, если есть install. В коде up действительно выполнял безусловный корневой npm ci, восстанавливал зависимости npm ci после ошибки компиляции и собирал образ snapshot-verifier. Такая подготовка могла снова обратиться к npm при старте уже установленного проекта.

Теперь install/build владеют подготовкой образа через buildDevSnapshotImage. Эта операция проверяет настройки build, CA/proxy/DNS/TLS, собирает и инспектирует образ; PostgreSQL, ключи и runtime state для неё не нужны. Готовый SNAPSHOT_VERIFIER_IMAGE по-прежнему только проверяется.

Up/watch после проверки Docker выполняют только inspectDevSnapshotImage, до ассетов, npm-компиляции, PostgreSQL и остановки прежних процессов. Выбранный immutable image ID передаётся проверке ключей и runner без повторной сборки/разрешения mutable tag. Нет общего npm ci и автоматической установки после ошибки компиляции. Локальный npm run build сохраняется; при отказе команда указывает install и сохраняет прежний запуск. Для отсутствующего явно выбранного prebuilt-образа инструкция предлагает загрузить его или убрать SNAPSHOT_VERIFIER_IMAGE перед install/build, чтобы не повторять неработающий выбор. Up не проверяет исходную свежесть произвольного образа и не защищает его от внешнего удаления после inspect.

Профили ассетов/моделей, установка Compose, явное восстановление зависимостей при build, обновление уже установленного моста и signing identity не переработаны. Поэтому отсутствие npm ci не означает отсутствие любого сетевого действия в full/standard-профиле. Удаление образов и node_modules не выполнялось.
