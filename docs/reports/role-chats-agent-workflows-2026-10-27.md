# Отдельные чаты ролей и BMAD/OpenSpec — 27 октября 2026

Реализован связный сценарий: проект → привязанная папка → задача по методике → изменение кода → независимые команды проверки → сохранённый результат. Сервисные роли получили отдельные приватные чаты. Сводка нового ответа создаётся после успешных ответов как минимум двух уникальных агентов.

Продуктовая цель — мощная и удобная площадка командной работы. Проект связывает участников и права, общие решения и задачи, агентов, навыки, плагины, OpenCode и проверяемые результаты. Текущий срез укрепляет эту основу; общая готовность всех командных сценариев им не объявляется. Дальнейшая совместная дискуссия, последовательный контекст и общий механизм инструментов имеют отдельные условия в [очереди командных агентов](../agent-discussions-tooling-backlog-2026-10-23.md).

Ветка `feature/unified-agent-workflows`, исходная ревизия main `0249e2916b681d86655f3a8cf02e1e60f9ef7988`. Изменение OpenSpec: `role-chats-and-agent-methods`. Исходники и локальная проверка отделены от установки, CI и production. Предыдущий срез инструментов/Playwright находится в отдельном [draft PR33](https://github.com/ghost-raven1/neurocenter/pull/33).

## Поведение

- Пять чатов: Координатор, AI-админ, Автоконфигуратор, Индексатор, Упаковщик. У каждого свои история и черновик. Общий «Сервисный чат» убран из навигации. Новая роль закрепляется сервером и БД; исторические смешанные диалоги доступны владельцу с исходными ID, без переноса сообщений или публикации участникам проекта.
- Один успешный исполнитель возвращает свой ответ без дополнительного synthesis. Ошибки других видны отдельно. После принятия второго успешного уникального ответа появляется общая сводка. Сохранены атрибуция контекста, повтор недостающего ответа, отмена и прежние завершённые итоги.
- В проектной вкладке «Агенты» доступны BMAD, OpenSpec и BMAD → OpenSpec. Совместный режим использует BMAD для требований и архитектуры, затем одну реализацию через OpenSpec. Проверяются закреплённые версии и реальные проектные workflows; автоматической установки нет.
- Задание использует существующую очередь моста. До dispatch сохраняется локальная приватная квитанция, результат сохраняется до ACK. Неизвестный исход не вызывает повторного выполнения. Отмена завершает собственное дерево процессов; уже записанные файлы не откатываются.
- Ошибка настройки сохраняет задачу и показывает следующий шаг. UI различает проверку `passed`, `failed`, `not_run`, показывает наблюдаемые пути/хеши и доступную историю при OFF. Восстановление неизвестного POST сохраняет прежний ключ и папку.
- Перед загрузкой OpenCode-плагина Quirk JSONL читается строго и целиком без мутаций. Повреждение блокирует запуск с `QUIRK_STORAGE_INVALID`; автоматические reconcile, очистка и переиндексация не запускаются. Здоровые append/create/atomic rewrite допустимы. Этот guard не доказывает целостность всех индексов LanceDB.

Сервер фиксирует текст задачи, методику, команды и точную привязку. Файлы читаются при фактическом старте; изменение документа во время ожидания будет использовано исполнителем. Это явно показано в UI и справке. Захват утверждённой ревизии файлов до admission остаётся отдельным протоколом, файловый CAS и ОС-песочница не заявлены.

## Исправления после проверки

Независимые замечания привели к исправлениям: запрет перезаписи непрочитанного pending; сохранение текста при отказе localStorage; восстановление неполной записи; UTF-8 лимит отправки без потери русского черновика; выход из подтверждённого stale-binding отказа; сохранение более свежих durable facts; наблюдение частичных изменений после остановки; URL-encoding Unicode-папки вместо несовместимого raw header.

Первый `opencode run` завершался exit0 без model call, что не принято как успех. Production путь заменён собственным HTTP-сервером с ожиданием финального ответа и независимыми postconditions. Первоначальные неуспешные native/PG прогоны сохранены: нагрузочные timeouts, отказ cleanup при живых собственных соединениях и старое сравнение SELECT* через аддитивную миграцию не скрыты финальными повторами. Неправильный запуск native OpenSpec бинарника через Node — ошибка команды проверки; прямой CLI затем отработал успешно.

## Поставка и оставшаяся приёмка

Исходники моста — **0.9.22**. `agent_method_workflows` выключен по умолчанию, зависит от agents/computer_connections; `service_role_conversations` зависит от system_role_chat. Флаги не заменяют права. Применение требует согласованных Catalog/frontend/flags и нового моста; отключение сохраняет разрешённые history/cancel/recovery.

Следующие отдельные проверки:

1. Установленный архив0.9.22 и рабочая цепочка UI → main backend → подключённый мост → выбранная настоящая модель. Текущая readiness Catalog/flags/RAG/bridge возвращает503; главная БД не использовалась для QA и не перезапускалась.
2. Полные native BMAD и combined workflows на собственной папке; модель должна переиспользовать planning artifacts без двойного PRD/implementation. Unit routing/completion не заменяет эту проверку.
3. Native Linux, CI и production. Windows получает явное отсутствие поддержанного process lifecycle. Общая приёмка всех функций и 100% покрытия не заявляются.
4. Отдельный протокол утверждения ревизии локальных входных документов до постановки в очередь, если потребуется такая гарантия.

Собственный PostgreSQL16.15 работал в ephemeral контейнере на loopback55629 с tmpfs. После проверок точные ID/name/label сверены, контейнер остановлен. Собственные браузерные сессии и временные runtime-профили закрыты/удалены. Пользовательские отчёты, главная БД, установленный мост и ручные профили сохранены.
