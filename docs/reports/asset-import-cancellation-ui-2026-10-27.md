# Отмена импорта и понятный результат — 27 октября 2026

Локально воспроизведены ошибки отмены импорта и перегруженный первый экран. Исправление сохраняет принятую остановку, уже опубликованные карточки и историю. Статус операции и «Новый выбор» показаны перед справкой о поставке; результат отмены свёрнут до количества готовых позиций.

## Причина и изменение

1. Поздний план мог записать `NEEDS_INPUT` поверх уже принятого `CANCELLED`. Запись задания теперь сохраняет завершённые `SUCCEEDED` и `CANCELLED`; worker учитывает возвращённое терминальное состояние.
2. Отмена могла подтвердиться, пока worker ожидал блокировку карточки, после чего worker публиковал её. После получения блокировки карточки worker блокирует строку задания, повторно проверяет отмену и удерживает строку до COMMIT. Если публикация уже пересекла эту границу, подтверждение отмены ждёт её завершения. Порядок блокировок проверен независимо.
3. Запоздавший GET мог снять признак принятой остановки или вернуть терминальный результат в `RUNNING` в том же React batch. Hook сохраняет принятую отмену и неизменяемые терминальные состояния. Явные retry/resolve из `FAILED`, `PARTIAL`, `NEEDS_INPUT` остаются доступны.
4. UI показывает «Остановка запрошена», отключает повторный клик и сохраняет этот статус после reload. Пустого списка результатов нет; технический `PENDING` заменён понятным текстом. Уже готовые карточки не окрашиваются как ошибка отмены. На 1280×720 итог и «Новый выбор» видны с начала страницы без прокрутки.

Это исправление существующего импорта под `asset_sources`, без новой функции, API или миграции. Выключение флага запрещает новый импорт, сохраняя историю и остановку принятого задания; авторизация остаётся независимой.

## Проверка через интерфейс

Собственный стенд `qa-import-cancel.localhost:61849`, in-app Chromium на macOS arm64, desktop 1280×720. Архивы 1.0.0 и 2.0.0 содержат собственные MCP и навык. Управляемая пауза находится после настоящей проверки файлов, до транзакции публикации; CLI не меняет состояние задания и не вызывает импорт или отмену вместо UI.

| Сценарий | Наблюдаемый результат |
| --- | --- |
| Остановить до первой публикации → reload | До исправления UI сохранял обычную кнопку остановки, хотя сервер уже принял запрос. После исправления виден отключённый статус ожидания; итог `CANCELLED`, 0/2, native-карточек нет |
| Остановить после COMMIT первого MCP, до публикации навыка → reload | Принятая остановка сохранена; итог `CANCELLED`, 1/2. MCP, его история и source receipt не изменились, навык не опубликован |
| Выключить `asset_sources` во время импорта → reload → остановить | Новый импорт недоступен с объяснением; история и остановка доступны. Итог `CANCELLED`, прежние карточки сохранены |
| Включить флаг → новый выбор → импорт 2.0.0 | Оба ассета успешны. MCP обновлён до native v2 при прежних ID/имени; новый навык имеет native v1 и инструкцию из источника 2.0.0 |
| Повторить тот же архив клавишей Enter → reload | Успешная квитанция восстановлена. Native head, история и source receipts не изменились; новых редакций нет |
| Повторить остановку после перестановки блоков UI | Итог и «Новый выбор» видны в первом экране; последний `CANCELLED` не изменил ранее добавленные MCP и навык |

Шесть явно запущенных через UI заданий: четыре `CANCELLED`, два `SUCCEEDED`; четыре POST отмены ответили 201. Reload восстанавливает состояние чтением, без нового POST. Рабочий список операций в оболочке стенда подставлен пустым и не является доказательством проверки всех очередей. SQL READ ONLY и чтение собственного skill-файла подтверждают сохранность опубликованного результата. Первая демонстрация UI-дефекта выполнялась на исходном backend; последующие проходы — на пересобранном backend с исправлением.

## Проверки кода

- Причинный серверный RED: 2 отказа и 2 проходящих контроля на базе `1791f99`; те же четыре теста после исправления — 4/4. Расширенный новый набор — 5/5, включая ожидание COMMIT перед подтверждением отмены. Существующий SQL-набор — 9/9.
- Первый смешанный серверный прогон остаётся **14 PASS / 3 FAIL**: три существующих FS-теста отказали при нехватке диска. Делегирующий наблюдатель первого исходного lost-ACK случая подтвердил `CAPACITY_LOW`/507 при запросе 70 544 байт и резерве 1 ГиБ. Это отдельная причина, а не ошибка блокировки строки задания.
- Три исходных FS-теста прошли **3/3** с ограниченным замером `statfs` только для собственных временных fixtures: максимум 512 КиБ на операцию, 4 МиБ суммарно, реальный свободный минимум 128 МиБ. Фактически зарезервировано 366 072 байта, минимально свободно 275 939 328 байт. Реальные FS journal, SQL, lost ACK, assertions и production-резерв 1 ГиБ сохранены. Это функциональная проверка, не доказательство достаточной ёмкости рабочей машины.
- `asset-import-transaction-postgres.test.ts` **не запускался**: действующий admission требует 4 ГиБ, на машине меньше. Проверка и порог не менялись, пропуск не включён в успешный счётчик.
- Причинный frontend RED: сначала 4 отказа для интерфейса остановки; ещё 2 теста воспроизвели терминальный ACK и поздний GET в одном batch. Добавлены также четыре контроля допустимых retry/resolve.
- Первый финальный frontend-прогон: **154/159**, два тайм-аута 5 секунд и три последующих отказа. Изолированный повтор файла восстановления без изменения исходников и тайм-аутов — **30/30**. Возможен перенос неиспользованных mock-ответов после тайм-аута; первопричина задержек не доказана. Неуспешный прогон сохранён отдельно.

Финальный повтор семи frontend-файлов — **159/159, без failed/skipped/TODO**, с прежними тайм-аутами. В наборе 10 новых сценариев. TypeScript frontend и Catalog, изолированная Vite-сборка прошли; осталось прежнее предупреждение о chunks более 500 kB. Исходники до/после всех четырёх шагов совпадают по SHA; `final-checks2.receipt.json` содержит команды, времена и снимок 2148 файлов. Независимое ревью production-изменений и границ отчёта — PASS. Первый неуспешный прогон сохранён в `final-checks.receipt.json` и `frontend-final.results.json`.
