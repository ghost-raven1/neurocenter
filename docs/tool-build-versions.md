# Новая версия пакета из каталога

Главный администратор открывает карточку MCP или плагина и выбирает «Новая версия». Упаковщик получает актуальную общую редакцию каталога, даже если проект закреплён за более ранней. Пользователь подтверждает выбранную основу, задаёт новый исходник и запускает сборку. Имя и вид существующей карточки закреплены за выбранной целью.

Для новой работы требуются существующие `tool_builds` и `tool_catalog`. Права проверяются отдельно. Выключенные флаги сохраняют историю, отмену и восстановление уже принятого запроса. Отдельная новая возможность вне упаковщика не вводится.

## Сохранность и повтор

- Новая сборка под занятым именем без явного намерения обновления отклоняется до дорогой работы. Уже принятый request UUID сначала восстанавливает свой запрос.
- `publication: {catalogId, expectedVersion, expectedSourceHash}` связывает POST с подтверждённой основой. `expectedVersion` — числовая редакция каталога; это не строковая версия исходного пакета.
- Сервер фиксирует полное происхождение исходников и проверяет его повторно при публикации. Клиент не выбирает произвольные связи для замены.
- До принятия запроса конкурентная правка карточки или её источника даёт 409. Если основа меняется во время сборки, конфликт виден в результате задания. Форма и исходник сохраняются; пользователь обновляет сведения и подтверждает новую основу. Новый известный запрос получает новый UUID.
- При потерянном ответе ручной повтор использует тот же UUID и то же тело. Reload не отправляет POST автоматически.
- Успех атомарно сохраняет новую редакцию, квитанцию происхождения и результат задания. Прежние редакции, исходники и runtime-архивы сохраняются. Назначения проектов автоматически не перемещаются.
- Возврат проекта меняет закреплённую редакцию; отдельная установка применяет её на компьютере. Общая актуальная редакция каталога сохраняется.

Если сохранена другая активная форма или незавершённое задание, оно имеет приоритет над попыткой начать обновление другой карточки. Архив сохраняет идентификатор цели и подтверждённую основу вместе с остальным запросом.

## Контракт

`GET /api/tool-builds/publication-target?kind=plugin&catalogId=…` возвращает `catalogId`, имя, описание, вид, `expectedVersion`, непрозрачный `expectedSourceHash`, список источников и `updateSupported`. Для MCP используется `kind=mcp`.

Версию skill этим действием пока обновить нельзя: сервер возвращает явную причину неподдерживаемого действия. Обычная новая упаковка skill также не должна скрыто перезаписывать существующий slug. Отдельный явный импорт и повтор уже принятой публикации сохраняют свои контракты.

Публикация использует единый порядок блокировок: ресурс → граф зависимостей → строки карточки и источников. Права и флаги перепроверяются после ожидания. Неопределённый откат уничтожает собственную SQL-сессию или инвалидирует заимствованный lease; первичная ошибка сохраняется. Повтор после неизвестного COMMIT не создаёт вторую редакцию.

## Локальная проверка 23 октября

- На настоящем PostgreSQL: 12 сценариев CAS, блокировок, отзыва прав/флага, обоих порядков одновременного update/replay и потери ответа после фактического COMMIT.
- Отдельно: три воспроизведённых дефекта ROLLBACK и три здоровых контроля. После исправления все шесть прошли; чужой последующий COMMIT больше не публикует неудавшуюся операцию.
- На macOS: настоящий маленький JS-плагин прошёл очередь, сборщик, каталог, закрепление проекта и отдельный процесс bridge installer. Установлены обе версии, затем восстановлена прежняя; SQL, старые байты и ручные записи OpenCode сохранены.
- В Chromium: 11 проверок настоящей формы React/Ant Design/IndexedDB с управляемым HTTP; отдельно две визуальные проверки компактной панели. Потерянный ACK, reload, 409, архив и OFF проверены. Пять ожидаемых HTTP-отказов и оборванный ответ сохранены в журнале; исключений страницы нет.

Это разные свидетельства. В native roundtrip авторизация Gateway и доставка runtime управляются стендом; обычный OpenCode не запускается, проверяется вызов установленного hook через сгенерированную конфигурацию. Переходы из контейнера Store проверены компонентными тестами; браузер использует его реальные форму, Details и штатный launcher в отдельном стенде. Другие рецепты, skill update, корпоративный Linux, Windows, реальный IdP, внешнее Ceph, CI и production остаются отдельной приёмкой.
