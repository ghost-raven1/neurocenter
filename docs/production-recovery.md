# Резервное копирование и восстановление площадки

Операторская процедура для одного production-стека Docker Compose. Требуются Node.js 24, Docker Compose и **те же проверенные образы**, которыми создана копия. Смена версии приложения и восстановление данных выполняются отдельно. [Подготовка конфигурации](production-setup.md).

## Что сохраняется

Один комплект включает PostgreSQL `catalog`, прежнюю общую `rag` с реестром, **все** `nc_rag_<hash>` — в том числе базы удалённых проектов, — Markdown-том `skills`, серверный том `projects` и том сохранённых копий `backups`, а также неизменяемые готовые комплекты в томе `runtime-artifacts`. В каталоге находятся также пользователи, роли, назначения, пакеты/версии, подключения устройств и история операций.

Карточки моделей и назначения `model_catalog`/`project_models` входят в дамп `catalog`. Том `model-weights` с воспроизводимым кешем весов **не входит** в комплект. Две встроенные модели восстанавливаются по [описи с SHA](../scripts/models/bundle-release.json) из закреплённого [release `models-2026-10-19.1`](https://github.com/ghost-raven1/neurocenter/releases/tag/models-2026-10-19.1): 9 файлов, 4 427 274 223 байта. Сохраните доступ к этому выпуску либо отдельную проверенную копию всего каталога `models/` и закреплённого runtime-образа. Пользовательские модели вне описи требуют собственной копии файлов и сведений об источнике; записи в БД их веса не заменяют.

Закрытые файлы production-конфигурации — пароли PG, SSO-реквизиты и TLS — **не включаются** в комплект данных. Их нужно независимо хранить в защищённом хранилище. Данные/JSONB пакетов и метаданные устройств входят в копию и могут быть чувствительными. Восстановление поддерживает новую конфигурацию и новые пароли PG-ролей. Локальные папки, OpenCode, LanceDB и закрытые файлы параметров MCP на компьютерах сотрудников резервируются отдельно. Серверная копия не откатывает уже выполненную локальную установку.

Новый комплект записывается в формате **`neurocenter-recovery-v2`** с четырьмя файловыми томами. Исторический v1 читается и восстанавливается с пустым новым томом артефактов. Реестр SHA находится в дампе каталога; точные байты архивов — в новом томе. Импорт артефактов и backup/restore используют общую maintenance-блокировку.

Рабочие сервисы останавливаются на время копирования, PostgreSQL остаётся запущен. Это согласует последовательные `pg_dump` и файловые тома. Дамп каждой БД сам по себе не синхронизирует разные базы: [правила PostgreSQL](https://www.postgresql.org/docs/16/backup-dump.html). Перед остановкой и после неё не должно быть незавершённых заданий MCP; перед/после чтения данных проверяется отсутствие других клиентских PG-сессий. Оператор не запускает прямые SQL-записи, `docker compose up` и другие обходы maintenance-блокировки в это окно.

## Создание и проверка

Пример для настроенного стека `neurocenter-production` с закрытой конфигурацией `/etc/neurocenter`:

```sh
install -d -m 700 /mnt/neurocenter-backups
node scripts/production/recovery.mjs backup \
  --directory /etc/neurocenter \
  --project-name neurocenter-production \
  --offline \
  --destination /mnt/neurocenter-backups/backup-id
```

`backup-id` каждый раз новый. Родительский каталог должен заранее существовать с правами 700. Назначение внутри рабочих Docker mounts отвергается, чтобы не копировать backup-том в себя и не писать внутрь PostgreSQL. Заранее проверьте, что `/mnt/neurocenter-backups` — действительно независимое хранилище/диск с достаточным местом; скрипт не создаёт внешний storage и не проверяет его независимость. Папка на основном диске не защищает от потери хоста. Резервное хранилище с данными/токенами устройств должно быть зашифровано и доступно только оператору.

Команда печатает JSON-квитанцию: `destination`, `sha256` описи, время, количество БД/файлов, байты и длительность. Сохраните квитанцию **отдельно от комплекта**, в защищённом месте. SHA256 обнаруживает повреждения; сохранённая рядом подменённая опись с заново вычисленным хэшем не доказывает подлинность.

```sh
node scripts/production/recovery.mjs verify \
  --source /mnt/neurocenter-backups/backup-id \
  --expect-sha256 ЗНАЧЕНИЕ_ИЗ_СОХРАНЁННОЙ_КВИТАНЦИИ
```

`verify` не требует Docker. Проверяются каждый байт файлов, типы, пути, размеры, SHA256, точный состав каталогов, обязательные тома, имена и владельцы БД, идентификаторы образов. Недостающие, лишние, изменённые файлы и ссылки отклоняются.

Копирование потоковое; содержимое больших файлов и дампов целиком в память не читается. Опись ограничена 200 000 записей, 64 МиБ, глубиной 128 и путями до 4096 байт; список БД — 10 000. При превышении комплект не публикуется. Симлинки, hard links, специальные файлы и управляющие символы в именах не поддерживаются: операция завершится ошибкой, исходные данные останутся на месте. Права обычных файлов и исполняемые биты сохраняются; владельцы Unix, ACL и xattrs не переносятся. Для стандартных production-томов сервисов это не требуется.

Файловый помощник использует проверенный catalog-образ без сети, с read-only rootfs, лимитами CPU/памяти/PID и только необходимыми capabilities для чтения томов. Docker daemon должен быть локальным: bind-пути относятся к машине, на которой выполняется CLI. Для remote Docker сначала перенесите выполнение/источник на хост daemon.

## Восстановление на чистой машине

1. Подготовьте закрытый конфиг через `setup.mjs configure`, TLS и исходный комплект. Доставьте **точные образы**: проверяются image ID семи приложений, включая `feature-flags-service`, и PostgreSQL. Текущая реализация ещё не публикует их в registry автоматически. Встроенный `nc_rag_template` и фиксированные роли создаются initializer из этого же выпуска; произвольные глобальные настройки/дополнительные роли PostgreSQL требуют отдельной процедуры.
2. Проверьте хэш из ранее сохранённой квитанции. Дампы должны происходить из доверенного источника: при restore PostgreSQL исполняет SQL, а SHA256 не является SQL-песочницей. [Предупреждение pg_restore](https://www.postgresql.org/docs/16/app-pgrestore.html).
3. Выберите **новое имя Compose-проекта**, без его контейнеров и томов, включая `model-weights`, если он определён в конфигурации. Рабочий стек никогда не является целью восстановления.

```sh
node scripts/production/recovery.mjs restore \
  --directory /etc/neurocenter-recovery \
  --project-name neurocenter-recovery-id \
  --source /mnt/neurocenter-backups/backup-id \
  --expect-sha256 ЗНАЧЕНИЕ_ИЗ_СОХРАНЁННОЙ_КВИТАНЦИИ
```

Весь комплект проверяется **до создания целевого PostgreSQL**. Затем создаются роли с новыми секретами, восстанавливаются БД с исходными владельцами и правами, выполняется `ANALYZE`, переносятся и повторно сверяются файловые тома. Каждый `pg_restore` выполняется с `--exit-on-error --single-transaction`; общей транзакции на несколько баз и файловую систему нет. При сбое частично подготовленная **новая** цель остаётся остановленной для разбора; повторная команда не перезапишет её. Выберите другую чистую цель после устранения причины.

Одноразовые коды привязки удаляются, индикатор online устройств сбрасывается до нового heartbeat. Завершённые задания, подключения и привязки сохраняются. Восстановление не создаёт администратора заново через seed. Права пользователей и отзывы устройств возвращаются **на дату копии**: до открытия доступа сверьте последующие изменения по независимо сохранённому аудиту. Более поздний отзыв не может сохраниться в более раннем снимке. Браузерные сессии не переносятся; понадобится новый вход.

Успех записывается в `/etc/neurocenter-recovery/recovery-receipts/` с правами 600. Приложения ещё остановлены — поле `applicationsStarted: false`. После проверки и подготовки DNS/SSO можно запустить стек:

```sh
node scripts/production/setup.mjs up \
  --directory /etc/neurocenter-recovery \
  --project-name neurocenter-recovery-id
```

Не выполняйте `seed` поверх восстановленных пользователей. Публичные 80/443 на целевой машине должны быть свободны. На той же машине для параллельной репетиции нужен отдельный Compose override с loopback-портами; готовый автоматический сценарий ниже создаёт его сам.

При последующем `setup.mjs up` контейнер `model-volume-init` подготавливает встроенные веса в новом томе до запуска `model-runtime`. Для пустого тома нужен доступ к закреплённому GitHub Release. При изолированном восстановлении после restore заранее перенесите проверенный каталог `models/` в новый модельный том и доставьте runtime-образ; полный комплект проходит подготовку без сетевых запросов. Пользовательские веса восстановите отдельно до открытия доступа соответствующим проектам. Наличие файлов и SHA не подтверждает inference: после запуска выполните содержательную проверку embedding- и vision-моделей через каталог.

Значения `feature_flags` и аудит входят в дамп `catalog` и после восстановления сохраняются. Новый формат описи требует семь точных образов приложений; комплект прежнего стека из шести приложений восстанавливается его прежним checkout и образами. Автоматическая миграция топологии не выполняется; не подменяйте опись или SHA, чтобы обойти проверку.

## Ошибки и прерывание

Операции `up`, `seed`, backup и restore имеют общую атомарную блокировку — контейнер `neurocenter-maintenance-<имя проекта>` на Docker daemon. Другая команда отказывает до остановки/записи. CLI сравнивает реальные mounts и запущенные образы с конфигурацией: смена имени тома не превращается в успешную пустую копию.

При штатной ошибке копирования временный каталог удаляется, ранее запущенные приложения возвращаются в работу. Существующий комплект не перезаписывается, предыдущие копии автоматически не удаляются. Успех требует и создания комплекта, и успешного запуска прежних сервисов. При аварии хоста, SIGKILL оператора или ошибке рестарта автоматического обещания восстановления нет. Проверьте `setup.mjs status`, контейнеры и логи. Убедитесь, что прежний оператор завершён; только после этого удалите **проверенный** контейнер-блокировку и повторите штатный `up`. Сам скрипт чужую/зависшую блокировку не снимает.

Подробный stderr Docker/PG может содержать пользовательские сведения: CLI сохраняет его только в `operation-logs/` внутри закрытого config-каталога и печатает путь к журналу. Публичный вывод не содержит SQL/пароли. Журнал не следует публиковать без проверки. Именованный файловый помощник удаляется и при штатном разрыве Docker-клиента, чтобы не продолжать запись в partial-каталог.

Непустой журнал скиллов блокирует копию: запустите исходный skills-сервис, проверьте восстановление журнала и повторите backup. Незавершённые задания MCP сначала должны завершиться или быть разобраны оператором. Не выполняйте параллельно копирование и локальные действия пользователей.

## Лимиты и прерванные копии из панели

HTTP-кнопки проекта и `/maintenance` используют общий `BACKUP_DIR` и файловую блокировку `.neurocenter-backup.lock/owner`. Production задаёт `/app/backups`, dev-launcher — абсолютный `data/backups` checkout. Без `BACKUP_DIR` обе функции теперь используют `data/backups` от cwd; старые системные копии в `~/lancedb-backups` самостоятельно не переносятся и не удаляются. Все файлы внутри корня, включая старые и не зарегистрированные в БД, входят в бюджет. Новый файл — 0600, новые каталоги — 0700; права прежних файлов автоматически не мигрируют.

Общий лимит по умолчанию 64 ГиБ, один файл — 16 ГиБ, резерв свободного диска — 1 ГиБ. [Параметры конфигурации](production-setup.md) задаются в байтах; ноль не отключает защиту. Для следующей копии нужно место **до** очистки retention. Превышение лимита/ENOSPC даёт 507; предыдущие копии сохраняются. Лимит является бюджетом файлов приложения, а не OS-квотой: посторонний процесс может занять диск между проверкой и записью. Полный комплект CLI во внешнем каталоге этими параметрами не ограничивается; свободное место и срок хранения там контролирует оператор.

Основная HTTP-операция имеет deadline 20 секунд, затем выполняются остановка процесса и cleanup. Для большой БД используйте полный операторский backup. Сервер не ставит параллельные HTTP-копии в очередь: занятый mutex даёт 409. При штатном SIGTERM поток останавливается, собственный PG-процесс отменяется своей ролью, временный файл и mutex удаляются. После аварии хоста/SIGKILL блокировка автоматически не протухает.

Если 409 остаётся после перезапуска:

1. Приостановите новые операции и остановите **все экземпляры catalog-service этого стека** через соответствующий Compose-профиль. Убедитесь, что прежнего оператора/`pg_dump` нет; в `pg_stat_activity` не должно оставаться его `nc-backup-*`. Часы и возраст файла не доказывают отсутствие писателя.
2. Сохраните диагностику и проверьте точный backup-том, `owner`, `.dump.partial`, окончательные файлы и строки `project_backups`. Копии содержат знания и секреты каталога: работайте в закрытом хранилище.
3. Частичный файл не объявляется готовым переименованием. При ошибке `BACKUP_CONFIRMATION_FAILED` **окончательный файл намеренно остаётся**: БД могла подтвердить запись после потери ответа. Проверьте метаданные, `pg_restore --list` и пробное восстановление; старые копии в этом случае не удаляются. Автоматической сверки/регистрации осиротевшего файла пока нет.
4. Только после подтверждения отсутствия писателей разберите принадлежащую этой операции блокировку и partial. Неучтённые файлы при необходимости перенесите в закрытый независимый архив с контрольной суммой; не удаляйте их ради освобождения места без проверки. Запустите сервисы и обновите список, затем выполните новую копию.

DR отказывает до остановки приложений, если видит активную/оставшуюся API-блокировку; файловый помощник также отклоняет lock и `.dump.partial` до переноса томов. После штатного отказа DR возвращает приложения в работу. Это предотвращает публикацию незавершённого набора; не заменяет процедуру разбора аварии.

## Репетиция и допуск

```sh
node --test scripts/test/production-recovery.test.mjs
NEUROCENTER_TEST_RELEASE=verify-20261018-v09-final node scripts/test/production-recovery-stack.mjs
```

Сценарий создаёт два независимых стека и конфигурации с разными паролями, тестовый TLS и Blitz. Сохраняет каталог, два проектных индекса, оставшуюся отдельную БД, скилл, пакет, готовый runtime-архив с SHA, роли, серверный файл и существующий проектный дамп; затем восстанавливает в новый кластер и проверяет данные и API. Дополнительно проверяются отказы до восстановления при повреждённом архиве и несовпадении образов, затем чтение точного архива из восстановленного каталога. Его собственные контейнеры/volumes удаляются; каталог свидетельств задаёт `NEUROCENTER_TEST_EVIDENCE`. Исторические результаты этого DR-кандидата — в [отчёте 0.9.0](reliable-installation-0.9-2026-10-18.md), прежняя репетиция — в `.run/production-stage-2/`. Актуальный выпуск и ещё не принятые условия — в [реестре готовности](implementation-readiness.md). Реальные данные локального стенда не используются.

Это локальная репетиция, **не промышленный допуск PR-04**. Нужны согласованные RPO/RTO, настроенные на целевой площадке независимое внешнее хранилище, расписание и контроль свежести, проверка доступности секретов/образов при потере сервера и измерение на целевой нагрузке. [Внешняя HTTPS S3-доставка с полным SHA readback](external-backups.md) и [операторский runner расписания](maintenance-schedule.md) реализованы отдельно. Их независимый внешний DR ещё не принят. WAL/PITR и шифрование средствами самого CLI пока не реализованы. Свежесть и RTO малого тестового набора не являются гарантией для рабочего объёма.
