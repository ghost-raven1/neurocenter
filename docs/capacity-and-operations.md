# Нагрузка после релиза, хранение и масштабирование

## 1. Параметры площадки

Публичное описание не задаёт число пользователей и проектов, объём образов, состав команд, частоту релизов или ресурсы конкретной организации. Эти параметры оператор собирает для своей площадки и хранит отдельно от репозитория. Производительность определяется измерениями, а не расчётной конфигурацией.

| Параметр | Значение для расчёта |
| --- | --- |
| P | Число проектов |
| N | Число скачиваний в релизной волне |
| R | Число новых образов в волне |
| L | Размер текущего образа |
| V | Число сохраняемых снимков |
| d | Измеренная доля новых физических байтов на публикацию |
| f | Частота релизов |
| EC_factor | Накладные расходы выбранной схемы хранения |
| u | Допустимая доля заполнения дисков |

Число пользователей не равно числу проектов или передач: пользователь может участвовать в нескольких проектах. Размер образа включает устанавливаемые данные и индексы; историю Lance и служебные данные измеряют отдельно. Десятичные ГБ/ТБ и двоичные МиБ при расчёте не смешиваются.

## 2. Хранение

Текущие образы: `S_current = P × L`.

Полные независимые снимки: `S_full = P × L × V`.

При переиспользовании одинаковых чанков: `S_delta ≈ P × L × [1 + (V − 1) × d]`. Формула предполагает примерно стабильный размер базы. Для растущих баз и неодинаковых релизов считается фактическое объединение живых blobs.

Сырые диски: `S_raw = S_logical × EC_factor / u`. Backup, staging, скиллы, пакеты расширений, архивы и дисковая metadata добавляются отдельно. Retention в версиях не равен календарному сроку: он зависит от частоты публикаций.

Перестроение индексов, compaction и перепаковка архивов увеличивают число новых байтов. Server-side дедупликация и доля отсутствующих данных у клиента измеряются отдельно. До замеров retention ограничивают физической квотой наряду с числом snapshots.

## 3. Скиллы, pgvector и объекты

Для каталога измеряют число общих и проектных скиллов, размер Markdown, глубину истории, число фрагментов и размерность модели. Размер отдельного vector: `4 × dimensions + 8` байт. Строки, текст, индексы, WAL, временные построения и backup в эту формулу не входят. [Формат vector](https://github.com/pgvector/pgvector).

Для транспортного чанка размером C число позиций в манифесте: `Σ ceil(file_bytes / C)`. Пустые файлы описываются без data chunk. Это число позиций, а не гарантированное число уникальных blobs. Множество маленьких файлов увеличивает metadata независимо от общего размера образа.

Admission проверяет размер манифеста, число файлов/чанков, уникальных refs и бюджет metadata. GC и запись refs работают пакетами; длительная подготовка refs не держит транзакцию активации. На пилоте измеряют S3 object overhead и скорость LIST/HEAD/GET на мелких объектах.

## 4. Релизная волна

Последовательность: экспорт и upload кандидата → серверная проверка → атомарный релиз профиля → уведомление или явный sync → скачивание недостающих данных → локальная проверка и установка. Число получателей не умножает серверные проверки одного образа.

Входящий объём: `Σ new_server_bytes(project)`. При одинаковой доле изменений — `R × L × d`.

Исходящий объём: `Σ missing_image_bytes(client, project) + Σ missing_skill_bytes(client)`. Пропущенные релизы, очищенный кэш, новый компьютер и compaction могут увеличить скачивание до полного образа. Общие скиллы передаются только при отсутствии нужной версии и наличии доступа.

Для завершения передачи за W секунд: `line_bits_per_second ≥ total_bytes × 8 / (W × utilization)`. Это нижняя граница по общему каналу; клиентская сеть, S3, диски, повторы и локальная установка добавляют ограничения. Месячный трафик считают суммой реальных волн.

Полный срок готовности: `T_export + T_upload + T_queue + T_verify + T_commit + T_distribution + T_local_install`. Срок передачи нельзя выдавать за время релиза целиком.

## 5. API, admission и Worker

Клиент проверяет профиль при открытии проекта, явном sync или релизном сигнале. Уведомление служит подсказкой для чтения авторизованного каталога; offline-клиент получает текущую версию при следующем обращении. Постоянный массовый polling не требуется.

Batch permissions и URL, backoff, jitter и rate limits защищают API и внешний сервис прав. Профиль нагрузочного теста задают по ожидаемой волне, повторным запросам, числу мелких файлов и размеру URL batches. Уведомления и polling учитываются отдельно.

Admission выдаёт слот передачи или проверки до большого upload. Ожидающий клиент видит очередь и не держит бессрочный signed URL. Сетевой лимит обеспечивается storage или traffic shaping: signed URL сам по себе не ограничивает скорость. Проекты получают справедливые квоты.

Для одинаковых заданий срок обработки: `ceil(R / slots) × t`, где t — измеренное время проверки снимка. Для дедлайна W и j слотов на реплику: `slots_required = ceil(R / floor(W/t))`, затем `ceil(slots_required/j) + 1` реплик для отказа одной, если W ≥ t. Расчёт требует проверки конкуренции за диски, сеть и память.

Проверенные immutable blobs не хешируются заново при каждом переиспользовании, но переносимость снимка и ссылки проверяются. Индексы Lance готовит издатель до релиза; server-side rebuilding — отдельная тяжёлая задача. Небольшие skills jobs имеют отдельные лимиты.

## 6. Ресурсы и staging

| Компонент | Что измерить до выбора ресурсов |
| --- | --- |
| API | Одновременные запросы, память, CPU, задержки ACL/PG и bounded pools |
| Worker | Время SDK-проверки, память, IO и число безопасных параллельных jobs |
| PostgreSQL | Metadata, refs, индексы, WAL/PITR, replication lag и failover |
| S3 | Retained graph, версии, multipart parts, quorum, healing и резерв места |
| Сеть | Одновременные verification, download, backup и restore |
| Backup | Независимый отказный домен, retention и доступность согласованного комплекта |

Staging reservations ограничивают принятые задания, но reusable presigned PUT в versioned bucket может создавать дополнительные версии. Учитываются все object versions и multipart parts. Клиентские PUT ограничиваются подписанным размером/контрольной суммой; совместимость условного создания проверяется на выбранном S3.

До подтверждения ограничения всех физических записей staging остаётся бюджетом с мониторингом, очисткой и остановкой admission. Для hard quota нужен проверенный storage enforcement либо отдельный upload gateway. SEALED versions защищены до завершения или истечения операции. Счётчик квоты освобождается после подтверждённой очистки.

## 7. Масштабирование и метрики

| Сигнал | Действие |
| --- | --- |
| Волна превышает окно раздачи | Увеличить канал/слоты или разнести публикации |
| Очередь превышает бюджет релиза | Увеличить Worker с учётом отказа реплики; ограничить backlog |
| Растут API latency и CPU | Проверить ACL/PG, затем увеличить API replicas |
| Растёт заполнение storage | Расширить поддерживаемой процедурой до исчерпания резерва |
| Churn выше измеренного | Пересчитать retention, staging и объём раздачи |
| Растёт backup lag | Ограничить новые передачи или выделить канал копирования |
| Много файлов/refs | Пересчитать metadata и object overhead; ограничить admission |

Для нескольких API нужен общий Socket.IO adapter и session affinity при polling. LISTEN использует отдельное session connection. Масштабирование S3 выполняется поддерживаемой процедурой выбранного продукта; добавление pod-ов не меняет erasure set автоматически. Поддерживаемую редакцию, версии и параметры хранения фиксируют до внедрения.

## 8. Квоты и восстановление

Квоты охватывают current bytes, retained physical bytes, защищённые snapshots, skills/packages, staging versions/parts, файлы/чанки, параллельные jobs/transfers и объём передач. Значения и цели RPO/RTO задаёт оператор площадки после измерений.

Метрики: release ID, ожидаемые/активные/успешные/ошибочные sync, missing/new/reused bytes, прогноз завершения, API/ACL latency, очередь и runtime Worker, retry rate, throughput, quorum/healing, PG lag, backup lag и restore drill. Offline-клиент не считается гарантированно обновлённым. Аудит не содержит токены, URL или приватный контент.

Канал backup рассчитывают на релизный всплеск с WAL, повторами и конкурирующей раздачей. При недостаточной полосе нужны резерв канала, pacing публикаций либо подтверждение backup до признания релиза защищённым. Настройка асинхронной копии сама по себе не подтверждает RPO.

Checkpoint закрепляет согласованные manifests, blobs и PG recovery point. Primary GC сохраняет объекты незавершённого backup; независимая копия защищает graph на глубину retention/PITR. Восстановление PG до точки без соответствующих blobs запрещено. Реплика без retention не заменяет backup.

Время холодного восстановления включает передачу объектов, запуск приложений и проверку данных. Доступность каталога не означает восстановление всей площадки. До открытия доступа проверяют manifest references, подписи и открытие LanceDB.

## 9. Проверки перед production

1. Репрезентативный образ: portable export, full/delta, пропущенные релизы, мелкие файлы и churn.
2. Плановая и стрессовая волны: срок установки, справедливость admission, full installs отдельно от delta.
3. Один образ для многих клиентов: одна серверная проверка; skills-only release не пересылает базу.
4. Head/profile CAS, rollback ABA, stale Worker и идемпотентный finalize.
5. Независимые права автора и активатора; отзыв прав до принятия кандидата.
6. Reusable PUT, pinned versions, квоты noncurrent/parts и cleanup при очереди.
7. API, S3 throughput, URL batches и число ACL RPC под нагрузкой.
8. Отказ реплики/узла, failover PG, reconnect/affinity и пропуск уведомлений.
9. GC одновременно с upload/download/backup без потери защищённых ссылок.
10. Restore независимого checkpoint и backup lag при всплеске публикаций.

Это параметры проектирования и план проверки. Они не заменяют свидетельства реализации или измеренной производительности на конкретной площадке.
