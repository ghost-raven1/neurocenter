# Доступ во время публикации skill

Сборка skill и импорт готового skill повторно проверяют права и флаги после ожидания блокировки, непосредственно перед native-записью. Нужны активная роль главного администратора и включённые `tool_builds`/`tool_catalog`. Фичафлаг не заменяет проверку роли.

В той же SQL-транзакции строка пользователя удерживается через `FOR SHARE`. Поэтому публикация и изменение роли имеют определённый порядок: отзыв, завершившийся до допуска, запрещает запись; уже допущенная публикация завершает транзакцию перед подтверждением конкурирующего изменения роли. Это соответствует [семантике блокировок PostgreSQL 16](https://www.postgresql.org/docs/16/explicit-locking.html). У фоновой сборки после асинхронных проверок дополнительно проверяется её текущая lease.

Перед COMMIT доступ проверяется снова. Прежние ограничения ожидания SQL и правила уничтожения сессии после неподтверждённого отката сохранены. Создание skill по-прежнему не обновляет чужой или изменённый slug без явного решения администратора; поддержка новой версии skill через упаковщик этим изменением не добавляется.

## Если флаг выключен после записи

Отправленный native-запрос может уже записать skill до получения ответа. Откат SQL не удаляет эту файловую запись. Задание получает `FAILED`, публичный импорт возвращает отказ, исходники и native-журнал с прежним ключом сохраняются. Успешная SQL-публикация в этом случае не объявляется.

После восстановления разрешения администратор может явно повторить действие с новым UUID при неизменных исходниках и настройках, сохранив тот же `asset.id`/`asset.version` и точный payload. Стабильный ключ native-публикации вычисляется из этой пары id/version; проверенный native-журнал позволяет сохранить связь с SQL без второй записи, нового события аудита или лишней версии. Версия собираемого skill зависит и от исходников, и от карточки/настроек: их изменение не является точным повтором. Автоматического повтора с новым ключом и удаления уже записанного skill нет. После отзыва роли доступ к действию требует её нового назначения.

## Локальные свидетельства — 23 октября 2026 года

На исходном коде воспроизведены четыре нарушения: сборка и публичный `Service.importAsset(skill)` после подтверждённого отзыва роли или OFF `tool_builds` при ON `tool_catalog` всё равно выполняли native-запись. При отзыве роли SQL откатывался, но skill оставался на диске; при OFF флага оба пути сообщали об успехе. Два положительных контроля проходили. Роль менялась настоящим `AccessDb.save` вторым главным администратором, с сохранённым аудитом; ожидание подтверждалось `pg_blocking_pids`.

На окончательных байтах QA старый кандидат повторно дал те же четыре причинных RED и два положительных контроля. Исправленный кандидат прошёл 10/10:

- Четыре отказа до native-записи: нет skill, native-вызова, события файлового аудита и SQL-квитанции; точные исходные байты сохранены.
- Два успешных контроля: реальная native-версия и неизменяемая квитанция исходника совпадают.
- Два порядка конкуренции с отзывом роли: реальный `AccessDb.save` ждёт строку, удерживаемую публикацией; после COMMIT публикации отзыв завершается и сохраняет аудит.
- Два отказа после записи, до ACK: native-журнал сохраняется, SQL-успех отсутствует; явный повтор после ON восстанавливает квитанцию той же версии 1 без второй native-записи и изменения файлов/аудита.

Во время прогона 58 критических хешей не изменились; 12 исходных файлов из выбранной source-freeze квитанции до подключения к БД совпали с текущим деревом. Отдельная корневая проверка сопоставила все 1303 текущих файла `src/shared` с изолированной сборкой без различий. Все собственные БД удалены, stages очищены, процессы запуска завершены. Квитанция: `.run/skill-build-authorization-20261023/final-native-receipt.json`.

Backend-регресс — 399/399 в 36 файлах, без пропусков; 18 целевых проверок входят в этот набор. Они дополнительно проверяют потерю lease, недоступность сервиса флагов после ожидания, OFF во время native/сохранения квитанции и неподтверждённый ROLLBACK с сохранением первичной ошибки. Production и новые/изменённые тесты прошли отдельную строгую проверку TypeScript. Все восемь пакетов собраны из отдельного снимка. Отдельно повторены семь SQL-проверок B11 и шесть rollback-сценариев; собственный PostgreSQL штатно остановлен с проверкой PID, порта и финального списка БД.

Свежий общий unit-safe прогон восьми пакетов — 7992 pass / 0 fail / 53 skip, 582/582 выбранных файлов; 125 потенциально инфраструктурных файлов исключены, включая SQL-моки с прямыми `pg` type-imports. Исходники во время прогона не менялись. AST lines — 65,47% (21493/32828), functions — 59,74%, branches — 63,13%, statements — 61,51%; `complete:false`, весь workspace знаменатель не охвачен. В этом профиле весь изменённый `import-skill-publication.ts` покрыт: 10/10 инструментированных строк, 1/1 функция, 24/24 выражения, 2/2 ветви. Поднаборы и native-свидетельства не суммируются в общий процент. Квитанция: `.run/coverage/skill-authorization-final-20261023/manifest.json`.

Это локальная приёмка на собственном PostgreSQL 16.15 и macOS ARM64. Методы Catalog, Skills-контроллер, файловое хранилище и компилятор данных skill настоящие; Skills transport задан внутри процесса, сервис флагов — управляемый HTTP с настоящим evaluator. Файловый аудит наблюдается через делегат; внешняя доставка аудита, HTTP middleware, браузер, обычный OpenCode, другие ОС, CI и production этим прогоном не приняты. Жизненный цикл worker проверяется отдельными сценариями; здесь вызывается настоящий `Service.execute` с собственной SQL-lease.

Совместимость нестандартного dev-principal — регистр/пробелы `DEV_USER_EMAIL` и сохранность старых raw-actor запросов — принята отдельным [срезом B15](dev-actor-publication.md): четыре причинных отказа на старом кандидате, 9/9 на исправленном. Указанные здесь десять сценариев с каноническими адресами повторены на его кандидате. Общий unit-safe замер выше относится к срезу B14; актуальный общий результат приведён в [границе MVP](stable-mvp-2026-10-22.md).
