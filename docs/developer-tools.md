# Разработка и поиск дефектов

Рабочий цикл Neurocenter: установить причину → воспроизвести отказ тестом → исправить код → повторить тест с покрытием → собрать текущие исходники → провести независимое ревью. Команды используют уже установленный Node 24 и зависимости; они не устанавливают недостающий runtime.

## Найти причину

Для Codex настроен диагностический MCP `neurocenter-dev`: `workspace_status` показывает checkout и версии, `services_health` проверяет фиксированные локальные endpoints, `service_logs` читает ограниченный журнал сервиса, `verification_summary` объясняет сохранённый отчёт покрытия. Доступность инструментов уже открытого чата проверяй отдельно от записи конфигурации. [Подключение и ограничения](agent-kit.md#mcp-для-разработки-neurocenter).

Сопоставляй действие пользователя с ошибкой, временем, загруженным артефактом и ревизией. Затем попроси Codex добавить воспроизводящий регрессионный тест, исправить причину и запустить относящиеся проверки. Код меняется обычными средствами редактирования; диагностический MCP не выполняет произвольные команды и не меняет рабочие данные.

## Проверить выбранный модуль

```sh
npm run check -- --help
npm run check -- --package frontend --step typecheck
scripts/dev.sh check --package frontend --step typecheck
```

`--package` и `--step` можно повторять. Выбор ограничивает план их пересечением. Отдельный шаг `test` не запускает сборку. Пустое пересечение возвращает ошибку: например, у API Gateway нет npm-скрипта `test`, поэтому его тесты запускай командой покрытия ниже. Селекторы не включают общие контракты или Compose. Вызов без селекторов сохраняет прежний полный план, включая сборку в обычный `dist`.

Справка и неверные аргументы обрабатываются до создания отчёта и запуска проверок. `dev.sh check` передаёт выбранные параметры и код результата, не загружая активные dotenv-файлы. Отчёт выполненного плана сохраняется в `.run/check/<попытка>/report.json`.

## Воспроизвести баг и измерить покрытие

```sh
npm run coverage -- --package frontend --test-file test/error-message.test.ts
```

Укажи ровно один пакет и до 32 относительных `--test-file` внутри его `test/`. Допускаются обычные тестовые файлы без ссылок, обхода каталогов и инфраструктурных сценариев. Команда запускает только выбранные unit-тесты. Для PostgreSQL, S3, native и integration нужны отдельные профили с собственными фикстурами.

Если один файл из выбранного набора требует инфраструктуры, ошибка указывает его относительное имя. Отчёт и worker до прохождения этого допуска не создаются. Проверка остаётся консервативной: импорт типов из `pg` также может отнести SQL-мок к инфраструктурным наборам.

В отчёте перечислены запрошенные файлы, фактически выполненные тесты, исключения по выбору и отдельные инфраструктурные исключения. Невыполненный или лишний файл делает проверку неполной. Знаменатель покрытия включает исходники выбранного пакета, в том числе не импортированные выбранным тестом модули. `complete` относится к запрошенному набору; это не 100% покрытия модуля или проекта.

Без `--test-file` остаётся прежний режим покрытия пакетов; без `--package` он выбирает все восемь. HTML, исходный JSON и `manifest.json` сохраняются в новом `.run/coverage/<попытка>/`. Не смешивай AST unit-покрытие и native V8 как один процент.

## Собрать текущие правки отдельно

```sh
npm run build:isolated -- --package frontend --plan
npm run build:isolated -- --package frontend
npm run build:isolated -- --all
```

Проверка копирует текущие отслеживаемые и новые неигнорируемые файлы Git, учитывая локальные правки и удаления. Активные dotenv, файлы секретов по известным именам, пользовательские npm-настройки, зависимости и готовые выходы исключаются из снимка. Состав и SHA сохранены в отчёте. Изменение исходников во время подготовки останавливает сборку; изменение после запуска не считается проверкой текущего состояния.

Компиляторы работают последовательно в `.run/isolated-build/<попытка>/repository` с отдельными HOME, кэшем и журналами. Никаких установок зависимостей; кандидат не копируется в рабочий `dist`. Отчёт проверяет ожидаемые точки входа, SHA артефактов и сохранность рабочих выходов всех восьми пакетов. Отказ и отмена сохраняют причину и частичный результат.

Это изоляция исходников и выходов, а не защитная песочница: уже установленные `node_modules` подключаются ссылками, содержимое зависимостей не заморожено. Доверенный build-скрипт может писать через ссылку; offline-настройка npm не является сетевым фильтром. Отмена завершает только собственную группу процессов; эта проверка жизненного цикла подтверждена на macOS. Сборка не подтверждает работу API, браузера, миграций или production.

Канонические идентификаторы: `frontend`, `catalog-service`, `api-gateway`, `feature-flags-service`, `oauth2-bridge`, `rag-sync-service`, `skills-service`, `bridge`. Тяжёлые сборки и профили покрытия запускай по очереди. Сохраняй отдельно пройденное, пропущенное и непроверенное; бэклог обновляй после реализации и проверок.

## Проверить отмену упаковки на реальной БД

Сначала собери `catalog-service` через `build:isolated`. Возьми абсолютный путь `repository/services/catalog-service/dist` из полученного кандидата и задай `TOOL_BUILD_TEST_DIST`. Проверки используют этот код, не рабочий `dist`.

`TOOL_BUILD_CANCEL_TEST_PG_URL` должен указывать на собственный одноразовый PostgreSQL: `127.0.0.1`, явно заданный порт кроме `5432`, административная БД `/postgres`, без query/hash. Храни URL с паролем в приватной конфигурации, не в отчёте или Git. Каждый CLI создаёт свою случайную БД, применяет настоящие миграции, удаляет только её и сверяет исходный список БД. Допуска к основной БД по умолчанию нет.

После настройки этих двух переменных выполни из корня тем же Node 24:

```sh
node scripts/test/tool-build-cancellation-db.mjs
node scripts/test/tool-build-cancellation-worker.mjs
```

Первый CLI проверяет оба порядка SQL-блокировок, tombstone потерянного запроса, границу публикации, отзыв прав и исполнение отмены через журнал операций. Второй на POSIX запускает настоящий worker и supervisor с управляемым тестовым сборщиком и дочерним writer: проверяет запрет START до SQL commit, отмену, SIGKILL владельца и потерю lease. Этот сборщик не проверяет компиляцию, публикацию или установку настоящего пакета. Windows и восстановление на другом хосте требуют отдельной приёмки.

JSON-результат указывает квитанцию в `.run/`. Отказ, незавершённая остановка собственного процесса или ошибка удаления тестовой БД дают ненулевой exit и сохраняются в квитанции. Защиту самого стенда можно проверить без БД:

```sh
node --test scripts/test/tool-build-cancellation-admission.test.mjs \
  scripts/test/tool-build-cancellation-lease.test.mjs \
  scripts/test/tool-build-cancellation-worker-guard.test.mjs \
  scripts/test/tool-build-cancellation-barrier.test.mjs
```

## Прогнать настоящую сборку, установку и возврат версии

Собери все пакеты через `npm run build:isolated -- --all`. В том же явно выбранном кандидате задай абсолютные пути:

- `TOOL_BUILD_TEST_DIST` — `repository/services/catalog-service/dist`;
- `TOOL_BUILD_BRIDGE_DIST` — `repository/mcp/neurocenter-asset-sync/dist`;
- `TOOL_BUILD_SCRIPT` — `repository/scripts/catalog-plugins/build.mjs`.

`TOOL_BUILD_CANCEL_TEST_PG_URL` имеет тот же строгий допуск собственной одноразовой БД, что и проверки отмены выше. Затем:

```sh
node scripts/test/tool-build-roundtrip.mjs
```

CLI строит маленький JS-плагин настоящим сборщиком, дожидается публикации, закрепляет пакет за проектом и устанавливает отдельным процессом моста в собственный HOME. Затем публикует изменённый исходник как явную новую версию, устанавливает её и возвращает проект и установку к первой. Проверяет SQL, байты старых исходников/runtime, сохранение ручных записей конфигурации и отсутствие дополнительной сборки при точном повторе UUID.

Нужны Node 24 и POSIX; подтверждённая ОС — macOS ARM64. Runtime transport и Gateway/device authorization задаются стендом; установленный hook вызывается через сгенерированную конфигурацию без запуска обычного OpenCode. Проверка не подтверждает его первый запуск, корпоративный Linux/Windows, произвольные рецепты или внешние сервисы. Она не использует рабочий профиль моста или основной PostgreSQL.

Квитанция содержит SHA harness, путь кандидата, результат каждого шага и ошибки очистки. Незавершённые собственные процессы, ошибку удаления тестовой БД и изменение проверяемого harness нельзя считать GREEN. Защиты процесса и финализаторов проверяются без PostgreSQL:

```sh
node --test --test-concurrency=1 \
  scripts/test/tool-build-roundtrip-process.test.mjs \
  scripts/test/package-publication-rollback-finalizer.test.mjs
```

Для углублённого аудита сохранены `scripts/test/native/package-publication-rollback.test.mjs` и `scripts/test/tool-build-version-cas.mjs`: реальный SQL с потерянным ACK, последующим чужим COMMIT, блокировками и отзывом прав. Сейчас они требуют специально подготовленный собственный PostgreSQL 16.15 с приватной описью владельца, PID, сроком lease и source-freeze receipt; один PG URL не заменяет этот допуск. Исторический `connection.json` остановленного стенда использовать нельзя. Универсальная переносимая команда подготовки такого стенда ещё не поставляется; эти два harness не входят в обычный `check` и не должны запускать чужую инфраструктуру. Общая команда roundtrip выше от этой исторической описи не зависит.

[Контракт новой версии](tool-build-versions.md) отделяет общую редакцию каталога, закрепление проекта и локальную установку.

## Проверить продолжение после timeout публикации

Используй собственный `TOOL_BUILD_CANCEL_TEST_PG_URL` с допуском выше, `TOOL_BUILD_TEST_DIST` и настоящий `TOOL_BUILD_SCRIPT` из одного изолированного кандидата. Node 24 и POSIX обязательны; отдельный bridge dist для этой проверки не нужен.

```sh
node scripts/test/tool-build-publication-recovery.mjs
```

CLI запускает настоящий worker и JS-сборщик, удерживает SQL-блокировку после COMMIT барьера публикации и проверяет создание и новую версию плагина. Он требует `FAILED` до снятия блокировки, сохранность исходников и прежней версии, отсутствие дубля при точном UUID, выполнение следующего уже поставленного задания и успех явного повтора с новым UUID. Следующая задача добавляется реальным repository; конкурентный HTTP-допуск при занятом worker этим не принимается. Стенд использует меньшие унаследованные SQL-лимиты 1250 мс/20 с; проверка значений по умолчанию 5/30 с — отдельный профиль.

Квитанция фиксирует настоящие SQL-версии и происхождение исходника, байты архивов, SHA harness, восстановление настроек сессии, удаление stages/собственной БД и отсутствие всех наблюдавшихся native PID. Смена группы процесса или повторное использование PID не дают ложного доказательства остановки и не расширяют право завершать чужой процесс. Guard-проверки выполняются без PostgreSQL:

```sh
node --test --test-concurrency=1 \
  scripts/test/tool-build-roundtrip-process.test.mjs \
  scripts/test/tool-build-publication-recovery-guard.test.mjs
```

`tool-build-publication-deadline.mjs` отдельно проверяет три вида блокировок, меньшие SQL-лимиты, COMMIT/ROLLBACK и skill. Пока он использует тот же специальный приватный допуск PostgreSQL 16.15, что B09/CAS, а не только URL; переносимый bootstrap ещё не поставляется. Ни один из этих opt-in CLI не запускает PostgreSQL из обычного `check`. [Поведение, доказательства и пределы проверки](tool-build-publication-deadline.md).

## Проверить доступ и восстановление публикации skill

`scripts/test/skill-build-authorization.mjs` проверяет сборку skill и публичный `Service.importAsset(skill)` на настоящих Catalog/Skills методах, SQL и файловом хранилище. Нужны Node 24/POSIX, один явно собранный кандидат всех восьми пакетов и его квитанция замороженных исходников. Он использует специальный приватный допуск собственного PostgreSQL 16.15; одного PG URL недостаточно, переносимый bootstrap остаётся B12.

Явные параметры окружения:

- `SKILL_BUILD_AUTHORIZATION_CANDIDATE` — абсолютный путь `repository` из изолированной сборки;
- `SKILL_BUILD_AUTHORIZATION_SOURCE_RECEIPT` — абсолютный путь к квитанции с `sourceFiles` и SHA каждого исходника;
- `SKILL_BUILD_AUTHORIZATION_CONNECTION_FILE` — приватная опись свежего собственного кластера с действующим допуском;
- `SKILL_BUILD_AUTHORIZATION_PHASE=candidate` — десять проверок исправленного кандидата. Фаза `baseline` исполняет шесть проверок старого кандидата; четыре воспроизведённых нарушения дают ненулевой exit и `causalRed:true`.

```sh
node scripts/test/skill-build-authorization.mjs
```

Профиль проверяет отказ после отзыва роли/OFF во время SQL-ожидания, порядок конкурирующего штатного `AccessDb.save`, а также OFF после native-записи до ACK и явное восстановление без новой версии. Перед подключением к БД фаза `candidate` требует совпадения текущих исходников и выбранного кандидата; после прогона проверяются SHA, удаление stages и собственной БД. При timeout финализатор отслеживает и текущий повторный запрос. Ошибка очистки исключает GREEN.

Skills transport и доставка файлового аудита задаются внутри процесса; HTTP evaluator флагов настоящий на собственном управляемом endpoint. Профиль не принимает внешний middleware, весь жизненный цикл worker, браузер или обычный OpenCode. [Контракт доступа и восстановления](skill-publication-authorization.md).

## Проверить адрес исполнителя и сохранённые запросы

`scripts/test/actor-canonical-publication.mjs` воспроизводит прохождение исходного dev-principal через настоящий profile HTTP, Gateway headers и Catalog actor decoding до SQL/native-публикации. Он проверяет регистр/внешние пробелы, канонические контроли, повтор запроса, отмену и поздний POST, сохраняя прежнего владельца. Нужны Node 24/POSIX и тот же специальный допуск собственного PostgreSQL 16.15; переносимый bootstrap остаётся B12.

Явно задай абсолютные пути `ACTOR_CANONICAL_PUBLICATION_CANDIDATE` к `repository` отдельной сборки всех восьми пакетов, `ACTOR_CANONICAL_PUBLICATION_SOURCE_RECEIPT` к source/SHA-квитанции и `ACTOR_CANONICAL_PUBLICATION_CONNECTION_FILE` к приватной описи свежего собственного кластера. Фаза `candidate` требует совпадения текущих исходников с кандидатом до подключения к БД.

```sh
ACTOR_CANONICAL_PUBLICATION_PHASE=candidate node scripts/test/actor-canonical-publication.mjs
```

Фаза `baseline` исполняет те же девять сценариев на старом кандидате; четыре точных отказа и пять здоровых контролей дают `causalRed:true` и ненулевой exit. Произвольная ошибка таким подтверждением не считается. SHA, очистка своих stages/БД и сохранность остальных БД проверяются после прогона; ошибка очистки исключает GREEN. Эти opt-in проверки не запускаются обычным `check`.

Методы Gateway и transport Skills вызываются внутри процесса; profile HTTP и SQL настоящие. Профиль не принимает полный HTTP middleware, SSO/cookies, браузер, пользовательский OpenCode или production. [Контракт и локальные свидетельства](dev-actor-publication.md).
