# Разработка и поиск дефектов

Рабочий цикл Neurocenter: установить причину → воспроизвести отказ тестом → исправить код → повторить тест с покрытием → собрать текущие исходники → провести независимое ревью. Команды используют уже установленный Node 24 и зависимости; они не устанавливают недостающий runtime.

## Найти причину

Для Codex настроен диагностический MCP `neurocenter-dev`: `workspace_status` показывает checkout и версии, `services_health` разделяет liveness, пассивную readiness и принадлежность listener, `service_logs` читает ограниченный журнал сервиса, `verification_summary` объясняет сохранённые отчёты покрытия/check/сборки, `coverage_gaps` выбирает цели для регресса, `check_plan` показывает ограниченный план. Доступность инструментов уже открытого чата проверяй отдельно от записи конфигурации. [Подключение и ограничения](agent-kit.md#mcp-для-разработки-neurocenter).

Сопоставляй действие пользователя с ошибкой, временем, загруженным артефактом и ревизией. Затем попроси Codex добавить воспроизводящий регрессионный тест, исправить причину и запустить относящиеся проверки. Код меняется обычными средствами редактирования; диагностический MCP не выполняет произвольные команды и не меняет рабочие данные.

### Получить план и прочитать свидетельства

Вызови MCP `check_plan` с явным списком пакетов и необязательным выбором шагов:

```json
{"packages":["frontend","api-gateway"],"steps":["typecheck","test"]}
```

План переиспользует CLI-планировщик, читая ограниченные package manifests без символических ссылок. В ответе есть точные команды, порядок шагов и пакеты без npm `test`. Пустое пересечение отклоняется. Полные контракты workspace, gate генерации, Compose, покрытие и native/integration профили не включаются. План ничего не запускает и не создаёт `.run`; последующее исполнение `build` обычным `check` пишет рабочий `dist`.

`verification_summary` читает ровно один явно выбранный файл:

```json
{"report":".run/check/<попытка>/report.json"}
```

Также доступны `.run/isolated-build/<попытка>/receipt.json` и прежний `.run/coverage/<попытка>/manifest.json`. Общего поиска по `.run` нет; вложенные пути, ссылки и посторонние файлы отклоняются. Новые check/build-сводки ограничены 1 МиБ входного JSON и не выдают исходные журналы, команды, сообщения ошибок или окружение.

Отчёт `check` версии 3 сохраняет запрошенный план, выполненные шаги, терминальное состояние, отдельные test counters и результат очистки собственной группы процессов. До и после проверки фиксируются ограниченные снимки текущих Git tracked/nonignored untracked файлов: SHA, HEAD, число новых/удалённых файлов и исключений. Обнаруженное изменение исходников завершает проверку отказом `SOURCE_CHANGED`. Неподготовленная Git-фикстура, лимит, отключённый capture или недоступный источник дают `unknown`, а не придуманное соответствие. MCP считает v3 завершённым только при согласованном результате, очистке процессов и неизменном источнике без пропусков/TODO.

В 0.3.1 общий Node gate пишет отдельный JSONL-отчёт из итогового `test:summary`: passed, failed, skipped, TODO и cancelled. Отсутствующий или противоречивый отчёт даёт `TEST_REPORT_FAILED`; exit 0 не заменяет проверку счётчиков. Исторический Node gate без них остаётся неполным, а неизвестные totals возвращаются как `null`. Шаги build/typecheck без тестов сохраняют собственную область. Планировщик сверяет использованные bytes manifest и инвентаря общих тестов перед первым subprocess; смена входов, даже при том же списке шагов, даёт `PLAN_SOURCE_CHANGED`.

Версия 2 продолжает читаться как результат записанного плана без SHA исходников. Более ранние отчёты неполны по области; отсутствие `selection` означает неизвестный объём запроса. Новые и старые сводки не сравнивают текущие файлы с сохранённым SHA автоматически: `currentSourceEquivalent` остаётся `unknown`. Снимки до/после не замораживают зависимости, исключённую конфигурацию или промежуточное изменение с возвратом прежних байтов. `NEUROCENTER_CHECK_SOURCE=0` отключает захват; проверка команд остаётся доступной, происхождение неизвестно. Допустимы только `0`/`1`, по умолчанию включён.

На POSIX SIGINT/SIGTERM и timeout завершают свою группу с ограниченным grace period; отчёт сохраняет отмену/причину, выполненный префикс и состояние cleanup. Посторонние группы не выбираются по имени. `cancelled` не считается успехом; невозможность проверить очистку тоже не считается успехом. Финализация повторно читает снимок; timeout шага не задаёт общего срока для файлового I/O финализации. Управляемый runner на Windows пока не поддержан, допуск отклоняет запуск до создания отчёта.

`built-snapshot` подтверждает записанный результат отдельной компиляции и её checks в момент завершения. SHA относится к сохранённому снимку. Совпадение HEAD и чистое дерево не сравнивают текущие байты с этим снимком; MCP не объявляет их эквивалентными. `in-progress` в любом отчёте описывает сохранённое состояние, а не наличие живого процесса. Отказ, отмена, пропуски и отсутствие сведений видны отдельно; локальные JSON остаются недоверенными свидетельствами.

Для проверки актуальности установленного kit используй `npm run agent-kit:doctor`. Команда не меняет файлы; без переданного каталога клиента обнаружение tools остаётся `unverified`. [Подробности и локальный флаг `check_plan`](agent-kit.md#диагностика-набора).

### Готовность окружения

`services_health` и dev CLI используют один каталог фиксированных loopback-портов. Ответ содержит отдельные `liveness`, `readiness`, `compilation` и `ownership`. Backend `/health` не доказывает готовность PostgreSQL. Пассивные `/ready` проверяются с отдельным бюджетом; skills и gateway пропускаются, поскольку их readiness прямо или транзитивно пишет временный файл. Этот пропуск виден и не означает готовность. Frontend CSS подтверждает только частичный compile probe.

Принадлежность сопоставляет PID реально слушающего сокета с текущей OS-идентичностью процесса и cwd checkout. Чужой listener остаётся `foreign`; недоступность метаданных, неоднозначный ответ или невозможность OS inspection дают `unknown`. Старая запись PID сама по себе не подтверждает принадлежность. Это не проверка версии уже загруженного артефакта и не сравнение работающего приложения с нынешними исходниками. CLI не пишет «Все сервисы готовы» по одному HTTP probe; непроверенная ось отображается явно. MCP не посылает сигналы работающим сервисам.

`NEUROCENTER_DEV_MCP_SERVICE_DETAILS=0` оставляет liveness/compile probe, отключая добавленные readiness и OS inspection. `NEUROCENTER_DEV_MCP_OUTPUT_SCHEMAS=0` отключает публикацию и проверку новых выходных схем. Оба локальных флага принимают `0`/`1`, по умолчанию включены; новый процесс MCP читает их при запуске. Схемы включённого режима описывают все шесть успешных ответов. Нарушение возвращает фиксированный `OUTPUT_CONTRACT_MISMATCH` без содержимого ответа; protocol/tool errors передаются отдельно. Чтение сохранённых свидетельств остаётся доступным.

В 0.3.2 `service_logs.details` содержит `observedAt`, `fileModifiedAt`, `fileBytes`, `bytesRead` и `currentProcessCorrelation: {state: "unknown", reason: "append-log-without-launch-provenance"}`. Время и размеры получены из того же проверенного FD-чтения; bytesRead относится к входному хвосту до отбора строк и маскирования. Append-файл может содержать прежние запуски, а внешний `LOGDIR` не меняет область MCP. Свежий mtime или похожая на служебную метка в тексте не устанавливают текущий PID/поколение. При `NEUROCENTER_DEV_MCP_SERVICE_DETAILS=0` поле details отсутствует, журнал остаётся доступен.

В 0.3.3 `service_logs.truncated` учитывает фактически пропущенные строки и байты. Завершающий перевод строки сам по себе не означает потерю данных.

### Сценарии использования инструментов

```sh
npm run agent-kit:evals
```

Шесть фиксированных offline-сценариев содержат 12 положительных/отрицательных controls. Они проверяют оценщик: отсутствие MCP, план вместо исполнения, неизвестный источник check, пределы build snapshot, пропуски покрытия и полномочия reviewer. Успешная классификация controls не является измерением поведения живой модели. Захваченный в том же mock-контракте trace можно оценить отдельно:

```sh
node scripts/agent-kit/evals/run.mjs --scenario check-source-unknown --trace .run/agent-kit-evals/<попытка>/trace.json
```

Результат сохраняет отдельные оценки цели, свидетельств, полномочий и ясности, версии и SHA сценария/инструкций/trace. Выдуманные свидетельства и запрещённые действия дают hard fail. Содержимое capture и идентичность модели не аутентифицируются самим оценщиком; live runner и оценка реальных моделей этим не подтверждаются. `NEUROCENTER_AGENT_EVALS=0` отключает запуск controls и новых live-серий, сохраняя чтение ранее захваченных traces; неверное значение отклоняется. [Контракт и rubric](../scripts/agent-kit/evals/rubric.md).

Для отдельно разрешённой серии предусмотрен `scripts/agent-kit/evals/live-runner.mjs`: `--prepare <run>` готовит шесть сценариев без обращения к модели, `--preflight <run>` проверяет metadata, `--run-six <run>` выполняет по одной попытке. Перед запуском нужны явный бюджет пользователя и свежий совместимый preflight. Runner переносит точные model/provider/reasoning в отдельный private Codex home и подключает только тестовый MCP. Ограниченный адаптер допускает встроенный OpenAI provider без профиля; неподдержанные настройки маршрутизации, каталога или записи identity отклоняются до копирования auth. Модель получает общий формат ответа и словарь идентификаторов; правильные ответы отдельных сценариев и controls ей не передаются.

Preflight выполняет 20 фиксированных локальных команд: версию CLI, `debug models --bundled` без обновления каталога и по три проверки features/MCP/rendered prompt для каждого из шести homes. Проверяются точный slug модели и reasoning, выключенные возможности, единственный mock MCP, отдельные native permissions `read-only`/`never` и cwd. Статус `compatible` относится к metadata; доступ аккаунта к inference и полный список tools фактического запроса остаются `unverified`. `--inventory <run>` доступен как отдельная диагностика и не заменяет этот допуск.

Приватная receipt действует 15 минут и привязана к плану, SHA captures, kit, prompts, конфигурации, Node и точному исполняемому файлу CLI/PATH. Перед marker runner повторно проверяет эти данные; отсутствующая, несовместимая, изменённая или просроченная receipt блокирует запуск. Native worker использует абсолютный проверенный путь CLI; модель автоматически не заменяется. `NEUROCENTER_AGENT_EVALS=0` блокирует prepare/inventory/preflight/новый запуск, сохраняя help, cleanup и переклассификацию истории.

Действия берутся из native JSONL и журнала mock MCP с точными аргументами/наблюдениями. Самоотчёт модели не создаёт свидетельств. Результат относится к шести задачам в ограниченном mock-контракте: это не приёмка всех 64 ролей или поведения в production. Marker запрещает повтор той же серии; внутреннее число запросов CLI может не сообщаться, бюджет измеряется запусками сценариев. Неуспех и неизвестная ревизия модели сохраняются явно. `--cleanup <run>` удаляет только принадлежащие серии private homes; сохранённые результаты остаются доступны.

Начатый MCP-вызов учитывается как попытка отдельно от выполненного действия. Согласованные started/completed события сопоставляются по id и аргументам; незавершённая, неизвестная или запрещённая попытка не исчезает после финального ответа или инфраструктурного отказа. Полученное наблюдение по-прежнему требует completion и совпадающего host ledger.

Серия останавливается при первом инфраструктурном отказе; receipt отдельно перечисляет неисполненные сценарии. Отказ модели/авторизации до действий означает «поведение не измерено», а не нарушение роли. Предупреждение `item.error` само по себе не является действием; malformed MCP calls и запрещённые попытки остаются ошибками. Переклассификация сохранённых логов через `--rescore-infrastructure <run>` не обращается к модели и не переписывает исходный receipt.

Capture 1.1.1 требует событие `turn.completed` даже при exit 0 процесса. Пустая запись или одни события запуска дают `AGENT_TURN_INCOMPLETE` и `unmeasured` без числовой оценки. Сохранённые попытки действий, ответ или reasoning без завершённого turn остаются `partially-observed`; серия останавливается, сохраняя увиденное.

Rescore schema 2 сохраняет исходные и текущие версии kit/prompt/scenario/evaluator, SHA текущих scorer/capture и исходных файлов. Совпадения id недостаточно: изменённый или отсутствующий исходный SHA сценария даёт `scenario-version-mismatch`, `not-scored` и пустую rubric. Неизвестные исторические версии сохраняются как `null`.

## Выбрать цели для регресса

Вызови MCP `coverage_gaps` с явным завершённым отчётом и пакетом, у которого в нём есть unit-результаты:

```json
{"report":".run/coverage/dev-tools-unit-profile-20261023/manifest.json","package":"catalog-service","limit":10}
```

Инструмент возвращает ограниченный список функций и ветвей без исполнения, строки, отсутствующие в измерении исходники и отдельные исключения unit-наборов. `limit` — от 1 до 20. Выбери пользовательское поведение, воспроизведи отказ, исправь причину и повтори проверку; сами счётчики не определяют правильное поведение кода.

Сохраняются отдельные SHA manifest/gaps, состояние исходников и неполнота прогона. Targets должны присутствовать в измеренном production-инвентаре; данные других пакетов не выдаются, дубли отклоняются. Для retained merge исключения объединяются по всем записям выбранного пакета. HTTP-only отчёт без unit-пакетов используй через `verification_summary`. Смешанные AST/c8 счётчики не получают сопоставимых процентов.

TODO и неизвестные счётчики проходят через coverage manifest, retained merge, MCP summary и `coverage_gaps`; полнота не выводится из одного exit 0. В gaps счётчики сохранены по отдельным retained entries, их нельзя суммировать как уникальные тесты. Старый формат без достаточных данных остаётся неполным; проценты и знаменатели покрытия этим исправлением не пересчитываются.

## Проверить инструментарий

```sh
npm run check -- --tooling
```

Режим проверяет актуальность generated kit и запускает один Node gate по явному списку `scripts/workspace/check-tooling-tests.json`. В него входят локальные fixtures agent-kit, MCP, check и coverage, включая отказ и повтор OS inspection при управлении дочерними процессами; произвольный поиск всех `coverage*.test` не используется. Продуктовые typecheck/build/test, Compose и настоящие PG opt-in наборы исключены. Stub Codex в тестах не обращается к модели.

`--tooling` не совмещается с `--package` или `--step`. JSON списка, выбранные test-файлы и generator участвуют в привязке входов плана; отсутствующие файлы, ссылки, дубли и изменение входов блокируют исполнение. Сохраняется обычный `.run/check/<попытка>/report.json` версии 3 с `selection.tooling: true`, Node counters, cleanup и состоянием исходников. Для чтения этой selection используй MCP 0.3.2 или новее. Проценты покрытия продукта этим режимом не измеряются.

`NEUROCENTER_CHECK_TOOLING=0` отключает новое исполнение режима до выбора runtime и создания отчёта; остальные проверки, помощь и чтение истории сохраняются. Допустимы только `0`/`1`, по умолчанию режим включён. Как и в обычном check, изменение исходников за время прогона не позволяет объявить результат актуальным.

## Проверить выбранный модуль

```sh
npm run check -- --help
npm run check -- --package frontend --step typecheck
scripts/dev.sh check --package frontend --step typecheck
```

`--package` и `--step` можно повторять. Выбор ограничивает план их пересечением. Отдельный шаг `test` не запускает сборку. Пустое пересечение возвращает ошибку. API Gateway и OAuth2 Bridge имеют обычный `test`: их Vitest-наборы теперь входят и в полный план, и в выбранный `--step test`. Например: `npm run check -- --package api-gateway --package oauth2-bridge --step test`. Селекторы не включают общие контракты или Compose. Вызов без селекторов включает сборку в обычный `dist`.

Справка и неверные аргументы обрабатываются до создания отчёта и запуска проверок. `dev.sh check` передаёт выбранные параметры и код результата, не загружая активные dotenv-файлы. Отчёт выполненного плана сохраняется в `.run/check/<попытка>/report.json`.

## Воспроизвести баг и измерить покрытие

```sh
npm run coverage -- --package frontend --test-file test/error-message.test.ts
```

Укажи ровно один пакет и до 32 относительных `--test-file` внутри его `test/`. Допускаются обычные тестовые файлы без ссылок, обхода каталогов и инфраструктурных сценариев. Команда запускает только выбранные unit-тесты. Для PostgreSQL, S3, native и integration нужны отдельные профили с собственными фикстурами.

Если один файл из выбранного набора требует инфраструктуры, ошибка указывает его относительное имя. Отчёт и worker до прохождения этого допуска не создаются. Для 49 проверенных SQL-моков с type-only `pg` есть явный профиль `scripts/coverage/unit-safe-profile.mjs`: точный путь, SHA теста и разрешённого helper. Изменение этих файлов требует повторного аудита изоляции и обновления SHA после ревью; до этого runner объясняет отказ до запуска worker. Неизвестный type-only тест автоматически не допускается. Настоящие PG fixtures остаются за opt-in; профиль не является сетевой песочницей или анализом всего production-графа импортов.

В отчёте перечислены запрошенные файлы, фактически выполненные тесты, исключения по выбору и отдельные инфраструктурные исключения. Невыполненный или лишний файл делает проверку неполной. Знаменатель покрытия включает исходники выбранного пакета, в том числе не импортированные выбранным тестом модули. `complete` относится к запрошенному набору; это не 100% покрытия модуля или проекта.

Без `--test-file` остаётся прежний режим покрытия пакетов; без `--package` он выбирает все восемь. HTML, исходный JSON и `manifest.json` сохраняются в новом `.run/coverage/<попытка>/`. Не смешивай AST unit-покрытие и native V8 как один процент.

### Остановить coverage и прочитать частичный результат

```sh
npm run coverage -- --package frontend --test-file test/error-message.test.ts --timeout-ms 600000
```

`--timeout-ms` — положительное целое число миллисекунд на каждый тестовый subprocess; по умолчанию 600000. Это не общий срок подготовки, PostgreSQL cleanup, чтения исходников и генерации отчётов. Unit, native и integration используют тот же POSIX supervisor, что изолированная сборка: собственная группа процессов, ограничение журнала 32 МиБ, SIGTERM и ограниченное ожидание перед SIGKILL. SIGINT/SIGTERM сохраняют отмену и прекращают переход к следующим пакетам. Проверка ОС с прерванным `ps` повторяется ограниченно; устойчивый отказ наблюдения оставляет очистку неподтверждённой.

Manifest версии 2 получает дополнительный `lifecycle` версии 1: план, выполненный префикс, фазы `preparing`/`running`/`finalizing` и итог `passed`/`failed`/`cancelled`. Начальная квитанция с `complete:false` сохраняется до первого subprocess. Замена manifest атомарна; первичная причина и ошибки финализации записываются отдельно. Корректные JSON/TAP-счётчики сохраняются и при ненулевом exit тестов. Отсутствующие результаты не заменяются нулями. `passed` описывает исполнение, а skipped/TODO могут сохранять `complete:false`.

MCP 0.3.4 читает ранние failed/cancelled без итоговых метрик и возвращает проверенный `lifecycle`. Старые отчёты сохраняют прежний контракт. `coverage_gaps` объясняет отсутствие targets после раннего отказа кодом `COVERAGE_TARGETS_UNAVAILABLE`; корректные сохранённые partial targets остаются неполными. Merge повторно проверяет lifecycle входов и не повышает прерванное измерение до полного.

`NEUROCENTER_COVERAGE_LIFECYCLE=0` запрещает новые прогоны; помощь и чтение сохранённой истории доступны. Флаг принимает только `0`/`1`, по умолчанию включён. Справка и проверка аргументов не требуют библиотек collector. Изменение флага не отключает обработчик отмены уже начатого запуска.

После SIGKILL, отказа диска или невозможности финальной записи может остаться предыдущая неполная квитанция. `running` не подтверждает живой процесс; автоматический recovery/kill по сохранённому PID не выполняется. Успешно полученная owned-PG fixture закрывается общим finally; частичный отказ внутри её подготовки остаётся границей существующего bootstrap. Управляемая очистка Windows этим срезом не реализована.

## Собрать текущие правки отдельно

```sh
npm run build:isolated -- --package frontend --plan
npm run build:isolated -- --package frontend
npm run build:isolated -- --all
```

Проверка копирует текущие отслеживаемые и новые неигнорируемые файлы Git, учитывая локальные правки и удаления. Активные dotenv, файлы секретов по известным именам, пользовательские npm-настройки, зависимости и готовые выходы исключаются из снимка. Состав и SHA сохранены в отчёте. Изменение исходников во время подготовки останавливает сборку; изменение после запуска не считается проверкой текущего состояния.

Компиляторы работают последовательно в `.run/isolated-build/<попытка>/repository` с отдельными HOME, кэшем и журналами. Никаких установок зависимостей; кандидат не копируется в рабочий `dist`. Отчёт проверяет ожидаемые точки входа, SHA артефактов и сохранность рабочих выходов всех восьми пакетов. Отказ и отмена сохраняют причину и частичный результат.

Это изоляция исходников и выходов, а не защитная песочница: уже установленные `node_modules` подключаются ссылками, содержимое зависимостей не заморожено. Доверенный build-скрипт может писать через ссылку; offline-настройка npm не является сетевым фильтром. Отмена завершает только собственную группу процессов; эта проверка жизненного цикла подтверждена на macOS. Сборка не подтверждает работу API, браузера, миграций или production.

Канонические идентификаторы: `frontend`, `catalog-service`, `api-gateway`, `feature-flags-service`, `oauth2-bridge`, `rag-sync-service`, `skills-service`, `bridge`. Тяжёлые сборки и профили покрытия запускай по очереди. Сохраняй отдельно пройденное, пропущенное и непроверенное; бэклог обновляй после реализации и проверок.

Храни URL с паролем в приватной конфигурации, не в отчёте или Git. Каждый CLI создаёт свою случайную БД, применяет настоящие миграции, удаляет только её и сверяет исходный список БД. Этот сборщик не проверяет компиляцию, публикацию или установку настоящего пакета. Windows и восстановление на другом хосте требуют отдельной приёмки.

## Прогнать настоящую сборку, установку и возврат версии

Собери все пакеты через `npm run build:isolated -- --all`. В том же явно выбранном кандидате задай абсолютные пути:

- `TOOL_BUILD_TEST_DIST` — `repository/services/catalog-service/dist`;
- `TOOL_BUILD_BRIDGE_DIST` — `repository/mcp/neurocenter-asset-sync/dist`;
- `TOOL_BUILD_SCRIPT` — `repository/scripts/catalog-plugins/build.mjs`.

`TOOL_BUILD_CANCEL_TEST_PG_URL` имеет тот же строгий допуск собственной одноразовой БД, что и проверки отмены выше. Затем:

```sh

```

CLI строит маленький JS-плагин настоящим сборщиком, дожидается публикации, закрепляет пакет за проектом и устанавливает отдельным процессом моста в собственный HOME. Затем публикует изменённый исходник как явную новую версию, устанавливает её и возвращает проект и установку к первой. Проверяет SQL, байты старых исходников/runtime, сохранение ручных записей конфигурации и отсутствие дополнительной сборки при точном повторе UUID.

Нужны Node 24 и POSIX; подтверждённая ОС — macOS ARM64. Runtime transport и Gateway/device authorization задаются стендом; установленный hook вызывается через сгенерированную конфигурацию без запуска обычного OpenCode. Проверка не подтверждает его первый запуск, корпоративный Linux/Windows, произвольные рецепты или внешние сервисы. Она не использует рабочий профиль моста или основной PostgreSQL.

Квитанция содержит SHA harness, путь кандидата, результат каждого шага и ошибки очистки. Незавершённые собственные процессы, ошибку удаления тестовой БД и изменение проверяемого harness нельзя считать GREEN. Защиты процесса и финализаторов проверяются без PostgreSQL:

```sh
node --test --test-concurrency=1 \
  scripts/test/tool-build-roundtrip-process.test.mjs \

```

Для углублённого аудита сохранены `scripts/test/native/package-publication-rollback.test.mjs` и `scripts/test/tool-build-version-cas.mjs`: реальный SQL с потерянным ACK, последующим чужим COMMIT, блокировками и отзывом прав. Сейчас они требуют специально подготовленный собственный PostgreSQL 16.15 с приватной описью владельца, PID, сроком lease и source-freeze receipt; один PG URL не заменяет этот допуск. Универсальная переносимая команда подготовки такого стенда ещё не поставляется; эти два harness не входят в обычный `check` и не должны запускать чужую инфраструктуру. ## Проверить приём и отмену при SQL-блокировке

`scripts/test/build-admission-reliability.mjs` — opt-in проверка B13. На старом кандидате подтверждены пять ожиданий с `lock_timeout=0` / `statement_timeout=0`: строка READY upload, asset-lock обновления, dependency graph, общая очередь и строка задания перед барьером публикации. Исправленный кандидат прошёл 8/8: ограниченный отказ, сохранение UUID/исходников, повтор отмены и восстановление очереди. [Контракт и границы](tool-build-admission-deadline.md).

Нужны Node 24/POSIX, абсолютные `BUILD_ADMISSION_CANDIDATE` к одному изолированному `repository`, `BUILD_ADMISSION_SOURCE_RECEIPT` к source/SHA-квитанции и `BUILD_ADMISSION_CONNECTION_FILE` к приватной описи свежего собственного PostgreSQL 16.15. Используется тот же специальный допуск B12, что у B14/B15; одного URL недостаточно. Для baseline выберите снимок до исправления, для candidate — текущую сборку и её source-квитанцию; переключение фазы само не меняет исходники. После задания соответствующих параметров:

```sh
BUILD_ADMISSION_PHASE=baseline node scripts/test/build-admission-reliability.mjs
BUILD_ADMISSION_PHASE=candidate node scripts/test/build-admission-reliability.mjs
```

Для принятия baseline нужны одновременно exit 1 и `causalRed:true`: пять точных графов блокировок, три здоровых контроля, продолжение очереди после снятия каждой блокировки и успешная очистка. Произвольная ошибка таким RED не считается. Входы проверяются настоящими compiled-валидаторами до подключения к БД; барьер одноразовый, watchdog дренирует собственные операции. SHA, исходники, прежние версии и список остальных БД проверяются после прогона.

Фаза `candidate` требует exit 0 и `ok:true` для всех восьми случаев. Реальный timeout записи FAILED проверяется отдельно от timeout первого барьера; внешняя блокировка может оставить строку RUNNING до unlock. DELETE общей очереди также может вернуть 503: после unlock стенд повторяет тот же DELETE и проверяет tombstone до позднего POST. Ограничения 5 с на отдельную попытку блокировки и 30 с на SQL-запрос не образуют общий HTTP deadline. Методы контроллера вызываются внутри процесса; Gateway HTTP, браузер, настоящий MCP builder/установка и другие ОС не входят в этот профиль. Переносимый bootstrap остаётся B12.
